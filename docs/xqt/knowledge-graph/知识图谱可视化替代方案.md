# 知识图谱可视化替代方案

## 问题诊断

当前系统使用 ECharts 力导向图（force-directed graph）渲染知识图谱。在 `depth=2`（仅课程+章节，10-30 节点）时效果尚可；但在 `depth=5`（全部 5 层类型，100-500+ 节点）时，出现以下核心问题：

| 问题 | 表现 | 根本原因 |
|------|------|----------|
| 毛线团效应 | 节点密集堆叠，连线交叉如乱麻 | 力导向布局对 100+ 节点无法有效分离聚类 |
| 小节点淹没 | Concept（10px）和 SubPoint（20px）几乎不可见 | 线性尺寸映射无法覆盖 9:1 的尺度跨度 |
| 语义层次丢失 | 课程/章节/知识点混在一起，看不出教学层级 | 力导向不利用数据本身的层级结构 |
| 缩放疲劳 | 用户需要频繁滚轮放大缩小来找节点 | 缺乏 overview→detail 的渐进式导航 |
| 交互卡顿 | 拖拽/缩放有明显延迟 | N>200 时力导向迭代计算开销大 |

力导向图天然适合**无先验结构的探索性图数据**（如社交网络），但本系统的知识图谱具有明确的**五层教学层级 + 四种关系类型**，这种"有结构的数据"更适合层级化、可导航的展示方式。

---

## 推荐方案

### 方案 A：可折叠树图 + 跨层级连线（推荐首选）

**核心思路：** 用 ECharts `tree` 组件展示 IS_PART_OF 层级结构，RELATED_TO / REQUIRES 作为跨分支的辅助连线。

**布局方式：**
- 采用**从左到右（LR）或从上到下（TB）的缩进树**，根节点为 Course，逐层展开
- 每个父节点可**点击折叠/展开**子节点，默认仅展开到 Chapter 层
- RELATED_TO 和 REQUIRES 边以**半透明虚线**连接跨分支节点

**优势：**
- 教学层级一目了然，符合用户的认知模型（课程→章→节→知识点）
- 折叠机制天然解决节点过多问题，按需展开
- ECharts 原生支持 `tree` 系列，改动成本低
- 标签位置固定，不会重叠

**劣势：**
- 跨层级边较多时，虚线会显得杂乱
- 宽树（同级节点多）需要横向滚动

**交互设计：**
- 默认展开 2 层（Course + Chapter），KnowledgePoint 以下折叠
- 点击节点 = 展开/折叠子节点
- 双击节点 = 聚焦该子树（类似文件管理器）
- 右侧保留"关联资源"侧边栏

**预估工作量：** 3-5 天（ECharts tree + 数据转换 + 折叠交互）

---

### 方案 B：旭日图（Sunburst） + 节点列表

**核心思路：** 用同心圆环表示层级，圆心是 Course，向外依次是 Chapter → KnowledgePoint → SubPoint → Concept。每个扇区的大小按子节点数量等比例分配。

**优势：**
- 空间利用率极高，500 个节点也能塞进一个屏幕
- 层级关系直观（越靠近圆心层级越高）
- 适合展示"某课程下各章节的知识点密度"
- ECharts 原生支持 `sunburst` 系列

**劣势：**
- 无法展示 RELATED_TO / REQUIRES 跨层级关系
- 标签长时会被裁切
- 交互以 hover + tooltip 为主，不适合需要连线的场景

**交互设计：**
- 点击扇区 = 钻入该子树（sunburst 原生支持 `drill-down`）
- 面包屑导航显示当前钻入路径
- 右下角节点列表显示当前选中扇区下的所有叶子节点
- 列表中的节点可点击跳转到"生成学习资源"

**适用场景：** "概览"模式，快速了解知识分布

**预估工作量：** 2-3 天

---

### 方案 C：径向树（Radial Tree）

**核心思路：** 以选中节点为中心，按同心圆向外辐射展开子树。内圈为焦点节点，第二圈为其直接子节点，第三圈为孙节点，依此类推。

**优势：**
- 聚焦单一节点，适合"我要学这个知识点，它有哪些前置知识？"的场景
- 空间效率优于传统树图
- 学术研究表明径向布局的聚类辨识准确率高于力导向（IEEE TVCG 2025）
- 自然支持"深钻"（drill-down）交互

**劣势：**
- 中心区域在大图时会拥挤（星爆效应）
- 非焦点节点的可发现性弱
- ECharts 无原生径向树支持，需要自定义布局或使用 D3.js

**交互设计（与现有 `focusOnNode` 功能衔接）：**
- 点击节点 → 该节点移到圆心，重新辐射展开
- 顶部面包屑导航显示焦点路径
- 每次最多显示 3 层，更深层通过继续点击展开

**适用场景：** "探索"模式，以某个知识点为中心展开

**预估工作量：** 5-8 天（需要自定义布局算法或引入 D3.js）

---

### 方案 D：混合双视图（Tree + Force）

**核心思路：** 左侧层级树 + 右侧力导向局部图，两个视图联动。

- **左侧**：可折叠的缩进树（方案 A 的简化版），展示 IS_PART_OF 层级，用于导航和概览
- **右侧**：力导向子图，仅显示左侧选中节点的**局部邻域**（1-2 跳内的邻居节点 + 它们的 RELATED_TO / REQUIRES 关系），用于展示交叉引用

**优势：**
- 层级导航和关系探索各司其职，互不干扰
- 右侧子图节点数可控（通常 <30），力导向效果好
- 左侧树的结构清晰，右侧图的交叉关系直观
- 可以逐步替换现有实现，兼容性好

**劣势：**
- 占用更多屏幕空间
- 两个视图的联动逻辑需要仔细设计
- 首次加载时用户需要理解两个视图的作用分工

**交互设计：**
- 左侧树默认展开至 Chapter，折叠低层节点
- 点击左侧树的节点 → 右侧力导向图展示该节点的局部图
- 右侧图的节点可点击 → 打开详情侧栏 + 可选择"聚焦此节点"
- 支持拖拽分割条调整两个视图的宽度比例

**适用场景：** "浏览 + 探索"模式，兼顾结构与关系

**预估工作量：** 5-7 天

---

### 方案 E：Sankey 学习路径流图

**核心思路：** 用桑基图展示从课程入口到目标知识点的学习路径，流的宽度表示该路径上已学习/待学习的节点数量。

**优势：**
- 直观展示"前置依赖"和"学习流向"
- 适合与"学习路径"功能深度整合
- 流图视觉效果新颖，适合展示给用户

**劣势：**
- 仅适合路径视图，不适合全局图谱浏览
- 数据准备复杂（需要从路径中提取层级流向）
- 无法展示 RELATED_TO 这种对等关系

**适用场景：** "我的学习路径"页面的可视化升级

**预估工作量：** 2-3 天

## 实施建议

**分阶段推进，不一次性替换现有力导向图：**

### 第一阶段（当前迭代，1 周）

实现**方案 D 的简化版**：在现有力导向图上方增加一个"层级树"开关按钮，点击后切换到**方案 A（可折叠树图）**。两个视图共享同一数据 API 和节点详情侧栏。

- 默认仍用力导向图（向后兼容）
- 用户可一键切换到层级树视图
- 树视图默认展开至 Chapter 层，折叠低层节点
- RELATED_TO / REQUIRES 边以虚线叠加在树上

### 第二阶段（下个迭代，1 周）

基于用户反馈，优化默认视图：

- 如果树视图反馈好 → 将树视图设为默认，力导向作为"交叉引用视图"
- 如果用户需要两者 → 实现完整的方案 D 双视图

### 第三阶段（按需）

- 为"我的路径"页面引入方案 E（Sankey 流图）
- 为"概览仪表盘"引入方案 B（旭日图）展示全局知识分布

## 数据适配说明

五个方案均复用现有 `GET /kg/graph` API，仅在**前端做数据转换**：

| 方案 | 数据转换 |
|------|----------|
| A 树图 | `IS_PART_OF` 边 → tree children；`REQUIRES`/`RELATED_TO` → markLine |
| B 旭日图 | `IS_PART_OF` 边 → sunburst parent-child；叶节点 value=1 |
| C 径向树 | 以 focus 节点为根，`IS_PART_OF` 正向边构建子树，反向边构建"父路径" |
| D 双视图 | 左侧树同方案 A，右侧力导向复用现有 `renderGraph` |
| E Sankey | 从学习路径 API 提取层级流向，`source→target` = 路径顺序 |

**无需后端改动。**
