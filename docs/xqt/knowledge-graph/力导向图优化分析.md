# 力导向图优化分析

## 当前实现概览

当前力导向图实现位于 `frontend/pathway.html`，核心函数包括 `forceRender`（首次渲染）、`forceUpdateVisibilityByZoom`（缩放自适应可见性）、`forceFocusOnNode`（搜索定位镜头动画）和 `forceHighlightSearchResults`（搜索结果高亮）。数据来源为 `GET /kg/graph` API（`backend/main.py:1008`），支持按 depth（1-5 层）和 root_id 裁剪返回的子图。

## 优势（应保留）

| 特性 | 说明 |
|------|------|
| 缩放自适应可见性 | 小节点在缩小时自动弱化/隐藏，减少毛线团效应，是本实现的核心亮点 |
| 学习状态覆盖 | 已学习节点提亮（HSL 饱和度×1.4 + 亮度×1.3），未学习节点弱化至 0.15 不透明度，差异明显 |
| 学习路径叠加 | 支持将某条学习路径的 completed/current/planned 状态叠加到图谱上（边框颜色区分） |
| 五层类型体系 | Course(90px) → Chapter(55px) → KnowledgePoint(30px) → SubPoint(20px) → Concept(10px)，尺寸跨度 9:1 |
| 关系型边长 | IS_PART_OF(120-380)、REQUIRES(220)、RELATED_TO(260)、CONTAINS(160)，不同关系有不同的视觉距离 |
| 搜索+镜头动画 | 搜索后自动聚焦目标节点，高亮匹配节点，其余弱化 |
| 深色背景 + 星空粒子 | 视觉质感好，与系统整体风格一致 |

## 问题诊断

### 问题 1：zoom 事件性能瓶颈（严重）

**表现：** 滚轮缩放时图表有明显延迟和卡顿，N>200 时尤为突出。

**根因：**
```
graphRoam → currentZoom 更新 → forceUpdateVisibilityByZoom(currentZoom)
                                              ↓
                              getOption() → 遍历全部 nodes + links
                              → 逐节点计算 visible/size/opacity
                              → setOption({data: updated, links: updatedLinks})
```
此调用链在每次滚轮事件（高频，通常 60-120Hz）上都完整执行一次。`setOption()` 即使只更新样式属性，ECharts 也要走完整的 merge + dirty check + repaint 流程。

**当前代码路径：** `pathway.html:1433-1438`, `:1355-1408`

---

### 问题 2：forceUpdateVisibilityByZoom 中 getOption/setOption 往返开销（严重）

**表现：** 每次 `setOption` 都包含完整 nodes 数组（展开风格），即使只改了 opacity/symbolSize。

**根因：**
- `getOption()` 返回整个 series 的 deep clone
- 展开每个 node 的所有属性（包括自定义的 `_baseSize`、`_baseOpacity`、`_learned`）再写回
- 对于 200 节点 + 400 条边，单次 `setOption` 传输约 50-80KB 的序列化数据
- links 也被全量更新，即使只有少数边连接了被隐藏的节点

---

### 问题 3：力导向参数不适应图规模（中等）

**表现：** 10 个节点时稀疏空旷，500 个节点时挤成一团。

**根因：** 参数硬编码，不分规模：

```javascript
force: {
    repulsion: 500,    // 斥力：固定值，大图应增大到 800-2000
    gravity: 0.05,     // 向心力：固定值，大图应减小到 0.02-0.03
    edgeLength: [80, 380],  // 边长范围：大图小节点间距应缩小
    friction: 0.6,     // 阻尼：固定值
}
```

ECharts 力导向的 `repulsion` 是全局斥力常数，节点数翻倍时斥力不足以推开所有节点，导致中心堆叠。

---

### 问题 4：搜索结果使全图不可用（中等）

**表现：** 搜索一个节点后，其余所有非匹配节点被设为 opacity: 0.3，标签颜色也弱化到近乎透明。用户无法同时看到搜索结果和图谱上下文。

**代码路径：** `pathway.html:1260-1289`（`forceHighlightSearchResults`）

---

### 问题 5：dblclick 事件未注册（轻微）

**表现：** `initChartInstance` 中 `off('dblclick')` 但 `forceRender` 从未 `on('dblclick', ...)`。双击节点无任何响应。之前的双击交互（聚焦子树）已被删除但清理不彻底。

**代码路径：** `pathway.html:1415`

---

### 问题 6：force 模拟在每次过滤变更时完全重启（中等）

**表现：** 切换"已学习视图"或搜索时，所有节点重新从随机位置开始做力导向迭代，导致短暂的"爆炸然后收敛"动画。

**根因：** `forceRender` 每次都调用 `setOption({series: [{data: chartNodes, links: chartEdges}]}, true)`，`notMerge: true` 导致 ECharts 丢弃旧布局状态，重新开始力模拟。

---

### 问题 7：小节点（SubPoint, Concept）在大图时完全无法交互（轻微）

**表现：** Concept 节点（10px 直径 + 4px 阴影）在 200+ 节点图中需要非常大的缩放才能准确点击。在当前缩放级别下，Concept 在缩小时被隐藏（阈值 1.0），但用户需要滚轮放大很多才能看到它们。

**根因：** `zoomThresholds.Concept = 1` 意味着只有 `zoom >= 1` 时才可见。但初始 zoom=1 时，是否可见取决于力模拟收敛后的实际 zoom 值。实际上，由于 `graphRoam` 的 zoom 是乘性的，初始 zoom 确实是 1，所以初始加载时 Concept 节点就是可见的（但极小）。

---

### 问题 8：缺少渐进式加载（优化建议）

**表现：** 用户选择 depth=5 后，API 可能返回 500+ 个节点，前端一次性全部塞入力导向图。

**根因：** 无分页、无懒加载、无虚拟化。ECharts 力导向图不是为 500+ 节点设计的——它的力模拟是 O(n^2) 每次迭代。

---

## 优化方案

### 方案 A：缩放手柄节流 + 样式批量更新（推荐优先实施）

**目标：** 解决问题 1、2，让 zoom 操作流畅。

**措施：**
1. `graphRoam` 回调中加 `requestAnimationFrame` 节流，最多每帧执行一次 `forceUpdateVisibilityByZoom`
2. 用 `ECharts.dispatchAction` 的 `highlight`/`downplay` 机制替代全量 `setOption` 更新节点样式（`highlight` 只走 repaint，不 rebuild）
3. 如果必须用 `setOption`，传入增量数据而非全量 nodes/links

**预估工作量：** 1-2 天

**关键实现思路：**
```javascript
let rafId = null;
chartInstance.on('graphRoam', function(params) {
    if (params.zoom) currentZoom *= params.zoom;
    if (rafId) cancelAnimationFrame(rafId);
    rafId = requestAnimationFrame(() => {
        rafId = null;
        forceUpdateVisibilityByZoom(currentZoom);
    });
});
```

---

### 方案 B：力导向参数按节点数自适应

**目标：** 解决 10 节点和 500 节点共用同一套参数的问题。

**措施：**
根据 `nodes.length` 动态调整力参数：

| 节点数 | repulsion | gravity | edgeLength | friction |
|--------|-----------|---------|------------|----------|
| <50 | 400 | 0.08 | [100, 400] | 0.6 |
| 50-150 | 800 | 0.05 | [80, 300] | 0.5 |
| 150-300 | 1200 | 0.03 | [60, 220] | 0.4 |
| >300 | 2000 | 0.02 | [40, 160] | 0.35 |

**预估工作量：** 0.5 天

---

### 方案 C：搜索结果改为环状高亮而非全局弱化

**目标：** 搜索时保留图谱上下文可见性。

**措施：**
- 匹配节点：提高 `borderWidth` + `shadowBlur` + 橙色边框
- 非匹配节点：保持原样（不降不透明度），但标签使用稍淡颜色
- 匹配节点关联的边：提高线宽和不透明度
- 其他边：降低不透明度至 0.15

**预估工作量：** 0.5 天

---

### 方案 D：保存/恢复力模拟状态，避免重启

**目标：** 切换筛选条件时保持节点位置，不重新跑力模拟。

**措施：**
1. 过滤/搜索时使用 `notMerge: false`（默认），这样 ECharts 会保留现有布局
2. 对于新增的节点：给它们在已有节点的质心附近随机初始化位置
3. 对于移除的节点：只删数据，不影响其余节点位置
4. `forceRender` 中将 `notMerge: true` 改为 false，并在首次加载（无已有布局）时通过 `chartInstance.clear()` + 重建来区分"首次渲染"和"增量更新"

**预估工作量：** 1-2 天

---

### 方案 E：分层渲染（深度剔除）

**目标：** depth>=4 时不在力导向图中展示 SubPoint 和 Concept，而是通过节点列表和详情面板按需展示。

**措施：**
- 力导向图默认仅渲染前三层（Course, Chapter, KnowledgePoint）
- 第四、五层节点仅在以下情况展示：
  - 点击 KnowledgePoint 节点时，在详情面板中列出其下的 SubPoint 和 Concept
  - 用户通过"深度"选择器明确选择了 depth>=4
- 即使渲染 depth>=4，也通过 `zoomThresholds` 默认隐藏 SubPoint 和 Concept（需要放大到一定级别才显示），这已经在做了，但 `Concept` 阈值 1.0 太严格

**调整 zoomThresholds：**
```javascript
const zoomThresholds = {
    'Course': 0.0,
    'Chapter': 0.1,
    'KnowledgePoint': 0.2,
    'SubPoint': 0.5,
    'Concept': 0.7,    // 从 1.0 降到 0.7
};
```

**预估工作量：** 0.5 天（改阈值）+ 1 天（如果做前端按需加载）

---

### 方案 F：力模拟完成后缓存布局坐标

**目标：** 同一图数据重复渲染时跳过力模拟。

**措施：**
1. 在 `forceRender` 中监听 ECharts 的 `graphRoam` 或 `finished` 事件判断力模拟是否收敛
2. 将收敛后的 `(nodeId → [x, y])` 坐标保存到 `sessionStorage`（key 为 `nodes 的 id 列表 hash`）
3. 下次相同数据渲染时，直接设置 `x`、`y` 属性 + `force: { layoutAnimation: false }`，跳过力模拟

**预估工作量：** 1-2 天

---

### 方案 G：为 Concept 节点增加 hover 放大交互

**目标：** 解决小节点（Concept, SubPoint）难以点击和阅读的问题。

**措施：**
利用 ECharts 的 `emphasis` 配置，在 hover 时将小节点的 `symbolSize` 放大 3-4 倍并提升 z-index：

```javascript
emphasis: {
    focus: 'adjacency',
    scale: true,
    itemStyle: { borderWidth: 3, borderColor: 'rgba(255,255,255,0.8)' },
    // 针对小节点
    symbolSize: (params) => {
        const base = nodeTypeSize[params.data.node_type] || 10;
        return params.data.node_type === 'Concept' ? base * 4 :
               params.data.node_type === 'SubPoint' ? base * 2.5 : base * 1.5;
    },
}
```

**预估工作量：** 0.5 天

## 注意事项

1. 方案 A 中的 `requestAnimationFrame` 节流 + `dispatchAction` 替代 `setOption` 需要验证 —— ECharts 的 `dispatchAction({type: 'highlight'})` 只能操作已有 category/dataIndex，不能更新 opacity 自定义值。如果 `highlight` 方案行不通，退回到"节流 + 减少 setOption 数据量"。
2. 方案 D 的 `notMerge: false` 在首次渲染时可能导致残留旧数据。需要区分"是否有旧图表"：无旧图表时 `clear() + setOption(..., true)`，有旧图表时 `setOption(..., false)`。
3. 力参数自适应值（方案 B）需要在真实数据（depth=2~5）上测试调优，表中数值为经验估算。
4. 布局缓存（方案 F）的 key 需要包含 nodes 和 edges 的集合，任一变化（增删节点/边）都应使缓存失效。
