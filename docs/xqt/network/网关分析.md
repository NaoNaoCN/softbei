# 网关层分析报告

## 一、现状：是否存在网关层

**结论：当前项目不存在任何形式的网关层。**

经全面排查：

| 检查项 | 结果 |
|--------|------|
| Nginx 配置文件 | 无 |
| Docker / Docker Compose | 无 |
| Kubernetes 部署清单 | 无 |
| 反向代理配置 | 无 |
| API Gateway（Kong / Traefik 等） | 无 |
| 限流中间件（slowapi 等） | 无 |
| 请求体大小限制 | 无 |
| SSL/TLS 终端 | 无 |

当前项目只有一个 FastAPI 进程（`backend/main.py`），通过 uvicorn 直接监听 8000 端口对外提供服务，客户端直接访问该端口。

## 二、当前架构概述

### 2.1 整体形态：单体应用

```
客户端（浏览器）
    │
    ▼
uvicorn (单进程, 端口 8000)
    │
    ├── StaticFiles Mount (/app) → 前端 HTML/CSS/JS
    ├── CORSMiddleware          → 允许所有来源
    ├── LoggingMiddleware       → trace_id 注入 + 请求日志
    │
    └── 路由处理（均在 main.py 中，约 1960 行，~50 个端点）
         ├── /auth/*         → bcrypt + JWT 认证
         ├── /chat/*         → LangGraph 9 Agent 对话链路
         ├── /generate/*     → 异步生成任务 + 状态轮询
         ├── /kg/*           → 知识图谱 CRUD + 异步构建
         ├── /resources/*    → 学习资源管理
         ├── /quiz/*         → 测验提交 + 评估
         ├── /pathways/*     → 学习路径 CRUD
         ├── /documents/*    → 文档上传 + 向量索引
         ├── /records/*      → 学习行为记录
         ├── /eval/rag/*     → RAG 评测
         ├── /analytics/*    → 学习仪表盘
         └── /health         → 健康检查
```

### 2.2 中间件现状

仅注册了两个中间件：

1. **CORSMiddleware** — `allow_origins=["*"]`，允许所有来源/方法/头部
2. **LoggingMiddleware**（自定义）— 注入 `trace_id`（来自 `X-Trace-ID` 头或自动生成 UUID），记录请求耗时

**没有**以下中间件：
- 限流（Rate Limiting）
- 请求体大小限制
- 全局鉴权拦截
- IP 黑白名单
- 请求/响应转换（除 BigIntJSONResponse 自定义编码器）

### 2.3 鉴权方式

- JWT 令牌（HS256，24 小时过期），登录时签发
- 通过 FastAPI `Depends(get_current_user_id)` 按路由注入
- **存在过渡期设计**：若无 `Authorization` 头，回退读取 `user_id` 查询参数
- 资源访问控制在各路由内手动校验 `resource.user_id != user_id`

### 2.4 静态文件

前端文件（`frontend/` 目录）由 FastAPI 的 `StaticFiles` 挂载在 `/app` 路径，与应用服务共享同一进程。

### 2.5 数据层

- PostgreSQL 单实例（`asyncpg` 驱动），16 张 ORM 表
- pgvector 扩展（HNSW 索引），用于向量相似度检索
- 连接池：base 10 + overflow 20，开启 `pool_pre_ping`

## 三、是否适合配置网关层

### 3.1 适配性评估

| 维度 | 当前状态 | 网关价值 |
|------|----------|----------|
| 架构形态 | 单体应用，单进程 | **低** — 无多服务路由需求 |
| 服务数量 | 1 个 FastAPI 进程 | **低** — 无需服务发现/负载均衡 |
| 入口点数量 | 1 个（端口 8000） | **低** — 无多入口统一需求 |
| 鉴权集中化 | 按路由 Depends 注入 | **中** — 可在网关层统一验证 JWT |
| 限流需求 | 完全缺失 | **高** — LLM 调用有成本，需要限流保护 |
| API 版本化 | 无 | **低** — 可后续按需引入 |
| 静态文件 | FastAPI 进程内服务 | **中** — 可由 nginx 卸载以提升性能 |
| SSL 终端 | 无 | **高（生产环境）** — 必须 HTTPS |
| 请求大小限制 | 无 | **中** — 文件上传端点需要限制 |

### 3.2 综合判断

**当前阶段不适合引入完整的 API 网关（Kong / Traefik / APISIX 等），但适合引入轻量级反向代理（nginx）。**

理由：
- 项目为单体应用，没有多服务路由、服务发现、负载均衡的刚需
- 引入重量级网关会显著增加部署和维护复杂度，收益有限
- 但 nginx 作为反向代理可以低成本解决 SSL 终端、静态文件加速、请求大小限制、基础限流等实际问题

## 四、分阶段建议

### 4.1 短期（当前即可实施，无需新增服务）

在 FastAPI 层引入限流中间件：

```python
# 方案：slowapi（基于 limits 库，内存或 Redis 后端）
from slowapi import Limiter
from slowapi.util import get_remote_address

limiter = Limiter(key_func=get_remote_address)
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)

# 对生成类接口施加较严格限制（LLM 调用有成本）
@router.post("/generate")
@limiter.limit("5/minute")
async def generate(...): ...

# 对认证接口施加防暴力破解限制
@router.post("/auth/login")
@limiter.limit("10/minute")
async def login(...): ...
```

优点：零新增服务，部署方式不变，开发体验不变。

### 4.2 中期（部署到生产环境时）

在 uvicorn 前增加 **nginx 反向代理**，承担以下职责：

```nginx
server {
    listen 443 ssl;
    server_name your-domain.com;

    ssl_certificate     /etc/ssl/certs/server.crt;
    ssl_certificate_key /etc/ssl/private/server.key;

    # 静态文件直接由 nginx 返回（不再经过 FastAPI）
    location /app/ {
        root /opt/softbei/frontend;
    }

    # API 请求代理到 uvicorn
    location / {
        proxy_pass http://127.0.0.1:8000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        client_max_body_size 50m;  # 限制上传文件大小
    }

    # 基础限流
    limit_req_zone $binary_remote_addr zone=api:10m rate=10r/s;
    limit_req zone=api burst=20 nodelay;
}
```

收益：
- SSL/TLS 终端
- 静态文件性能提升（不需要经过 Python 进程）
- 请求体大小限制
- 基于 IP 的基础限流
- 不改变应用代码

### 4.3 长期（如果系统拆分为多服务）

仅当出现以下情况时，才值得引入完整 API 网关：

- 系统拆分为多个独立部署的微服务（如鉴权服务、Agent 执行服务、RAG 检索服务、KG 构建服务分别部署）
- 需要统一的服务发现、负载均衡、熔断降级
- 需要 API 版本管理、流量灰度发布

届时可考虑 Kong、Traefik 或云厂商的 API 网关产品。

## 五、当前安全缺口汇总

| 缺口 | 严重程度 | 建议修复方式 |
|------|----------|-------------|
| 无限流机制 | **高** | slowapi 中间件或 nginx `limit_req` |
| CORS 允许所有来源 (`*`) | 中 | 在 `configs/config.yaml` 中限制 `cors_origins` |
| `user_id` 作为查询参数回退 | 中 | 完成向纯 JWT 鉴权的迁移 |
| 无请求体大小限制 | 中 | FastAPI Request 限制或 nginx `client_max_body_size` |
| 静态文件由应用服务器提供 | 低 | 交由 nginx 处理 |
| 无 HTTPS（开发环境） | 低（开发）/ 高（生产） | nginx SSL 终端 |
