# 现有函数迁移为标准化工具的利弊分析

## 概述

本文档分析将项目中现有的命令式 Python 函数迁移为标准化 LLM 工具调用（OpenAI function calling / tool use）的**优点**与**缺点**，并给出按函数分类的迁移建议。

当前状态：所有"工具"（RAG 检索、视频搜索、画像查询等）均为 Python 函数，在 Agent 代码中**命令式调用**，LLM 完全不参与工具的选择与参数构造。迁移意味着将这些函数包装为 JSON Schema 定义的工具，由 LLM 自主决定何时调用、传什么参数。

---

## 1. 现有函数分类（按迁移可行性）

### 1.1 知识获取类（适合迁移）

| 函数 | 当前调用位置 | 当前调用时机 |
|------|-------------|-------------|
| `retrieve_context()` | 6 个生成 Agent 各自的 `run()` | 每次生成前**强制调用** |
| `search_videos()` | doc_agent、summary_agent 等 | 与 LLM 生成**并行调用**（`asyncio.gather`） |
| `resolve_kp_name()` | 各 Agent 的 `run()` 开头 | 每次**无条件调用** |

### 1.2 状态持久化类（不适合迁移）

| 函数 | 当前调用位置 | 原因 |
|------|-------------|------|
| `merge_chat_updates()` | profile_agent | 确定性副作用，不需要 LLM 决策 |
| `load_chat_history()` | graph `invoke()` | 基础设施操作，与 LLM 推理无关 |

### 1.3 输出解析类（迁移后消失）

| 函数 | 当前用途 | 迁移后 |
|------|----------|--------|
| `parse_json_llm_response()` | 剥离 Markdown 代码块 | 不再需要（工具返回结构化 JSON） |
| `safe_json_loads()` | 多策略 JSON 修复 | 不再需要（工具返回结构化 JSON） |

### 1.4 应保持强制执行的函数（绝不应迁移）

| 函数 | 原因 |
|------|------|
| `safety_agent` 的审查逻辑 | 安全审查必须**强制运行**，不能让 LLM 决定是否跳过 |
| `profile_agent` 的画像完备性检查 | 准入控制必须是确定性的，不能由 LLM 自主决定 |

---

## 2. 迁移的优点

### 2.1 结构化输出的可靠性提升

**当前问题**：JSON-in-Prompt 模式下，LLM 输出的 JSON 经常需要修复。`safe_json_loads()`（`backend/agents/utils.py:75-161`）包含 80+ 行的多策略修复逻辑：LaTeX 转义处理、截断 JSON 修复、从混合文本中提取 JSON 片段等。

```python
# 当前的脆弱模式（以 planner_agent 为例）
response = await chat_completion(messages)         # LLM 返回：```json\n{...}\n``` 或裸 JSON
result = safe_json_loads(response)                 # 可能失败，需要多层 fallback
resource_type = result.get("resource_type", "doc") # 缺字段时静默降级
```

**迁移后**：工具调用的 `arguments` 字段由模型在生成时即遵循 JSON Schema，不会出现 Markdown 包裹、字段缺失、类型错误等问题。`parse_json_llm_response()` 和 `safe_json_loads()` 可直接删除。

### 2.2 LLM 自主决定检索时机

**当前问题**：RAG 检索在每次生成前**无条件执行**。即使用户问的是"你好"或"刚才那份文档再显示一次"，也会触发一次完整的向量检索 + 查询改写（可能消耗 1-3 秒 + 额外 LLM 调用）。

```python
# doc_agent.py:38 — 无条件检索
context, retrieved_texts = await retrieve_context(state, "DocAgent", config)
```

**迁移后**：LLM 可以判断当前问题是否需要检索。对于简单对话、重复请求、纯闲聊，可直接跳过检索，节省延迟和 Token。

```
用户: "刚才的文档能再给我看看吗？"
LLM: 无需调用 search_knowledge_base，直接从历史中复述
用户: "解释一下反向传播的原理"  
LLM: → 调用 search_knowledge_base("反向传播 原理")
```

### 2.3 并行工具调用

**当前问题**：多个工具的协调依赖代码手动编排。`doc_agent.py:47-54` 使用 `asyncio.gather` 并行调用 LLM 和视频搜索，但这种并行是硬编码的——如果要同时检索知识库、查询 KG、搜索视频，需要手动修改每个 Agent 的代码。

```python
# doc_agent.py:47 — 硬编码的并行：仅 LLM + 视频搜索
draft, videos = await asyncio.gather(
    chat_completion(...),
    search_videos(kp_name),
)
```

**迁移后**：LLM 可在一个回合内发起多个独立的工具调用，框架自动并行执行：

```
LLM 单轮决策:
  → search_knowledge_base("决策树 信息增益")
  → search_videos("决策树 教学")
  → query_knowledge_graph("决策树")
  → get_student_profile_weaknesses()
四个调用并行执行，结果一次性返回给 LLM
```

### 2.4 动态工具组合

**当前问题**：工具调用链是代码固定的。以 doc_agent 为例，其流程不可变：检索 -> 生成 -> 视频搜索。如果 LLM 检索后发现内容不够，无法主动发起第二轮检索。

**迁移后**：LLM 可根据检索结果动态决策：

```
Turn 1: LLM → search_knowledge_base("CNN 卷积层")
        Tool → 返回 5 条结果，但缺少"padding 计算"细节
Turn 2: LLM → search_knowledge_base("CNN padding same valid 计算公式")
        Tool → 返回 3 条补充结果
Turn 3: LLM → 基于 8 条结果生成完整文档
```

这是 ReAct 模式的核心优势——Agent 可以"看到中间结果后再决定下一步做什么"。

### 2.5 减少 Prompt 体积

**当前问题**：所有上下文（检索结果、学生画像、视频列表、KG 数据）都在调用 LLM **之前**注入 system prompt。当上下文很大时（`context_max_tokens=3000`），prompt 长度膨胀，增加推理成本和延迟。

**迁移后**：上下文按需获取。LLM 在推理过程中发现缺少某方面信息时，主动调用工具获取，而非一次性塞入所有可能相关的数据。

### 2.6 模型供应商的原生支持

主流模型（GPT-4、Claude、Gemini、Qwen）对 function calling 的支持已非常成熟。部分模型（如 GPT-4 的 `strict` 模式）可**保证**输出的 JSON 完全符合 Schema，这是 prompt 约束无法达到的可靠性等级。

## 3. 迁移的缺点

### 3.1 API 延迟增加

**核心问题**：每次工具调用都是一次完整的 API 往返。

```
当前模式（1 次 LLM 调用）:
  代码检索(本地 500ms) → LLM 生成(3s) → 总计 ~3.5s

迁移后（可能 2-4 次 LLM 调用）:
  LLM 决策是否检索(1s) → 代码执行检索(500ms) → LLM 生成(3s) → 总计 ~4.5s
  如果 LLM 决定补充检索：
  LLM 决策(1s) → 代码检索(500ms) → LLM 生成(3s) → 总计 ~9s
```

在多轮工具调用场景下，延迟可能翻倍。对于教育场景中"学生等待课件生成"的体验，这是显著的退化。

### 3.2 Token 消耗增加

每次工具调用的额外 Token 开销：

| 开销项 | 估计 Token 数 |
|--------|--------------|
| 工具定义（每个工具的 JSON Schema） | 200-800 tokens |
| 工具调用消息（LLM 输出的 `tool_calls`） | 50-150 tokens |
| 工具返回结果（检索到的文本） | 500-3000 tokens |
| 多轮对话中的重复工具定义 | 取决于是否使用 `tool_choice` 控制 |

以 5 个工具定义、每次调用 2 个工具为例，每次请求的固定开销约 2000-4000 tokens。在日均 1000 次调用的规模下，这是可观的成本增长。

### 3.3 LLM 可能做出错误的工具决策

**核心风险**：LLM 不是确定性的，它可能：

| 错误类型 | 具体表现 | 后果 |
|----------|----------|------|
| 跳过检索 | LLM 认为"自己知道"，不调用检索工具 | 凭记忆编造内容（教育场景的高危行为） |
| 错误参数 | 传给 `search_knowledge_base` 的 query 质量差 | 检索结果不相关，生成质量下降 |
| 多余调用 | LLM 调用不需要的工具 | 浪费延迟和 Token |
| 漏调用 | 应该调用但没调用某个工具 | 缺少关键信息 |

**反例**：在当前的确定性模式下，"每次生成前必定检索"虽然"浪费"了不必要的检索，但**确保了不会出现 LLM 跳过检索直接编造**的情况。在教育场景中，宁可多检索一次，也不能让 LLM 凭空生成错误的教学内容。

### 3.4 当前模型的 Function Calling 质量存疑

项目当前使用 `qwen3.6-plus-2026-04-02`。千问系列模型的 function calling 能力相比 GPT-4/Claude 存在差距：

- **工具选择准确性**：多工具场景下是否稳定选择正确的工具
- **参数填充质量**：复杂参数（如嵌套对象、数组）的填充是否正确
- **并行调用判断**：是否能正确识别可并行的工具调用
- **不调用判断**：是否能正确判断"不需要调用工具"的场景

在切换到 function calling 之前，需要对当前模型进行针对性的工具调用准确率评估。

### 3.5 流式输出复杂度大幅上升

**当前问题**：`stream_chat_completion()`（`backend/services/llm.py:135-177`）仅处理 `delta.content`，逻辑简单直接。

**迁移后**：需要处理 `delta.tool_calls` 的增量累积：

```
流的每个 chunk 可能包含:
  - content delta（文本片段）
  - tool_call delta（工具调用的 id、name、arguments 片段）
  - 两者同时出现

需要维护的状态:
  - 当前正在累积的 tool_call 对象
  - 已完成的 tool_call 列表
  - 是否所有 tool_calls 已结束（finish_reason == "tool_calls"）
```

前端也需要相应改造：当前前端假设流式输出是纯文本，如果 LLM 中途决定调用工具，前端需要展示"正在检索知识库..."等中间状态。

### 3.6 图路由逻辑需要重构

**当前模式**：`graph.py` 的条件路由基于 `AgentState` 的枚举字段（`resource_type`、`intent_type`），清晰且可预测。

**迁移后**：如果 LLM 通过工具调用决定行为，路由逻辑需要解析 `tool_calls` 消息。LangGraph 虽然提供了 `ToolNode` 来简化工具执行-反馈循环，但将其集成到现有的 11 节点图中需要：

```
当前图的节点: agent 函数
迁移后可能新增: ToolNode（工具执行）、should_continue（判断是否继续调用工具）
图的复杂度: 条件边从当前的 3 条增加到 6+ 条
```

### 3.7 调试和可观测性退化

**当前模式**：每个工具调用都是 Python 函数调用，可以直接在代码中打断点、加日志。

```python
logger.info("[DocAgent] RAG 检索到 %d 条参考资料" % len(chunks))  # 清晰
```

**迁移后**：工具调用的决策在 LLM 的消息中，需要解析 `tool_calls` 才能知道 LLM 做出了什么决策。日志需要额外记录：

```python
logger.info("[DocAgent] LLM 调用了工具: %s, 参数: %s" % (tool_name, args))
logger.info("[DocAgent] 工具返回: %d 条结果" % len(result))
```

### 3.8 当前方案在自身场景中已经够用

这是最关键的反驳论点。本项目的任务类型是**封闭的教育资源生成**：

- 资源类型只有 6 种（文档、测验、思维导图、代码、动画、摘要）
- 每个生成任务一定需要检索知识库
- 检索和生成之间没有"根据检索结果动态调整"的需求（当前的策略 A+B+C 查询改写已经覆盖了检索质量优化）
- 没有需要 LLM 动态发现的外部 API

**在确定性场景中，确定性代码比 LLM 决策更可靠。** 当前架构在这个场景下不存在"不够用"的问题，迁移的主要驱动力是"架构形式上的标准化"而非"功能上的必须"。

## 4. 分类评估：哪些函数值得迁移

### 4.1 推荐不迁移

| 函数 | 理由 |
|------|------|
| `retrieve_context()` | 教育资源生成**必须检索**，不应让 LLM 决定是否跳过。当前查询改写（策略 A+B+C）已足够优化检索质量。 |
| `safety_agent` | 安全审查是硬约束，不能被 LLM 绕过。 |
| `profile_agent` 的画像检查 | 准入控制必须是确定性的。 |
| `merge_chat_updates()` | 数据库写入是副作用，不需要 LLM 参与。 |
| `load_chat_history()` | 基础设施操作。 |

### 4.2 可选迁移（收益有限）

| 函数 | 场景 | 收益 |
|------|------|------|
| `search_videos()` | LLM 根据生成内容的相关性决定是否搜索视频、搜索什么关键词 | 避免无关视频搜索浪费 API 配额 |
| `planner_agent` 的资源类型分类 | 用工具 Schema 的 `enum` 约束 `resource_type` 字段 | 消除 `safe_json_loads` + 缺省值 fallback |

### 4.3 建议迁移（但优先级低）

| 函数 | 场景 | 收益 |
|------|------|------|
| `recommend_agent` 的知识点推荐 | Schema 约束 `recommendations` 必须是 `available_kps` 列表中的值 | 当前 prompt 约束已能做到，迁移主要消除解析脆弱性 |

### 4.4 总结

```
适合迁移的函数占比: 约 10-20%
不适合迁移的函数占比: 约 80-90%
```

大多数现有函数的"命令式调用"特征与教育场景的确定性需求是吻合的，迁移的收益不足以覆盖成本。

---

## 5. 如果决定迁移：建议路径

### 5.1 前置条件

1. **模型评估**：对 `qwen3.6-plus` 进行工具调用准确率基准测试（工具选择准确率、参数填充正确率、并行调用识别率）
2. **成本模拟**：基于当前日均调用量，模拟迁移后的 Token 消耗增量
3. **延迟预算**：确认产品可接受的端到端延迟上限，评估多轮工具调用的延迟是否超限

### 5.2 渐进式路径

```
阶段 1（试点）:
  选择最独立的场景——planner_agent 的资源类型分类
  将 JSON-in-Prompt 替换为 function calling
  对比格式正确率、解析失败率、延迟差异
  
阶段 2（评估）:
  如果阶段 1 的结果显著优于当前模式（正确率提升 >5%，延迟增加 <20%）
  则推进到 search_videos 的工具化
  
阶段 3（谨慎扩张）:
  仅在确认收益的场景中逐步推广
  核心检索（retrieve_context）保持命令式调用
  
阶段 4（长期观察）:
  等待 qwen 模型的 function calling 能力进一步成熟
  或切换到 function calling 更强的模型后再评估全量迁移
```

### 5.3 需要改造的模块

如果迁移 `planner_agent` 和 `search_videos`，需要改动：

| 模块 | 改动内容 | 工作量估计 |
|------|----------|-----------|
| `backend/services/llm.py` | `chat_completion()` 增加 `tools`、`tool_choice` 参数；返回值从 `str` 改为 `ChatResponse` 结构体 | 60-80 行 |
| `backend/services/llm.py` | `stream_chat_completion()` 处理 `delta.tool_calls` 增量累积 | 50-70 行 |
| `backend/agents/planner_agent.py` | prompt 中的 JSON 格式说明改为工具定义；解析逻辑从 `safe_json_loads` 改为读取 `tool_calls` | 30-40 行 |
| `backend/agents/doc_agent.py` 等 | 视频搜索从 `asyncio.gather` 改为工具调用（如果迁移 search_videos） | 每个 Agent 20-30 行 |
| `backend/agents/graph.py` | 可选的 `ToolNode` 集成（如果引入需要结果反馈的工具） | 30-50 行 |
| `backend/config.py` | 工具配置项（启用列表、超时等） | 15-25 行 |
| `configs/prompts.yaml` | 部分 prompt 调整为适配工具调用模式 | 20-40 行 |

## 6. 结论

| 维度 | 评估 |
|------|------|
| **功能必要性** | 低。当前命令式模式在封闭的教育场景中功能完全满足需求。 |
| **质量提升** | 中。结构化输出的可靠性会提升，但消除的 `safe_json_loads` 脆弱性在整体错误率中占比不大。 |
| **灵活性提升** | 高。LLM 自主工具选择带来动态组合能力，但教育场景对这种灵活性的需求有限。 |
| **成本增加** | 中高。延迟和 Token 消耗均有可观的增量。 |
| **风险** | 中高。LLM 可能做出错误的工具决策（跳过检索、错误参数），教育场景对此类错误的容忍度极低。 |
| **工程复杂度** | 高。LLM 服务层、流式处理、图路由、前端均需改造。 |

**当前不建议全量迁移。** 如果未来出现以下需求，再重新评估：

1. 系统需要接入动态变化的外部 API（如实时论文检索、在线编译器）
2. 用户交互模式从"一次性生成"转向"多轮对话式探索"
3. 当前模型的 function calling 能力经过评估确认可靠
4. 产品对"延迟少量增加"可接受，且愿意用 Token 成本换取灵活性

在此之前，保持当前的命令式工具调用模式是合理的选择。
