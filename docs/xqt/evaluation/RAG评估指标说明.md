# RAG 评估指标说明

> 对应报告文件：`logs/rag_eval_report_*.md`

---

## 一、报告结构

报告分三大板块：**检索质量**（Retrieval）、**生成质量**（Generation）、**系统效率**（Latency）。每项指标附参考标准（业界基准）和达标状态（✅ / ❌）。

---

## 二、检索质量

检索质量衡量**从知识库中召回参考资料的能力**。这些指标由 LLM-as-Judge 对召回的 5 个 chunk 进行相关度标注（0=无关, 1=部分相关, 2=高度相关）后计算得出。

### Precision@5

> 前 5 个结果中，相关结果的比例。

**公式：** `相关文档数 / 5`

```
召回了 5 个 chunk，其中 3 个相关 → P@5 = 3/5 = 0.60
```

**含义：** 搜回来的东西有多"准"。越高说明搜索结果越少噪音。值低意味着 top-5 里夹了很多无关内容，会影响 LLM 生成质量。

**参考标准：** > 0.60

### Recall@5

> 前 5 个结果中命中了多少"应该被找到的"文档。

**公式：** `命中的相关文档数 / 知识库中相关文档总数`

```
知识库中实际有 8 篇相关内容，只搜到了 3 篇 → R@5 = 3/8 = 0.375
```

**含义：** 搜回来的是否够"全"。值低说明知识库中有很多相关内容没有被检索到。Precision 和 Recall 通常需要一起看——Precision 高但 Recall 低，说明搜得准但搜得不全。

**参考标准：** > 0.70

### MRR (Mean Reciprocal Rank)

> 第一个相关结果出现位置倒数的均值。

**公式：** `1 / (第一个相关结果的排名)`

```
第 1 名的 chunk 就相关 → MRR = 1/1 = 1.000
第 3 名的 chunk 才相关 → MRR = 1/3 = 0.333
没有一个相关            → MRR = 0
```

**含义：** 衡量"最相关的文档是否排在第一"。RAG 系统中，最相关的 chunk 排在越前面，LLM 越容易利用它的信息。多条查询取平均值。

**参考标准：** > 0.50

### NDCG@5 (Normalized Discounted Cumulative Gain)

> 考虑排序位置加权的综合排名质量。

**核心思想：** 相关文档排在前面比排在后面更有价值，而且高度相关（2 分）比部分相关（1 分）更好。

**公式：** `DCG@5 / IDCG@5`

- DCG = 每个位置上 (2^相关分 - 1) / log₂(排名+1)，位置越靠后折扣越大
- IDCG = 理想排序（相关分从高到低）的 DCG，作为归一化分母

```
实际排序：相关分 [2, 1, 0, 2, 0]
理想排序：相关分 [2, 2, 1, 0, 0]
NDCG = DCG(实际) / DCG(理想)
```

**含义：** NDCG 是检索排序的最综合指标，同时评估"准不准"和"顺序对不对"。1.0 表示完美排序。

**参考标准：** > 0.60

### Hit Rate@5

> Top-5 中至少有一条相关结果的查询占比。

**公式：** `至少命中一条的查询数 / 总查询数`

```
10 条查询中，8 条至少搜到了 1 个相关文档 → Hit Rate = 0.80
```

**含义：** 也就是"不空手而归"的概率。对 RAG 来说非常关键——哪怕 Precision 看起来一般，只要 Hit Rate 高，LLM 总能至少拿到一点参考资料。

**参考标准：** > 0.80

### Score P50

> 检索分数的中位数。

**公式：** 所有检索结果分数的第 50 百分位。

```
5 个 chunk 分数：[0.72, 0.68, 0.65, 0.55, 0.42]
P50 = 0.65（排序后取中间值）
```

**含义：** 反映向量检索的"置信度水平"——chunk 与查询的余弦相似度中位值。持续走低可能说明 embedding 模型不适配当前文档内容，或知识库需要更新。

**参考标准：** > 0.65

## 三、生成质量

生成质量由 **LLM-as-Judge** 评估。系统会用另一个 LLM 调用对生成内容打分，而非简单的规则匹配。

### Avg Faithfulness（忠实度）

> 生成内容中有多少陈述可以被参考资料"证实"。

**评估流程：**

1. Judge LLM 先把生成内容拆成多条原子陈述（statements）
2. 逐条与检索到的参考资料比对
3. 标注每条是 `supported`（有据可查）还是 `unsupported`（无中生有）

**公式：** `supported 陈述数 / 总陈述数`

```
生成了 9 条陈述 → Judge 判定 7 条 supported, 2 条 unsupported
Faithfulness = 7/9 ≈ 0.78
```

**含义：** 这是 **RAG 最重要的生成指标**。值低说明 LLM 在"编造"而不是"引用"——也就是幻觉。0.82 意味着仍有 18% 的内容无法从参考资料中验证。

**参考标准：** > 0.70

### Avg Hallucination Rate（幻觉率）

> 生成内容中无法被参考资料证实的比例。

**公式：** `unsupported 陈述数 / 总陈述数` = 1 - Faithfulness

**含义：** Faithfulness 的反面。0.18 表示 18% 的陈述是 LLM 自己的知识补充或编造。一定的补充（如举例、比喻）对教学来说可以接受，但超过 30% 需要警惕。

**参考标准：** < 0.30

### Avg Concept Coverage（概念覆盖率）

> 生成内容涵盖了知识点的多少关键方面。

**评估流程：**

1. Judge LLM 先根据知识点名称，生成该知识点"应该涵盖的核心方面"列表（通常 5-8 个）
2. 再逐一检查生成内容是否覆盖了这些方面
3. 覆盖的方面数 / 总方面数

```
知识点"机器学习"应有 7 个核心方面：
  "定义与问题形式"          ← 已覆盖
  "监督/无监督/强化学习分类" ← 已覆盖  
  "训练/验证/测试集划分"    ← 已覆盖
  "过拟合与欠拟合"          ← 未覆盖
  "常见算法概览"            ← 未覆盖
  "评估指标"                ← 未覆盖
  "应用场景"                ← 未覆盖
Completeness = 3/7 ≈ 0.43
```

**含义：** 衡量生成内容是否"讲全了"。值低不一定是幻觉——可能只是内容不完整。教学场景中，如果学生只需要入门介绍，低 coverage 也可以接受。但配合高 faithfulness + 低 coverage，通常意味着内容偏"浅"。

**参考标准：** > 0.60

## 四、系统效率

### P50 Retrieval Latency

> 检索延迟中位数——50% 的检索请求在这个时间内完成。

**含义：** 反映"典型用户体验"的检索速度。包括 embedding + 向量检索 + DB 查询的全链路耗时。当前 2641ms 偏高，说明向量检索或 DB 查询是瓶颈。

**参考标准：** < 500 ms

### P95 Retrieval Latency

> 检索延迟第 95 百分位——最慢的 5% 请求的耗时。

**含义：** 反映"最坏情况"。P95 和 P50 差距大说明延迟波动剧烈（可能有排队或冷启动问题），两者接近说明性能稳定。

**参考标准：** < 1000 ms

### P50 Generation Latency

> LLM 生成内容耗时的中位数。

**含义：** 从调用 LLM 到拿到完整回复的时间。受模型速度、生成 token 量、API 负载影响。当前为 0ms 是因为生成耗时未被正确记录到 collector（agent 没有回写 `generation_latency_ms` 到 state.metadata）。

**参考标准：** < 5000 ms

## 五、如何解读一份报告

### 理想情况

```
Precision@5 = 1.0, Recall@5 = 0.8+ → 检索又准又全
Faithfulness = 0.9+                   → 几乎无幻觉
Completeness = 0.7+                   → 内容覆盖全面
P50 Latency < 500ms                   → 检索速度快
```

### 常见异常模式和排查方向

| 现象 | 可能原因 | 排查方向 |
|------|---------|---------|
| Precision 低、Hit Rate 正常 | 检索回了相关但不精确的文档 | 调高 score_threshold 或缩小 chunk_size |
| Precision 高、Recall 低 | 知识库内容不全 | 补充知识库文档，检查 chunk_overlap |
| Faithfulness 低 | LLM 过度自由发挥 | 优化 agent prompt 强调"严格基于参考资料" |
| Completeness 低、Faithfulness 高 | 内容准确但不全面 | 调高 context_max_tokens，增加检索数量 |
| Faithfulness 和 Completeness 都低 | 检索回了无关内容，LLM 在瞎编 | 检索质量是根因，先解决 Precision |
| P50 延迟高、结果稳定 | 系统性能瓶颈 | 检查 embedding API 耗时、DB 连接池 |
| P50 和 P95 差距大 | 冷启动或排队 | 检查连接池预热、embedding 并发设置 |

### 最重要的一条

**Faithfulness > Completeness。** 宁可内容不全面，也不要内容不准确。学生拿到一份有 60% 覆盖但全部正确的资料，远比拿到一份 100% 覆盖但有错误信息的资料要好。
