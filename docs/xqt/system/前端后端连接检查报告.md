# 前端后端连接检查报告

检查日期: 2026-06-10
检查范围: 前端 (frontend/) 与后端 (backend/) 的 API 连接、字段对齐、代码 bug


## 一、Security 问题

### 1.1 部分端点缺少身份验证

**文件**: `backend/main.py:554,563,573,1200,1558` 等多处

以下端点使用裸 `user_id: int` 而非 `user_id: int = Depends(get_current_user_id)`：

| 端点 | 行号 |
|------|------|
| `GET /profile` | 554 |
| `PUT /profile` | 563 |
| `GET /profile/history` | 573 |
| `POST /generate/smart` | 1178 |
| `GET /resources` | 1200 |
| `POST /records` | 1546 附近 |

这意味着任何调用者传入任意 `user_id` 即可读取/修改其他用户的画像和资源。虽然前端 `api.js` 会附加 JWT token 到 `Authorization` header，但**后端未校验 token 所有者与请求 `user_id` 是否一致**。通过 curl 等工具可直接跨用户访问。

**建议**: 统一使用 `user_id: int = Depends(get_current_user_id)`，用认证后的 user_id 代替请求参数中的 user_id。

### 1.2 `/kg/graph` 端点无认证参数

**文件**: `backend/main.py:878`

`GET /kg/graph` 不强制要求 `user_id` 参数（仅作为可选查询参数），这意味着未登录调用可能获取到所有用户的知识图谱数据。

**建议**: 将 `user_id` 改为必填并通过 `Depends(get_current_user_id)` 传入。


## 二、Schema 与 ORM 字段命名不一致（设计风险）

### 2.1 LearningPath: `name` vs `title`

| 层次 | 字段名 |
|------|--------|
| ORM (`LearningPath`) | `title` |
| Schema (`LearningPathOut`, `LearningPathCreate`, `LearningPathUpdate`) | `name` |
| 前端 HTML (`pathway.html`) | `.name` |

目前通过 `backend/services/pathway.py:_path_to_out()` 手动映射，功能正常，但有潜在风险：

- `LearningPathOut` 设置了 `model_config = {"from_attributes": True}`（schemas.py:232），但由于 ORM 无 `name` 属性，若任何代码直接调用 `LearningPathOut.model_validate(orm_obj)`，将**静默产生 `name=None` 的响应**。
- 这违反了 `CLAUDE.md` 的命名约定（"Schema field names must exactly match ORM field names"）。

**建议**: 将 Schema 的 `name` 改为 `title` 匹配 ORM，或给 `LearningPathOut` 添加 `field_validator` 做 `name = title` 的 fallback 映射。

### 2.2 KGNodeOut: `type` vs `node_type`

| 层次 | 字段名 |
|------|--------|
| ORM (`KGNode`) | `node_type` |
| Schema (`KGNodeOut`) | `type` |
| 前端 (`pathway.html`, `generate.html`) | `.type` |

在 `main.py:965` 处手动构建 `KGNodeOut(type=KGNodeType(n.node_type), ...)` 实现映射。当前前端均使用 `.type`，功能正常。但与 2.1 同样存在 `from_attributes=True` 无法自动映射的隐患。

### 3.3 pathway.html 绕过 api.js 直接 fetch

**文件**: `frontend/pathway.html:1873`

```javascript
await fetch(`/pathways/${pathId}/items/${itemId}?user_id=${encodeURIComponent(userId)}`, { method: 'DELETE' });
```

此调用绕过了 `apiFetch()` 的 401 统一处理和 auth header 注入，与其他页面的 API 调用模式不一致。如果 token 过期，用户不会自动跳转到登录页。

**建议**: 将该调用移到 api.js 提供统一封装（如 `deletePathwayItem`）。


## 四、前端代码问题

### 4.1 未使用的 import

| 文件 | 行号 | 未使用的导入 |
|------|------|-------------|
| `evaluate.html` | 601 | `clearAuth` |
| `library.html` | 616 | `clearAuth`, `postLearningRecord` |
| `pathway.html` | 764 | `clearAuth` |

虽不影响功能，但增加代码噪音。

### 4.2 auth.html catch 块为死代码

**文件**: `frontend/auth.html:158, 186`

```javascript
try {
    const result = await authLogin(username, password);
    // ...
} catch (e) { showAlert('网络异常，请稍后重试'); }   // 永远不可达
```

`authLogin` / `authRegister` 在 `api.js` 内部已经 `try/catch` 所有异常并返回 `null`，不会对外抛出。因此 auth.html 中的 `catch (e)` 块永远不会执行，`showAlert('网络异常，请稍后重试')` 是死代码。

**建议**: 移除 `try/catch`，仅依赖函数返回值的 null 检查。

### 4.3 chat.html 学习路径保存失败静默无提示

**文件**: `frontend/chat.html:655-660`

```javascript
const path = await createPathway(userId, '智能推荐路径');
if (path && path.id) {
    // loop and add items...
    showToast('已保存为学习路径', 'success');
}
// 如果 path 为 null/undefined → 静默无提示，用户不知道失败
```

当 `createPathway` 返回 `null`（如网络故障或 401）时，用户点击"保存为学习路径"按钮后完全无反馈。

**建议**: 添加 else 分支显示错误提示。

### 4.4 chat.html 批量状态轮询卡死

**文件**: `frontend/chat.html:686`

```javascript
const status = await getBatchStatus(batchId);
if (!status) return;  // 返回 null 时直接退出，polling 终止
```

当 `getBatchStatus` 因网络故障返回 `null` 时，`setTimeout` 轮询链断裂，进度卡片永久停留在"正在为您生成额外资源..."，不会报告错误也不会重试。

**建议**: 添加错误计数和重试机制，或至少显示失败状态。

### 4.5 profile.html `getLearningAnalytics` 数据取而未用

**文件**: `frontend/profile.html:412-414`

```javascript
const [profile, analytics] = await Promise.all([
    getProfile(userId),
    getLearningAnalytics(userId),   // 发起请求但 analytics 从未被使用
]);
```

`analytics` 变量解构后从未被读取。这是一个无效的网络请求和服务器负载。

**建议**: 如需使用分析数据则消费它，否则删除此调用。

### 4.6 `postLearningRecord` 导入但未用（library.html）

**文件**: `frontend/library.html:616`

`library.html` 导入了 `postLearningRecord` 但从未调用。用户在资源库中浏览/预览资源时，学习行为未被记录。

**建议**: 在资源查看交互中加入 `postLearningRecord` 调用，记录 "view" 行为。

### 4.7 `generate.html` 缺少 `kg` 资源类型卡片

**文件**: `frontend/generate.html`

后端 `ResourceType` 枚举包含 7 种类型，`plan_resource_types()` 可能返回 `"kg"`。但 generate.html 只有 6 张资源类型卡片（doc / mindmap / quiz / code / summary / animation），**缺少 `data-type="kg"` 的卡片**。

当 `/generate/smart` 推荐 `kg` 类型时，前端找不到对应卡片并静默忽略。

**建议**: 若要支持知识图谱作为生成资源类型，需添加对应 UI 卡片；否则后端应排除 `kg` 类型。

### 4.8 `KGNodeOut.difficulty` 和 `is_core` 永为固定值

**文件**: `backend/main.py:962-971`, `backend/models/schemas.py:180-181`

`/kg/graph` 端点返回的节点中：
- `difficulty` 始终为 `null`
- `is_core` 始终为 `false`

这两个字段在 `kg_node` 表中没有对应列，没有任何代码会填充真实值。前端 `pathway.html` 和 `evaluate.html` 不直接访问这两个字段，目前无前端 bug，但若未来前端依赖它们会出问题。

**建议**: 如暂时不需要，从 `KGNodeOut` 中移除这两个字段；如需要，在 `kg_node` 表中添加对应列。
