# 日志系统优化与升级方案

> 状态: 提案 | 日期: 2026-05-28 | 作者: 日志系统审查

---

## 一、现状总览

| 维度 | 当前状态 |
|------|---------|
| 框架 | loguru |
| 配置文件 | `backend/logging_config.py`（模块级副作用） |
| 配置来源 | `configs/config.yaml` → `backend/config.py` → `LoggingConfig` |
| 控制台输出 | 彩色、INFO+、stdout |
| 文件日志 | `logs/app_YYYY-MM-DD.log`（DEBUG+、每日轮转、ZIP 压缩、保留 30 天） |
| 错误日志 | `logs/error_YYYY-MM-DD.log`（ERROR+、每日轮转、**无压缩**、保留 90 天） |
| 请求中间件 | `LoggingMiddleware`，含 trace_id + 请求/响应耗时 |
| trace_id 传播 | **仅写入消息文本**，未注入 loguru `extra` |
| 结构化/JSON 日志 | 无 |
| 日志级别可配置性 | **全部硬编码**，无法通过环境变量或配置调整 |
| 数据库日志 | 无（仅有 SQLAlchemy `echo` 到 stdout） |
| 消息格式一致性 | 混合 f-string / %-格式化 / 字符串拼接 |
| Agent 前缀约定 | 统一 `[AgentName]`，执行良好 |
| `print()` 误用 | 3 个生产文件 + 若干 evaluation 脚本 |

## 二、问题分级

### P0 — 严重问题（应立即修复）

#### 2.1 `clarify_agent.py` 使用 stdlib `logging`，日志静默丢失

```python
# backend/agents/clarify_agent.py:75-76
import logging
logging.getLogger(__name__).warning(f"[ClarifyAgent] LLM 调用失败: {e}")
```

stdlib `logging` 在项目中没有配置任何 handler，这条 warning **永远不会出现在任何日志输出中**。

#### 2.2 错误日志文件无压缩

`error_{date}.log` 保留 90 天但不压缩，随着系统运行可能积累数十 GB。对比 `app_{date}.log` 正确配置了 `compression="zip"`。

#### 2.3 `generation.py` 使用 `traceback.print_exc()` 绕过 loguru

```python
# backend/services/generation.py:167-171
import traceback as tb
tb.print_exc()
logger.error("[run_generation] unexpected error: %s | %r", exc, exc)
```

`print_exc()` 输出到 stderr，不经过 loguru 的 sink 管道，在重定向 stderr 的环境中会丢失。

### P1 — 高优先级（影响可观测性）

#### 2.4 trace_id 未注入 loguru `extra`，无法结构化过滤

当前 trace_id 仅存在于消息字符串中（`[{trace_id}]`），无法被 loguru 的 `filter` 或 `extra` 机制识别。后果：
- 无法按 trace_id 过滤或聚合日志
- 后台任务/异步上下文中 trace_id 不自动携带
- 若后续接入 ELK/Datadog 等平台，无法按 trace_id 搜索

#### 2.5 日志级别全部硬编码，不可动态调整

控制台固定 INFO，文件固定 DEBUG。线上排查时无法临时提升日志级别，也无法在开发环境降低为 DEBUG 控制台输出。缺少 `LOG_LEVEL` 环境变量。

#### 2.6 数据库模块零日志

`backend/db/database.py` 没有任何 logger 调用。连接池状态、会话异常、事务回滚全部静默。SQLAlchemy 的 `echo=True` 直接写入 stdout，不使用 loguru。

#### 2.7 `print()` 在生产代码中误用

| 文件 | 行号 | 内容 |
|------|------|------|
| `backend/agents/clarify_agent.py` | 56, 58 | `print("提取的对话主题:", topic)` |
| `backend/services/video_search.py` | 60 | `print("视频提取关键词:", ...)` |

此外 `backend/evaluation/` 下的 `ab_experiment.py`、`analyzer.py`、`golden_dataset.py`、`reporter.py` 也大量使用 `print()`，但这些主要是 CLI 工具，优先级较低。

### P2 — 中优先级（影响开发效率与长期维护）

#### 2.8 消息格式不一致

三种格式化风格混合使用：

```python
# 风格 A — f-string（每次都计算，忽略日志级别过滤）
logger.info(f"[DocAgent] kp_name={kp_name}")

# 风格 B — %-格式化（延迟求值，仅在需要输出时计算）
logger.info("[DocAgent] kp_name=%s", kp_name)

# 风格 C — 手动字符串拼接
logger.info("[chat] returning metadata keys=%s" % list(result.metadata.keys()))
```

风格 A 即使日志级别被过滤也会执行 f-string 求值，对于频繁调用且包含复杂计算的场景存在性能浪费。风格 B 是 loguru 推荐的方式。

#### 2.9 无健康检查端点过滤

`LoggingMiddleware` 对所有请求一视同仁地记录。Kubernetes 探活/探就绪通常每秒 1-2 次，产生大量无意义日志。

#### 2.10 无业务事件日志

当前日志全是技术日志（函数名、行号），缺少业务语义。例如"生成了文档资源"、"测验提交成功"等业务事件没有统一的记录格式，不利于产品和运营分析。

### P3 — 低优先级（锦上添花）

#### 2.11 无用 logger 导入

多个文件包含 `from loguru import logger  # noqa: F401`，其中部分文件的 logger 确实未被使用（如 `backend/services/llm.py`）。属于轻度技术债务。

#### 2.12 日志模块初始化方式不够优雅

`backend/logging_config.py` 在 import 时产生副作用（创建目录、修改全局 logger 状态）。这是 loguru 的常见用法，但如果多个模块以不同顺序 import 可能导致配置被覆盖。

## 三、优化方案（分阶段实施）

### 阶段一：紧急修复（1-2 小时）

#### 3.1.1 修复 `clarify_agent.py` 的日志丢失

# 改前

#### 3.1.3 错误日志文件添加压缩

**影响文件**：`backend/logging_config.py`

#### 3.1.4 `print()` 替换为 logger

**改动**：
- `clarify_agent.py` 第 56、58 行 → `logger.debug(...)`
- `video_search.py` 第 60 行 → `logger.debug(...)`

**影响文件**：`backend/agents/clarify_agent.py`、`backend/services/video_search.py`

### 阶段二：结构化与可观测性升级（3-5 小时）

#### 3.2.1 trace_id 注入 loguru `extra`

**核心思路**：利用 `logger.contextualize()` 或 `logger.bind()` 将 `trace_id` 注入 loguru record 的 `extra` 字典。

**方案对比**：

| 方案 | 优点 | 缺点 |
|------|------|------|
| A. `logger.configure(patcher=...)` | 全局自动化，无需改动业务代码 | patcher 在每次日志调用时执行 |
| B. `logger.bind(trace_id=...)` | 标准 loguru API | 需要手动在每处获取 logger 时 bind |
| C. `logger.contextualize(trace_id=...)` | 上下文管理器，自动传播 | 需要包裹业务逻辑 |

**推荐方案 A + C 组合**：

1. 在 `logging_config.py` 中添加 `patcher`，自动从 `ContextVar` 读取 `trace_id` 注入 `extra`：

```python
# backend/logging_config.py 新增

from backend.middleware.logging_middleware import trace_id_var

def _inject_trace_id(record):
    """将 ContextVar 中的 trace_id 注入每条日志的 extra 字段。"""
    record["extra"]["trace_id"] = trace_id_var.get()

logger.configure(patcher=_inject_trace_id)
```

2. 更新日志格式，在控制台和文件 sink 中包含 trace_id：

```python
format=(
    "<green>{time:YYYY-MM-DD HH:mm:ss}</green> | "
    "<level>{level: <8}</level> | "
    "{extra[trace_id]} | "           # ← 新增
    "<cyan>{name}</cyan>:<cyan>{function}</cyan>:<cyan>{line}</cyan> - "
    "<level>{message}</level>"
)
```

3. 对于后台任务，在入口处绑定 trace_id：

```python
# backend/services/generation.py
from backend.middleware.logging_middleware import trace_id_var, generate_trace_id

async def run_generation(...):
    trace_id_var.set(generate_trace_id())
    ...
```

**注意**：移除中间件消息中的手动 `[{trace_id}]` 前缀，避免重复。

**影响文件**：`backend/logging_config.py`、`backend/middleware/logging_middleware.py`、`backend/services/generation.py`

#### 3.2.2 JSON 结构化日志（可切换）

**目标**：支持开发环境的可读格式 + 生产环境的 JSON 格式，通过配置切换。

**实现**：在 `configs/config.yaml` 中添加：

```yaml
logging:
  dir: "logs"
  retention_days: 30
  error_retention_days: 90
  trace_id_length: 8
  json_format: false          # ← 新增：生产环境设为 true
  level: "DEBUG"              # ← 新增：全局日志级别
  console_level: "INFO"       # ← 新增：控制台级别
```

在 `logging_config.py` 中添加 JSON sink（仅在 `json_format=true` 时启用）：

```python
import json

def json_formatter(record):
    """将 loguru record 序列化为 JSON 行。"""
    log_entry = {
        "timestamp": record["time"].isoformat(),
        "level": record["level"].name,
        "trace_id": record["extra"].get("trace_id", "-"),
        "logger": record["name"],
        "function": record["function"],
        "line": record["line"],
        "message": record["message"],
    }
    if record["exception"]:
        log_entry["exception"] = {
            "type": record["exception"].type.__name__,
            "value": str(record["exception"].value),
            "traceback": record["exception"].traceback,
        }
    return json.dumps(log_entry, ensure_ascii=False, default=str) + "\n"

if config.logging.json_format:
    logger.add(
        LOG_DIR / "app_{time:YYYY-MM-DD}.jsonl",
        format=json_formatter,
        level=config.logging.level.upper(),
        rotation="00:00",
        retention=f"{config.logging.retention_days} days",
        compression="zip",
        enqueue=True,
    )
```

**影响文件**：`configs/config.yaml`、`backend/config.py`、`backend/logging_config.py`

#### 3.2.3 可配置日志级别

**改动**：从 `config.yaml` 或环境变量读取日志级别，替换硬编码值。

```python
# backend/config.py 新增字段
class LoggingConfig(BaseModel):
    dir: str = "logs"
    retention_days: int = 30
    error_retention_days: int = 90
    trace_id_length: int = 8
    json_format: bool = False
    level: str = "DEBUG"           # 文件日志级别
    console_level: str = "INFO"    # 控制台日志级别

# backend/logging_config.py 使用配置
logger.add(sys.stdout, level=config.logging.console_level.upper(), ...)
logger.add(LOG_DIR / "app_{time}.log", level=config.logging.level.upper(), ...)
```

**影响文件**：`configs/config.yaml`、`backend/config.py`、`backend/logging_config.py`

#### 3.2.4 数据库日志集成

**目标**：捕获 SQLAlchemy 的连接池事件和 SQL 执行日志，通过 loguru 统一输出。

**实现**：

```python
# backend/db/database.py 新增

from loguru import logger
import logging as stdlib_logging

class LoguruHandler(stdlib_logging.Handler):
    """将 stdlib logging 桥接到 loguru。"""
    def emit(self, record):
        logger.opt(depth=6, exception=record.exc_info).log(
            record.levelname, record.getMessage()
        )

# 在 create_async_engine 之前配置
sqlalchemy_logger = stdlib_logging.getLogger("sqlalchemy.engine")
sqlalchemy_logger.addHandler(LoguruHandler())

# 在 config.yaml 中新增
database:
  log_queries: false       # 设为 true 输出 SQL（替代 echo）
  log_pool_events: true    # 连接池创建/销毁/超时日志
```

**影响文件**：`backend/db/database.py`、`configs/config.yaml`

### 阶段三：治理与规范（2-3 小时）

#### 3.3.1 统一日志格式为延迟求值风格

**规则**：所有日志消息统一使用 `{}` 占位符 + 参数传递，禁止 f-string 和 `%` 格式化。

```python
# ✅ 正确
logger.info("[DocAgent] kp_name={}, draft_len={}", kp_name, len(draft))

# ❌ 禁止
logger.info(f"[DocAgent] kp_name={kp_name}")
logger.info("[DocAgent] kp_name=%s" % kp_name)
```

**执行方式**：在 `ruff` 或 `flake8` 配置中添加自定义规则（若使用 pre-commit），或通过 code review 逐步推进。不要求一次性全部修改，但新代码必须遵守。

#### 3.3.2 健康检查端点排除

**改动**：在 `LoggingMiddleware.dispatch()` 开头添加路径过滤。

```python
# backend/middleware/logging_middleware.py

HEALTH_CHECK_PATHS = {"/health", "/healthz", "/ready", "/livez"}

async def dispatch(self, request: Request, call_next: Callable) -> Response:
    if request.url.path in HEALTH_CHECK_PATHS:
        return await call_next(request)
    # ... 原有逻辑
```

**影响文件**：`backend/middleware/logging_middleware.py`

#### 3.3.3 建立日志等级使用约定

在 `CLAUDE.md` 或单独文档中明确各级别语义：

| 级别 | 语义 | 示例 |
|------|------|------|
| `TRACE` | 极细粒度调试（函数入参、每步返回值） | `logger.trace("query_vector shape={}", vec.shape)` |
| `DEBUG` | 开发者关心的调试信息 | `logger.debug("[DocAgent] LLM prompt length={}", len(prompt))` |
| `INFO` | 业务流程关键节点 | `logger.info("[DocAgent] 文档生成成功, kp={}, draft_len={}", kp, len)` |
| `SUCCESS` | 业务操作成功完成 | `logger.success("[Generation] 批次 {} 完成, 耗时 {}s", batch_id, elapsed)` |
| `WARNING` | 可恢复的异常、降级行为 | `logger.warning("[LLM] 第 {} 次重试，原因: {}", retry, reason)` |
| `ERROR` | 不可恢复的错误、需要人工介入 | `logger.error("[Database] 连接池耗尽，等待 {}s", wait_time)` |
| `CRITICAL` | 系统级故障（服务不可用） | `logger.critical("[App] 启动失败，端口 {} 被占用", port)` |

#### 3.3.4 清理无用导入

移除所有包含 `# noqa: F401` 且确实未调用 logger 的导入语句。可以用 `autoflake` 或手动清理。

**影响文件**：`backend/services/llm.py` 等

### 阶段四：业务事件日志（4-6 小时，可选）

#### 3.4.1 设计业务事件 Schema

定义统一的业务事件结构，写入独立的 `events_{date}.jsonl` 文件或数据库表：

```python
# backend/logging/events.py
from pydantic import BaseModel
from datetime import datetime
from typing import Any

class BusinessEvent(BaseModel):
    event: str                    # e.g. "resource.generated", "quiz.submitted"
    trace_id: str
    user_id: int | None
    session_id: str | None
    timestamp: datetime
    duration_ms: float | None
    metadata: dict[str, Any] = {}
```

#### 3.4.2 在关键节点记录事件

```python
# 示例：资源生成完成

async def generate_resource(...):

        event="resource.generated",

        metadata={

            "knowledge_point": kp_name,
            "draft_length": len(draft),
            "llm_calls": llm_call_count,

    )
```

#### 3.4.3 事件存储

按需选择：
- **轻量方案**：写入 `logs/events_{date}.jsonl`，与现有文件日志一致
- **完整方案**：写入 PostgreSQL `business_event` 表，配合 Grafana 面板

## 六、实施建议

1. **阶段一立即执行**（P0 的问题属于 bug，无需讨论）
2. **阶段二在下一个迭代中完成**：trace_id 注入和可配置级别是提升可观测性的基础设施
3. **阶段三随日常开发逐步推进**：不需要专门排期，在修改代码时顺便统一格式即可
4. **阶段四按需启动**：如果近期有数据分析或运营看板需求，再投入开发

JSON 结构化日志的开关建议开发环境默认 `false`（可读性强），生产/预发环境默认 `true`（方便日志采集）。
