## 3.1 总体设计

### 3.1.1 设计目标与原则

#### 设计目标

本系统的核心目标是：**把通用大模型改造成可被高等教育场景信赖的「垂直领域教学助手」**。围绕该目标，§3.1 给出五项可衡量的设计目标：

| 序号 | 设计目标 | 衡量指标 |
|---|---|---|
| G1 | 个性化 | 8 维学生画像（专业 / 学习目标 / 认知风格 / 每日学习时长 / 已掌握 / 薄弱 / 易错 / 当前进度）驱动资源生成与路径规划 |
| G2 | 准确性 | 黄金集 15 条查询 Faithfulness ≥ 0.85、Citation Accuracy ≥ 0.90、Hallucination ≤ 0.05 |
| G3 | 可扩展 | 新增 Agent / 新增资源类型 / 新增 Provider 三类扩展均不需要改动核心调度 |
| G4 | 可观测 | 端到端 trace_id；单次生成全链路日志；四层评估常态化 |
| G5 | 可运维 | 启动即用（一条 uvicorn 命令），自动建库、自动索引、自动热加载 |

#### 设计原则

为了把上述目标落到代码层面，本系统在架构设计阶段遵循七条原则：

1. **单一可信源（Single Source of Truth）**：所有 Pydantic Schema 字段名严格匹配 ORM 列名（`backend/db/models.py` 第 37-489 行）；时间戳统一使用 `created_at` / `updated_at`；主键统一命名为 `id`。这是 CLAUDE.md 中明确强制的命名约束，避免后端字段名漂移。
2. **基座引擎下沉（Engine Below）**：所有 LLM / Embedding / RAG / 工具调用下沉至「基础能力层」，业务 Agent 只调用统一接口；上层不感知 Provider 差异。
3. **条件路由而非并行扇出（Conditional, Not Parallel）**：LangGraph 状态机中每个 run 只调度一条路径，由 `route_by_resource_type()` 选择具体生成 Agent，避免资源浪费。
4. **配置外部化（Configuration as Data）**：所有阈值、Prompt、Provider、引用规则均在 `configs/config.yaml` 与 `configs/prompts.yaml` 中声明，禁止硬编码。
5. **异步优先（Async First）**：FastAPI + SQLAlchemy async + asyncpg 全链路异步；RAG 检索、子查询、Provider 调用均支持并发。
6. **只审不修（Audit, Don't Patch）**：SafetyAgent 仅审核不修改生成内容，问题写入 `metadata.safety_issues`，原始 `draft_content` 保留。
7. **fail-open（保守通过）**：审核、降级、检索任一环节失败时保守通过主流程，避免教育场景因技术抖动而中断。

#### 3.1.2.2 三层架构设计动机

三层划分并非追求形式上的对称，而是为了解决三类具体的工程痛点：

1. **基础能力层下沉是为了「让上层专心做事」**：在没有基座引擎之前，每个 Agent 都要自己处理 LLM 重试、Embedding 批量化、RAG 检索、关键词字典等重复代码；下沉后，新增 Agent 只需关注「生成什么、引用什么」，接入成本从「一周」降到「一天」。
2. **智能体中枢层独立是为了「让调度逻辑可被观测」**：把所有 Agent 编排、状态路由、DB 会话注入、超时控制集中在一处（`backend/agents/graph.py`，共 211 行），运维人员可以一眼看清一次 run 走了哪条路径、卡在哪一步、有没有触发降级。
3. **功能层上浮是为了「让业务语义可被复用」**：相同的 RAG 检索能力既被「对话式辅导」调用，也被「文档生成 Agent」调用；如果不把功能层独立，每个端点都要重复写一遍调用。

#### 3.1.2.3 模块化单体 vs 微服务取舍

本系统选择「模块化单体」而非微服务，三个关键理由：

| 维度 | 模块化单体（本系统） | 微服务（未采用）|
|---|---|---|
| 部署复杂度 | 一条 `uvicorn backend.main:app` 命令 | 11 个 Agent 各自容器化 + 服务网格 |
| 状态一致性 | LangGraph 单进程内 `AgentState` 共享，无需分布式事务 | 跨服务状态同步（最终一致性）|
| 首字时延 | 进程内函数调用 < 1 ms | HTTP/RPC 调用 ≥ 5 ms |
| 扩展性 | 新 Agent 只需在 `graph.py:76-87` 注册新节点 | 需新增服务 + 注册中心 + 熔断 |
| 运维成本 | 单数据库 + 单进程 + 单日志目录 | 多数据库 + 多进程 + 链路追踪 |

权衡：本系统当前阶段的核心矛盾是「准确性与可解释性」而非「并发与吞吐」，单体化让链路更短、更易调试。未来若并发成为瓶颈，可按 `graph.py` 中的节点切分为独立微服务，迁移路径明确。

## 3.2 基础能力层：垂直领域模型基座引擎

> 本章对应 **创新点一（教材驱动知识库）** 与 **创新点二（基座引擎）**。基础能力层把「LLM 接入 / Embedding / 文档加载 / 向量索引 / 检索 / 工具调用」六个独立子系统统一封装为可被智能体中枢层直接调用的「基座引擎」。本层只解决「怎么把原始素材变成可被引用的知识」，不解决「生成什么资源」——后者由 §3.3 智能体中枢层决定。

### 3.2.1 引擎定位与边界

#### 业务痛点

在没有基座引擎之前，本系统面对三类反复出现的工程痛点：

1. **多 Provider 散落**：项目先后接入过 OpenAI、DashScope、讯飞星火、DeepSeek 四个 LLM Provider，每次切换都要在十几个 Agent 文件里搜索替换 import 路径和 base_url；维护成本随 Agent 数量线性增长。
2. **RAG 重复实现**：每个 Agent（doc/code/anim/summary 等）都要自己实现「加载文档 → 切块 → 嵌入 → 检索 → 拼装 prompt」一条完整链路，重复代码 ≥ 300 行 / Agent。
3. **Prompt 硬编码**：早期版本中 system_prompt 直接写在 Python 源码里，调整一个标点都需要重新部署；不同 Agent 之间无法复用同一段提示词模板。

#### 设计目标

基座引擎的设计目标是「让上层 Agent 只需说『帮我用 RAG 生成某知识点的文档』，不必关心底层用哪个模型、怎么分块、怎么检索」：

- **统一接口**：所有 Agent 调用同一个 `retrieve_context(state, agent_label, config_dict)` 函数（`backend/agents/utils.py:472`），传入状态对象与 Agent 标签即可获得 `retrieved_docs` 与引用列表。
- **Provider 可插拔**：通过 `configs/config.yaml` 中 `llm.providers` 表切换模型，重启即生效；无需修改业务代码。
- **Prompt 外置**：所有 system_prompt 集中在 `configs/prompts.yaml`，由 `backend/config.py:514` `_load_prompts()` 加载；Agent 通过 `config.prompts["agents"][name]["system_prompt"]` 获取。
- **可观测**：每次 RAG 检索输出 `n_retrieved / score_p50 / score_min / score_max / latency_ms`，自动喂给 §3.2.9 评估子系统。

#### 引擎边界

明确「什么属于基座引擎、什么不属于」，避免职责蔓延：

| 属于基座引擎 | 不属于基座引擎（由上层负责）|
|---|---|
| LLM 调用、重试、流式输出 | 资源类型的「生成逻辑」（文档 / 思维导图 / 测验等）|
| Embedding 批量化与健康检查 | 用户意图识别与路由 |
| 文档加载与多格式解析 | 对话历史管理 |
| 向量索引与 HNSW 维护 | 知识图谱节点抽取 |
| 混合检索 + RRF 融合 + 多样性 | 业务层异常恢复策略 |
| 引用格式化与可解释性 | 学生画像构建 |
| 视频检索 / WebSearch 工具 | 学习路径规划 |

### 3.2.3 LLM 接入子系统

#### 3.2.3.1 统一接口

`backend/services/llm.py` 暴露四个核心函数：

| 函数 | 行号 | 用途 |
|---|---|---|
| `chat_completion(messages, **kwargs)` | `:90` | 同步非流式调用，返回完整文本 |
| `stream_chat_completion(messages, **kwargs)` | `:135` | 流式调用，逐 token yield |
| `get_embedding(text)` / `get_embeddings_batch(texts)` | `:201` / `:219` | 同步 / 批量 Embedding |
| `check_embedding_health()` | `:239` | 健康检查 |

所有函数接受统一参数：`temperature` / `max_tokens` / `response_format`（JSON 模式）/ `stop` / `timeout`，业务 Agent 不必关心 Provider 差异。

#### 3.2.3.2 OpenAI 兼容 SDK 适配

`chat_completion()` 内部统一调用 `openai.OpenAI` SDK（`openai>=1.25.0`）。DashScope、讯飞星火、DeepSeek 均提供 OpenAI 兼容接口，因此一个 SDK 即可覆盖所有 Provider；切换 Provider 仅修改 `configs/config.yaml` 中的 `provider` 字段。

#### 3.2.3.3 重试与降级

使用 `tenacity` 实现指数退避（`backend/services/llm.py:90-130`）：

- 重试条件：捕获 `RateLimitError` / `PermissionDeniedError` / `APITimeoutError` / `APIConnectionError`
- 退避策略：`max_attempts=5`，`initial_delay=1.0 s`，`backoff_factor=2.0`（1→2→4→8→16 秒）
- 异常抛出：5 次仍失败则抛出 `LLMError`（自定义异常），由 §3.4.2 资源生成服务捕获后写入 `GenerationTask.error_message`

**降级策略**（fail-open）：当 LLM 连续 3 次调用失败时，自动切换到备用 Provider（`configs/config.yaml` 中声明的第二个 Provider）；若备用也失败，记录 ERROR 日志后保留最后一次的部分输出。

#### 3.2.3.4 流式输出

`stream_chat_completion()` 通过 OpenAI SDK 的 `stream=True` 实现逐 token 输出；前端通过 `chat.html` 中 `sendChatMessage()` 走非流式 POST（详见 §3.6.2.1），不使用 SSE；这是当前实现的简化方案，未来可平滑切换为 `text/event-stream`。

### 3.2.4 Embedding 子系统

#### 3.2.4.1 模型选型

`backend/rag/indexer.py` 与 `backend/services/llm.py:201` `get_embedding()` 均使用 **DashScope `text-embedding-v4`**（1024 维）：

```
embedding:
  api_model: text-embedding-v4
  vector_dimension: 1024
  use_spark: true
  concurrency: 8
  index_batch_size: 128
  api_max_batch_size: 10
```

**历史方案**（已弃用）：早期版本使用本地 BGE-M3（`embedding.use_spark=false`），但 2GB 内存环境下频繁 OOM，已迁移到云端 Embedding（`docs/xqt/system/2GB内存环境瓶颈分析.md` 记录迁移原因）。

#### 3.2.4.2 批量化与并发控制

`get_embeddings_batch()` 行为（`backend/services/llm.py:219`）：

- **批大小硬上限**：DashScope API 单次最多接收 25 条，超过会被拒；函数自动按 `api_max_batch_size=10`（更保守，避免单批失败全量重试）切分。
- **并发控制**：`concurrency=8`，使用 `asyncio.Semaphore(8)` 限制同时在飞请求数。
- **失败重试**：批内任意一条失败 → 整批按 `tenacity` 指数退避重试 3 次；最终失败的 chunk 标记 `embedding=NULL` 跳过，不阻塞索引流程。

#### 3.2.4.3 健康检查

`check_embedding_health()` 探测模型连通性，指标写入 `backend/evaluation/health_check.py` 滑动窗口；失败时主流程降级到「纯关键词检索」（`rag.hybrid.paths=["keyword"]`）。

### 3.2.5 文档加载与解析子系统

#### 3.2.5.1 多格式支持

`backend/rag/loader.py:138-178` `convert_to_markdown()` 支持 5 种格式（`configs/config.yaml:194` `storage.supported_extensions`）：

| 扩展名 | 解析路径 | 关键调用 |
|---|---|---|
| `.pdf` | PDF → Markdown | `pymupdf4llm.to_markdown(str(path))`（loader.py:158） |
| `.docx` / `.doc` | DOCX → Markdown | `mammoth.convert_to_markdown(f)`（loader.py:163） |
| `.md` | 直接读取 | `path.read_text(encoding="utf-8")`（loader.py:173） |
| `.txt` | 直接读取 | 同上 |

PDF 解析的容错：`load_file()`（loader.py:181-221）优先调用 `pymupdf4llm`，失败时回退到 `PyPDFLoader`（loader.py:443），保证单文档失败不影响整体索引。

#### 3.2.5.2 结构保留

PDF 与 DOCX 解析过程中，标题（`#`/`##`/`###`）、表格、列表结构被完整保留：

- **PDF**：通过 `pymupdf4llm` 的 `extract_words=True` 模式保留标题层级；标题层级被 `_parse_markdown_to_chunks()`（loader.py:605-663）识别后作为 `section` 字段写入 `TextChunk`。
- **DOCX**：通过 `mammoth` 的样式映射保留 Heading 1/2/3。
- **Markdown 表格保护**：`split_text()`（loader.py:272-397）在切分时检测表格边界，跨页表格自动复制表头（loader.py:317-378）。
- **代码块保护**：使用占位符替换避免代码块被错误切分（loader.py:300）。

#### 3.2.5.3 父-子分块策略

**动机**：单一粒度切块在「精确检索」与「上下文完整」之间存在矛盾——小块精确但缺上下文，大块完整但易引入噪声。本系统采用 **parent-child chunking**：

- **父块（parent）**：按章节 + 段落切分，单块最大 `parent_max_chars=2000`（约 1000 中文字符）。父块用于「上下文回填」。
- **子块（child）**：在父块内继续切分，单块 `child_chunk_size=500`（默认沿用 `rag.chunk_size`），`child_chunk_overlap=100`。子块用于「向量检索」。
- **回指关系**：每个子块通过 `parent_chunk_id` 字段指向其父块。

**实现**（loader.py:666-751 `_parse_markdown_to_chunks_parent_child()`）：
- 父块切分优先级：`\n\n`（段落边界）> `\n`（行尾）> 句子边界（`split_sentence_lookback_ratio=0.2`）> 硬截断
- 子块切分通过 `split_text()`，在父块内部递归执行
- 触发条件：`rag.parent_chunking.enabled=true`（configs/config.yaml:107）

**检索时回填**：`backend/rag/retriever.py:581-645` `_resolve_parent_chunks()` 收集子块的 `parent_chunk_id`，调 `get_parent_texts_batch()` 取父块完整文本；最终喂给 LLM 的是父块文本，但保留子块的相似度分数与来源标记，保证「检索精确、生成完整」。

### 3.2.6 向量索引子系统

#### 3.2.6.1 pgvector + HNSW 索引

`document_chunk` 表的 `embedding` 列类型为 `Vector(1024)`，使用 pgvector 扩展提供余弦距离计算：

- **扩展启用**：`migrations/versions/8a3f2e1b4c5d_migrate_embedding_to_pgvector.py` 中 `CREATE EXTENSION IF NOT EXISTS vector`
- **HNSW 索引**：`migrations/versions/6f9a2b3c4d5e_switch_ivfflat_to_hnsw.py:27-32` 创建，参数 `m=16`（每个节点最大边数）、`ef_construction=200`（构建时候选集大小）、`vector_cosine_ops`（余弦距离算子）
- **历史演进**：早期版本使用 IVFFlat（`docs/xqt/database/IVFFlat与HNSW索引对比分析.md` 记录对比），因召回率与构建时间权衡，最终切换到 HNSW。

#### 3.2.6.2 to_tsvector 全文索引

`document_chunk` 表的 `text_search` 列类型为 `TSVECTOR`，由 jieba 分词后写入：

- **分词**：`backend/rag/indexer.py:28-40` `_tokenize_for_tsvector()` 使用 jieba 精确模式
- **索引**：`models.py:168` `postgresql_using='gin'`，GIN 倒排索引支持全文检索
- **写入**：`backend/db/vector.py:160-224` SQL 拼接中 `to_tsvector('simple', :text_search_i)` 实时生成

#### 3.2.6.3 应用启动时自动建库

`backend/main.py:151-158`（lifespan 上下文）：

```python

```

启动时若 `document_chunk` 表为空，自动索引 `configs/config.yaml:193` 中声明的 `knowledge_base_dir` 目录（默认 `knowledge_base/ai_intro`）。这样首次部署即开箱即用，不需要手动跑索引脚本。

### 3.2.7 检索子系统

检索子系统是基础能力层最复杂、最关键的部分，承担「将 query 转化为可被 LLM 引用的高质量片段」的核心职责。

#### 3.2.7.1 核心数据结构

`backend/rag/retriever.py` 定义两个 dataclass：

- **`RetrievedChunk`**（:21-30）：`chunk_id / text / score / doc_id / source / page / section / metadata`
- **`CitationSource`**（:33-43）：`index / source / page / section`（与正文 `[n]` 严格对齐，便于前端渲染）

#### 3.2.7.2 混合检索（向量 + jieba 关键词双路召回）

`retrieve_hybrid()`（retriever.py:311-413）同时调用两条召回路径：

- **向量路**：通过 pgvector 的 `<=>` 余弦距离算子执行 HNSW KNN 检索（`backend/db/vector.py:288-305`），SQL 形如：
  ```sql
  SELECT chunk_id, text, ..., embedding <=> CAST(:embedding AS vector) AS distance
  FROM document_chunk
  WHERE collection_name=:cn AND is_parent=FALSE ...
  ORDER BY embedding <=> CAST(:embedding AS vector)
  LIMIT :n_results
  ```
  每次查询前 `SET LOCAL hnsw.ef_search = config.vector_db.hnsw_ef_search`（默认 100，平衡召回与时延）。

- **关键词路**：通过 jieba 分词 + PostgreSQL `to_tsquery` 全文检索（`vector.py:476-493`）：
  ```sql
  SELECT ..., ts_rank(text_search, to_tsquery('simple', :tsquery)) AS rank
  FROM document_chunk
  WHERE text_search @@ to_tsquery('simple', :tsquery)
    AND is_parent=FALSE AND text_search IS NOT NULL
  ORDER BY rank DESC
  ```
  tsquery 用 `&` 连接 jieba 关键词（vector.py:466），仅检索子块（`is_parent=FALSE`）。

两条路径并行执行（`asyncio.gather`），结果送入下一阶段的 RRF 融合。

#### 3.2.7.3 RRF 融合排序

`_rrf_fusion_cross_path()`（retriever.py:272-308）实现 Reciprocal Rank Fusion：

```
rrf_score = w / (k + rank)
```

- 默认 `rrf_k=60`、`vector_weight=1.0 / keyword_weight=1.0`（`configs/config.yaml:104-106`）
- 按 `chunk_id` 合并去重，保留更高 `chunk.score`

#### 3.2.7.4 Query 改写（去上下文化 + 画像感知扩展 + 多查询）

`backend/agents/utils.py` 提供三种改写策略，分别对应五层防幻觉中的「第零层」（§3.3.5.2）：

- **策略 A：去上下文化**（`_rewrite_query()` :323-383）—— 对最近 6 轮对话窗口做指代消解，把「这个」「那个」「它」还原为具体名词。失败时回退 `_build_fallback_query()`（:386-392）。
- **策略 B：画像感知扩展** —— 在改写 query 中注入学生薄弱知识点（如「重点讲清楚反向传播的链式法则推导」）。
- **策略 C：多角度扩展**（`_expand_queries()` :402-427）—— 通过 `rag.expand` prompt 让 LLM 生成 N 个角度的子查询（概念定义 / 原理推导 / 应用示例 / 常见误区 / 跨概念关联），默认 `multi_query_count=3`，前置原 query 后最多返回 4 条。

三种策略的输出统一进入 `retrieve_with_queries()`（retriever.py:139-174）并发执行 RAG 检索，再次 RRF 融合。

#### 3.2.7.5 多样性感知重排（按章节轮转）

`_diversify_order()`（retriever.py:524-564）解决「top-k 同源」问题：避免检索结果的前 5 条全部来自同一章节，导致 LLM 看到的引用过分集中。

- 按 `chunk.section` 分组后 round-robin 交错
- 保证 top-k 中至少包含 ≥ 3 个不同章节
- 在 4 章节、每章节 5 条候选时，top-5 输出顺序为 `章节A-1, 章节B-1, 章节C-1, 章节A-2, 章节B-2`

#### 3.2.7.6 引用格式化与可解释性

`format_context_with_sources()`（retriever.py:441-521）把检索结果格式化为可被 LLM 引用的 prompt 片段：

- 输出格式：`[n] （来源：file.pdf，第 2 页，章节）\n{text}`
- 按 `context_max_tokens=3000`（configs/config.yaml:97）截断
- 截断时尾部追加 `[注意：以上仅展示了前 N 条...请勿引用 [N+1]...]`（retriever.py:512-515），从源头杜绝 LLM 引用未实际看到的片段
- 附加扩展元数据标签：`chunk_type / language / difficulty`（retriever.py:476-491）

#### 3.2.7.7 整体检索流程

```
user_query + chat_history + profile
        │
        ▼
  _rewrite_query() ─→ _build_fallback_query() （失败回退）
        │
        ▼
  _expand_queries() （multi-query 模式）
        │
        ▼
  retrieve_with_queries() [并发]
        │
        ▼
  混合检索 (vector + keyword) → RRF 融合 (60)
        │
        ▼
  score_threshold 过滤 (0.5)
        │
        ▼
  _rerank_by_keyword_overlap() （boost 0.25）
        │
        ▼
  _diversify_order() （section round-robin）
        │
        ▼
  _resolve_parent_chunks() （parent 回填）
        │
        ▼
  format_context_with_sources()
        │
        ▼
  AgentState.retrieved_docs + citations
```

#### 3.2.8.1 视频检索工具调用

- **降级链** `search_videos()`（:151-177）：B 站优先 → Tavily 兜底 → 静默失败
- **正文注入** `inject_video_citations()`（:180-223）：按视频标题关键词匹配正文最佳段落，在段尾插入 `[v1][v2]` 标记；末尾追加 `**视频参考**` 区

调用入口：clarify_agent 与 doc_agent 通过 `asyncio.gather(chat_completion, search_videos)` 并发执行（`backend/agents/clarify_agent.py:28` 与 `doc_agent.py:25`）。

#### 3.2.8.2 WebSearch 预留接口

项目当前未实现独立的通用 WebSearch 工具（区别于视频检索的「专域」工具）。通用 LLM 联网能力由 `backend/services/llm.py` 通过 DashScope/OpenAI provider 提供；外部检索能力仅 `video_search.search_tavily()`。

未来若需扩展，预留接口规范：实现 `async def search(query: str, top_k: int = 3) -> list[SourceResult]` 即可被 `backend/agents/utils.py:472` `retrieve_context()` 调用。

### 3.2.9 基座引擎对外接口契约

基座引擎对外（智能体中枢层）暴露 4 个核心接口，定义在 `backend/agents/utils.py`：

| 接口 | 签名 | 用途 |
|---|---|---|
| `chat_completion(messages, **kwargs)` | `backend/services/llm.py:90` | 同步 LLM 调用 |

## 3.3 智能体中枢层：基于 LangGraph 的多智能体调度

> 本章对应 **创新点三（多智能体调度中枢）**。智能体中枢层把基础能力层提供的统一接口组装为「理解 → 规划 → 生成 → 审核 → 推荐」的端到端流水线。LangGraph 状态机作为唯一调度入口，11 个 Agent 节点（含 clarify 共 12 个）通过条件路由完成意图分发与产物交接。**五层递进防幻觉架构（§3.3.5）** 贯穿整个中枢层，是教育场景「内容准确性」硬指标的工程保证。

### 3.3.1 中枢层设计动机与边界

#### 动机

教育场景的多智能体协同存在三类工程问题，本层均给出明确解法：

| 问题 | 解法 |
|---|---|
| 多个 Agent 各自定义私有状态，难以追踪 | 引入 LangGraph 状态机，全局 `AgentState`（Pydantic 单一可信源）|
| 意图分发逻辑分散在 router.py 中难以审计 | 集中在 `planner_agent.route_by_resource_type()` 一处（planner_agent.py:171）|
| 生成 Agent 直接读 DB 易绕过安全 | 所有 DB 访问通过 `config.configurable.db` 注入，统一审计 |
| 调度可观测性差 | trace_id 全链路注入（`backend/logging_config.py` 的 patcher）|
| 新 Agent 接入无章法 | §3.3.7「新增 Agent 标准化接入流程」明确 4 步 |

#### 边界

中枢层只负责「意图理解、任务调度、产物交接」，不承担「具体内容生成」与「数据持久化」：

| 属于中枢层 | 不属于中枢层 |
|---|---|
| LangGraph 状态机编排 | LLM / Embedding / RAG 检索的实现（基础能力层）|
| 11 个 Agent 的输入输出契约 | 业务数据写入 ResourceMeta / QuizItem 等（功能层）|
| 条件路由函数 | 权限校验（auth 层） |
| 提示词加载与替换 | 提示词的编写（人工维护） |
| DB session 注入 | 连接池配置（数据层） |

### 3.3.2 LangGraph 状态机设计

#### 3.3.2.1 LangGraph 核心概念

LangGraph 是 LangChain 团队推出的状态机编排框架，三个核心概念：

- **StateGraph**：以状态（State）为中心的图结构，节点（Node）是状态转换函数，边（Edge）描述转换关系
- **Node**：函数签名 `(state: AgentState, config: RunnableConfig) -> AgentState`，接收当前状态、返回新状态
- **Conditional Edge**：基于当前状态动态决定下一节点的路由函数，签名 `(state: AgentState) -> str`（返回节点名或 `END`）

本系统使用 LangGraph ≥ 0.1.0 版本（`requirements.txt`）。

#### 3.3.2.2 全局状态 AgentState

`AgentState`（`backend/models/schemas.py:483-505`）是 Pydantic v2 BaseModel，作为整个状态机的「单一可信源」：

| 字段 | 类型 | 用途 |
|---|---|---|
| `user_id` | int | 当前用户 ID |
| `session_id` | int | 当前会话 ID |
| `user_message` | str | 用户最新输入 |
| `chat_history` | list[dict[str, str]] | 多轮对话历史（`[{"role": ..., "content": ...}]`）|
| `intent_type` | Optional[str] | 意图分类结果（"clarify" / "generate" 等）|
| `profile` | Optional[StudentProfileIn] | 学生画像 |
| `kp_id` | Optional[str] | 知识点 ID（如 "kp_03_01"）|
| `resource_type` | Optional[ResourceType] | 资源类型枚举 |
| `retrieved_docs` | list[str] | RAG 检索结果 |
| `draft_content` | Optional[str] | 生成 Agent 的草稿 |
| `final_content` | Optional[str] | 最终输出（澄清、生成或推荐）|
| `safety_passed` | bool | 安全审核结果（默认 True）|
| `error` | Optional[str] | 错误信息 |
| `metadata` | dict[str, Any] | 灵活扩展（如 video_refs / recommendations / kg_result）|
| `kg_doc_id` | Optional[str] | 知识图谱构建的文档 ID |
| `is_onboarding` | bool | 是否首次进入（画像冷启动）|
| `profile_complete` | bool | 画像是否足够完整 |
| `clarify_message` | Optional[str] | 追问消息 |
| `num_questions` | int | 测验题数（默认 4）|
| `question_type_counts` | dict[str, int] | 各题型配额 |

**约束**：所有节点函数必须返回 `state.model_copy(update={...})`，禁止原地修改 state。这保证 LangGraph 的状态快照与回放机制正常工作。

#### 3.3.2.4 条件路由

状态机中存在两处条件路由：

**路由 1：profile → planner/END**（`graph.py:93-100`）

```python
graph.add_conditional_edges(
    "profile_agent",
    profile_agent.route_after_profile,
    {"planner_agent": "planner_agent", END: END}
)
```

`route_after_profile()`（`profile_agent.py:270-279`）基于 `state.profile_complete` 决定：
- `True` → `planner_agent`（画像足够，进入规划）
- `False` → `END`（追问用户，由 `state.clarify_message` 携带追问文本）

**路由 2：planner → 9 出口**（`graph.py:103-117`）

```python
graph.add_conditional_edges(
    "planner_agent",
    planner_agent.route_by_resource_type,
    {
        "doc_agent": "doc_agent",
        "mindmap_agent": "mindmap_agent",
        "quiz_agent": "quiz_agent",
        "code_agent": "code_agent",
        "anim_agent": "anim_agent",
        "summary_agent": "summary_agent",
        "kg_agent": "kg_agent",
        "clarify_agent": "clarify_agent",
        "recommend_agent": "recommend_agent",  # 兜底
    }
)
```

`route_by_resource_type()`（`planner_agent.py:171-191`）逻辑：
1. 若 `state.intent_type == "clarify"` → `clarify_agent`
2. 否则按 `state.resource_type` 枚举映射到对应生成 Agent
3. 未匹配 → `recommend_agent` 兜底（无需生成资源，仅做知识点推荐）

**固定边**（`graph.py:120-127`）：
- 6 个生成 Agent（doc / mindmap / quiz / code / anim / summary）→ `safety_agent` → `recommend_agent` → END
- `kg_agent` 旁路 safety 直达 `recommend_agent`（KG 构建无幻觉风险）
- `clarify_agent` → END（跳过 safety，因为是追问，不直接输出教学内容）

#### 3.3.2.5 数据库会话注入约定

所有需要 DB 的 Agent 节点通过 `config["configurable"].get("db")` 读取 session：

```

调用方约定：
- `POST /chat/{session_id}` 等端点从 FastAPI Depends 注入 `db: AsyncSession`

- 各 Agent 通过 `config["configurable"].get("db")` 取出后即可使用

**RAG 检索缓存清空约定**：`graph.invoke/stream_invoke` 入口均调用 `clear_retrieval_cache()`（`graph.py:155-156` 与 `:192-193`），保证跨请求隔离；同一请求内多 Agent 共享 `_retrieval_cache[(kp_name, user_id)]`（`utils.py:304-309`）。

### 3.3.3 十一智能体详细设计

本节按「职责 / 输入输出 / 路由出口 / 提示词节选 / 示例」五个维度描述 12 个 Agent（含 clarify）。每个 Agent 的代码入口集中于 `backend/agents/<name>_agent.py`。

#### 3.3.3.1 profile_agent — 画像增量提取

- **职责**：从多轮对话中增量提取学生画像（专业、学习目标、认知风格、每日学习时长、已掌握、薄弱知识点等），并判断画像是否足够完整以进入规划阶段。
- **输入**：依赖 `state.user_message` / `state.chat_history` / `config.configurable.db`
- **输出**：更新 `state.profile`（增量合并 `state.profile` 已有字段）、`state.profile_complete`、`state.clarify_message`（不完整时）
- **路由出口**：`route_after_profile()`（profile_agent.py:270）→ `planner_agent` 或 `END`

- **关键文件**：`backend/agents/profile_agent.py:86` `run()`，调用 LLM 2-3 次（提取 + 完整性判断 + 追问文本生成）

#### 3.3.3.2 planner_agent — 意图识别与路由

- **职责**：识别用户意图（clarify vs generate）+ 选择具体资源类型 + 解析 kp_id。
- **输入**：`state.user_message` / `state.chat_history` / `state.profile` / `db`
- **输出**：`state.intent_type` / `state.resource_type` / `state.kp_id` / `state.metadata.extra_resource_types`（批量生成场景）
- **路由出口**：`route_by_resource_type()`（planner_agent.py:171）→ 9 出口
- **提示词**：`configs/prompts.yaml: agents.planner.intent_classify` + `smart_plan`
- **关键方法**：`plan_resource_types()`（planner_agent.py:197）—— 智能生成模式下推荐 3-4 种互补资源类型
- **示例**：用户说「帮我讲讲反向传播算法」→ `intent_type="generate"`、`resource_type="doc"`、`kp_id="kp_xxx_backprop"`

#### 3.3.3.3 clarify_agent — 澄清问询

- **职责**：当画像或意图不明确时，反问用户以获取必要信息；与视频检索增强并发。
- **输入**：`state.chat_history` / `state.profile` / `state.user_message`
- **输出**：`state.final_content`（追问文本）、`state.metadata.video_refs`

#### 3.3.3.4 doc_agent — 文档生成

- **职责**：基于 RAG 检索结果生成 Markdown 格式学习文档（含小节、公式、示例、引用标注）。
- **输入**：`state.kp_id` / `state.profile`（RAG 检索）
- **输出**：`state.draft_content`（Markdown 文档）、`state.retrieved_docs`（已通过 `retrieve_context()` 填充）、`state.metadata.video_refs`
- **路由出口**：→ `safety_agent`
- **提示词**：`configs/prompts.yaml: agents.doc.system_prompt`，遵循 NEVER（不编造事实）/ IMPORTANT（必须引用）/ Do NOT（不要忽略空引用声明）三级
- **示例输出**（节选）：
  ```
  # 反向传播算法

  ## 1. 链式法则基础
  反向传播的核心是链式法则的应用[1]。对于复合函数 f(g(x))，其导数可分解为各层导数的乘积[1]。

  ## 2. 计算流程
  前向传播计算各层激活值；反向传播从输出层向输入层逐层计算梯度[2]。

  ## 3. 公式推导
  ∂L/∂w^(l) = δ^(l) * (a^(l-1))^T，其中 δ^(l) 为第 l 层误差项[1]。

  ---
  **参考资料**
  [1] 《深度学习》教材，第 4 章，第 2 节
  [2] 《神经网络与深度学习》课程讲义，第 3 章
  ```

#### 3.3.3.5 mindmap_agent — 思维导图

- **输入**：`state.num_questions`（默认 4）/ `state.question_type_counts` / `state.profile`（用于难度适配）

#### 3.3.3.7 code_agent — 代码示例

- **职责**：生成带注释的代码示例或练习题（Python / C++ / Java 等）。
- **输入**：`state.kp_id` / `state.profile`（RAG 检索）
- **输出**：`state.draft_content`（含 Markdown 代码块）
- **路由出口**：→ `safety_agent`
- **提示词**：`configs/prompts.yaml: agents.code.system_prompt`，强调「不编造 API、不引用未在 context 中出现的库」
- **示例输出**：
  ```python
  # 反向传播实现示例[1]
  def backward_pass(activations, deltas, weights):
      """根据输出层误差逐层计算梯度[1]"""
      grads = {}
      for l in reversed(range(1, len(weights) + 1)):
          grads[f'W{l}'] = np.outer(deltas[l], activations[l-1])
          grads[f'b{l}'] = deltas[l]
          # 误差项反向传播：δ^(l-1) = (W^l)^T δ^l ⊙ σ'(z^(l-1))[1]
          deltas[l-1] = (weights[l].T @ deltas[l]) * activations[l-1] * (1 - activations[l-1])
      return grads
  ```

#### 3.3.3.8 summary_agent — 总结生成

- **职责**：基于 RAG 检索结果生成章节复习总结（Markdown 格式，含要点回顾、考点提示、易错点）。
- **输入**：`state.kp_id`（RAG 检索）
- **输出**：`state.draft_content`
- **路由出口**：→ `safety_agent`
- **提示词**：`configs/prompts.yaml: agents.summary.system_prompt`
- **特色**：输入的 query 通常包含「总结 / 复习 / 概括」关键词，Agent 自动切换到「要点归纳 + 表格化呈现」模式

#### 3.3.3.9 kg_agent — 知识图谱节点

- **职责**：调用 `backend.services.kg_builder.build_kg()` 异步构建知识图谱，是 12 个 Agent 中**唯一不调用 LLM 生成教学内容**的节点。
- **输入**：`state.kg_doc_id` / `state.metadata.doc_id` / `db`
- **输出**：`state.final_content`（提示文本）/ `state.draft_content` / `state.metadata.kg_result`（节点 / 边数量）
- **路由出口**：→ `recommend_agent`（**跳过 safety**，因为无幻觉风险）
- **实现细节**：参见 §3.4.5 知识图谱服务
- **示例**：用户上传 PDF 教材并说「帮我构建知识图谱」→ 后台异步构建，写入 `KGNode` / `KGEdge` / `KGBuildTask` 表

#### 3.3.3.10 safety_agent — 内容安全

- **职责**：对生成 Agent 的草稿做「独立审核」，但**只审不修**——保留原始 `draft_content`，问题写入 `metadata.safety_issues`。
- **输入**：`state.draft_content` / `state.retrieved_docs`
- **输出**：`state.safety_passed` / `state.final_content` / `state.metadata.safety_issues`
- **路由出口**：→ `recommend_agent`
- **提示词**：`configs/prompts.yaml: agents.safety.system_prompt`
- **4 项审核清单**：事实核查 / 引用验证 / 误导检测 / 学习场景适配（详见 §3.3.5.5）
- **fail-open**：审核失败保守通过，避免阻塞主流程
- **temperature=0.1**：确保审核输出确定性
- **独立 LLM 角色**：与生成 Agent 解耦，避免「自己审自己」

#### 3.3.3.11 recommend_agent — 资源推荐

- **职责**：在生成资源后推荐 Top-N 相关知识点（兜底路由时仅做推荐）。
- **输入**：`state.profile` / `state.kp_id` / `db`
- **输出**：`state.final_content` / `state.metadata.recommendations` / `state.metadata.recommendations_text` / `state.metadata.kp_name`
- **路由出口**：→ `END`
- **关键约束**：DB 强制过滤不存在的 `kp_id`，从源头拒绝幻觉知识点（参见 §3.3.5.6「代码级硬约束」）
- **提示词**：`configs/prompts.yaml: agents.recommend.system_prompt`
- **配置项**：`{min_recommendations}` `{max_recommendations}` 从 `configs/config.yaml` 解析后注入

#### 3.3.3.12 clarify_agent — 已于 §3.3.3.3 详述

### 3.3.4 提示词工程体系

#### 3.3.4.1 提示词层级（NEVER / IMPORTANT / Do NOT / Avoid）

所有生成类 Agent 的 system_prompt 遵循四级关键词优先级（详细规范见 `docs/xqt/rag/系统提示词书写原则.md`）：

| 优先级 | 关键词 | 适用场景 | 示例 |
|---|---|---|---|
| 最高 | **NEVER** | 不可逆的伤害：编造、幻觉、虚假引用 | 「NEVER 编造不存在于参考资料中的公式」|
| 高 | **IMPORTANT** | 必须做到的质量门：引用、校验、画像适配 | 「IMPORTANT 每个事实声明必须紧跟 [n] 引用」|
| 中 | **Do NOT** | 默认禁止，允许例外 | 「Do NOT 使用 '根据我的知识' 这类表述」|
| 低 | **Avoid** | 偏好，可被覆盖 | 「Avoid 长段落，单段不超过 200 字」|

每条规则都附带 *why* 解释（如「because the LLM will rationalize otherwise」），降低 LLM「自作主张」的概率。

#### 3.3.4.2 标准结构

每个生成 Agent 的 system_prompt 严格遵循四段结构：

```
# Role — what the agent IS and IS NOT
# Rules — NEVER/IMPORTANT/Do NOT/Avoid hierarchy, each with a reason
# Pre-generation Check — mental checklist before output (NOT included in output)
# Output — format specification
```

**Pre-generation Check** 是「内心自查清单」，不输出给用户，仅约束生成路径。例如 doc_agent 的 Pre-generation Check：

```
- 我已经看过 retrieved_docs 了吗？
- 我是否在每个事实声明后添加了 [n] 引用？
- 若 retrieved_docs 为空，我是否声明了「暂无参考资料」？
- 我是否考虑了用户的认知风格（视觉 / 听觉 / 动手）？
```

#### 3.3.4.3 配置外置与模板变量规范

- **配置外置**：所有 system_prompt 在 `configs/prompts.yaml` 中声明，Agent 通过 `config.prompts["agents"][name]["system_prompt"]` 获取；运行时通过 `.format()` 替换运行时占位符。
- **角色约定**：所有生成类 prompt 使用 `role="system"`（更高 LLM 遵循度），不使用 `role="user"`。
- **温度控制**：生成类 Agent 默认 `temperature=0.1-0.4`（`configs/config.yaml: agents.<name>.temperature`），平衡创造性与准确性。

#### 3.3.4.4 资源类型特定的提示词模板

每个资源类型的 prompt 在「标准结构」之上有差异化定制：

- **doc_agent**：强调结构化输出（H1/H2/H3 分级、表格、列表），强调引用 `[n]` 紧跟事实。
- **mindmap_agent**：强调 JSON 格式严格性、层级深度限制、空引用时返回固定结构。
- **quiz_agent**：强调 JSON 数组格式、题型多样性、`_note` 兜底字段。
- **code_agent**：强调代码块使用 ```` ```python ```` 包裹、不编造 API、内置 `不要做` 模式。
- **summary_agent**：强调表格化要点回顾、易错点独立成节。
- **anim_agent**：强调 `defineAnimation(p5) { ... }` 函数签名可被前端直接执行。

### 3.3.5 五层递进防幻觉架构

> 防幻觉是教育场景的架构核心约束，不是选配功能。本系统采用从「检索前到生成后」全覆盖的五层递进防护，对应代码仓库 `docs/xqt/rag/防幻觉机制.md` 与 `backend/evaluation/judge.py`。每一层解决一类特定幻觉风险，层间存在显式依赖与失败回退。

#### 3.3.5.1 防幻觉问题分析

**三类幻觉风险与危害**：

1. **事实捏造**：LLM 编造不存在的公式（如「反向传播的 Hessian 矩阵闭式解」实际上不存在）、定理、算法步骤。这是教育场景最危险的幻觉类型，直接误导学生学习。
2. **概念混淆**：LLM 将概念 A 的定义套到概念 B 上（如把「梯度下降」与「随机梯度下降」的收敛性条件混淆）。这类错误在表面上「看起来正确」，对教学危害更大。
3. **来源不明**：LLM 声称「根据教材……」但教材根本没有该内容；或「研究表明……」但没有具体研究出处。

**根本矛盾**：LLM 是「语言模型」而非「知识模型」——其训练目标是预测下一个 token，而非保证事实正确性。在通用领域可以通过 RLHF 部分缓解，但在垂直领域（具体课程、具体教材）几乎必然出现幻觉。

**教育场景的底线要求**：教育内容的错误会被学生长期记忆且难以纠正，比通用领域更严苛。任何「凑合能用」的生成都不合格。

**五层递进总架构图**：

```
输入 query
    │
    ▼
[第零层] Query Rewrite + 画像感知
    │  去上下文化、画像扩展、多查询
    ▼
[第一层] 多策略检索 + 置信度过滤
    │  混合检索、RRF 融合、score_threshold、
    │  关键词重叠 re-rank、parent 回填、多样性
    ▼
[第二层] Prompt 约束 + NEVER/IMPORTANT 分级禁令
    │  role="system"、低温度、引用规范、
    │  Pre-generation Check
    ▼
   <LLM 生成>
    │
    ▼
[第三层] SafetyAgent 独立审核
    │  4 项清单：事实核查 / 引用验证 /
    │  误导检测 / 学习场景适配
    ▼
[第四层] 代码级硬约束 + 评估监控
    │  recommend_agent DB 过滤、
    │  safe_json_loads、judge.py、
    │  golden_dataset 回归
    ▼
输出 final_content
```

每层作用时机不同（第零层在检索前、第一层在检索中、第二层在生成中、第三层在生成后、第四层贯穿全流程），形成「检索前预防 → 检索中过滤 → 生成中约束 → 生成后审核 → 全流程兜底」的全链路防护。

#### 3.3.5.2 第零层：检索前 — Query Rewrite + 画像感知

**作用时机**：向量检索之前。
**关键文件**：`backend/agents/utils.py` `_rewrite_query()` (`:323-383`) + `_expand_queries()` (`:402-427`)。

**策略 A：对话去上下文化**（指代消解，最近 6 轮窗口）

对多轮对话中的指代词进行还原。例如将「它是怎么算的」「那个公式怎么推」还原为「反向传播算法是怎么算的」「反向传播的链式法则公式怎么推」。

实现：取 `state.chat_history[-6:]`（最多 6 轮）作为上下文，与 `state.user_message` 一起喂给 LLM（使用 `configs/prompts.yaml: rag.rewrite` prompt），生成去上下文化后的查询。

**策略 B：学生画像感知改写**（偏向薄弱知识点 / 学习目标）

在去上下文基础上，注入画像信息。例如学生画像标记「薄弱：反向传播」，改写时加入「重点讲清楚反向传播的链式法则推导」。

实现：在 prompt 中拼接 `state.profile.knowledge_weak / learning_goal` 字段。

**策略 C：多角度查询扩展**（概念定义 / 原理推导 / 应用示例 / 常见误区 / 跨概念关联）

通过 `rag.expand` prompt 让 LLM 生成 N 个角度的子查询：

- 子查询 1：「反向传播算法的定义」（概念定义角度）
- 子查询 2：「反向传播的链式法则推导」（原理推导角度）
- 子查询 3：「反向传播在 CNN 中的应用」（应用示例角度）
- 子查询 4：「反向传播常见误区：梯度消失」（常见误区角度）

默认 `multi_query_count=3`，最终列表 `[原查询, 子查询1, 子查询2, 子查询3]` 最多 4 条。

**RRF 融合**：4 条子查询并发执行检索（`retrieve_with_queries()`），结果再次 RRF 融合。

**容错设计**：每次改写失败都有 `_build_fallback_query()`（:386-392）回退：

- 短消息且含 kp_name → 直接拼接
- 否则 → `"{kp_name}：{user_message[:120]}"`

回退查询不阻断检索流程，保证至少有一条「可用」查询进入第一层。

**核心价值**：把「模糊 / 简短 / 有上下文」的查询转化为「具体 / 完整 / 多角度」的高质量查询，是后续所有层效果的前提。

#### 3.3.5.3 第一层：检索中 — 多策略检索 + 置信度过滤

**作用时机**：LLM 生成之前。
**关键文件**：`backend/rag/retriever.py` 全部 + `backend/db/vector.py` 全部。

**混合检索**：BGE-M3 / DashScope `text-embedding-v4` 语义路 + jieba 关键词路

- **语义路**（`backend/db/vector.py:288-305`）：pgvector `<=>` 余弦距离 + HNSW KNN，参数 `hnsw_ef_search=100`
- **关键词路**（`backend/db/vector.py:476-493`）：jieba 分词 + `to_tsquery` + `ts_rank`，仅检索子块（`is_parent=FALSE`）

**RRF 融合排序**：`_rrf_fusion_cross_path()` (retriever.py:272-308)，参数 `rrf_k=60 / vector_weight=1.0 / keyword_weight=1.0`

**相似度阈值过滤**：默认 `score_threshold=0.5`（`configs/config.yaml:96`），低于阈值的 chunk 直接丢弃，避免 LLM 引用「勉强相关」的内容。

**关键词重叠 re-rank**：`_rerank_by_keyword_overlap()` (retriever.py:657-685)，通过 jieba 关键词与 chunk.text 的匹配率计算 boost：

```
boost = min(overlap / len(keywords), 1.0) * re_rank_keyword_boost
```

默认 `re_rank_keyword_boost=0.25`（`configs/config.yaml:118`）。语义相似但术语不匹配的 chunk 被降级。

**父-子块回填**：`_resolve_parent_chunks()` (retriever.py:581-645)，子块检索后用父块文本替换，保证 LLM 看到完整上下文。

**多样感知排序**：`_diversify_order()` (retriever.py:524-564)，按 section 分组后 round-robin 交错，保证 top-k 至少覆盖 3 个章节。

**Citation 编号安全提示**：`format_context_with_sources()` 在截断时追加 `[注意：以上仅展示了前 N 条...请勿引用 [N+1]...]`，从源头杜绝 LLM 引用未实际看到的片段。

**用户级数据隔离**：检索时通过 `user_id` 过滤，避免跨用户数据泄露（`DocumentChunk.user_id` 字段，参考 `backend/rag/retriever.py:50-117` 的 `where` 参数）。

#### 3.3.5.4 第二层：生成中 — Prompt 约束 + NEVER/IMPORTANT 分级禁令

**作用时机**：LLM 生成过程中。
**关键文件**：`configs/prompts.yaml` 全部生成类 prompt。

**NEVER 绝对禁止条款**（共 3 条，所有生成类 Agent 共有）：

1. **NEVER 编造事实**：禁止在参考资料之外构造公式、定理、步骤。任何事实必须可追溯到 `context` 中的片段。
2. **NEVER 凭记忆补充**：禁止「根据我的知识」「通常情况下」这类自我补充；只能基于 `context` 回答。
3. **NEVER 跳过空引用声明**：当 `context` 为空时，必须输出「⚠️ 当前知识库暂无参考资料」开头声明，而非静默生成。

**IMPORTANT 必须做到条款**（共 3-6 条，因 Agent 而异）：

- **引用追溯**：每个事实声明必须紧跟 `[n]` 引用标注
- **覆盖声明**：明确说明「参考资料覆盖了哪些方面」「未覆盖哪些方面」
- **难度适配**：根据用户认知风格调整内容深度
- **结构清晰**：H1/H2/H3 分级、表格、列表
- **完整公式**：数学公式用 `$...$` 或 `$$...$$` 包裹，保留推导步骤

**Pre-generation Check 内心自查清单**（不输出，仅约束生成路径）：

```
1. 我已经仔细阅读了所有 retrieved_docs 吗？
2. 我的每个事实声明是否都有 [n] 引用？
3. 若 retrieved_docs 为空，我是否声明了「暂无参考资料」？
4. 我是否考虑了用户的认知风格与基础水平？
5. 我是否避免了「似乎」「可能」「通常」这类模糊表述？
```

**`[n]` 引用标注规范 + 「补充」自我知识前缀**：

- `[n]` 标注紧跟事实声明：「反向传播通过链式法则实现[1]」
- 自我知识（基于 LLM 通用知识但不在参考资料中）必须以「补充」前缀：「补充：实际训练中常使用 Adam 优化器代替 SGD（不在本节参考资料范围内）」

**`role:"system"` + 低温度（0.1-0.4）确保高遵循度**：所有生成类 prompt 使用 `role="system"`，温度从 `configs/config.yaml: agents.<name>.temperature` 读取。

**核心价值**：把「禁止」与「必须」以可被 LLM 理解的语言写在 prompt 中，并通过温度与角色控制生成行为的稳定性。LLM 偏离 prompt 的概率显著降低。

#### 3.3.5.5 第三层：生成后 — SafetyAgent 独立审核

**作用时机**：LLM 生成完成之后。
**关键文件**：`backend/agents/safety_agent.py:23` `run()` + `configs/prompts.yaml: agents.safety.system_prompt`。

**4 项审核清单**：

| 审核项 | 检查内容 | 输出 |
|---|---|---|
| **事实核查** | 声明是否能在 `retrieved_docs` 中找到依据 | supported / unsupported |
| **引用验证** | 每个 `[n]` 是否对应真实片段 | accurate / inaccurate / vague |
| **误导检测** | 是否存在「似是而非」的表述（如把 A 的性质说成 B 的） | misleading / ok |
| **学习场景适配** | 是否符合用户画像与目标层次 | suitable / over-complex / over-simplified |

**「只审不修」原则**：

- SafetyAgent **不修改** 原始 `draft_content`；若发现问题，仅写入 `state.metadata.safety_issues`（list[str]）
- 前端可读取 `safety_issues` 并以「⚠️ 以下内容可能存在问题：...」形式展示，但不替换内容
- 保留原始输出的好处：教师 / 高级用户可以看到完整草稿，便于人工审阅；学生用户可以选择信任或质疑

**fail-open 策略**：审核失败保守通过，避免阻塞主流程。当 LLM 调用连续失败 3 次时，SafetyAgent 自动 pass 并写入 `metadata.safety_status="fail_open"`。

**temperature=0.1 确定性输出**：审核 prompt 与生成 prompt 分离，温度固定 0.1，确保审核输出可复现。

**独立 LLM 角色与提示词**：

- SafetyAgent 使用与生成 Agent **不同的提示词**（`agents.safety.system_prompt`），明确「你是审核员而非生成者」
- 通过解耦角色，避免 LLM 「自己审自己」时倾向于放行自己的输出

**核心价值**：在 prompt 约束不能 100% 生效时，提供「最后一道防线」；同时保留原始内容供高级用户审阅。

#### 3.3.5.6 第四层：代码级 — 硬约束校验 + 评估监控

**作用时机**：贯穿全流程。
**关键文件**：`backend/agents/recommend_agent.py` + `backend/evaluation/*` + `backend/evaluation/health_check.py`。

**硬约束校验**：

1. **`recommend_agent`：DB 强制过滤不存在的 `kp_id`**（`recommend_agent.py:25`）

   ```python
   # 推荐前先查 DB，过滤掉不存在的 kp_id
   valid_kps = await db.execute(
       select(KGNode.id, KGNode.name).where(KGNode.id.in_(candidate_kp_ids))
   )
   filtered_kps = [kp for kp in candidates if kp.id in {row.id for row in valid_kps}]
   ```

   从源头拒绝「LLM 幻觉知识点」进入推荐结果。

2. **`safe_json_loads`：5 策略递进式 JSON 解析**（`backend/agents/utils.py` 或 `backend/utils/`）

   - 策略 1：直接 `json.loads()`
   - 策略 2：修复单引号 → 双引号后重试
   - 策略 3：修复多余转义符
   - 策略 4：从 Markdown 代码块中提取 JSON（正则匹配 ```` ```json...``` ````）
   - 策略 5：兜底正则提取最外层 `{...}` / `[...]`

   避免 LLM 输出格式微偏差（如多余逗号、未转义引号）导致 quiz_agent / mindmap_agent 输出解析失败。

**持续质量监控**：

1. **`judge.py`：4 维度 LLM-as-Judge**

   - Judge1 Chunk Relevance（0/1/2 三级评分）
   - Judge2 Faithfulness（逐句 supported/unsupported）
   - Judge3 Completeness（自动生成 expected_aspects，覆盖度 covered/partial/missing）
   - Judge4 Citation Accuracy（抽取 `[n]` 引用，逐条评估 accurate/inaccurate/vague）

   触发时机：默认 `evaluation.mode=development` 采样率 1.0（每条都评估），生产模式 `prod` 采样率 0.1。

2. **`golden_dataset.py`：15 条人工标注查询的端到端回归测试**

   每次重大版本变更前运行 `python -m backend.evaluation.golden_dataset --run`，生成 `logs/golden_eval_<时间戳>.md` 报告。`_detect_regression()`（`:275-336`）自动对比上一轮结果，指标下降 > 10% 触发告警。

3. **`health_check.py`：无 LLM 代理指标监控**

   - 向量库连通性（< 5 ms）
   - 索引统计（chunk 总数、覆盖率）
   - 滑动窗口内 P50/P95 检索时延

   用于 7×24 监控，不依赖 LLM 调用。

4. **多 LLM 交叉验证**（`_cross_validate` in `backend/evaluation/judge.py:604`）

   当 Judge 输出置信度 < 0.3 时，触发第二个 Provider 重新评估。两次评估分歧大时标记 `disagreement`，由人工介入。

**核心价值**：把「LLM 不确定的事」通过代码硬约束兜底；把「LLM 评估的事」通过持续监控防退化。这是工程层而非 prompt 层的防护。

#### 3.3.5.7 防幻觉效果度量

**关键指标**：

| 指标 | 定义 | 目标 |
|---|---|---|
| **幻觉率**（Hallucination Rate） | `unsupported_count / total_sentences` | ≤ 0.05 |
| **引用准确率**（Citation Accuracy） | `accurate_count / total_citations` | ≥ 0.90 |
| **误导率**（Misleading Rate） | `misleading_count / total_responses` | ≤ 0.05 |

### 3.4.5 知识图谱服务

知识图谱服务是本系统的核心数据资产之一，承担「把教材自动转化为可检索、可推理的图结构」的关键任务。

#### 3.4.5.1 五层节点结构

`backend/services/kg_builder.py` 与 `backend/main.py:1062` 硬编码五层节点类型：

```
type_levels = ["Course", "Chapter", "KnowledgePoint", "SubPoint", "Concept"]
```

层级关系：每个 `Concept` IS_PART_OF 一个 `SubPoint`，每个 `SubPoint` IS_PART_OF 一个 `KnowledgePoint`，依此类推，最顶层为 `Course`。

#### 3.4.5.2 四类关系边

`backend.models.schemas.KGRelation` 枚举定义允许的关系类型：

- **IS_PART_OF**：父子层级关系（SubPoint → KnowledgePoint 等）
- **CONTAINS**：包含关系（反向 IS_PART_OF，用于 BFS 时反向遍历）
- **REQUIRES**：前置依赖（学习 A 之前必须掌握 B）
- **RELATED_TO**：一般关联（横向拓展）

#### 3.4.5.3 课程图谱建模

PDF 教材中提取出的目录（TOC）按层级映射为节点类型（kg_builder.py:37）：

| TOC 层级 | 节点类型 |
|---|---|
| 1 (一级标题) | `Chapter` |
| 2 (二级标题) | `KnowledgePoint` |
| 3 (三级标题) | `SubPoint` |
| 4 (四级及以上) | `Concept` |

`Course` 节点由系统自动创建（kg_builder.py:715-728），LLM 提取时被强制降级为 `Chapter`（kg_builder.py:342）。

#### 3.4.5.4 知识图谱自动构建管道

`backend/services/kg_builder.py:574` `build_kg(doc_id, db, on_progress, user_id)` 是核心入口：

**双路径策略**：

1. **TOC 路径**（PDF 目录 ≥ 3 项时启用）：
   - `extract_toc()`（loader.py:78）→ 提取 PDF 目录
   - `_build_toc_skeleton()`（kg_builder.py:165）→ 建骨架节点 + IS_PART_OF 边
   - `_group_by_toc()`（:202）→ 按页码聚合 chunk
   - `_extract_nodes_with_context()`（:493）→ LLM 提取细粒度节点
   - `_attach_details_to_sections()`（:248）→ 自动挂载
   - `_extract_cross_edges()`（:516）→ 推断 REQUIRES / RELATED_TO
   - `_fill_missing_hierarchy_edges()`（:264）→ 兜底补齐遗漏 IS_PART_OF

2. **Fallback 路径**：
   - `_group_by_page()`（:107）→ 按页聚合 chunk
   - `_extract_nodes()`（:358）→ LLM 提取节点

**异步任务包装**：`run_kg_build()`（kg_builder.py:780）作为后台任务，由 `POST /kg/build`（main.py:1153）触发，写入 `KGBuildTask` 表后由前端通过 `GET /kg/build/{task_id}/status`（main.py:1187）轮询。

## 3.5 数据与接口设计

> 数据与接口层是基础能力层、智能体中枢层、功能层共同依赖的「底部契约」。本节从「设计原则 → 数据库 → API → 错误处理」四方面给出完整规约。

### 3.5.1 设计原则

#### 3.5.1.1 ORM ↔ Schema 严格对齐

`backend/db/models.py` 是 **单一可信源**。Pydantic Schema 字段名严格匹配 ORM 列名：

- 时间戳统一 `created_at` / `updated_at`（禁止 `submitted_at` / `modified_at` 等别名）
- 主键统一 `id`（禁止 `task_id` / `record_id` 等）
- 错误文本统一 `error_message`（禁止 `error_msg` / `err`）
- 实体标题统一 `title`（禁止改名 `name`）

新增模型时必须验证：
1. 所有时间戳用 `created_at` / `updated_at`
2. 每个 Schema 字段名严格匹配 ORM 列名
3. 不用 `model_validator` 做字段重命名
4. `main.py` 中手动构造 Schema 时直接引用 ORM 字段名
5. 前端 `.get("field_name")` 键名匹配 API 实际响应

#### 3.5.1.2 关系型 + 向量型混合

选用 PostgreSQL + pgvector 扩展实现「关系型 + 向量型」混合存储：

- 关系型：用户、画像、会话、消息、资源、路径、答题
- 向量型：`document_chunk.embedding Vector(1024)` + HNSW 索引
- 全文型：`document_chunk.text_search TSVECTOR` + GIN 索引

混合存储的优势：
- **事务一致性**：向量数据与元数据在同一 DB 同一事务，避免分布式事务
- **运维简单**：单数据库单备份策略
- **成本可控**：无需独立向量数据库授权

#### 3.5.1.3 Alembic 版本化迁移

`migrations/` 目录管理 schema 演进，共 17 个版本文件：

- 初始 schema（`a6844ed9ad28`）
- document_chunk 表创建（`9069c06f0251`）
- UUID → Snowflake（`db2c961ff39d`）
- pgvector embedding 列（`8a3f2e1b4c5d`）
- IVFFlat → HNSW 切换（`6f9a2b3c4d5e`）
- tsvector + GIN（`9c2d5e7f8a9h`）
- 父子分块支持（`8b3c4d5e6f7g`）
- 邮箱验证（`14d2f3e4f5a6`）
- 学习计划（`c3d4e5f6a7b8`）
- ... 等

迁移命令：`alembic upgrade head`（首次启动或 schema 变更后）。

#### 3.5.1.4 RESTful + Pydantic v2 + JWT

接口设计遵循 RESTful 规范：

- HTTP 方法语义：GET（读）/ POST（创建）/ PUT（更新）/ DELETE（删除）/ PATCH（部分更新）
- 资源路径名词化：`/resources/{id}` 而非 `/getResource?id={id}`
- 状态码：200 OK / 201 Created / 400 Bad Request / 401 Unauthorized / 404 Not Found / 500 Internal Server Error
- 响应统一 JSON：`{"code": 0, "data": ..., "message": "..."}` 或直接返回对象
- 请求 / 响应模型均使用 Pydantic v2（自动 OpenAPI 文档生成）

身份认证：所有非 `/health` / `/auth/*` 端点通过 `backend.auth.deps.get_current_user_id` 依赖注入校验 JWT。

#### 3.5.4.1 错误码全表

| 400 | 4000 | 请求参数错误 |

#### 3.5.4.2 loguru 分级规范

`backend/logging_config.py` 配置 loguru，按级别使用：

| 级别 | 场景 | 示例 |
|---|---|---|
| TRACE | 极详细（函数参数、逐步返回值）| `logger.trace("query_vector shape={}", vec.shape)` |
| DEBUG | 开发者调试 | `logger.debug("[DocAgent] LLM prompt length={}", len(prompt))` |
| INFO | 关键业务里程碑 | `logger.info("[DocAgent] doc generated, kp={}, len={}", kp, n)` |
| SUCCESS | 操作成功完成 | `logger.success("[Generation] batch {} done, {}s", id, t)` |
| WARNING | 可恢复错误、降级 | `logger.warning("[LLM] retry {} due to {}", n, reason)` |
| ERROR | 不可恢复错误 | `logger.error("[Database] connection pool exhausted")` |
| CRITICAL | 系统级失败 | `logger.critical("[App] startup failed, port {} in use", p)` |

**消息格式**：使用 **延迟求值** `{}` 占位符，禁止 f-string：

```python
# 正确：延迟格式化，级别未触发时不计算
logger.info("[DocAgent] kp={}, draft_len={}", kp_name, len(draft))

# 错误：f-string 总是立即求值
logger.info(f"[DocAgent] kp={kp_name}")
```

**Agent 前缀**：所有 Agent 日志带 `[AgentName]` 前缀，便于 grep。

**异常日志**：使用 `logger.exception()`（自动包含 traceback），不用 `logger.error()`。

#### 3.5.4.3 trace_id 全链路追踪

`backend/logging_config.py` 的 patcher 自动注入 `trace_id` 到每条日志的 `extra`：

```python
def patcher(record):
    record["extra"]["trace_id"] = get_current_trace_id()
```

trace_id 由 `backend.middleware.logging_middleware` 在请求入口生成（UUID），写入 `contextvars`，响应头 `X-Trace-Id` 同时回传前端。

前端日志：错误响应中包含 `trace_id`，用户反馈问题时可直接提供给开发人员用于日志检索。

### 3.7.1 性能优化

#### 3.7.1.1 全链路异步与并发

本系统从入口到出口全链路异步：

| 层级 | 异步实现 |
|---|---|
| Web 框架 | FastAPI async def 路由 + `asyncio` 事件循环 |
| 数据库 | SQLAlchemy 2.0 async + asyncpg 异步驱动 |
| LLM 调用 | `await chat_completion()` + `asyncio.Semaphore` 并发控制 |
| 检索 | `asyncio.gather(vector_query, keyword_query)` 并发双路 |
| 视频检索 | `asyncio.gather(chat_completion, search_videos)` 并发 |
| 后台任务 | `asyncio.create_task(run_generation(...))` 异步派发 |

并发控制点：
- Embedding：`concurrency=8`（`configs/config.yaml:83`）
- LLM：`max_attempts=5`（指数退避），单 Provider 无并发限制
- KG 构建：`knowledge_graph.llm_concurrency=10`（kg_builder.py 内部 `asyncio.Semaphore`）

#### 3.7.1.2 缓存策略

**RAG 检索缓存**：

- 实现：`backend/agents/utils.py:304` `_retrieval_cache: dict[(kp_name, user_id), list[RetrievedChunk]]`
- 写入：`retrieve_context()` 命中后写入缓存
- 失效：`graph.invoke/stream_invoke` 入口调用 `clear_retrieval_cache()`（graph.py:155-156）
- 价值：同一请求内多 Agent 共享检索结果，避免重复调用 Embedding 与 DB

**画像快照缓存**：

- 实现：`backend/services/profile.py:77` `create_or_update_profile()` 时同步写 `ProfileHistory` 快照
- 价值：用户可回溯历史版本；调试时可对比变更前后差异

**前端 localStorage**：

- `access_token`：JWT Token（避免每次请求都登录）
- `softbei_guide_done_${userId}`：引导完成状态
- `assistant_visible`：助手面板可见性

#### 3.7.1.3 流式输出降低首字时延

虽然当前实现走非流式 POST，但接口已预留 SSE 流式：

- 后端：`graph.stream_invoke()`（graph.py:186）使用 LangGraph updates 模式
- 前端：`EventSource` 订阅 `data: {event}\n\n`
- 价值：用户从「等待 5-10 秒整段渲染」变为「看到 200 ms 第一个字」

未来切换只需修改 `chat.html` 调用方式，无需后端改动。

| 水平扩展 | 单进程模块化单体；并发瓶颈时按 graph 节点切分微服务 |

### 3.8.4 各模块在该案例中的协作分工

| 步骤 | 涉及的 Agent | 涉及的服务模块 | 涉及的数据表 |
|---|---|---|---|
| 1 注册登录 | — | 用户认证服务 | user |
| 2 首次对话追问 | profile_agent → END | 对话式画像服务 | chat_session, chat_message |
| 3 文档生成 | profile_agent → planner_agent → doc_agent → safety_agent → recommend_agent | 资源生成 + 智能辅导 | resource_meta, document_chunk, quiz_item |
| 4 加入路径 | recommend_agent → END | 学习路径服务 | learning_path, learning_path_item |
| 5 查看资源库 | — | 资源库服务 | resource_meta |
| 6 上传教材 | — | 文档服务 | document_chunk |
| 7-8 知识图谱构建 | kg_agent → recommend_agent | 知识图谱服务 | kg_node, kg_edge, kg_build_task |
| 9 知识图谱可视化 | — | 前端渲染 | kg_node, kg_edge |
| 10 生成测验 | planner_agent → quiz_agent → safety_agent → recommend_agent | 资源生成服务 | resource_meta, quiz_item |
| 11 答题反馈 | — | 学习评估服务 | quiz_attempt, learning_record, student_profile |

**全流程用到的 11 个 Agent**：profile_agent、planner_agent、clarify_agent（步骤 2 隐含）、doc_agent（步骤 3）、quiz_agent（步骤 10）、safety_agent（步骤 3、10）、recommend_agent（步骤 3、4、10）、kg_agent（步骤 7），加 doc_agent / quiz_agent / safety_agent / recommend_agent 共 11 个；步骤 11 不调用 Agent，仅触发 `update_profile_from_quiz`。

**全流程涉及的五层防幻觉**：步骤 3 与 10 同时启用五层防幻觉（Query Rewrite → 混合检索 → Prompt 约束 → SafetyAgent → DB 过滤），是「内容准确性」的最高优先级场景。

**全流程产生的数据资产**：

- 1 张 user 记录
- 1 张 student_profile（含 mastered=[反向传播]）
- 1 张 chat_session + 5 张 chat_message
- 1 张 resource_meta（doc 类型）+ 1 张 resource_meta（quiz 类型）
- 6 张 quiz_item + 5 张 quiz_attempt
- 5 张 learning_record（含 view / complete / quiz_correct / quiz_incorrect / stay）
- 1 张 learning_path + 1 张 learning_path_item
- 117 张 kg_node + 156 张 kg_edge
- 500+ 张 document_chunk

从冷启动到完整知识图谱与个性化学习路径，11 步操作，约 15 分钟（不含用户阅读与答题时间）。
