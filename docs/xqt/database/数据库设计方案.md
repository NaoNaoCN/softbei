# 数据库设计文档

> 更新时间：2026-05-21 | PostgreSQL 17.10 + pgvector | SQLAlchemy 2.0 异步 ORM | 13 张表

---

## 一、快速概览

这个数据库为一个**多智能体学习系统**服务——它接收学生的学习请求，调用 9 个 AI Agent 生成个性化学习资源（文档、题目、思维导图、代码示例等），并追踪学生的整个学习过程。

为此，数据库需要记住五件事：**你是谁、你学过什么、知识怎么组织、AI 生成了什么、你学得怎么样**。这恰好对应了 13 张表的组织逻辑。

## 三、主键策略：Snowflake ID

全部主键使用 **64 位 Snowflake 算法**生成的 BIGINT，而非数据库自增或 UUID。

| 方案 | 优点 | 缺点 |
|------|------|------|
| 自增 ID | 简单 | 分布式冲突、暴露业务量 |
| UUIDv4 | 全局唯一 | 索引膨胀、不可排序 |
| **Snowflake** | 全局唯一 + 时间有序 + 高性能 | 依赖时钟 |

项目最初使用 UUIDv4，在迁移 `db2c961ff39d` 中全部改为 Snowflake BIGINT。原因：
- **索引友好**：BIGINT 比 UUID 字符串小 4 倍，B+Tree 索引更紧凑
- **时间有序**：Snowflake ID 高位是时间戳，写入顺序天然递增，减少页分裂
- **分布式就绪**：Worker ID + Datacenter ID 占 10 位，最多 1024 个节点

```python
# backend/utils/snowflake.py:26-55
def generate_id() -> int:
    """结构: 41bit时间戳 | 5bit数据中心 | 5bit机器 | 12bit序列号"""
```

> 注意：`learning_path_item.kp_id` 和 `learning_record.kp_id` 等引用 `kg_node.id`，而 `kg_node.id` 是 VARCHAR(64) 而非 Snowflake（知识点 ID 如 `kp_03_01` 由业务生成，非系统生成）。

## 四、表结构详解

### 4.1 用户系统（user + student_profile + profile_history）

```
user ──1:1── student_profile ──1:N── profile_history
```

**user** 是最简模型——只存认证必需字段：

| 列 | 类型 | 说明 |
|------|------|------|
| `id` | BIGINT | Snowflake ID |
| `username` | VARCHAR(64) UNIQUE | 登录名 |
| `hashed_password` | VARCHAR(128) | bcrypt 哈希 |
| `created_at` | DATETIME | 注册时间 |

**student_profile** 是用户的"学习画像"，1:1 关系（`user_id` 唯一约束）：

| 列 | 类型 | 说明 |
|------|------|------|
| `major` | VARCHAR(128) | 专业 |
| `learning_goal` | TEXT | 学习目标 |
| `cognitive_style` | ENUM | 视觉型 / 阅读型 / 动手型 |
| `daily_time_minutes` | INT | 每日学习时间（分钟） |
| `knowledge_mastered` | JSON | 已掌握知识点列表 |
| `knowledge_weak` | JSON | 薄弱知识点列表 |
| `error_prone` | JSON | 易错点列表 |
| `goal_questions` | JSON | 目标摸底的历史提问 |
| `version` | INT | 画像版本号（每次更新递增） |

设计要点：`knowledge_mastered` / `knowledge_weak` / `error_prone` 使用 JSON 数组存知识点 ID，而非拆成关联表。这是刻意的取舍——这些数组在 Agent 的 prompt 中直接序列化注入，不需要跨表 JOIN 查询。代价是无法用数据库约束保证引用完整性，但换来了 Agent 场景下的读取效率。

**profile_history** 是画像的版本快照：

```python
# 每次更新画像时，旧版本序列化为 JSON 存入 history
snapshot: Mapped[dict] = mapped_column(JSON, nullable=False)
```

保留了最近 10 个版本（由 Agent 配置控制），类似 Git 的 commit 历史——可以回溯学生的学习轨迹。

---

### 4.2 对话系统（chat_session + chat_message）

```
chat_session ──1:N── chat_message
```

**chat_session** 代表一次对话：

| 列 | 类型 | 说明 |
|------|------|------|
| `title` | VARCHAR(256) | LLM 自动生成的对话标题 |
| `last_used_at` | DATETIME | 最后活跃时间（排序用） |

**chat_message** 存所有对话消息。值得注意的是，项目**没有**为每个 session 建独立的消息表（早期设计的 `messages_table` 字段已移除），而是用一张静态表存所有消息：

```python
# chat_message
session_id  ──FK──>  chat_session.id (CASCADE)
role         VARCHAR(16)           # "user" | "assistant"
content      TEXT
resource_type VARCHAR(16)          # 消息关联的资源类型
created_at   DATETIME
```

索引 `(session_id, created_at)` 支持按会话 + 时间高效取最近消息。CASCADE 删除意味着删除会话时自动清理所有关联消息。

---

### 4.3 知识图谱（kg_node + kg_edge）

```
kg_node ──source── kg_edge ──target── kg_node
```

这是系统的知识骨架。KG 从上传的教材文档自动构建（由 LLM 抽取知识点和关系）。

**kg_node** 用业务生成的字符串 ID（如 `kp_03_01`），而非 Snowflake：

| 列 | 类型 | 说明 |
|------|------|------|
| `id` | VARCHAR(64) PK | 知识点 ID，如 `kp_03_01` |
| `name` | VARCHAR(256) | 知识点名称 |
| `node_type` | ENUM | Course / Chapter / KnowledgePoint / SubPoint / Concept |
| `description` | TEXT | 知识点描述 |
| `course_id` | VARCHAR(64) | 所属课程 |
| `user_id` | BIGINT NULL | 创建者（NULL = 系统预置，全局共享） |

`user_id` 支持两种模式：NULL 表示系统预置的公共知识点（所有用户可见），非 NULL 表示用户私有知识点。查询时用 `WHERE user_id = :uid OR user_id IS NULL` 同时获取。

**kg_edge** 定义知识点间的关系：

| 列 | 类型 | 说明 |
|------|------|------|
| `source_id` | FK → kg_node.id | 源节点 |
| `target_id` | FK → kg_node.id | 目标节点 |
| `relation` | ENUM | IS_PART_OF / REQUIRES / RELATED_TO / CONTAINS |

`(source_id, target_id, relation)` 唯一约束防止重复边。双向关系通过 ORM 的 `out_edges` 和 `in_edges` 导航。

---

### 4.4 向量存储（document_chunk）

```
document_chunk (pgvector)
  embedding: VECTOR(1024)  ← IVFFlat 索引 (cosine)
```

知识库文档被切分为文本块，通过 Embedding API 向量化后存入此表：

| 列 | 类型 | 说明 |
|------|------|------|
| `chunk_id` | VARCHAR(128) UNIQUE | 块的唯一标识 |
| `doc_id` | VARCHAR(128) | 所属文档 ID |
| `collection_name` | VARCHAR(64) | 集合名（默认 `knowledge_base`） |
| `text` | TEXT | 原始文本内容 |
| `embedding` | VECTOR(1024) | 1024 维向量（text-embedding-v4） |
| `source` | VARCHAR(512) | 来源文件路径 |
| `page` | INT | 页码 |
| `section` | VARCHAR(256) | 所属章节 |
| `user_id` | VARCHAR(64) | 上传用户 ID |

检索时，查询向量与 `embedding` 列做余弦相似度计算，取 top-K 结果。IVFFlat 索引（`probes=10`）在精度和速度间取平衡。向量查询绕过 ORM 会话，直接用 `engine.connect()` 获取原始连接执行 SQL。

---

### 4.5 资源生成流水线（resource_meta + generation_batch + generation_task）

```
generation_batch ──1:N── generation_task ──1:1── resource_meta
```

这是系统最核心的写入路径。当用户说"帮我生成量子力学的学习资料"，流程是：

1. **GenerationBatch** — 创建一个批次，记录意图（kp_id、resource_types 数组）
2. **ResourceMeta** — 为每个资源类型预创建一条记录（此时 content 为空）
3. **GenerationTask** — 为每个资源穿创建异步任务（status=pending）
4. Agent 后台执行，完成后更新 task 状态 + 写入 resource 内容

**GenerationBatch** 跟踪整体进度：

| 列 | 说明 |
|------|------|
| `kp_id` | 目标知识点 |
| `resource_types` | JSON 数组，如 `["doc", "quiz", "mindmap"]` |
| `status` | pending → running → done/failed |
| `progress` | 0-100 百分比 |

**GenerationTask** 是单个资源的执行状态：

| 列 | 说明 |
|------|------|
| `resource_id` | 1:1 关联 ResourceMeta |
| `batch_id` | 所属批次（可为 NULL，支持单独生成） |
| `status` / `progress` | 执行状态 |
| `error_message` | 失败时的错误信息 |

**ResourceMeta** 是生成结果的载体：

| 列 | 说明 |
|------|------|
| `kp_id` | 关联知识点 |
| `resource_type` | ENUM: doc / mindmap / quiz / code / summary / kg |
| `title` | 资源标题 |
| `content` | 文本内容（doc/summary/code 类型使用） |
| `content_json` | JSON 结构化内容（mindmap 使用，与 content 互斥） |

> 设计决策：`content` 和 `content_json` 互斥使用。文本型资源（文档、代码）写 `content`，结构化资源（思维导图的树形结构）写 `content_json`。这样避免了 JSON 字段里存 Markdown 的不匹配问题。

**KGBuildTask** 是一个独立的异步任务表，追踪从文档构建知识图谱的进度：

| 列 | 说明 |
|------|------|
| `doc_id` | 源文档 ID（对应 document_chunk.doc_id） |
| `status` | 构建状态 |
| `stage` | 当前阶段：toc_extract / node_extract / edge_infer |
| `nodes_count` / `edges_count` | 已构建的节点/边数量 |

---

### 4.6 测验系统（quiz_item + quiz_attempt）

```
resource_meta ──1:N── quiz_item ──1:N── quiz_attempt
```

生成资源类型为 `quiz` 时，ResourceMeta 下挂多条 QuizItem。

**QuizItem** 定义题目：

| 列 | 说明 |
|------|------|
| `question_type` | ENUM: single(单选) / multi(多选) / fill(填空) / short(简答) |
| `stem` | 题干 |
| `options` | JSON 数组（选择题的选项） |
| `answer` | 标准答案 |
| `explanation` | 解析 |
| `order_index` | 排序序号 |

四种题型的存储策略：
- **单选/多选**：`options` 存 `["A.xxx", "B.xxx", ...]`，`answer` 存 `"A"` 或 `"AB"`
- **填空**：`options` 为 NULL，`answer` 存正确答案文本
- **简答**：`options` 为 NULL，`answer` 存参考答案，评分由 LLM 完成

**QuizAttempt** 记录每次作答：

| 列 | 说明 |
|------|------|
| `user_answer` | 学生提交的答案 |
| `is_correct` | 是否正确 |
| `score` | 得分（简答题用） |
| `submitted_at` | 提交时间 |

> 命名不一致：此表的 `submitted_at` 按项目规范应为 `created_at`。这是已知的技术债（见优化分析报告第 4.3 节）。

---

### 4.7 学习路径（learning_path + learning_path_item）

```
learning_path ──1:N── learning_path_item ──M:1── kg_node
```

学习路径是一条有序的知识点学习路线。

| 列 | 说明 |
|------|------|
| `title` / `description` | 路径名称和描述 |
| `created_at` | 创建时间 |

**LearningPathItem** 维护路径中的顺序和完成状态：

| 列 | 说明 |
|------|------|
| `kp_id` | FK → kg_node.id，关联知识点 |
| `order_index` | 学习顺序（0, 1, 2...） |
| `is_completed` | 是否已完成 |

`order_index` 在 ORM relationship 中配置了 `order_by`，加载路径时自动排序。

### 4.8 学习记录（learning_record）

```
user ──1:N── learning_record ──M:1── resource_meta
                               └── M:1── kg_node
```

记录用户的所有学习行为：

| 列 | 说明 |
|------|------|
| `action` | view(浏览) / complete(完成) / quiz(答题) |
| `duration_seconds` | 学习时长 |
| `recorded_at` | 记录时间 |

这是系统的"行为日志"——不仅可以统计学习时长，还能关联到具体知识点（`kp_id`），用于分析学生的薄弱环节。复合索引 `(user_id, kp_id)` 加速了"某学生对某知识点的历史学习情况"这类查询。

## 五、索引策略

系统共创建了 **25+ 个索引**，遵循"查询驱动"原则——只为高频查询条件建索引。

### 建索引的规则

1. **所有外键 = 索引**。除少数低频场景外，每个 FK 列都有对应 BTREE 索引，保证 JOIN 和 WHERE 过滤走 Index Scan。
2. **高频查询组合 = 复合索引**。例如 `(user_id, resource_type)` 加速"我的文档"列表，`(session_id, created_at)` 加速按时间取消息。
3. **唯一约束即索引**。`(source_id, target_id, relation)` 的唯一约束天然提供边的去重和快速查找。
4. **向量用专用索引**。`document_chunk.embedding` 使用 IVFFlat 余弦索引，非 BTREE。

## 七、关键设计决策

### 7.1 JSON 字段：灵活性与规范性的取舍

`student_profile` 的 `knowledge_mastered` / `knowledge_weak` / `error_prone` 存的是 JSON 数组而非外键关联。原因：

- 这些字段主要在 **Agent prompt 中拼接为文本**（如"已掌握：量子态、波函数..."），从不做跨表 JOIN
- 画像是一个"文档"而非"关系"——一次读取整体，一次写入整体
- 如果用关联表，每次读画像要做 3 次 JOIN，写画像要删旧插新，复杂度远大于 `json.dumps(list)`

同理，`generation_batch.resource_types` 存 JSON 数组、`ResourceMeta.content_json` 存思维导图的树形结构，都是"值的容器"而非"关系的表达"。

> 代价：JSON 字段不能建外键约束，不能做内容级索引（当前也不需要）。如果未来需要"查询所有掌握某知识点的用户"，则需改为 JSONB + GIN。

### 7.2 画像版本化

`profile_history` 表实现了画像的"Git 式"版本管理。每次更新不是覆盖旧数据，而是：
1. 将当前 `student_profile` 序列化为 `snapshot` JSON
2. 插入 `profile_history`
3. 更新 `version += 1`

这允许 Agent 回溯学生画像的演变轨迹，识别学习进展。

### 7.3 知识点的多租户策略

`kg_node.user_id` 设为 **可空**，形成两层知识体系：
- `user_id IS NULL` → 系统预置知识点（如《人工智能导论》教材的标准章节结构），所有用户共享
- `user_id = :uid` → 用户自建知识点（如个人笔记中提炼的概念）

查询时用 `WHERE user_id = :uid OR user_id IS NULL` 一次取到公共 + 个人知识。

### 7.4 任务与结果分离

资源生成的核心模式是"先创建空的 ResourceMeta，再异步填充内容"：

```
用户请求 → 创建 ResourceMeta(content=NULL) + GenerationTask(pending)
         → Agent 后台生成
         → 写入 content + 更新 task 状态为 done
```

好处：
- 用户可以立即拿到 `resource_id`，前端可以轮询任务状态
- 生成失败时 ResourceMeta 仍在，可以重试而不丢失关联关系
- `resource_id` 在 generation_task 中是 UNIQUE，保证一资源一任务

### 7.5 聊天消息：一张静态表 vs 动态表

早期设计为每个 `chat_session` 动态创建一张消息表（`messages_table` 字段），后来改为所有消息存在一张 `chat_message` 表中。原因：
- 动态建表在 ORM 中几乎不可管理（SQLAlchemy 的声明式映射需要预先定义模型）
- 单表 + 索引 `(session_id, created_at)` 的查询效率完全够用
- 配合 DESC + LIMIT 的分页查询，单次只取最近 N 条，无需分区

## 九、性能要点

### 当前状态
- **连接池**：pool_size=10 + max_overflow=20，峰值 30 连接，pre_ping 开启（详见 `docs/DATABASE_CONNECTION_POOL.md`）
- **N+1 查询**：已全部修复（`loadRelations` 预加载 / IN 批量查询 / `insert_many`）
- **向量检索**：IVFFlat + probes=10，pgvector codec 直传向量
- **写入**：`add_all` 批量提交，Snowflake ID 预生成避免逐条 flush
- **查询**：所有高频路径有索引覆盖，聊天历史 DB 层分页，KG 节点查询加 LIMIT

### 后续优化方向

1. **向量索引升级**：数据量 > 10 万条时 IVFFlat → HNSW
2. **JSON 列**：需要内容查询时 JSON → JSONB + GIN
3. **KG 子图**：多跳遍历改用递归 CTE（当前 Python 端 BFS）
4. **列命名**：`submitted_at` → `created_at`，`recorded_at` → `created_at`
