### 2.2 `submit_quiz()` 线性扫描全部测验资源 ✅ 已修复

**文件**: `backend/main.py:977-1036`

**原代码**：每次提交答案时，先查 QuizItem 表（O(1)），如未找到则加载用户**全部** quiz 资源在 Python 层逐个 item 线性匹配。

```python
if not quiz_item:

    for res in resources:                          # 遍历全部 quiz 资源

            if expected_id == str(body.quiz_item_id):
                ...
```

**修复后（O(1) 主键查询）**：
```python
quiz_item = await select_one(db, QuizItem, filters={"id": body.quiz_item_id})
if not quiz_item:
    raise HTTPException(status_code=404, detail="Quiz item not found")
```

## 三、高优先级问题

### 3.1 ORM ForeignKey 定义与数据库实际约束不一致

**文件**: `backend/db/models.py` vs `migrations/versions/db2c961ff39d_uuid_to_snowflake.py`

| 表 | FK 列 | models.py 声明的 ondelete | 迁移中实际创建的 ondelete |
|----|-------|:-------------------------:|:-------------------------:|
| `chat_session.user_id` | `user.id` | CASCADE | CASCADE |
| `student_profile.user_id` | `user.id` | **无** | CASCADE |
| `resource_meta.user_id` | `user.id` | **无** | CASCADE |
| `learning_path.user_id` | `user.id` | **无** | CASCADE |
| `kg_node.user_id` | `user.id` | **无** | SET NULL |
| `profile_history.profile_id` | `student_profile.id` | **无** | CASCADE |
| `learning_record.resource_id` | `resource_meta.id` | **无** | SET NULL |
| 其余 6 个 FK | — | **无** | CASCADE / SET NULL |

后果：
- 阅读 `models.py` 无法了解真实的级联删除行为
- ORM 层 `session.delete(user)` **不会**级联删除关联记录
- 任何人通过 `Base.metadata` 反射得出的 schema 与真实数据库不一致

**修复方向**：给 `models.py` 中每一个 `ForeignKey(...)` 补上 `ondelete` 参数，使其与迁移脚本一致。

### 3.2 缺失关键索引

| 表 | 建议索引 | 原因 |
|----|---------|------|
| `generation_task` | `(status)` | 状态轮询是最频繁的查询 |
| `resource_meta` | `(created_at)` | 列表接口按时间倒序排列 |
| `chat_session` | `(user_id, last_used_at)` | 会话列表按最近使用排序 |
| `quiz_attempt` | `(kp_id)` | 按知识点查询答题记录 |
| `learning_path_item` | `(kp_id)` | 查询"哪些学习路径包含此知识点" |

`chat_session` 当前只有单列索引 `ix_chat_session_user_id`，`ORDER BY last_used_at DESC` 时无法利用索引避免 filesort。

### 3.3 `get_kg_graph()` 全量加载边表

**文件**: `backend/main.py:571-625`

```python
all_nodes = await db.execute(sa_select(KGNode).where(and_(*base_conditions)))
all_nodes = all_nodes.scalars().all()

for e in await db.execute(sa_select(KGEdge)):   # 无条件加载全部边
    e = e[0]
    # 然后在 Python 中做 BFS ...
```

知识图谱到上千节点/边时，每次请求将全部数据加载到 Python 再 BFS，内存和网络开销不可接受。

**修复方向**：用 PostgreSQL 递归 CTE 在数据库内完成遍历：
```sql
WITH RECURSIVE descendants AS (
    SELECT id FROM kg_node WHERE id = :root_id
    UNION
    SELECT n.id FROM kg_node n
    JOIN kg_edge e ON e.target_id = n.id AND e.relation IN ('IS_PART_OF', 'CONTAINS')
    JOIN descendants d ON e.source_id = d.id
)
SELECT * FROM kg_node WHERE id IN (SELECT id FROM descendants);
```

### 3.4 多数 API 接口无鉴权

**文件**: `backend/main.py`

```python
# 仅依赖 user_id 查询参数，无 JWT 校验
@router.get("/profile")
async def get_profile(user_id: int, ...):      # 任何人可传任意 user_id
@router.get("/resources")
async def list_resources(user_id: int, ...):   # 同上
@router.post("/quiz/submit")
async def submit_quiz(user_id: int, ...):      # 同上
```

大量接口接受裸 `user_id: int` 作为 Query 参数，没有任何认证。任何人可以通过修改 URL 参数访问/修改其他用户的数据。

**修复方向**：统一使用 `user_id: int = Depends(get_current_user_id)` 从 JWT 中提取用户身份。

### 3.5 `upsert_documents` 参数爆炸风险

**文件**: `backend/db/vector.py:152-199`

```python
for i, (chunk_id, doc_text, emb, meta) in enumerate(zip(ids, documents, embeddings, meta_list)):
    # 每行 13 个命名参数
    row_placeholders = ", ".join([f":id_{i}", f":chunk_id_{i}", ...])  # 13 params/row
    value_rows.append(f"({row_placeholders})")
```

当前 `index_batch_size=128`，生成 128×13=1664 个绑定参数，在 PostgreSQL 上限（65535）以内。但如果有人将 `index_batch_size` 调到 5000 以上，会直接突破上限导致 INSERT 失败。此外，生成极长的 SQL 字符串也有性能开销。

**修复方向**：在函数入口校验 `len(ids) * 13 < 60000`，或拆分为多个较小的 INSERT。

### 3.6 降级迁移（downgrade）缺少索引

**文件**: `migrations/versions/db2c961ff39d_uuid_to_snowflake.py:339-560`

`_create_tables_uuid()`（downgrade 调用）丢失了 `_create_tables_bigint()`（upgrade 调用）中创建的 9 个索引：
- `ix_chat_session_user_id`
- `ix_learning_path_user_id`
- `ix_generation_batch_user_id`
- `ix_learning_record_user_id/kp_id/user_kp`
- `ix_quiz_attempt_user_time`
- `ix_resource_meta_user_kp/user_type`

执行 downgrade 后数据库性能显著下降。

### 3.7 `merge_chat_updates()` JSON 列表竞态条件

**文件**: `backend/services/profile.py:242-259`

```python
existing_list = list(getattr(existing, list_key, None) or [])  # ① 读取
# ... 合并逻辑 ...
merged = list(existing_list)
merged.append(key)                                               # ② 修改
update_data[list_key] = merged                                  # ③ 写回
```

模式：读 → 改 → 写。两个并发的聊天消息同时更新 `knowledge_weak` 列表时，后提交的请求会静默覆盖先提交的修改。

**修复方向**：使用 PostgreSQL JSONB 原子操作（`jsonb_insert`）或在读取时加 `SELECT ... FOR UPDATE`。

### 3.8 `submit_quiz` N+1 查询

**文件**: `backend/main.py:1127-1138`

```python
if kp_key not in resource_cache:
    res_list = await db.execute(
        sa.select(ResourceMeta).where(ResourceMeta.kp_id == kp_key, ...)
    )
```

每个唯一的 `kp_id` 触发一次独立 DB 查询。N 个不同知识点 = N 次额外查询。

**修复方向**：提前收集所有 `kp_id`，一次 `WHERE kp_id = ANY(:ids)` 批量加载。

## 四、中优先级问题

### 4.1 CRUD 层双重提交

**文件**: `backend/db/crud.py` + `backend/db/database.py`

```python
# crud.py: insert() 内部默认 commit=True
await session.commit()

# database.py: get_session() 依赖注入在 yield 后再次 commit
await session.commit()
```

每个 CRUD 函数默认 `commit=True`，而 FastAPI 的 `Depends(get_session)` 也会在 handler 返回后 commit。结果是同一事务被提交两次（第二次是空操作），但多次 CRUD 调用之间各自独立提交，无法形成原子操作。

**修复方向**：CRUD 函数默认 `commit=False`，由 `get_session()` 统一在 handler 结束时提交。

### 4.2 `select()` 缺少 `.unique()` 去重

**文件**: `backend/db/crud.py:137-138`

```python
result = await session.execute(stmt)
return result.scalars().all()     # 应该是 .scalars().unique().all()
```

当使用 `selectinload` 加载一对多关系时（如 `LearningPath` 有多个 `LearningPathItem`），SQL JOIN 会产生笛卡尔积，同一个父对象在结果中出现多次。缺少 `.unique()` 导致调用方收到重复数据。

影响范围：`list_pathways()` 和 `get_pathway()`（`backend/services/pathway.py`）。

### 4.3 `datetime.utcnow` 已废弃（17 处）

**文件**: `backend/db/models.py`（17 处）、`backend/main.py`（1 处）

```python
default=datetime.utcnow    # Python 3.12+ 废弃，3.14 将移除
```

应统一替换为 `lambda: datetime.now(datetime.UTC)`。

### 4.4 重复的 DB 查询

| 位置 | 问题 |
|------|------|
| `graph.py:155` + `profile_agent.py:145` | 画像在同一次请求中被查询两次 |
| `planner_agent.py:115` + `recommend_agent.py:83` | 同一条管道中两个 Agent 查询几乎相同的 KGNode 数据 |
| `graph.py:155-158` | `get_profile()` 和 `load_chat_history()` 串行执行，可并行 |

### 4.5 `select_by_id` 未使用 `session.get()`

**文件**: `backend/db/crud.py:167-187`

```python
async def select_by_id(session, model, id, ...):
    return await select_one(session, model, filters={"id": id}, ...)
    # 构造 SELECT ... WHERE id = :id LIMIT 1，每次都查 DB
```

SQLAlchemy 的 `session.get(model, id)` 先查 identity map 缓存，命中则零查询。当前实现绕过了这个优化。

### 4.6 `get_batch_status()` 查询即写入

**文件**: `backend/services/resource.py:365-369`

```python
await update_by_id(db, GenerationBatch, batch_id, {
    "status": batch_status.value,
    "progress": avg_progress,
})
```

前端轮询批量生成状态的 GET 请求，每次都会触发一次 UPDATE。progress 和 status 是从子任务计算出来的，不应持久化存储。

### 4.7 `cleanup_uploaded_docs()` 加载全部 ResourceMeta

**文件**: `backend/services/cleanup.py:95`

```python
resources = await select(db, ResourceMeta, filters={"resource_type": "doc"})
# 无 limit，加载全部 doc 类型资源的完整行（含 content Text 列）
```

应只 SELECT 必要的列（`id`, `content` 的前若干字符），或加 LIMIT。

### 4.8 会话导入任务状态存内存

**文件**: `backend/main.py:104`

```python
_doc_import_tasks: dict[str, dict] = {}
```

服务重启后所有文档导入任务的状态丢失。应考虑持久化到 `GenerationTask` 表或 Redis。

### 4.9 `command_timeout=60` 对批量操作可能不足

**文件**: `configs/config.yaml:20`

KG 构建时 `db.add_all(数千个节点) + commit()` 可能在单条 INSERT 上超时。建议对已知的大批量操作使用独立的 longer timeout session。

### 4.10 连接池峰值 30 可能不足

```yaml
pool_size: 10
max_overflow: 20    # 峰值 = 30
```

并行场景：5 个 API 请求 + 5 个批量生成子任务 + 1 个 KG 构建 + 向量检索连接 = 可能超出 30。建议监控 `pg_stat_activity` 确认实际用量后调优。

### 4.11 `_build_where_clause` 列名未校验

**文件**: `backend/db/vector.py:233`

```python
parts.append(f"{key} = :{pname}")   # key 来自用户传入的 where dict
```

虽调用方目前只传 `user_id` 等已知 key，但没有白名单校验，存在 SQL 注入风险。

### 4.12 向量写入与资源记录的事务割裂

**文件**: `backend/services/document.py:77 + 85-94`

```python
indexed_count = await rag_indexer.index_chunks(chunks, ...)   # 向量写入（raw engine）
resource = await insert(db, ResourceMeta, data={...})          # ORM 写入（session）
```

两个操作使用不同的连接/事务。如果资源记录写入失败，向量数据已成孤儿。
