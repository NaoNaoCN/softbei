> 分析日期：2026-05-20 | PostgreSQL 17.10 | pgvector + BGE-M3 (1024 dim)

## 二、两种索引原理对比

### IVFFlat (Inverted File Flat)

```
[全文向量] → K-Means 聚类 → lists 个簇
查询时：选 probes 个最近簇 → 簇内暴力搜索 → 排序返回
```

- 本质是 **近似近邻搜索 (ANN)**，通过只搜索部分簇来加速
- `lists` 越大，每个簇越小，搜索越快，但召回率越低
- `probes` 越大，搜索的簇越多，召回率越高，但速度越慢

### HNSW (Hierarchical Navigable Small World)

```
[全文向量] → 构建多层 NSW 图 → 每层有长距离边（跳数少）和短距离边（精度高）
查询时：从顶层开始 → 贪心下降 → 在底层精排 → 返回
```

- 本质是 **基于图的 ANN**，利用图的连通性快速导航
- 构建时建立多层图结构，查询时利用层级跳转快速逼近目标
- `m` 控制每层每个节点的最大连接数（越大越精确，越占内存）
- `ef_construction` / `ef_search` 控制构建/搜索时的候选集大小

## 三、性能对比

### 3.1 查询性能

| 维度 | IVFFlat | HNSW |
|------|---------|------|
| 时间复杂度 | O(lists × probes) + 簇内暴力 | O(log N × m) |
| 典型 QPS (N=10万) | ~200-500 | ~1000-3000 |
| 延迟 (P50, N=10万) | 5-20 ms | 1-5 ms |
| 延迟 (P99, N=10万) | 30-80 ms（簇不均衡） | 3-10 ms（稳定） |
| 延迟受数据量影响 | **明显**（簇变大后暴力搜索变慢） | **轻微**（对数增长） |

**结论：HNSW 查询快 3-10 倍，且延迟更稳定。**

### 3.2 召回率 (Recall)

| 参数档位 | IVFFlat | HNSW |
|---------|---------|------|
| 速度优先 | 70-85% (probes=5) | 90-95% (ef_search=40) |
| 均衡 | 85-95% (probes=10) | **95-99%** (ef_search=64) |
| 精度优先 | 95-98% (probes=20, 但速度骤降) | 99%+ (ef_search=128) |

**结论：HNSW 在同等或更快的速度下召回率更高。**

### 3.3 构建/维护成本

| 维度 | IVFFlat | HNSW |
|------|---------|------|
| 索引构建时间 (N=10万) | ~30 秒 | ~5-15 分钟 |
| 增量插入 | 快（直接加入簇） | **慢**（需更新图结构的多层边） |
| 重建需求 | 数据翻倍后建议重建 | **必须**定期重建以维持精度 |
| 构建时内存 | 低（只需存储簇中心） | **高**（需在内存中构建完整图） |
| `maintenance_work_mem` 要求 | 低 (64-256 MB) | **高** (建议 >= 1 GB) |

**结论：IVFFlat 构建快、增量插入友好；HNSW 构建慢、增量插入代价高。**

### 3.4 存储开销

| 维度 | IVFFlat | HNSW |
|------|---------|------|
| 索引大小 (N=10万, 1024维) | ~50-100 MB | ~200-500 MB |
| 索引大小 (N=100万, 1024维) | ~500 MB-1 GB | ~2-5 GB |
| 增长方式 | 线性 | 线性（系数更大） |

**结论：HNSW 内存/磁盘占用约为 IVFFlat 的 3-5 倍。**

## 四、项目适配性分析

### 4.1 对本项目有利的因素

1. **查询优先于写入**：本项目是学习资源系统，文档导入是低频批量操作（启动时 + 管理上传），而检索是高频操作（每次对话/生成都触发 RAG）。HNSW 的查询优化恰好匹配这个模式。

2. **PostgreSQL 17.10**：pgvector 对 PG17 的 HNSW 支持已成熟，无需额外适配。

3. **BGE-M3 的 1024 维向量**：高维向量在 IVFFlat 簇内暴力搜索时计算量大，HNSW 的图导航对高维向量优势更明显。

4. **已有 probes 配置**：如果这次优化中 IVFFlat 的 `probes=10` 被证实召回率不足，切换到 HNSW 可以直接解决。

### 4.2 对本项目不利的因素

1. **文档导入变慢**：`upsert_documents` 批量写入后，HNSW 需要更新图结构，导入时间显著增加。目前用 `ON CONFLICT ... DO UPDATE` 的 upsert 模式对 HNSW 尤其不友好（每次 update 都触发图更新）。

2. **内存压力**：当前服务器内存未知，但 HNSW 索引构建需要 `maintenance_work_mem >= 1GB`，运行时也需要将热数据保持在 shared_buffers 中。

3. **索引损坏风险**：HNSW 图结构比 IVFFlat 更复杂，非正常关机后需要 `REINDEX` 的概率更高。

4. **增量学习场景**：如果未来支持用户持续上传文档，IVFFlat 的增量插入优势会更明显。

## 六、切换建议

### 推荐策略：**暂不切换，但预留切换路径**

**理由：**

1. 当前 IVFFlat + probes=10 对于万级数据量已经足够，BGE-M3 的 cosine 相似度在这个参数下召回率通常在 90%+。

2. 本次优化已添加 `probes=10` 配置，解决了之前 probes 未设置（默认为 1）导致的召回率问题。先观察 probes=10 下的检索效果。

3. 项目的向量数据量尚在 IVFFlat 的优势区间（< 10 万条）。在 10 万 ~ 50 万之间两者持平，超过 50 万 HNSW 才有明显优势。

### 切换时机

| 触发条件 | 说明 |
|----------|------|
| `document_chunk` > 10 万行 | IVFFlat 开始吃力 |
| 用户反馈 RAG 结果不准 | 当前 probes=10 召回不足 |
| 检索延迟 P99 > 50ms | 影响用户体验 |
| 有充足的低峰维护窗口 | HNSW 构建需要时间 |

### 如果决定切换，迁移步骤

```sql
-- 1. 低峰期执行，预计耗时 5-15 分钟（取决于数据量）
-- 2. 先调高构建内存
SET maintenance_work_mem = '2GB';

-- 3. 删除旧索引，创建新索引（在同一事务中完成，无需重建表）
BEGIN;
DROP INDEX IF EXISTS ix_document_chunk_embedding_ivfflat;
CREATE INDEX ix_document_chunk_embedding_hnsw
ON document_chunk
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 200);
COMMIT;

-- 4. 查询前设置 ef_search（类似 IVFFlat 的 probes）
-- 在 vector.py 中: SET LOCAL hnsw.ef_search = 64;
```

### 代码侧需要的改动

如果切换，`vector.py` 需要修改：

```python
# 替换 probes 设置为 ef_search
# IVFFlat:
await conn.execute(text("SET LOCAL ivfflat.probes = 10"))

# HNSW:
await conn.execute(text("SET LOCAL hnsw.ef_search = 64"))
```

其余查询逻辑（cosine distance `<=>` 运算符、SELECT 语句）不变，pgvector 对两种索引使用相同的查询接口。
