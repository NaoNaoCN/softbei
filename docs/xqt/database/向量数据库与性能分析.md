# 向量数据库与性能分析

## 向量数据库

**PostgreSQL + pgvector 扩展**，与项目业务数据库共用同一个 PostgreSQL 实例，不引入独立向量数据库。

| 项目 | 选型 |
|------|------|
| 数据库本体 | PostgreSQL（项目唯一数据库） |
| 向量扩展 | pgvector |
| 索引算法 | **HNSW**（Hierarchical Navigable Small World） |
| 距离度量 | Cosine distance（`<=>` 操作符） |
| Embedding 模型 | DashScope `text-embedding-v4`，维度 **1024** |
| Embedding 并发 | 8（`config.yaml` 中 `embedding.concurrency` 配置） |

### HNSW 索引参数

```sql
CREATE INDEX IF NOT EXISTS ix_document_chunk_embedding_hnsw
ON document_chunk
USING hnsw (embedding vector_cosine_ops)
WITH (m = 16, ef_construction = 200);
```

| 参数 | 值 | 说明 |
|------|-----|------|
| `m` | 16 | 每节点最大邻居数，精度/内存/速度的平衡点 |
| `ef_construction` | 200 | 构建时搜索宽度，控制索引质量 |
| `ef_search` | 100 | 检索时搜索宽度，通过 `SET LOCAL hnsw.ef_search = 100` 在每次查询前设定 |

`ef_search=100` 是高精度设置（40=快速，100=高精度，200=极高精度），项目优先保障召回质量。

### 为什么选 pgvector

1. **统一技术栈** — 项目已经在用 PostgreSQL，pgvector 作为扩展零额外运维成本
2. **事务一致性** — 向量索引与文档元数据在同一事务中更新，不会出现不一致
3. **无网络开销** — 向量计算在数据库内完成，省去 Elasticsearch/Milvus 等独立服务的网络往返
4. **HNSW 支持增量写入** — 插入即索引，不需要 REINDEX（对比 IVFFlat 的关键优势）

## 数据量级

当前知识库约 **29,365 个 document chunk**（2026年5月 goldeneval 基线数据）。

每个 chunk 的存储开销：
- 向量：1024 维 × 4 字节(float32) = **4 KB**
- 文本 + 元数据：约 **2-5 KB**（chunk_size=500 字符）
- 索引：HNSW 图结构额外约 **1-2 KB** / chunk

**总存储估算**：约 200-300 MB（含索引），属于中小规模，完全在单机 PostgreSQL 的舒适区内。

### 文档切分配置

| 配置项 | 值 | 说明 |
|--------|-----|------|
| `chunk_size` | 500 字符 | 文档切分块大小 |
| 父子切割 | 启用 | 子块用于精确检索，父块提供完整上下文 |
| `child_chunk_size` | null（跟随 chunk_size） | 子块大小 |
| `split_sentence_lookback_ratio` | 0.2 | 句边界搜索回看比例 |

## 性能

### 各环节典型耗时

| 环节 | 典型耗时 | 说明 |
|------|---------|------|
| Embedding API 调用 | ~120ms | DashScope 远端 API，并发=8 |
| HNSW 向量检索 | <50ms | pgvector 库内计算，ef_search=100 |
| 关键词检索 | <30ms | jieba 分词 + PostgreSQL `tsvector`/`ILIKE` |
| 混合检索（向量+关键词并行） | ~150ms | 两路并行后 RRF 融合 |
| RAG 总耗时 | 200-500ms | 含 query rewrite + 检索 + format_context |
| 生成（LLM） | 2-5s | Kimi K2.6，取决于生成长度 |

### 连接池

```yaml
db:
  pool_size: 10       # 常驻连接数（懒加载）
  max_overflow: 20    # pool_size 全部占用时可额外创建数
  # 峰值连接数 = 10 + 20 = 30
  pool_pre_ping: true  # 连接前 ping 检测有效性
  command_timeout: 60  # SQL 命令超时（秒）
```

### 检索配置

```yaml
rag:
  n_results: 5               # 最终返回条数
  score_threshold: 0.5        # 余弦相似度最低阈值
  context_max_tokens: 3000    # 注入上下文的 token 预算上限
  prefetch_multiplier: 3      # 预取倍数（n_results × 3 = 15 候选供精排）
  prefetch_min: 15            # 预取候选数下限
  keyword_score_threshold: 0.0  # 关键词检索最低分数阈值
```

检索流程：先预取 `n_results × prefetch_multiplier = 15` 个候选，经 score_threshold 过滤和多样性重排后，取前 `n_results = 5` 个注入上下文。

### 健康检查告警阈值

部署了 L1 健康检查（`backend/evaluation/health_check.py`），持续 100 条记录的滑动窗口：

| 指标 | 告警阈值 |
|------|---------|
| 空结果率（empty_result_rate） | > 30% |
| 中位分数（score_p50） | < 0.3 |
| 检索 P95 延迟 | > 5000ms |
| 生成 P95 延迟 | > 30000ms |

健康检查不调用 LLM，纯统计计算，单次 <5ms。

## 遇到过的性能瓶颈

### 1. IVFFlat 索引与增量写入冲突（已解决）

**问题**：项目最初使用 IVFFlat 索引。IVFFlat 基于 K-means 聚类，聚类中心在索引创建时计算——后续增量插入的向量不会被新的聚类中心覆盖，必须定期执行 `REINDEX` 才能纳入新数据。而项目的写入模式正是"按文档增量更新"，每次新文档入库后召回率逐步下降。

**表现**：知识库从 5000 chunk 增长到 20000+ chunk 的过程中，新增文档的检索命中率明显低于旧文档，因为索引未更新。

**解决方案**：迁移到 HNSW（`migrations/versions/6f9a2b3c4d5e_switch_ivfflat_to_hnsw.py`）。

HNSW 是基于图的数据结构，插入时只需更新局部图连接，无需全局重建。核心区别：

| 特性 | IVFFlat | HNSW |
|------|---------|------|
| 索引构建 | 需要全量数据计算聚类中心 | 逐条插入构建图 |
| 增量写入 | 新数据不在索引中，需 REINDEX | 插入即索引 |
| 维护成本 | 需定期 REINDEX | 零维护 |
| 精度 | 近似搜索，依赖 lists 参数 | 高精度，可通过 ef_search 调节 |
| 内存 | 较低 | 略高（图结构开销） |

### 2. Embedding API 是吞吐天花板

`text-embedding-v4` 是 DashScope 远端 API，单次调用约 120ms。文档入库时批量 embedding 是吞吐瓶颈：

- 大量文档首次入库时需要数万次 API 调用
- 受 API 限流约束，不能无限提高并发
- 当前使用 `asyncio.Semaphore(8)` 控制并发

**应对**：批量入库采用异步流水线，入库操作与业务请求互不阻塞。对于日常增量更新（单次几到几十个文档），延迟完全可接受。

### 3. 关键词检索作为语义检索的互补优化

纯向量检索在专业术语精确匹配场景存在局限——通用 embedding 模型对领域术语（如 "softmax"、"LSTM"、"反向传播"）的语义理解有限。

**应对**：引入 jieba 分词 + PostgreSQL `tsvector`/`ILIKE` 全文检索作为并行路径，专门弥补术语精确匹配。两路结果通过 RRF（Reciprocal Rank Fusion）融合——RRF 按排名而非原始分数合并，避免向量分数和关键词分数不可比的问题。

### 4. HNSW 参数调优

`ef_search` 是检索时精度/速度的直接调节参数。增大 ef_search 扫描更多候选节点可提高召回但增加延迟：

| ef_search | 检索延迟 | 召回率 | 适用场景 |
|-----------|---------|--------|---------|
| 40 | 快速 | 中等 | 实时对话，可容忍降级 |
| 100（当前） | 平衡 | 高 | 当前默认，评估验证后选择 |
| 200 | 较慢 | 极高 | 离线评估、golden dataset 测试 |

当前选择 100 是在多轮 golden eval 验证后确定的平衡值。

## 扩容展望

当前 ~29K chunk / 1024维 的规模对 pgvector + HNSW 来说属于轻量级。pgvector 在百万级 chunk 仍有良好表现，短期无需引入独立向量数据库。如果未来数据量增长到十万级以上，可能的优化方向：

1. **分区表** — 按 `collection_name` 或知识领域分区
2. **ef_search 动态调低** — 对非关键查询降低 ef_search 以节省计算
3. **embedding 模型本地化** — 将 BGE-M3 等开源模型部署到本地，消除 API 网络延迟
4. **只读副本** — 检索走只读副本，写入走主库，读写分离
