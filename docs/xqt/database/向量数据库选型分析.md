# 向量数据库选型分析

> 分析日期：2026-05-21 | 当前方案：PostgreSQL + pgvector (IVFFlat)

---

## 1. 背景：为什么 RAG 系统需要向量数据库

在 RAG（检索增强生成）架构中，向量数据库承担**语义检索**的核心职责：将文档切分为文本块，通过 Embedding 模型转化为高维向量，存入数据库；用户提问时同样转化为向量，通过相似度计算找到最相关的文本块，注入 LLM 的上下文窗口。

选对向量数据库直接影响三个关键指标：

| 指标 | 含义 | 影响 |
|------|------|------|
| **检索延迟** | 从提问到返回相关文本块的时间 | 用户感知的响应速度 |
| **召回率** | 找到的相关文档占全部相关文档的比例 | 生成内容的事实准确性 |
| **可扩展性** | 随数据量增长性能是否线性可控 | 系统的生命周期 |

## 2. 市场主流向量数据库全景

截至 2026 年，向量数据库市场已分化为四个清晰的梯队：

### 2.1 第一梯队：专用分布式向量数据库

这类产品为向量检索而生，在性能和规模上处于领先地位。

#### Milvus

| 维度 | 说明 |
|------|------|
| **定位** | 开源分布式向量数据库，CNCF 毕业项目 |
| **语言** | Go + C++，核心引擎用 SIMD 指令集加速 |
| **GitHub** | 43k+ Stars |
| **索引类型** | HNSW / IVF_FLAT / IVF_PQ / DiskANN / GPU IVF |
| **最大规模** | 十亿~千亿级向量 |
| **部署方式** | 自托管（K8s/Docker Compose）或 Zilliz Cloud 全托管 |
| **亮点** | GPU 加速、存算分离、水平扩展、多模态支持 |

Milvus 是这个领域的事实标准。它的架构设计面向互联网级规模——推荐系统、以图搜图、金融风控等场景下动辄数十亿向量。但代价是运维复杂度：依赖 etcd、MinIO、Kafka/Pulsar 等多个中间件，最小化部署也需要 4-6 个容器。

**适用场景**：亿级以上向量、需要 GPU 加速、有专业运维团队。

#### Qdrant

| 维度 | 说明 |
|------|------|
| **定位** | Rust 编写的高性能向量数据库 |
| **语言** | Rust |
| **GitHub** | 29k+ Stars |
| **索引类型** | HNSW |
| **最大规模** | 亿级向量 |
| **部署方式** | 单二进制文件 / Docker / Qdrant Cloud |
| **亮点** | 极强的 Payload 过滤、极低延迟（P99 < 20ms）、原生全文搜索 |

Qdrant 是 2025-2026 年增长最快的开源向量数据库。Rust 带来的内存效率和 CPU 性能使其在性价比上极具竞争力。它的 Payload 过滤机制允许在向量检索的同时做复杂的标量条件筛选，且性能衰减极小。单二进制部署也大幅降低了运维门槛。

**适用场景**：百万~亿级向量、对延迟敏感的生产级 RAG、需要复杂过滤条件。

#### Weaviate

| 维度 | 说明 |
|------|------|
| **定位** | 开源向量检索引擎，内置向量化模块 |
| **语言** | Go |
| **GitHub** | 15k+ Stars |
| **索引类型** | HNSW |
| **最大规模** | 千万~亿级向量 |
| **部署方式** | Docker Compose / K8s / Weaviate Cloud |
| **亮点** | 原生 BM25 + 向量混合搜索、内置 text2vec 模块、GraphQL API |

Weaviate 的最大特色是**混合搜索**——将稀疏的 BM25 关键词匹配与稠密的向量语义搜索结合，避免了纯向量搜索在某些场景下"找不到精确术语"的尴尬。它的内置向量化模块可以直接存文本而无需外部 Embedding 服务。但 Go 运行时 + 内嵌 HNSW 图使其内存占用较高。

**适用场景**：企业知识库、需要混合搜索（关键词 + 语义）、智能问答。

### 2.2 第二梯队：全托管 SaaS

#### Pinecone

| 维度 | 说明 |
|------|------|
| **定位** | 商业全托管向量数据库 |
| **语言** | 闭源 |
| **开源** | 否 |
| **索引类型** | 自研（未公开） |
| **部署方式** | 仅云托管（AWS/GCP/Azure） |
| **亮点** | Serverless 自动伸缩、几分钟接入、与 LangChain/LlamaIndex 深度集成 |

Pinecone 的核心价值是"零运维"——不需要配置索引参数、不需要管理服务器、甚至不需要关心向量维度以外的任何东西。Serverless 架构按用量计费。代价是：闭源（数据出境）、成本随规模非线性增长（中大规模可达数千美元/月）、厂商锁定。

**适用场景**：快速原型验证、无 DevOps 团队的创业公司、合规要求宽松的产品。

### 2.3 第三梯队：数据库扩展

#### pgvector (PostgreSQL 扩展)

| 维度 | 说明 |
|------|------|
| **定位** | PostgreSQL 的原生向量检索扩展 |
| **语言** | C |
| **开源** | 完全开源（PostgreSQL License） |
| **索引类型** | IVFFlat / HNSW |
| **距离度量** | L2 / 余弦 / 内积 |
| **最大规模** | 千万级（视硬件而定） |
| **部署方式** | `CREATE EXTENSION vector` — 无需新服务 |

pgvector 的思路与 Milvus/Qdrant 完全不同：它不创造一个新的数据库，而是在 PostgreSQL 内部嵌入了向量类型和索引。这意味着向量数据和业务数据（用户、订单、课程）天然在同一个数据库中，可以用 SQL 直接 JOIN。

**适用场景**：已有 PostgreSQL 的技术栈、千万级以下向量、需要向量检索与业务数据联表。

#### 其他数据库扩展

| 产品 | 说明 |
|------|------|
| **Elasticsearch + kNN** | ES 8.0+ 原生支持向量检索，适合已有 ELK 栈的团队 |
| **Redis + RediSearch** | 内存级延迟，适合实时性要求极高的场景 |
| **MongoDB Atlas Vector** | NoSQL + 向量，适合 MongoDB 生态 |
| **ClickHouse + ANN** | OLAP + 向量，适合分析场景 |

### 2.4 第四梯队：轻量级嵌入式

#### ChromaDB

| 维度 | 说明 |
|------|------|
| **定位** | 开发者友好的嵌入式向量数据库 |
| **语言** | Python |
| **GitHub** | 26k+ Stars |
| **索引类型** | HNSW（通过 hnswlib） |
| **部署方式** | `pip install chromadb`，内存/持久化两种模式 |
| **亮点** | 极简 API、Python/JS SDK、内置 Embedding 集成 |

ChromaDB 是为**开发体验**设计的。安装即用、API 直觉友好、自带 Embedding 函数。但它的设计目标不是生产环境——百万级以上性能急剧下降、无内置权限控制、无分布式能力。

**适用场景**：本地开发、PoC 原型、教学、个人项目。

## 3. 性能基准对比

以下为业界公开的基准测试数据（100 万条 × 768 维向量，HNSW 索引，recall@10 > 95%）：

| 数据库 | QPS | P99 延迟 | 内存占用 | 索引构建时间 |
|--------|-----|----------|----------|-------------|
| **Qdrant** | 12,000 | ~18ms | 1.2 GB | 45s |
| **Milvus** | 10,000 | ~50ms | 1.8 GB | 40s |
| **Weaviate** | 8,500 | ~35ms | 2.1 GB | 60s |
| **Pinecone** | N/A（SaaS） | ~50-100ms | N/A | N/A |
| **pgvector (HNSW)** | 3,000+ | ~30-50ms | 1.5 GB | 5-15 min |
| **pgvector (IVFFlat)** | ~1,200 | ~200ms | 1.5 GB | 120s |
| **ChromaDB** | ~800 | ~150ms | 1.3 GB | 90s |

> 注：pgvector IVFFlat 的 P99 延迟约 200ms 是基于默认参数。本项目已将 `probes` 调至 10，实测小规模下延迟约 5-20ms。

## 4. 决策框架

向量数据库选型不是寻找"最好"的产品，而是找到与当前约束最匹配的产品。推荐按照以下顺序决策：

```
数据规模 → 运维能力 → 预算 → 搜索需求 → 技术栈
```

### 4.1 按规模

| 向量数量 | 推荐方案 |
|----------|----------|
| < 10 万 | ChromaDB（开发/原型）或 pgvector |
| 10 万 ~ 100 万 | pgvector（已有 PG）或 Qdrant |
| 100 万 ~ 1000 万 | Qdrant 或 Weaviate |
| 1000 万 ~ 5 亿 | Qdrant 或 Milvus |
| > 5 亿 | Milvus 分布式集群 |

### 4.2 按运维能力

| 团队情况 | 推荐方案 |
|----------|----------|
| 无专业运维 | Pinecone（全托管，最省心） |
| 有基本运维 | Qdrant 自托管 / Qdrant Cloud |
| 有专业运维 | Milvus 自托管 |
| 运维就是 DBA | pgvector（在已有 PG 上零增量运维） |

### 4.3 按搜索需求

| 搜索类型 | 推荐方案 |
|----------|----------|
| 纯语义搜索 | Qdrant / Milvus |
| 语义 + 关键词混合 | Weaviate / Qdrant |
| 语义 + SQL 联表 | **pgvector**（唯一能做高效 SQL JOIN 的） |

## 5. 本项目技术选型

### 5.1 当前方案

```
PostgreSQL 17 + pgvector 0.8.1
├── 索引: IVFFlat (lists=100, probes=10)
├── 距离: 余弦距离 (vector_cosine_ops)
├── 维度: 1024 (DashScope text-embedding-v4)
└── 混合搜索: 向量相似度过滤 + 关键词重排序
```

### 5.2 演进历程

本项目的向量存储经历了三次迭代，每一次都解决了前一代的核心痛点：

```
第一阶段: JSON + numpy（项目早期）
  向量以 JSON 文本数组存于 PostgreSQL，检索时拉取全量候选到 Python，用 numpy 做矩阵乘法
  痛点: 网络传输 30+ MB/次，LIMIT 5000 可能截断相关结果，O(N) 复杂度不可扩展
           ↓
第二阶段: pgvector + IVFFlat（当前方案）
  pgvector 原生 vector(1024) 类型 + IVFFlat 索引，距离计算下沉到数据库内
  改善: 存储减少 40%，网络传输减少 10,000×，O(√N) 复杂度，SQL 原生过滤
           ↓
第三阶段: pgvector + HNSW（待评估）
  当数据量超过 10 万条时，可将索引从 IVFFlat 升级为 HNSW
  收益: 查询快 3-10 倍，召回率更稳定（95-99%），P99 延迟更低
```

### 5.3 为什么选择 pgvector

**这是本项目最关键的技术决策。** 以下逐一说明 pgvector 与各竞品的对比判断。

#### vs. ChromaDB — 从原型到生产的必然跨越

ChromaDB 曾在本项目的早期 README 中被列为向量数据库方案，但代码层面从未正式实现。选择放弃 ChromaDB 的原因很明确：

- ChromaDB 的持久化可靠性远不如 PostgreSQL（非正常关机后易损坏）
- 无内置多用户隔离机制（需手动管理 Collection）
- 百万级以上性能急剧退化
- 在生产环境中，它意味着需要维护两套存储系统（PG + ChromaDB），运维负担翻倍

ChromaDB 是一个优秀的原型工具，但它不是为生产系统设计的。

#### vs. Milvus — 规模不需要

Milvus 是性能最强的向量数据库，但对本项目而言属于"杀鸡用牛刀"：

- 教育场景的知识库最多几千份文档，向量总量在万~十万级，远未触及 pgvector 的性能上限
- Milvus 的部署需要 etcd + MinIO + Kafka，运维复杂度远超项目规模
- 引入 Milvus 意味着要维护 PostgreSQL + Milvus 两个有状态服务

Milvus 适合推荐系统、图像搜索等十亿级场景，而非万级文档的 RAG 系统。

#### vs. Qdrant — 增量收益不抵运维成本

Qdrant 的性能确实优于 pgvector（查询快 5-10 倍），但：

- 在当前数据量下，pgvector 的检索延迟约 5-15ms，完全在可接受范围内
- Qdrant 需要用 Rust 编写的新服务，增加部署和监控成本
- Qdrant 的 Payload 过滤在本项目中不构成刚需（我们的过滤条件很简单：user_id + collection_name）

如果未来数据量增长到百万级以上，Qdrant 将成为自然的升级目标。

#### vs. Pinecone — 不适合中国教育场景

- Pinecone 服务器全在海外，国内访问延迟不可控
- 教育数据有合规要求，不适合出境
- 成本随规模增长快（中大规模可达数千美元/月）
- 闭源，无法定制

#### vs. Weaviate — 混合搜索可通过应用层实现

Weaviate 的 BM25 + 向量混合搜索确实优秀，但在本项目中可以等效实现：

- pgvector 提供向量相似度（余弦距离 `<=>`）
- 应用层在 `retriever.py` 中实现关键词重叠重排序（`_rerank_by_keyword_overlap`，最高加 0.15 分）
- 对于中文教育内容，这种轻量级混合已经足够

引入 Weaviate 换取的混合搜索质量提升，抵不上增加一个新有状态服务的运维代价。

#### pgvector 的独特优势

除了上述对比，pgvector 还有一些**其他方案不可替代**的优势：

1. **向量与业务数据自然 JOIN**

```sql
-- 检索某个知识点的文档块，并关联该文档的元信息
SELECT dc.text, dc.embedding <=> :query AS distance,
       ri.filename, ri.uploaded_at
FROM document_chunk dc
JOIN resource_metadata ri ON dc.doc_id = ri.doc_id
WHERE dc.collection_name = 'knowledge_base'
ORDER BY dc.embedding <=> :query
LIMIT 5;
```

Milvus、Qdrant、ChromaDB 要想实现这种跨系统联表查询，需要在应用层多次取数据再拼接。

2. **事务一致性**

向量写入（`upsert_documents`）与业务数据写入在同一 PostgreSQL 事务中。删除文档时，向量和业务数据同步删除，不存在"一个库删了另一个库没删"的数据不一致风险。

3. **运维零增量**

- 备份：`pg_dump` / `pg_restore` 直接支持，无需额外步骤
- 监控：复用 PostgreSQL 的 Prometheus exporter
- 迁移：Alembic 管理 Schema，`CREATE EXTENSION vector` 一条命令完成
- 高可用：复用 PostgreSQL 的主从复制 / Patroni

4. **团队技能匹配**

团队已经维护 PostgreSQL，DBA 直接能管 pgvector。引入 Milvus 或 Qdrant 需要学习新的查询语言、索引策略、故障排查流程。

5. **渐进式升级路径**

pgvector 支持从 IVFFlat 原地升级到 HNSW，只需重建索引，无需迁移数据：

```sql
DROP INDEX ix_document_chunk_embedding_ivfflat;
CREATE INDEX ix_document_chunk_embedding_hnsw
  ON document_chunk USING hnsw (embedding vector_cosine_ops)
  WITH (m = 16, ef_construction = 200);
```

### 5.4 选型总结

```
为什么选择 pgvector：

1. 已有 PostgreSQL → 零增量运维，一个 DBA 即可覆盖
2. 数据量 < 10 万 → 性能充足，IVFFlat 索引下有 5-15ms 延迟
3. 教育场景 → 需要 SQL JOIN 关联文档元数据、用户画像、学习记录
4. 事务要求 → 向量写入与业务数据需保持一致性
5. 团队能力 → 不需要学习新的数据库运维体系

什么时候需要考虑迁移：

- vector 数据超过 50 万条 → 考虑 HNSW 索引（仍在 pgvector 内）
- vector 数据超过 500 万条 → 考虑 Qdrant（单二进制，运维简单）
- 需要 GPU 加速 / 十亿级以上 → 考虑 Milvus（但教育场景几乎不可能）
```
