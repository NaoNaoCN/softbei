# 数据库连接池文档

## 概述

项目使用 **SQLAlchemy 2.0 异步引擎** + **asyncpg 驱动** 连接 PostgreSQL 数据库，通过模块级单例连接池管理数据库连接的生命周期。连接池在 FastAPI 应用启动时初始化，在关闭时释放，所有 HTTP 请求通过 FastAPI 依赖注入获取请求作用域的数据库会话。

## 配置参数

### 配置文件 (`configs/config.yaml`)

```yaml
database:
  url: "${DATABASE_URL}"          # 从环境变量读取，格式: postgresql+asyncpg://user:pass@host:5432/dbname
  echo: false                     # 是否打印 SQL 日志
  pool_size: 10                   # 连接池常驻连接数
  max_overflow: 20                # 超出 pool_size 后最多额外创建的连接数
  pool_timeout: 30                # 等待可用连接的超时秒数
  pool_recycle: 3600              # 连接最大存活秒数（到达后回收）
  command_timeout: 60             # 单条 SQL 语句执行超时秒数
```

### 配置数据类 (`backend/config.py:72-81`)

```python
@dataclass
class DatabaseConfig:
    url: str = ""
    echo: bool = False
    pool_size: int = 10
    max_overflow: int = 20
    pool_timeout: int = 30
    pool_recycle: int = 3600
    command_timeout: int = 60
```

配置通过 `config.yaml` 加载，支持 `${ENV_VAR}` 环境变量替换。`DatabaseConfig` 实例挂载在全局单例 `config.database` 上。

### 参数详解

| 参数 | 默认值 | 说明 |
|------|--------|------|
| `pool_size` | 10 | 连接池中保持的最小空闲连接数。这些连接在引擎启动时不会立即创建，而是按需懒加载，但一旦创建就会保持存活（除非被回收）。对于中等并发量的 Web 应用，10 个常驻连接通常足够。 |
| `max_overflow` | 20 | 当 `pool_size` 个连接全部被占用时，允许额外创建的最大连接数。峰值连接总数 = `pool_size + max_overflow` = **30**。超出后新的连接请求将在 `pool_timeout` 秒内阻塞等待。 |
| `pool_timeout` | 30 | 连接池耗尽时（已有 30 个连接在使用），新的连接请求最多等待 30 秒。超时后抛出 `asyncio.TimeoutError`。 |
| `pool_recycle` | 3600 | 单个连接的最大存活时间（秒）。超过此时间的连接会被自动关闭并替换，防止 PostgreSQL 服务端主动断开长时间闲置的连接（通常是 idle-in-transaction 超时）。设置为 3600 秒（1 小时）。 |
| `pool_pre_ping` | `True` | 每次从连接池取出连接时，先执行 `SELECT 1` 探测连接是否仍然有效。如果连接已被服务端关闭（如 PostgreSQL 重启或达到 `idle_in_transaction_session_timeout`），则自动丢弃并创建新连接。**强烈建议保持开启**，代价是每次获取连接多一次轻量级往返。 |
| `command_timeout` | 60 | 通过 asyncpg 传递给 PostgreSQL 的 `statement_timeout`，单条 SQL 超过 60 秒未完成则自动取消。防止慢查询长时间占用连接。 |
| `echo` | `false` | 设置为 `true` 时，SQLAlchemy 会将所有 SQL 语句打印到标准输出，仅用于开发调试。 |

## 连接池生命周期

### 启动 (`backend/db/database.py:46-76`)

```python
async def init_db() -> None:
    db_cfg = config.database

    connect_args = {
        "timeout": db_cfg.pool_timeout,
        "command_timeout": db_cfg.command_timeout,
    }

    _engine = create_async_engine(
        db_cfg.url,
        echo=db_cfg.echo,
        pool_size=db_cfg.pool_size,
        max_overflow=db_cfg.max_overflow,
        pool_timeout=db_cfg.pool_timeout,
        pool_recycle=db_cfg.pool_recycle,
        pool_pre_ping=True,
        connect_args=connect_args,
    )

    _session_factory = async_sessionmaker(
        bind=_engine,
        class_=AsyncSession,
        expire_on_commit=False,
    )
```

`init_db()` 在 FastAPI 的 `lifespan` 启动阶段被调用（`backend/main.py:124`）：

```python
@asynccontextmanager
async def lifespan(app: FastAPI):
    await init_db()           # 创建引擎 + 连接池
    init_vector_db()          # 初始化 pgvector
    get_graph()               # 预热 LangGraph
    # ... 启动后台任务 ...
    yield
    # ... 停止后台任务 ...
    await close_db()           # 释放连接池
```

要点：
- `_engine` 和 `_session_factory` 是 **模块级单例**，整个应用生命周期内只有一个引擎实例。
- `create_async_engine` 本身不立即创建连接，连接是懒加载的——第一次执行查询时才从池中获取。
- Schema 管理由 Alembic 负责，`init_db()` 不调用 `create_all`。

### 关闭 (`backend/db/database.py:79-83`)

```python
async def close_db() -> None:
    global _engine
    if _engine:
        await _engine.dispose()
        _engine = None
```

`engine.dispose()` 会关闭连接池中的所有连接并释放资源。

### 健康检查 (`backend/db/database.py:100-107`)

```python
async def health_check() -> bool:
    try:
        async with get_engine().connect() as conn:
            await conn.execute(text("SELECT 1"))
        return True
    except Exception:
        return False
```

从连接池获取一个连接，执行 `SELECT 1`，验证数据库可达。

## 会话管理

### 会话工厂

```python
_session_factory = async_sessionmaker(
    bind=_engine,
    class_=AsyncSession,
    expire_on_commit=False,  # 提交后不使属性过期，避免在 commit 后访问属性触发懒加载
)
```

`expire_on_commit=False` 是一个重要设置：默认为 `True` 时，每次 `commit()` 后所有加载过的属性会被标记为过期，下次访问会触发新的 SELECT。设为 `False` 后，提交后的对象仍然可以直接读取属性，适合 Web 请求-响应场景。

### 请求级会话 (`backend/db/database.py:87-97`)

```python
async def get_session() -> AsyncGenerator[AsyncSession, None]:
    if _session_factory is None:
        raise RuntimeError("Database not initialized.")
    async with _session_factory() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise
```

这是 FastAPI 的依赖项，每个 HTTP 请求获得一个独立的数据库会话。使用方式：

```python
@app.get("/api/users")
async def get_users(db: AsyncSession = Depends(get_session)):
    users = await select(db, User)
    return users
```

自动事务管理：
- **成功**：`yield` 后的 `await session.commit()` 自动提交事务。
- **失败**：`await session.rollback()` 回滚事务，然后重新抛出异常。

这确保了每个 HTTP 请求是一个完整的事务边界，避免了手动 `commit`/`rollback` 的样板代码。

## CRUD 层对会话的使用

`backend/db/crud.py` 中的所有函数（`insert`、`select`、`update_`、`delete` 等）均接受 `AsyncSession` 作为第一个参数，并提供 `commit` 参数控制是否立即提交：

```python
async def insert(session, model, data, commit=True, refresh=True) -> ModelT:
    instance = model(**data)
    session.add(instance)
    if commit:
        await session.commit()
        if refresh:
            await session.refresh(instance)
    return instance
```

当 CRUD 函数用于 `get_session()` 提供的请求作用域会话时，函数内部的 `commit` 提交整个事务。这意味着：**在一个请求处理函数中，多次调用带 `commit=True` 的 CRUD 函数会各自提交独立事务**。如果需要在多个 CRUD 操作间保持原子性，应将它们放在同一会话中，且只提交一次。

## 连接池容量规划

### 默认配置

| 场景 | 值 |
|------|-----|
| 常驻连接数 | 10 |
| 峰值连接数 | 30 |
| 连接最大存活时间 | 1 小时 |
| 等待连接超时 | 30 秒 |
| SQL 执行超时 | 60 秒 |

### PostgreSQL 服务端配置建议

连接池需要 PostgreSQL 服务端的对应参数配合：

```ini
# postgresql.conf 建议值
max_connections = 50               # 大于 pool_size + max_overflow，为管理连接留余量
idle_in_transaction_session_timeout = 60000  # 60 秒，防止长时间持有未释放的事务
statement_timeout = 0              # 由客户端 command_timeout 控制，服务端不设全局限制
```

- `max_connections` 必须 **大于** `pool_size + max_overflow`（30），否则多实例部署或管理工具连接时可能被拒绝。
- `idle_in_transaction_session_timeout` 配合 `pool_pre_ping=True` 和 `pool_recycle=3600`，形成多层防护：事务超时 → 服务端断开 → 连接池探测发现 → 自动替换。

### 调整建议

| 场景 | pool_size | max_overflow | 说明 |
|------|-----------|-------------|------|
| 开发环境 | 5 | 10 | 减少资源占用 |
| 低并发（< 50 并发请求） | 10 | 20 | **当前默认** |
| 中等并发（50-200） | 20 | 30 | 峰值 50 连接 |
| 高并发（> 200） | 30 | 50 | 需同步调高 `max_connections` |
| 多 Worker 部署 | 每个 Worker 独立连接池，需计算 `(pool_size + max_overflow) × workers < max_connections` | |

## pgvector 集成

项目使用 pgvector 扩展存储向量嵌入（`backend/db/vector.py`）。向量操作与主数据库共享同一连接池：

```python
# asyncpg codec 自动将 list[float] 转换为 pgvector 格式
emb_data = {f"emb_{i}": emb for i, emb in enumerate(embeddings)}
```

pgvector 查询（如余弦相似度检索）通过 asyncpg 的 pgvector codec 自动序列化/反序列化，无需手动拼接向量字符串。向量操作与普通 CRUD 使用相同的 `AsyncSession`，共享连接池资源。

## 常见问题

### Q: 为什么服务空闲一段时间后第一次请求报错？

A: PostgreSQL 可能断开了闲置连接。当前配置通过 `pool_pre_ping=True` 在获取连接时验证，会自动替换已断开的连接。如果仍有问题，检查 PostgreSQL 的 `idle_in_transaction_session_timeout` 是否小于连接池的空闲检测间隔。

### Q: 日志中出现 "queue pool size 10 overflow 20" 超时错误？

A: 所有 30 个连接（10 + 20）都在使用中，新请求在等待 30 秒后仍无法获取连接。可能原因：
1. 某些请求持有连接时间过长（检查是否有慢查询或未释放的事务）
2. 并发量超过预期，考虑增大 `pool_size` 和 `max_overflow`
3. 存在连接泄漏（忘记关闭会话）

### Q: 如何查看当前连接池状态？

A: 可以使用 SQLAlchemy 的 `engine.pool.status()`：

```python
from backend.db.database import get_engine
engine = get_engine()
print(engine.pool.status())  # 显示 pool_size, checked_in, checked_out 等
```

### Q: CRUD 函数中 `commit` 参数默认 `True` 有什么影响？

A: 使用 `commit=True` 的 CRUD 函数会立即提交事务。在一个请求中调用多个带 `commit=True` 的 CRUD 操作会产生多个独立事务。如果需要原子性，应该将中间调用的 `commit` 设为 `False`，最后在 `get_session()` 的自动提交中统一完成。
