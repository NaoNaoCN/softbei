# BM25 方案分析

## 当前状态

本项目并未直接使用 BM25 算法，而是采用 **jieba 分词 + PostgreSQL tsvector/tsquery + ts_rank()** 作为关键词召回路，功能上与 BM25 等价——在混合检索（Hybrid Retrieval）中提供词汇级精确匹配，与向量语义检索互补。

### 当前架构

```
用户查询
  → jieba 精确模式分词（backend/rag/indexer.py:28, retriever.py:185）
    → 索引时写入 text_search (tsvector) 列（GIN 索引加速）
    → 查询时构建 to_tsquery('simple', kw1 & kw2 & ...)
      → ts_rank() 评分 + 按 rank DESC 排序
        → RRF 融合向量召回结果
```

相关文件：
- `backend/rag/retriever.py` — `_tokenize_keywords()`、`retrieve_keyword()`、`retrieve_hybrid()`
- `backend/db/vector.py` — `query_keyword()`（tsquery 构建与查询）
- `backend/rag/indexer.py` — `_tokenize_for_tsvector()`（索引时写入）
- `migrations/versions/9c2d5e7f8a9h_add_text_search_tsvector.py` — tsvector 列与 GIN 索引

## 当前方案（PostgreSQL ts_rank）的优劣

### 优势

**1. 零额外依赖，部署简单**
tsvector/tsquery 是 PostgreSQL 内置功能，无需引入 Elasticsearch、rank-bm25 等外部组件。一条 SQL 完成检索，与项目现有的 PostgreSQL + asyncpg 技术栈无缝集成。

**2. GIN 索引加速，查询性能可控**
`document_chunk.text_search` 列使用 `pg_trgm` GIN 索引，全文检索走索引扫描而非全表扫描。当前数据规模下，关键词召回延迟在毫秒级。

**3. jieba 分词适配中文**
PostgreSQL 原生分词对中文支持较差（默认按字切分）。本项目在索引和查询两端均使用 jieba 精确模式分词，以空格拼接后写入 tsvector，使用 `'simple'` 配置（不做 stemming/stopword），完全自主控制分词质量。**同样一套 jieba 分词逻辑可以被 re-rank 阶段复用**（`_rerank_by_keyword_overlap()`），避免了分词不一致问题。

**4. ts_rank() 与 BM25 排序效果接近**
`ts_rank()` 基于 TF-IDF 思想：词频（TF）越高、文档频率（DF）越低，权重越大。这与 BM25 的核心理念一致。在中文知识库场景中，ts_rank 与 BM25 的排序结果高度相关（Spearman ρ 通常 > 0.9）。

**5. RRF 融合弥补评分量纲差异**
无论 BM25 还是 ts_rank，关键词评分与向量余弦相似度的量纲不可比。RRF（Reciprocal Rank Fusion）只看排名不看绝对分值，天然规避了归一化问题。当前方案中 RRM 已在 `_rrf_fusion_cross_path()` 实现，向量路和关键词路分别配置权重。

### 劣势

**1. 'simple' 配置缺乏语言学处理**
使用 `'simple'` 配置意味着 PostgreSQL 不做停用词过滤和词干提取。停用词过滤在 Python 侧通过硬编码的 `_KEYWORD_STOP_WORDS` 集合处理（约 60 词），词干提取完全缺失。对于英文内容，"running" 和 "run" 会被视为不同 token，可能漏召回。

**2. ts_rank() 缺乏文档长度归一化**
BM25 的核心优势之一是**文档长度归一化**（通过 `b` 参数调节）：长文档不会仅因为包含更多词就获得虚高分数。`ts_rank()` 默认不归一化文档长度，长 chunk 在关键词密度相同时可能获得更高 rank，导致偏向长文本。

**3. 分词与 PostgreSQL 的耦合损耗**
索引时 jieba 分词后以空格拼接写入 tsvector，查询时 jieba 分词后以 `&` 连接为 tsquery。这个过程存在信息损耗：
- 词序信息：tsvector 不保留词的位置关系，"深度学习" 和 "学习深度" 在 tsvector 中完全相同
- 词权重：所有词在 tsquery 中等权（均为 `&` 连接），无法对核心词加权

**4. 无法做 BM25 的参数调优**
BM25 有两个可调参数 `k1`（词频饱和度）和 `b`（文档长度归一化），可以根据领域特点调节匹配策略。`ts_rank()` 不暴露这些参数，缺乏调优灵活性。

**5. 停用词表维护成本**
`retriever.py:169` 的 `_KEYWORD_STOP_WORDS` 是硬编码的静态集合，主要覆盖中文通用停用词。对于特定领域（如计算机科学），可能需要补充领域停用词，且当前实现不支持从配置文件加载。

## 引入真正 BM25 的优劣

### 场景一：替换当前 tsvector 方案

如果用 BM25 完全替换 PostgreSQL tsvector/tsquery：

**优势：**
- **精确的文档长度归一化**：消除长文本偏差，对父子切割场景尤其重要（父块长度可达子块的 3-5 倍）
- **参数可调**：`k1` 控制词频饱和（高频词不无限加分），`b` 控制长度归一化程度
- **跨数据库可移植**：不依赖 PostgreSQL 特有功能，迁移到 MySQL/SQLite 无额外成本
- **效果可复现**：BM25 是确定性算法，同一查询在所有环境中结果一致

**劣势：**
- **需引入外部库**（如 `rank-bm25`），增加依赖和内存开销。BM25 需在内存中构建倒排索引，全量数据加载到 Python 进程会显著增加内存占用
- **失去数据库级索引加速**：当前 GIN 索引在 PostgreSQL 内核完成检索，延迟 <10ms；BM25 需从 DB 拉取全量文本到 Python 侧计算，网络开销 + 计算开销显著增加
- **两条分词路径**：需要在 Python 侧维护独立的 jieba 分词 → BM25 索引构建流程，与向量检索的索引流程分离，增加维护复杂度
- **实时更新困难**：BM25 倒排索引在内存中，新增/删除文档需要重建或增量更新索引（rank-bm25 不原生支持增量）
- **需要引入中文分词器**：BM25 原生按空格分词，中文需预分词后以空格拼接传入

### 场景二：与 tsvector 并行（三路召回）

同时保留 tsvector 和 BM25，做向量 + BM25 + tsvector 三路 RRF 融合：

- 额外引入复杂度但边际收益低：ts_rank 与 BM25 排序高度相关，两路关键词召回的差异化有限
- 不推荐在当前规模下使用

## 是否值得引入 BM25？

| 维度 | 当前 ts_rank | BM25 | 评价 |
|------|-------------|------|------|
| 排序质量 | ★★★★☆ | ★★★★★ | BM25 略优，差距在 5% 以内 |
| 中文适配 | ★★★★☆（jieba） | ★★★☆☆（需自行分词） | 持平 |
| 集成成本 | ★★★★★ | ★★☆☆☆ | ts_rank 显著更优 |
| 性能 | ★★★★★（GIN 索引） | ★★★☆☆（内存计算） | ts_rank 显著更优 |
| 文档长度处理 | ★★★☆☆ | ★★★★★ | BM25 显著更优 |
| 可调性 | ★★☆☆☆ | ★★★★★ | BM25 显著更优 |
| 部署复杂度 | ★★★★★ | ★★★☆☆ | ts_rank 显著更优 |

### 建议

**短期（当前阶段）**：保持现有 ts_rank 方案，不做 BM25 迁移。理由：
1. 当前数据规模下（知识库文档量级），ts_rank 与 BM25 的排序质量差异不构成瓶颈
2. 混合检索 + RRF 融合 + re-rank 精排的三层架构已经提供了较好的结果质量
3. 引入 BM25 的集成和维护成本远大于收益

**中长期（优化方向）**：若未来出现以下情况，可考虑引入 BM25：
1. 文档数量增长到 10^4 级以上，长文档偏差开始显著影响检索质量
2. 需要跨数据库迁移（脱离 PostgreSQL）
3. 评估数据表明关键词召回的精确率/召回率成为瓶颈

**低成本的改进**（无需引入 BM25）：
1. **领域停用词外置**：将 `_KEYWORD_STOP_WORDS` 移到 `configs/config.yaml` 中，支持按领域配置
2. **tsquery 加权**：对核心查询词（如命名实体、专业术语）在 tsquery 中使用权重语法（`setweight()`），提升关键 token 的匹配权重
3. **文档分桶**：按 chunk 长度分桶，在桶内分别做 ts_rank 排序，间接实现粗粒度的长度归一化
4. **补充词干处理**：对英文内容在 jieba 分词后附加 `snowball` 词干，减少形态变化导致的漏召回
