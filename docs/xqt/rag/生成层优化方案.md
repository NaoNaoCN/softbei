## 二、已完成优化项

### 2.1 提示词全面重写（P0）

**文件**: `configs/prompts.yaml`

所有 5 个生成 Agent（doc / code / mindmap / quiz / summary）+ safety Agent 全部按 NEVER/IMPORTANT 两级禁令体系重写：

**统一结构**（以 doc_agent 为例，`prompts.yaml:63-97`）：

```
# Role — 明确"基于参考资料"的定位，声明"不是权威专家"
# Rules（优先级从高到低）
  ## NEVER — 绝对禁止（3 条）:
    1. 禁止编造事实 — 不得写入参考资料中不存在的数据、公式、定义、结论
    2. 禁止凭记忆补充 — 即使"知道"，也不能写入正文；补充内容用 💡 前缀
    3. 禁止跳过空引用检查 — context 为空时必须 ⚠️ 声明
  ## IMPORTANT — 必须做到（3 条）:
    4. 引用追溯 — 每条关键陈述标注 [n]
    5. 覆盖声明 — 文末区分"来自参考资料"和"学习建议/补充"
    6. 适配画像 — 难度和深度与当前学生画像匹配
# Pre-generation Check — 生成前内心自查（不输出）
# Output — 格式规范
---
参考资料：{context}
知识点：{kp_name}
```

**各 Agent 特殊规则**：

| Agent | 特殊 NEVER | 特殊 IMPORTANT |
|-------|-----------|---------------|
| code (`prompts.yaml:24-61`) | 禁止编造 API/函数签名 | 注释中标注 `[n]`；`💡 补充` 标注自行添加的逻辑 |
| mindmap (`prompts.yaml:98-140`) | 禁止编造概念节点；空引用返回 `{"name": "知识库暂无参考资料", "children": []}` | 层级保真（不重排、不嫁接） |
| quiz (`prompts.yaml:265-311`) | 禁止编造答案和虚假干扰项 | 解析溯源 `[n]`；素材不足减少题量 |
| summary (`prompts.yaml:375-409`) | 禁止编造数据/数字/公式 | `[n]` 来源标注；优先呈现核心概念 |
| safety (`prompts.yaml:337-373`) | 禁止放过捏造内容；禁止忽略引用错误；禁止输出修正内容 | 逐项对比；4 项审核清单 |

### 2.2 System Prompt 角色修正（P0）

**涉及文件**: 所有 Agent + `judge.py` + `golden_dataset.py`

所有生成类 Agent 和 Judge 的系统提示词从 `role: "user"` 改为 `role: "system"`：

```python
# 修改前
raw = await chat_completion(
    [{"role": "user", "content": prompt}], ...
)

# 修改后
raw = await chat_completion(
    [{"role": "system", "content": prompt}], ...
)
```

根据实验，`role: "system"` 对 LLM 的约束力显著强于 `role: "user"`，LLM 更倾向于遵守其规则。

**未改为 system 角色的位置**（属于对话性质，影响小）：
- `profile_agent.py` 的 guide/confirm 引导语 — 对话性质，`user` 角色可接受
- `recommend_agent.py:92` — 推荐 prompt 使用 `user` 角色
- `utils.py` 的 query rewrite / expand — 工具性调用

### 2.3 空上下文兜底（P0）

所有生成 Agent prompt 均包含空引用检查，当 `format_context()` 返回 `（暂无参考资料）` 时：

| Agent | 行为 | 位置 |
|-------|------|------|
| doc / code / summary | 开头声明 `⚠️ 当前知识库暂无此知识点的参考资料，以下内容基于通用知识，仅供参考` | `prompts.yaml:74, 35, 386` |
| mindmap | 返回 `{"name": "知识库暂无参考资料", "children": []}` | `prompts.yaml:109` |
| quiz | JSON 首个元素附加 `"_note": "当前知识库中暂无相关参考资料..."` | `prompts.yaml:289` |

### 2.4 自我知识与参考来源的区分（P0）

引入 `💡 补充` / `💡 学习建议` 前缀机制：

- **正文内容** — 必须来自参考资料，标注 `[n]`
- **补充内容** — LLM 根据通用知识添加的逻辑/建议，用 `💡` 前缀明确区分
- 读者可以清楚地知道哪些可追溯、哪些是 LLM 自身知识

### 2.6 Judge JSON 解析修复（P0）

**文件**: `backend/evaluation/judge.py`, `backend/agents/utils.py`

**修复 2 — `safe_json_loads` 返回 list 导致 `.get()` 报错** (`judge.py:253-256`)：

```python
# 新增类型守卫
if isinstance(result, list):
    logger.warning(f"[RAGJudge] faithfulness 返回了数组而非对象，取首个元素")
    result = result[0] if result else {}

```

**修复 3 — 新增截断 JSON 修复策略** (`utils.py:158-197`)：

`_repair_truncated_json()` 函数处理被 `max_tokens` 截断的 JSON：
- 检测并移除末尾未闭合的字符串

### 2.7 评估路径对齐（P1）

### 2.8 多样感知排序（P1）

**文件**: `backend/rag/retriever.py:488-528`, `_diversify_order()`

在 `format_context()` 中新增多样感知排序：

```python
def _diversify_order(chunks: list[RetrievedChunk]) -> list[RetrievedChunk]:
    """按 section 分组后 round-robin 交错排列，避免 top-k 全部集中在一个子主题。"""
    sections: dict[str, list[RetrievedChunk]] = {}
    for c in chunks:
        sec = c.section.strip() if c.section else ""
        if sec:
            sections.setdefault(sec, []).append(c)

    # Round-robin：轮流从每个 section 取一个 chunk
    result: list[RetrievedChunk] = []
    while len(result) < len(chunks):
        for key in section_keys:
            if idx[key] < len(sections[key]):
                result.append(sections[key][idx[key]])
                idx[key] += 1
```

效果：原先 top-5 可能 5 条全来自"定义"部分，现在交错排列保证了不同子主题（定义、原理、应用、示例）的覆盖均衡。

### 2.9 Citation 编号安全（P1）

**文件**: `backend/rag/retriever.py:472-484`

当 context 因 `max_tokens` 限制被截断时，在末尾显式标注：

[注意：以上仅展示了前 3 条参考资料，共检索到 5 条。请勿引用 [4] 及更大的编号。]

防止 LLM 引用不存在的编号（如正文出现 `[5]` 但只展示了 3 条）。

## 三、当前系统架构（优化后实际状态）

### 3.1 统一 RAG 管线

所有 5 个生成 Agent 通过 `backend/agents/utils.py:retrieve_context()` 走统一 RAG 管线：

```
retrieve_context(state, agent_name)
  ├── 1. Query Rewrite（config.rag.query_rewrite_decontextualize + profile_aware）
  │     · 策略 A: 对话去上下文化（最近 6 轮）
  │     · 策略 B: 画像感知（薄弱知识点、学习目标、认知风格）
  │     · 策略 C: 多角度查询扩展（当前 disabled）
  ├── 2. 检索路径选择
  │     · multi_query → retrieve_with_queries() + RRF 融合
  │     · hybrid → retrieve_hybrid()（向量 + 关键词双路）
  │     · 默认 → retrieve()（纯向量检索）
  ├── 3. 后处理
  │     · _rerank_by_keyword_overlap（关键词重叠加权重排）
  │     · _resolve_parent_chunks（子块→父块映射 + 去重）
  │     · format_context()（多样排序 + 引用格式 + 编号安全）
  └── 4. 评估采集
        · collector.record_retrieval() 记录检索元数据
```

## 四、Graph 路由与安全机制

### 4.1 当前路由拓扑

`backend/agents/graph.py:95-126`：

```
START → profile_agent
          ├─ profile_complete=False → END
          └─ profile_complete=True → planner_agent
                                        ├─ intent=clarify → clarify_agent → END
                                        └─ intent=generate → resource agent
                                              ├─ doc_agent ────────┐
                                              ├─ code_agent ────────┤
                                              ├─ mindmap_agent ─────┤
                                              ├─ quiz_agent ────────┤→ safety_agent
                                              ├─ summary_agent ─────┘         │
                                              │                                  ↓
                                              ├─ kg_agent ───────────→ recommend_agent → END
                                              └─ (direct) ───────────→ recommend_agent → END
```

**安全路由规则**：
- 5 个生成 Agent 全部经过 `safety_agent` 审核后输出
- `kg_agent` 绕过 safety（数据工程操作，非文本生成，幻觉风险天然低）
- `clarify_agent` 绕过 safety（对话追问，在历史基础上简短回复，低幻觉风险）

### 4.2 评估采集

`graph.py` 在每次 `invoke()` 完成后触发：

```python
# graph.py:175-177
_collect_generation_eval(state)       # 记录 agent_type, draft_length, latency, safety 结果
_maybe_trigger_async_judge(state)     # 按采样率异步触发 LLM Judge 评估
```

异步 Judge 以 `asyncio.create_task` 形式执行，不阻塞用户响应。Judge 完成后通过 collector 回写 faithfulness_score、hallucination_rate、completeness_score、citation 数据。

## 五、优化效果

### 5.1 核心指标对比

| 指标 | 优化前 | 优化后 | 变化 | 标准 | 判定 |
|------|--------|--------|------|------|------|
| Faithfulness | 0.445 | **0.915** | **+105%** | >=0.70 | PASS |
| Hallucination Rate | 0.333 | **0.085** | **-74%** | <=0.15 | PASS |
| Citation Accuracy | 0.750 | **0.867** | +16% | >=0.70 | PASS |

| Completeness | 0.409 | 0.168 | -59% | >=0.60 | FAIL |

### 5.2 关键发现

**Faithfulness 跃升 105%（最大成果）**：14/15 查询忠实度达标。根因是 NEVER 禁令 + system role + 低温度（0.1-0.4）三重约束，LLM 被严格限制在参考资料范围内。

**Completeness 下降是预期副作用**：不是退步，而是 anti-fabrication 优化的必然结果。LLM 严格遵守参考资料边界后，不再填补参考资料中缺失的内容。Completeness 低的根因在检索层（top-5 chunks 无法覆盖 5-8 个 expected aspects），需要在检索层解决。

**Hallucination 得到有效控制**：从"三成内容为编造"降至"不到一成"，低于 15% 警戒线。

## 七、验证方法

1. **黄金测试集回归**：`python -m backend.evaluation.golden_dataset --run`
   - 生成报告：`logs/golden_eval_*.md`
   - 自动对比上一次运行结果，任意指标下降 > 10% 触发告警
2. **实际生成路径评估**：通过 `POST /generate` 触发资源生成
   - 评估数据由 `collector` 自动采集
   - Judge 异步执行（采样触发，开发环境 100% 采样）
3. **Health Check**：通过 `backend/evaluation/health_check.py` 监控
   - `empty_result_rate > 30%` → 检索退化告警
   - `score_p50 < 0.3` → 检索质量告警
