# RAG 增量索引更新机制

> 实施日期：2026-05-25 | 迁移：`7a1b2c3d4e5f_add_content_hash.py`
> 相关文件：`backend/rag/indexer.py`, `backend/db/vector.py`, `backend/db/models.py`

---

## 1. 概述

增量索引的核心目标是：**当用户重新上传同一文档时，只对内容发生变化的 chunk 重新计算 Embedding，跳过未变化的 chunk，删除已移除的 chunk**。这消除了全量删除+重建带来的 Embedding API 浪费。

旧流程与增量流程对比：

```
旧（全量替换）：
  DELETE 该 doc_id 的所有 chunk → re-parse → re-embed ALL chunks → INSERT ALL

新（增量）：
  re-parse 文档 → 计算每个 chunk 的 MD5 → 查询旧 hash → diff →
    仅 embed 变化的 chunk → upsert → 删除多余的旧 chunk
```

## 2. 数据模型变更

### 2.1 content_hash 列

在 `document_chunk` 表新增 `content_hash VARCHAR(32)` 列（`models.py:152`）：

| 属性 | 值 |
|------|-----|
| 类型 | `VARCHAR(32)` |
| 可空 | `nullable=True`（兼容 legacy 数据） |
| 内容 | `hashlib.md5(text.encode("utf-8")).hexdigest()` |
| 用途 | 精确判断 chunk 文本内容是否变更 |

### 2.2 复合索引

```sql
CREATE INDEX ix_document_chunk_doc_id_hash
  ON document_chunk (doc_id, content_hash);
```

该复合索引加速了"查询某文档下所有 chunk 的 hash 映射"这一核心操作，可走 index-only scan 无需回表。

## 3. 三阶段增量算法

入口函数：`index_chunks()`（`indexer.py:31-204`）

### 3.1 Phase 1 — Diff（差异检测）

```python
# indexer.py:60-92

by_doc: dict[str, list[TextChunk]] = {}    # 按 doc_id 分组
to_embed: list[TextChunk] = []              # 需要嵌入的 chunk
to_delete: dict[str, list[str]] = {}        # 需要删除的过期 chunk_id
skipped_count = 0

for doc_id, doc_chunks in by_doc.items():
    # Step 1: 查询该文档在数据库中的旧 hash 映射
    old_hashes = await get_chunk_hashes_by_doc_id(doc_id)
    #   → 返回 {chunk_id: content_hash_or_None}

    # Step 2: 计算新 chunk 的 MD5
    new_hashes = {}
    for c in doc_chunks:
        new_hashes[c.chunk_id] = hashlib.md5(c.text.encode("utf-8")).hexdigest()

    old_ids = set(old_hashes.keys())
    new_ids = set(new_hashes.keys())

    # Step 3: 分类每个 chunk
    for c in doc_chunks:
        if c.chunk_id not in old_ids:
            to_embed.append(c)              # 新 chunk → 待 INSERT
        elif old_hashes[c.chunk_id] != new_hashes[c.chunk_id]:
            to_embed.append(c)              # 内容变更 → 待 UPDATE
        else:
            skipped_count += 1              # hash 一致 → SKIP

    # Step 4: 找出需要删除的 chunk
    removed_ids = old_ids - new_ids
    if removed_ids:
        to_delete[doc_id] = list(removed_ids)
```

**分类矩阵：**

| chunk_id 在旧集合中？ | content_hash 相同？ | 处理方式 |
|:---:|:---:|---|
| 否 | — | **INSERT**：新 chunk，需要嵌入 |
| 是 | 否 | **UPDATE**：内容变化，需要重新嵌入 |
| 是 | 是 | **SKIP**：无变化，零 API 调用 |
| 仅旧集合有 | — | **DELETE**：文档中已移除该 chunk |

### 3.2 Phase 2 — Embed + Upsert

仅对 Phase 1 中标记为 `to_embed` 的 chunk 进行处理。代码路径（`indexer.py:101-192`）区分两种块：

**Phase 2a — 父块写入（无嵌入）**

父子切割方案中，父块是子块的合并（大块文本），不参与向量检索，因此**不调用 Embedding API**：

```python
# indexer.py:108-133
await upsert_documents(
    ids=[c.chunk_id for c in batch],
    documents=[c.text for c in batch],
    embeddings=[None] * len(batch),  # 父块不需要向量
    metadatas=[...],
)
```

**Phase 2b — 子块嵌入 + Upsert**

子块是实际参与向量检索的单元，调用 Embedding API 后写入：

```python
# indexer.py:140-192
embeddings = await _embed_batch([c.text for c in batch])
# 校验：跳过空向量（API 失败时不应写入脏数据）
valid_pairs = [(c, emb) for c, emb in zip(batch, embeddings)
               if emb and len(emb) > 0]
# 计算 content_hash 随 metadata 写入
batch_hashes = [hashlib.md5(c.text.encode("utf-8")).hexdigest()
                for c in valid_batch]
await upsert_documents(
    ids=[c.chunk_id for c in valid_batch],
    documents=[c.text for c in valid_batch],
    embeddings=valid_embeddings,
    metadatas=[{
        "doc_id": c.doc_id,
        "source": c.source_path,
        "user_id": user_id or "",
        "content_hash": batch_hashes[idx],  # 写入 hash 供下次 diff 使用
        ...
        **c.metadata,
    } for idx, c in enumerate(valid_batch)],
)
```

**Upsert 实现**（`vector.py:144-222`）：

```sql
INSERT INTO document_chunk (id, chunk_id, doc_id, ..., content_hash, ...)
VALUES (...), (...), (...)
ON CONFLICT (chunk_id) DO UPDATE SET
    text = EXCLUDED.text,
    embedding = EXCLUDED.embedding,
    content_hash = EXCLUDED.content_hash,
    ...;
```

- `chunk_id` 是唯一业务标识，作为冲突判断键
- `ON CONFLICT DO UPDATE`：新 chunk INSERT，已有 chunk 则 UPDATE 全部字段
- content_hash 随每次写入更新，确保下次 diff 可检测到最新状态

### 3.3 Phase 3 — Delete 过期 chunk

```python
# indexer.py:194-200
for doc_id, delete_chunk_ids in to_delete.items():
    await delete_documents(delete_chunk_ids, collection_name=collection_name)
```

底层 SQL（`vector.py:347-354`）：

```sql
DELETE FROM document_chunk WHERE chunk_id = ANY(:ids)
```

删除操作在 upsert 之后执行，确保：
- 如果 Phase 2 的 upsert 失败，旧数据仍然存在（不会出现空窗）
- 删除失败不影响已写入的正确数据（`try/except` 仅 warn 不中断）

## 4. Hash 查询接口

```python
# vector.py:369-394
async def get_chunk_hashes_by_doc_id(
    doc_id: str,
    collection_name: Optional[str] = None,
) -> dict[str, Optional[str]]:
```

返回 `{chunk_id: content_hash_or_None}` 映射。对于在 `content_hash` 列添加前入库的 legacy 数据，该字段为 `NULL`。

**Legacy 兼容机制：**

```python
# NULL != "abc123" → True → 触发重新嵌入
if old_hashes[c.chunk_id] != new_hashes[c.chunk_id]:
    to_embed.append(c)  # legacy chunk 自动被标记为"变更"，重新嵌入后回填 hash
```

因此无需任何数据迁移脚本，legacy chunk 在首次增量索引时自动回填 `content_hash`。

## 5. 与 HNSW 索引的协同

向量索引已从 IVFFlat 切换为 HNSW（`M=16, ef_construction=200, ef_search=100`），其"插入即索引"特性与增量更新高度协同：

| 特性 | 对增量更新的意义 |
|------|-----------------|
| 插入即索引 | INSERT/UPDATE 后新向量立即可检索，无空窗期 |
| 无需 REINDEX | 不像 IVFFlat 需要定期重建索引来纳入"未索引堆" |
| 支持 DELETE | 删除后图结构自动调整，无残留 |

增量更新的累积量极大时（> 总数据量 200%），可考虑 `REINDEX INDEX CONCURRENTLY` 优化 HNSW 图结构——但属于罕见场景。

## 6. "同一文档"的定义与 doc_id 生成机制

增量索引依赖 `doc_id` 来判断"哪些旧 chunk 属于同一文档"。**Phase 1 的 diff 按 `doc_id` 分组——只有新旧 `doc_id` 相同时，才会进入 hash 对比和 skip 逻辑。**

### 6.1 doc_id 的两种生成方式

`doc_id` 并非来自文件内容哈希，而是由**调用方在解析阶段传入**（`loader.py:196`）：

```python
# loader.py:196
_doc_id = doc_id or path.stem  # 不传则默认为文件名（无扩展名）
```

不同调用路径的 `doc_id` 来源完全不同：

| 调用路径 | doc_id 来源 | 位置 | 相同文件重传时 doc_id 是否相同？ |
|----------|------------|------|:---:|
| **Web 上传** (`import_document`) | `f"doc_{hex(snowflake_id)[:N]}"` — 每次生成新 Snowflake ID | `document.py:57` | **否** |
| **CLI 命令** (`index_file`) | `Path.stem` — 文件名（去扩展名） | `loader.py:196` 默认值 | **是** |
| **CLI 命令** (`index_directory`) | `Path.stem` — 同上 | `loader.py:196` 默认值 | **是** |
| **知识图谱构建** (`run_kg_build`) | 从 `ResourceMeta.kp_id` 传入（即首次上传时的 Snowflake doc_id） | `document.py:89` | 取决于调用方 |

### 6.2 chunk_id 的组成

`chunk_id` 由 `doc_id` 派生，格式为 `{doc_id}_{chunk_index}`（`loader.py:653`）。这意味着即使两份完全相同的文件，如果 `doc_id` 不同，其 `chunk_id` 也完全不同，Phase 1 的 hash 对比（按 `chunk_id` 匹配）自然无法命中任何旧 chunk。

### 6.3 关键结论：Web 上传流程当前无法触发增量 skip

```
Web 上传流程（当前行为）：
  用户上传 math.pdf →
    import_document() 生成 doc_id="doc_a1b2c3d4" →
      所有 chunk 的 chunk_id 都是 "doc_a1b2c3d4_0", "doc_a1b2c3d4_1", ...
      → 数据库中旧数据属于 doc_id="doc_0000abcd" → chunk_id 完全无交集
      → Phase 1 diff: old_ids ∩ new_ids = ∅ → 全部标记为 INSERT
      → 增量 skip 数为 0 ❌

CLI 流程（可正常触发增量）：
  执行 index_file("data/math.pdf") →
    doc_id = "math"（文件名 stem） →
      chunk_id = "math_0", "math_1", ...
      → 与数据库中已存在的 doc_id="math" 匹配
      → Phase 1 diff: hash 对比成功 → 无变化 chunk 被 skip ✅
```

**Web 上传流程每次上传都是"新文档"，增量索引的 hash diff 机制无法生效。** 当前的增量更新仅在 CLI/脚本场景（`index_file`、`index_directory`）中真正发挥作用。

### 6.4 如果要让 Web 上传也支持增量更新

需要一种稳定的 `doc_id` 生成策略，使同一文件在重复上传时能生成相同的 `doc_id`。可选方案：

| 方案 | doc_id 来源 | 优点 | 缺点 |
|------|------------|------|------|
| A: 文件内容哈希 | `"doc_" + md5(file_bytes)` | 天然幂等，内容相同即 doc_id 相同 | 文件内容变了 doc_id 也变，旧数据变成孤儿 |
| B: user_id + 原始文件名 | `"doc_{user_id}_{original_name}"` | 简单直观 | 改名后视为新文档；多用户同名冲突 |
| C: ResourceMeta.kp_id 复用 | 检测到同一用户上传同名文件时，复用已有的 `kp_id` | 与现有 ResourceMeta 表对齐 | 需额外查表逻辑；改名后识别不到 |
| D: 前端显式声明"更新" | 上传时传入已有 `doc_id`，表示更新而非新建 | 语义明确 | 需前端配合 |

推荐方案 **C + D 结合**：前端提供"更新文档"入口传已有 `doc_id`；后端在上传接口中检测是否已有同名文档并提供复用选项。

## 7. 调用入口

增量索引通过 `index_chunks()` 统一入口，内部自动判断增量路径：

```python
# CLI: 单文件索引（doc_id = 文件名 stem，重复执行可触发增量 skip）
await index_file("path/to/doc.pdf")

# CLI: 目录批量索引
await index_directory("path/to/knowledge_base/")

# Web: import_document（doc_id = Snowflake，每次新 ID，不触发增量 skip）
from backend.services.document import import_document
result = await import_document(file_path, user_id=user.id, db=session)
```

## 8. 日志与可观测性

`index_chunks()` 在 Phase 1 diff 完成后输出汇总日志：

```
[Indexer] 增量索引：150 个 chunk → 嵌入 23 (新增/变更), 跳过 125 (无变化), 删除 2 (已移除)
```

特殊情况日志：

| 日志 | 含义 |
|------|------|
| `增量索引完成：所有 N 个 chunk 无变化，零 API 调用` | 完全相同的文件重传，无任何变更 |
| `Embedding API 返回空向量，跳过批次` | API 异常，该批次跳过不写入脏数据 |
| `N/M 个 chunk 嵌入为空，已过滤` | 部分 chunk 嵌入失败，已过滤后继续 |
| `已删除 doc_id=X 的 N 个过期 chunk` | Phase 3 删除完成 |

## 9. 收益总结

| 收益 | 量化 |
|------|------|
| **Embedding API 费用** | 修改文档一个章节时，仅 10-40% 的 chunk 需要重新嵌入，节省 60-90% |
| **索引延迟** | 仅解析+hash 计算全量 chunk，Embedding 仅对差异部分 |
| **数据一致性** | ON CONFLICT upsert 保证幂等；Phase 2 先于 Phase 3 避免空窗 |
| **Legacy 兼容** | NULL != hash → 自动触发回填，无需迁移脚本 |
| **运维复杂度** | HNSW 插入即索引，无需定期 REINDEX |
