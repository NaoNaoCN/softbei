## 1. 当前切分机制回顾

### 1.1 现状：两级固定切分

当前 `loader.py` 使用"章节切分 + 固定大小切分"两级策略：

```
原始文档 (PDF/DOCX/MD)
  → convert_to_markdown()          # 统一转为 Markdown
    → _split_markdown_by_headers() # 第1级：按 #/##/### 标题切分为章节
      → split_text()               # 第2级：每节按 500 字符 + 50 字符重叠切分
        → TextChunk                # 最终块，携带 section 元数据
```

关键参数（`configs/config.yaml`）：

| 参数 | 当前值 | 说明 |
|------|--------|------|
| `chunk_size` | 500 字符 | 每块字符数 |
| `chunk_overlap` | 50 字符 | 相邻块重叠字符数 |
| `max_sections_before_coarse_split` | 50 | 章节数超过此值时切换为更粗粒度 |

### 1.2 当前方案的优点

1. **实现简单**：纯规则切分，无外部依赖，逻辑集中在 `split_text()`（40 行）
2. **章节标题保留**：每个 chunk 携带 `section` 字段（`# 标题名`），在 `format_context()` 中渲染为引用信息
3. **句子边界感知**：`split_text()` 会回溯 20% 范围找最近的 `。！？.!?\n` 作为切分点
4. **代码块保护**：`_split_markdown_by_headers()` 预先提取代码块再按标题切分，避免代码中的 `#` 被误解析
5. **句子边界切分**：`split_text()` 优先在 `。！？.!?\n` 处切分，避免在词/句中间截断

### 1.3 当前方案的问题

#### 问题 0：特殊内容被截断（代码块 / 表格 / 公式）

当前 `split_text()` 的句子边界正则 `[。！？.!?\n]` 对以下内容无效：

**代码块**：代码中通常没有中文标点，500 字符一到就硬截断。

```
chunk_1（前 500 字符，截断在函数体中间）:
```python
def backward_propagation(self, X, y, learning_rate=0.01):
    """反向传播算法实现。"""
    m = X.shape[0]
    # Forward pass
    Z1 = np.dot(X, self.W1) + self.b1
    A1 = self.sigmoid(Z1)

chunk_2（后 500 字符，从残损代码开始）:
    dZ2 = A2 - y
    dW2 = (1/m) * np.dot(A1.T, dZ2)
```
```

LLM 看到 chunk_1 无法理解这个函数做了什么，看到 chunk_2 的 `dZ2 = A2 - y` 不知道这个变量从哪来的。

**Markdown 表格**：表格被从中截断后完全不可读。

```
chunk_1:
| 激活函数 | 公式 | 输出范围 | 优点 |

chunk_2:
| Sigmoid | σ(x)=1/(1+e^(-x)) | (0,1) | 可解释为概率 |
| Tanh | (e^x-e^(-x))/(e^x+e^(-x)) | (-1,1) | 零中心 |
```

chunk_1 只有表头，chunk_2 只有数据行，两者单独看都无法理解。

**数学公式（LaTeX）**：`$$...$$` 或 `$...$` 公式块被从中截断。

这在实际教育场景中非常常见——AI/数学教材天然包含大量代码、公式和表格。

#### 问题 1：语义碎片化

500 字符对于中文教材来说偏小。一段完整的数学推导可能是：

```
（前 500 字符—chunk_12）
梯度下降的更新公式为 θ = θ - η∇J(θ)。其中 η 是学习率，∇J(θ) 是损失函数
关于参数 θ 的梯度。下面证明该算法的收敛性。设损失函数 J(θ) 满足 L-Lipschitz

（后 500 字符—chunk_13，与前块有 50 字符重叠）
连续梯度条件，即 ||∇J(θ₁) - ∇J(θ₂)|| ≤ L||θ₁ - θ₂||，则对于任意步长 η < 2/L，
梯度下降迭代保证 J(θ_{t+1}) ≤ J(θ_t) - η(1 - ηL/2)||∇J(θ_t)||²。由于 η < 2/L
保证了 η(1 - ηL/2) > 0，因此损失函数单调递减...
```

当学生查询"梯度下降的收敛性证明"时，语义向量可能匹配到 chunk_12（包含"收敛性"关键词），但**完整的证明过程在 chunk_13**，而 chunk_13 本身可能因为缺少"收敛性"关键词而排在后面。

#### 问题 2：章节级上下文丢失

当前每个 chunk 只携带 `section` 标题字符串（如 `"梯度下降算法"`），但**不携带父章节的完整文本**。LLM 看到的是：

```
[1] （来源：optimization.pdf，梯度下降算法）
梯度下降的更新公式为 θ = θ - η∇J(θ)...

[2] （来源：optimization.pdf，梯度下降算法）
||∇J(θ₁) - ∇J(θ₂)|| ≤ L||θ₁ - θ₂||...
```

LLM 无法判断 chunk_1 和 chunk_2 之间的关系（前后相邻？还是来自同节的不同子话题？），也无法看到"梯度下降算法"这一整节的完整推导逻辑。

#### 问题 3：跨块概念的检索不对称

考虑一个教育学场景：

```
chunk_50（第 3 章的某个 500 字符片段）：
"...布鲁姆分类法将认知领域分为六个层次：记忆、理解、应用、分析、评价和创造..."

chunk_87（同一本书第 7 章的某个 500 字符片段）：
"...基于布鲁姆分类法设计教学目标时，应注意从低阶思维到高阶思维的递进..."
```

如果检索到 chunk_50，学生看不到 chunk_87；如果检索到 chunk_87，学生看不到 chunk_50。两者都是"布鲁姆分类法"的高相关内容，但因为属于不同章节，被当作独立块处理。

## 2. 父子切割方案概述

### 2.1 核心思想

父子切割（Parent-Child Chunking，也称 Small-to-Big Retrieval）将文档组织为两层结构：

```
┌─────────────────────────────────────────────────────┐
│  父块 (Parent Chunk)                                 │
│  - 较大粒度（如 2000-4000 字符）                       │
│  - 保留完整语义单元（如整个章节、完整证明）               │
│  - 存储但不参与向量检索（或仅作为辅助）                   │
│  - 作为最终返回给 LLM 的上下文                          │
│                                                     │
│  ┌──────────┐ ┌──────────┐ ┌──────────┐             │
│  │ 子块 1    │ │ 子块 2    │ │ 子块 3    │ ...         │
│  │ 200-500   │ │ 200-500   │ │ 200-500   │            │
│  │ 字符      │ │ 字符      │ │ 字符      │             │
│  └──────────┘ └──────────┘ └──────────┘             │
│  子块 (Child Chunk)                                  │
│  - 较小粒度，来自父块的切分或滑动窗口                     │
│  - 参与向量嵌入和语义检索（更精确的匹配）                  │
│  - 携带 parent_chunk_id 指回父块                       │
│  - 检索命中后，返回对应的父块文本                        │
└─────────────────────────────────────────────────────┘
```

**检索流程对比：**

```
传统固定切分:
  query → embed → HNSW 检索 → 返回 top-K 子块 → LLM

父子切割:
  query → embed → HNSW 检索 → 命中子块 → 查找父块 → 返回 top-K 父块 → LLM
```

### 2.2 三种经典变体

| 变体 | 父块定义 | 子块定义 | 适用场景 |
|------|---------|---------|---------|
| **A. 章节-段落** | 完整章节（按标题切分） | 段落级滑动窗口 | 结构化教材、技术文档 |
| **B. 大块-小块** | 1000-2000 字符固定块 | 200-500 字符滑动窗口 | 通用文档 |
| **C. 文档-段落** | 整个文档 | 段落级切分 | 小文档（< 5000 字） |

### 2.3 检索后处理：去重 + 合并

邻近的子块可能都指向同一个父块，检索后需要去重：

```
假设检索到 top-5 子块：
  子块_3 (score=0.82) → 父块_A
  子块_4 (score=0.79) → 父块_A
  子块_7 (score=0.75) → 父块_B
  子块_5 (score=0.72) → 父块_A  ← 与子块_3/4 同父，去重
  子块_11(score=0.68) → 父块_C

去重后返回：
  父块_A（来自子块_3/4/5，保留最高分 0.82）
  父块_B（来自子块_7，0.75）
  父块_C（来自子块_11，0.68）
```

如果去重后数量不足 `n_results`，可以补充次高分的其他父块。

## 3. 对当前项目的适用性分析

### 3.1 教育场景的天然适配

该项目的文档类型是**高等教育教材/讲义**，具有天然的层级结构：

```
├── 1. 神经网络基础（章）
│   ├── 1.1 感知机模型（节）
│   │   ├── 定义与数学表达（段落）
│   │   ├── 几何解释
│   │   └── 局限性分析
│   ├── 1.2 激活函数
│   └── 1.3 多层网络
├── 2. 反向传播算法
│   ├── 2.1 链式法则回顾
│   ├── 2.2 前向与反向传播
│   └── 2.3 梯度消失问题
```

这类内容的检索需求具有强**局部上下文依赖性**：
- 学生问"Sigmoid 函数求导"→ 期望的答案不仅包括导数公式本身，还包括它在反向传播中如何使用
- 学生问"为什么需要非零中心"→ 答案分散在同一节的不同段落中

**结论：教育类内容天然适合父子切割。章节 = 父块，段落 = 子块，匹配变体 A。**

### 3.2 与现有代码的兼容性

当前 chaining 已经在做"半步"的父子切割——`section` 元数据保留了层级信息，但未利用它来反查父块文本。

| 现有组件 | 父子切割需要改动 |
|----------|-----------------|
| `_split_markdown_by_headers()` | **无需改动** — 已经按标题切出章节 |
| `split_text()` | **升级** — 子块大小可适当缩小（如 300 字符）；新增特殊块保护（代码块/表格/公式不被截断） |
| `TextChunk` 数据结构 | **加 2 个字段** — `parent_chunk_id` + `is_parent` |
| `index_chunks()` (增量索引) | **加父块写入** — 在子块嵌入前先写入父块 |
| `upsert_documents()` | **无需改动** — 同一接口 |
| `retrieve()` | **加后处理** — 子块 → 父块映射 + 去重 |
| `format_context()` | **无需改动** — 输入仍是文本列表 |
| `query_documents()` | **无需改动** — HNSW 检索接口不变 |
| `content_hash` 增量索引 | **父块也享受增量** — 父块文本不变则跳过 |

### 3.3 存储与费用影响

| 维度 | 当前（仅子块） | 父子切割 | 增量 |
|------|-------------|---------|------|
| document_chunk 行数 | N | N（子块）+ M（父块） | +M 行 |
| 嵌入向量数 | N 个 1024 维 | N 个 1024 维（父块不嵌入） | 0 |
| Embedding API 调用 | N 次 | N 次（不变） | 0 |
| 存储空间 | N × (文本 + 1024 维向量) | +(M × 父块文本)，无向量增长 | +M × 文本大小 |
| 检索速度 | O(log N) HNSW | 同左（检索量不变） | 0 |

**关键洞察：父块不需要嵌入向量。** 父块的作用纯粹是"原文存储"，检索只发生在子块上。子块数量在父子切割中反而可能减少（因为子块粒度更细但总数未必增加），所以 **Embedding API 费用不会显著增加**。

估算：假设一个 100 页的 PDF 教材，当前 500 字符切分产生约 200 个 chunk。采用父子切割后：
- 子块：约 200 个（500 字符），或 300 个（300 字符更精粒度）
- 父块：约 30 个（按章节/大段），每段 1000-3000 字符
- 向量数：200-300 个（与现在相当或略多）
- 额外存储：约 60,000 字符 ≈ 120KB（可忽略）

## 4. 实现方案设计

### 4.1 数据模型变更

**TextChunk 新增字段：**

```python
@dataclass
class TextChunk:
    chunk_id: str
    text: str
    doc_id: str
    source_path: str
    page: Optional[int] = None
    section: Optional[str] = None
    parent_chunk_id: Optional[str] = None   # NEW: 指回父块的 chunk_id
    is_parent: bool = False                 # NEW: 自身是否为父块
    metadata: dict = field(default_factory=dict)
```

**document_chunk 表变更（迁移）：**

```sql
ALTER TABLE document_chunk ADD COLUMN parent_chunk_id VARCHAR(128);
ALTER TABLE document_chunk ADD COLUMN is_parent BOOLEAN DEFAULT FALSE;
CREATE INDEX ix_document_chunk_parent ON document_chunk (parent_chunk_id);
```

父块的 `embedding` 列为 NULL（不参与向量检索）。

### 4.2 切分逻辑变更

**核心思路**：在现有的 `_split_markdown_by_headers()`（第 1 级）和 `split_text()`（第 2 级）之间，插入父块的创建和父子关系的建立。

```
_current flow_:  section → split_text → children (independent)
_new flow_:      section → parent_chunk (full section text)
                        → split_text → child_chunks (linked to parent)
```

**loader.py 改动（伪代码）：**

```python
def _parse_markdown_to_chunks_parent_child(
    md_text: str,
    doc_id: str,
    source_path: str,
    parent_chunk_size: int = 2000,    # 父块大小阈值
    child_chunk_size: int = 500,      # 子块大小（可保持 500）
) -> list[TextChunk]:
    sections = _split_markdown_by_headers(md_text)
    chunks: list[TextChunk] = []
    chunk_index = 0

    for section_title, section_text in sections:
        parent_id = f"{doc_id}_p{chunk_index}"
        
        # 对大章节做二次父块切分（避免单父块 > 4000 字符）
        parent_sub_texts = _split_into_parents(section_text, parent_chunk_size)
        
        for parent_sub in parent_sub_texts:
            parent_id = f"{doc_id}_p{chunk_index}"
            chunk_index += 1
            
            # 写入父块（不嵌入，仅存储文本）
            parent_chunk = TextChunk(
                chunk_id=parent_id,
                text=parent_sub,
                doc_id=doc_id,
                source_path=source_path,
                section=section_title,
                is_parent=True,
            )
            chunks.append(parent_chunk)
            
            # 子块切割 + 建立父子关系
            child_texts = split_text(parent_sub, chunk_size=child_chunk_size)
            for child_text in child_texts:
                child_chunk = TextChunk(
                    chunk_id=f"{doc_id}_{chunk_index}",
                    text=child_text,
                    doc_id=doc_id,
                    source_path=source_path,
                    section=section_title,
                    parent_chunk_id=parent_id,
                    is_parent=False,
                )
                chunks.append(child_chunk)
                chunk_index += 1
    
    return chunks
```

**父块切分策略（`_split_into_parents`）**：

对于章节文本长度 ≤ `parent_chunk_size`（如 2000 字符）的短节，整节作为一个父块。对于长节，按 `parent_chunk_size` 切分为多个父块，每个父块在语义边界（如两个 `\n\n` 之间）切分。

#### 4.2.1 特殊内容边界保护（代码块 / 表格 / 公式）

这是父子切割与固定切分的**关键区别**：父块和子块的切分必须识别并保护特殊内容块的完整性。当前系统仅在 header 检测时保护代码块，`split_text()` 没有特殊内容感知。

**需要保护的块类型**：

| 类型 | Markdown 语法 | 示例 | 切分规则 |
|------|-------------|------|---------|
| **围栏代码块** | ` ``` ... ``` ` | Python/Java/SQL 代码 | **禁止在块内切分**，整个代码块必须落在同一个 chunk 内 |
| **缩进代码块** | 4 空格或 1 tab 缩进 | 简单代码片段 | 连续缩进行视为一个不可分割单元 |
| **表格** | `\|...\|...\|` + 分隔行 | Markdown 表格 | **禁止在表内切分**，表格头+分隔行+数据行保持在一起 |
| **LaTeX 块公式** | `$$...$$` | 数学公式 | 禁止在 `$$...$$` 内部切分 |
| **LaTeX 行内公式** | `$...$` | 单行公式 | 行内公式通常较短（< 100 字符），尽量不切分 |
| **列表** | `- / 1.` 开头的连续行 | 项目列表 | 连续列表项视为一个语义单元，在列表结束后切分 |

**实现方法：预扫描 → 标记保护区 → 在非保护区寻找切分点**

```python
import re

# 特殊块的正则模式
_BLOCK_PATTERNS = [
    # 围栏代码块 (```...```)
    (re.compile(r'```[\s\S]*?```', re.MULTILINE), "fenced_code"),
    # LaTeX 块公式 ($$...$$)
    (re.compile(r'\$\$[\s\S]*?\$\$'), "latex_block"),
    # Markdown 表格 (连续 |...|...| 行)
    (re.compile(r'(\|.+\|[\r\n]){2,}', re.MULTILINE), "table"),
]


def _find_safe_split_point(
    text: str,
    preferred_pos: int,
    lookback: int = 200,
) -> int:
    """
    在 preferred_pos 附近找到一个不在特殊块内部的切分点。

    算法：
    1. 预扫描文本，标记所有特殊块（代码块/表格/公式）的字符区间
    2. 从 preferred_pos 向回搜索，跳过保护区
    3. 在非保护区内找最近的句子边界（。！？.!?\n\n）
    4. 如果 lookback 范围内全在保护区内，向前搜索第一个保护区结束位置
    """
    protected = _mark_protected_ranges(text)

    def _in_protected(pos: int) -> bool:
        for start, end in protected:
            if start <= pos < end:
                return True
        return False

    # 向回搜索
    search_start = max(0, preferred_pos - lookback)
    for pos in range(preferred_pos, search_start, -1):
        if not _in_protected(pos) and text[pos] in '\n。！？.!?':
            # 找到句子边界，确认不在保护区内
            # 优先在 \n\n（段落边界）处切分
            if text[pos:pos+2] == '\n\n':
                return pos + 2
            return pos + 1

    # 向回搜索失败，向前搜索第一个非保护区位置
    for pos in range(preferred_pos, min(len(text), preferred_pos + lookback)):
        if not _in_protected(pos) and text[pos] in '\n。！？.!?':
            return pos + 1

    # 彻底失败 → 在 preferred_pos 硬切分（fallback）
    return preferred_pos


def _mark_protected_ranges(text: str) -> list[tuple[int, int]]:
    """标记所有特殊块的 (start, end) 字符区间。"""
    ranges = []
    for pattern, block_type in _BLOCK_PATTERNS:
        for match in pattern.finditer(text):
            ranges.append((match.start(), match.end()))
    # 按 start 排序，合并重叠区间
    ranges.sort()
    merged = []
    for start, end in ranges:
        if merged and start <= merged[-1][1]:
            merged[-1] = (merged[-1][0], max(merged[-1][1], end))
        else:
            merged.append((start, end))
    return merged
```

**对父块切分的影响**：

`_split_into_parents()` 也需要使用 `_find_safe_split_point()`，确保父块不在代码块/表格中间切分。实现方式与子块切分类似：

```python
def _split_into_parents(
    text: str,
    parent_chunk_size: int = 2000,
) -> list[str]:
    """将长章节切分为多个父块，保护特殊内容块完整性。"""
    if len(text) <= parent_chunk_size:
        return [text]

    chunks = []
    start = 0
    while start < len(text):
        end = min(start + parent_chunk_size, len(text))
        if end < len(text):
            # 在 parent_chunk_size 附近找安全的切分点
            safe = _find_safe_split_point(text, end, lookback=400)
            end = safe if safe > start else end
        chunks.append(text[start:end].strip())
        start = end
    return chunks
```

**对子块切分的影响**：

现有 `split_text()` 的句子边界正则 `[。！？.!?\n]` 无法避免在代码/表格内部切分。升级方案：

1. 在调用 `split_text()` 之前，先用 `_mark_protected_ranges()` 标注特殊块区间
2. `split_text()` 内部使用 `_find_safe_split_point()` 替代当前的简单句子边界回溯
3. 如果一个小 chunk 完全落在一个大的保护区内（如一个 300 字符的代码块），不强制切分——整个代码块作为一个子块

**性能考量**：`_mark_protected_ranges()` 对整个章节文本做一次正则扫描即可，O(n) 复杂度。章节文本通常 ≤ 5000 字符，正则匹配开销 < 1ms。标记结果可以在父块切分和子块切分之间复用（缓存）。

**效果对比**：

```
当前 split_text() 切分代码块:
  chunk_1: "def backward_propagation(self, X, y, learning_rate=0.01):\n    \"\"\"反向"  ← 截断
  chunk_2: "传播算法实现。\"\"\"\n    m = X.shape[0]"                           ← 残损

升级后 split_text() 切分代码块:
  chunk_1: "...（代码块前的文本）..."
  chunk_2: "```python\ndef backward_propagation(...)\n    ...\n```"           ← 完整
  chunk_3: "...（代码块后的文本）..."
```

**indexer.py 改动：**

```python
async def index_chunks(chunks, ...):
    # 分离父块和子块
    parents = [c for c in chunks if c.is_parent]
    children = [c for c in chunks if not c.is_parent]
    
    # Phase 1: Diff (基于 content_hash) — 父块和子块都参与
    # Phase 2: Embed — 只对子块做嵌入，父块只写入文本
    # Phase 3: Delete — 同上
    
    # 父块 upsert（无 embedding）
    await upsert_documents(
        ids=[p.chunk_id for p in parents],
        documents=[p.text for p in parents],
        embeddings=[None] * len(parents),  # 父块不嵌入
        metadatas=[...],
    )
    
    # 子块 upsert（正常嵌入）
    # ... 现有逻辑不变
```

**关键设计决策：父块也参与 content_hash 增量检测。** 如果父块文本未变（子块也未变），则父块 SKIP；如果子块因修改而重新嵌入，但父块文本未变，则父块仍 SKIP。

### 4.4 检索逻辑变更

**retriever.py 改动（新增父块回填函数）：**

```python
async def retrieve(query, ...):
    # 现有逻辑：获取子块检索结果
    child_chunks = ...  # 现有 HNSW 检索 + re-rank
    
    # NEW: 父块回填 + 去重
    enriched_chunks = await _resolve_parent_chunks(child_chunks)
    return enriched_chunks[:n_results]


async def _resolve_parent_chunks(
    child_chunks: list[RetrievedChunk],
) -> list[RetrievedChunk]:
    """
    将子块检索结果映射到父块文本，按父块去重。
    
    对于有 parent_chunk_id 的子块，返回父块文本（更大上下文）；
    对于无 parent_chunk_id 的子块（如旧数据），返回原始文本。
    """
    seen_parents = set()
    resolved = []
    
    for child in child_chunks:
        parent_id = child.metadata.get("parent_chunk_id")
        
        if parent_id:
            if parent_id in seen_parents:
                continue  # 去重：同一父块只返回一次
            seen_parents.add(parent_id)
            
            # 查询父块文本
            parent_text = await _get_parent_text(parent_id)
            if parent_text:
                resolved.append(RetrievedChunk(
                    chunk_id=parent_id,
                    text=parent_text,
                    score=child.score,  # 保留子块的检索分数
                    doc_id=child.doc_id,
                    source=child.source,
                    page=child.page,
                    section=child.section,
                    metadata={**child.metadata, "from_child_chunk": child.chunk_id},
                ))
                continue
        
        # 无父块的旧数据，直接返回
        resolved.append(child)
    
    # 按分数降序
    resolved.sort(key=lambda c: c.score, reverse=True)
    return resolved


async def _get_parent_text(parent_chunk_id: str) -> str | None:
    """按 chunk_id 从数据库读取父块文本。"""
    engine = get_engine()
    async with engine.connect() as conn:
        result = await conn.execute(
            text("SELECT text FROM document_chunk WHERE chunk_id = :cid"),
            {"cid": parent_chunk_id},
        )
        row = result.fetchone()
        return row[0] if row else None
```

**性能考量**：`_get_parent_text()` 单次查数据库，在 top-K 检索（K=5）时最多 5 次查询。可优化为一次批量查询：

```sql
SELECT chunk_id, text FROM document_chunk 
WHERE chunk_id = ANY(:parent_ids) AND is_parent = TRUE
```

### 4.5 前端 / Agent 调用方

**零改动**。`retrieve()` 的返回值仍是 `list[RetrievedChunk]`，`format_context()` 接口不变。唯一的区别是 `RetrievedChunk.text` 现在是父块的更大文本，而非原始 500 字符子块。

## 5. 方案变体对比

### 5.1 变体一：纯章节父块（推荐首期实施）

**父块 = 按 Markdown 标题切分的完整章节**（当前已有），子块 = 500 字符。

- 优点：改动最小，复用现有 `_split_markdown_by_headers()`
- 缺点：长章节（> 4000 字符）作为父块可能超出 LLM 上下文窗口（但 `format_context` 的 `context_max_tokens=3000` 已做了截断）
- 适合：教材、技术文档等结构化内容

### 5.2 变体二：大块-小块滑动窗口

**父块 = 2000 字符固定窗口**，**子块 = 300 字符滑动窗口**。

- 优点：不依赖文档的标题结构，适用于无标题或标题混乱的文档
- 缺点：父块可能在语义不完整处切分
- 适合：论文、非结构化文档

### 5.3 变体三：句子级检索 + 段落级返回

**子块 = 单个句子或 2-3 句**，**父块 = 自然段落**（以 `\n\n` 分割）。

- 优点：最精确的检索粒度
- 缺点：子块嵌入可能过于短小（单句 50-100 字符），语义信息不足，影响向量匹配质量
- 适合：FAQ、问答对等短文本场景

### 5.4 推荐：变体一（纯章节父块）

| 理由 | 说明 |
|------|------|
| **改动量最小** | `_split_markdown_by_headers()` 已产生天然的父块边界 |
| **数据结构稳固** | 章节标题作为自然边界，避免在公式/代码中间切分 |
| **教育场景匹配** | 学生的问题通常对应"某节的某概念"，整节上下文是最佳答案粒度 |
| **渐进式实施** | 可以先对章节 ≤ 2000 字符的做父块，长的保持现状，逐步优化 |

## 6. 效益与风险评估

### 6.1 预期收益

| 收益 | 量化预估 | 测量指标（全自动化） |
|------|---------|------|
| **上下文信息增益** | CIG +50-100% | 检索上下文 vs 完整章节文本的信息覆盖比（LLM 自动判定） |
| **检索精度** | 持平或 +5% | Precision@5 / NDCG@5（judge.chunk_relevance_batch 自动打分） |
| **LLM 答案完整性** | Completeness +10-15% | judge.judge_completeness() |
| **幻觉率降低** | Hallucination -5-10% | judge.judge_faithfulness() → hallucination_rate() |
| **跨块信息整合** | CCIR +200-400% | LLM 自动判断上下文是否含完整推理链 |
| **兄弟块利用** | SCG 0.50-0.70 | 程序化计算同父兄弟块的相关率 |
| **Embedding API 费用** | 不变 | `_embed_batch` 调用计数（父块不嵌入） |
| **存储成本** | +5-10% | `SELECT sum(length(text)) FROM document_chunk` |

详细测试方案和全自动化 A/B 框架见配套文档：`ANALYSIS_PARENT_CHILD_TESTING.md`。

### 6.2 风险与缓解

| 风险 | 影响 | 缓解措施 |
|------|------|---------|
| **父块过大** | 超出 LLM 上下文预算 | `format_context()` 已有 `context_max_tokens=3000` 截断；长父块（>2000 字符）按 `\n\n` 再切分 |
| **旧数据无父块** | 检索回退到原始子块 | `_resolve_parent_chunks()` 对无 `parent_chunk_id` 的 chunk 直接返回原文本 |
| **父块文本变更** | 增量索引需要重新判断 | 父块也参与 content_hash 检测，变更时自动更新 |
| **索引器复杂度增加** | 维护成本上升 | 父子分离逻辑可封装为独立函数，不影响现有三阶段增量框架 |
| **检索延迟增加** | 多一次 DB 查询 | 批量查询 + 索引 `ix_document_chunk_parent`，延迟 < 5ms |

### 6.3 不推荐的场景

父子切割**不适合**以下场景：
- 短文本问答（如 FAQ），文档本身就是一个回答，不需要更大上下文
- 跨章节概念检索（如"比较 A 和 B 的异同"），父子切割不解决跨父块检索，需要多跳检索或关键词融合

## 7. 与现有增强的协同效应

| 已有增强 | 与父子切割的协同 |
|----------|-----------------|
| **HNSW 索引** | 子块嵌入的 HNSW 检索不受影响；父块不参与检索，无需调整索引参数 |

| **Query Rewrite** | 查询改写后，子块检索命中率提升 → 父块回填的上下文更相关 |

## 9. 总结

父子切割方案**适合**当前项目，核心判断依据：

1. **教育内容的结构化特征**（章-节-段落天然层级）与父子切割的"章节=父块，段落=子块"模式高度匹配
2. **现有代码已具备 80% 基础设施**：`_split_markdown_by_headers()` 产生了天然的父块候选；`content_hash` 增量索引、HNSW 检索、`format_context()` 均无需实质性修改
3. **改动范围可控**：核心改动在 loader（加父块生成）+ retriever（加父块回填），indexer 和 API 接口不变
4. **成本几乎为零**：父块不参与嵌入（无额外 API 费用），仅增加少量文本存储
5. **可降级**：`enabled: false` 时完全回退到当前行为；旧数据无 `parent_chunk_id` 时自动回退到子块原文
6. **效果可量化且全自动化**：配套 `ANALYSIS_PARENT_CHILD_TESTING.md` 提供零人工标注的 A/B 测试框架（CIG + CRR + CCIR + SCG 四维指标 + 自动决策），人均参与约 10 分钟

**推荐实施变体一（纯章节父块），已于 2026-05-25 落地 Phases 1-4（迁移 `8b3c4d5e6f7g`），通过 `config.rag.parent_chunking.enabled` 控制开关（默认关闭），Phase 5 自动化评估待后续实施。**
