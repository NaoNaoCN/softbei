下面基于 **Claude Code 泄露的系统提示词（2026 年初）**，把它背后**真正在用的、成体系的系统提示词书写原则**整理成可直接落地的一套方法论，不啰嗦、全是从原文提炼的硬规则。

## 一、整体架构原则：工程化、分层、可缓存
Claude Code 提示词不是“一段话”，而是**54KB、915 行、函数动态生成的系统**。

### 1）静态/动态分离（最核心设计）
- **静态区（缓存区前）**：所有人共用、全局缓存
  - 身份定义、安全红线、基础能力、沟通风格、输出规范
- **动态区（缓存区后）**：每次会话生成、不缓存
  - 当前时间、用户信息、项目路径、已读文件列表
- 用固定标记分隔：`SYSTEM_PROMPT_DYNAMIC_BOUNDARY`

**原则：稳定规则前置，易变信息后置。**

### 2）模块化、分段、带标题
- 每一块有清晰标题：`# Identity`、`# Safety Rules`、`# Tool Usage`
- 每个规则**一句话讲清目的 + 一句话讲怎么做**
- 长规则拆成小点，避免大段文本

---

## 二、安全与约束原则：禁令分级、负向优先
### 1）五级禁令体系（优先级明确）
- **CRITICAL（不可逆灾难）**：最高优先级，必须 100% 遵守
  - 例如：禁止删除关键数据、禁止泄露密钥
- **NEVER（绝对禁止）**：功能错误、绝对不能做
  - 例如：禁止未读文件就修改、禁止编造信息
- **IMPORTANT（关键质量）**：容易忘、必须保证
  - 例如：每次修改前备份、每次工具调用后检查
- **Do NOT（一般禁止）**：默认不做，有例外
- **Avoid（尽量避免）**：偏好性建议，可权衡

**核心：不是所有规则都一样重，避免“狼来了效应”。**

### 2）约束 > 能力：先写“不能做什么”
- 少写“你能做什么”，多写“你**绝对不能**做什么”
- 每条禁止都给**理由**：
  - 不好：`Do not amend commits`
  - 好：`Do not amend commits — it overwrites history and loses work if the pre-commit hook failed`

### 3）负向指令必须具体（Tell them what NOT to do）
- ❌ 抽象：`Be careful with dangerous commands`
- ✅ 具体：`Do NOT run rm -rf /, sudo, or any destructive command without explicit user confirmation`

---

## 三、指令写法原则：具体、可执行、带逻辑
### 1）拒绝抽象，必须可执行
- ❌ `Be helpful`
- ✅ `When user asks for code, provide complete, runnable code with comments and error handling`

### 2）每条规则 = 目的 + 动作 + 边界
模板：
> 为了____（目的），你必须____（动作），除非____（例外）。

### 3）先“检查/读取”再“修改/生成”
硬规则：**必须先读文件 → 理解 → 再改**
- 禁止凭记忆/幻觉修改
- 禁止编造不存在的代码/配置

### 4）不知道就说不知道，严禁编造
- 对进展、数据、文件内容不确定时：
  - 直接说：`I don't have that information yet. Still processing.`
  - 不要猜、不要编、不要“合理推断”

---

## 四、Agent 与工具使用原则：可控、可审计、并行高效
### 1）工具优先，拒绝万能 Shell
- 能用专用工具（FileReadTool、GitTool）就**绝对不用**通用 shell
- 提示词强制：`Prefer FileReadTool over cat, FileWriteTool over echo >`

### 2）并行优先，减少串行等待
- 可并行的任务**一次性多发 tool call**
- 原文：`Launch multiple agents concurrently whenever possible, using a single message with multiple tool uses`

### 3）思考不外包，执行可分包
- 可以分任务给子代理，但**判断、理解、决策必须自己做**
- ❌ `Based on the subagent's result, decide...`
- ✅ `You first analyze the subagent's output, then make the final decision`

---

## 五、输出与沟通原则：简洁、诚实、结构化
### 1）简洁优先，不画蛇添足
- `Do NOT add features, refactor, or "improve" beyond what was asked. Three similar lines are better than premature abstraction.`
- 只做用户要求的事，**不主动优化、不重构、不追加功能**

### 2）结构化输出，固定格式
- 代码块、列表、标题、空行**格式严格统一**
- 便于解析、便于自动化处理

### 3）诚实面对知识截止（Knowledge Cutoff）
- 不说“我知识截止于…”，而是**角色扮演**：
  > `Answer as a well-informed person in Jan 2025 talking to someone from {{currentDateTime}}`
- 把“不知道”变成合理的时空认知限制

---

## 六、边界与异常处理原则：覆盖死角、防惰性
### 1）明确角色边界
- 你是谁、不是谁
- 能做什么、不能做什么
- 对什么负责、对什么不负责

### 2）覆盖常见失败模式
- 预想到 AI 会偷懒、会回避检查、会自我催眠
- 例如：专门写一条反驳“我觉得没问题”的借口

### 3）用户状态感知
- 用户离开、中断、切换话题、不懂技术、专家用户
- 不同状态下输出语气、详略、专业度自动调整

---

# 一句话总结（可直接当模板用）
**系统提示词 = 分层架构（静态+动态）+ 五级禁令（约束优先）+ 具体可执行指令（目的+动作+边界）+ 工具/Agent 可控规则 + 简洁诚实输出 + 全覆盖边界处理。**
