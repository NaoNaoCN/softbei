# 多路召回可行性分析

> 2026-05-21 | 分析当前 RAG 检索架构，评估引入多路召回的可行性、收益与成本
> 2026-05-26 | **路径 A（关键词召回）已落地**，详见第七章

---

## 一、什么是多路召回？为什么需要它？

### 问题

当前系统只有**一条检索路径**——pgvector 余弦相似度。这带来两个问题：

1. **语义匹配的盲区**：向量检索擅长"意思相近"，但遇到专有名词、代码片段、公式时，向量相似度经常失效。比如用户搜 `torch.nn.Linear` 和知识库里的 `全连接层`，语义上是一回事，但字面上毫无交集。
2. **单一信号的偏见**：每条 chunk 只有一个打分来源（余弦相似度），如果这个分数不准，没有其他信号来纠正。

### 解决思路

**多路召回（Multi-Recall）**就是同时从多个角度搜，再把结果合并：

```
用户提问: "什么是梯度下降？"
          │
          ├──→ 向量召回: 语义相似的 chunk（当前已有）
          ├──→ 关键词召回: 精确命中"梯度下降"的 chunk（✅ 已实现）
          ├──→ 知识图谱召回: 通过 KG 找到前置知识点的 chunk（规划中）
          └──→ 元数据过滤: 指定难度/类型的 chunk（规划中）
                   │
                   ▼
            结果融合 + 重排序 → 最终 Top-K
```

**收益**：不同召回路径互补短板。向量管语义泛化，关键词管精确匹配，KG 管知识关联。

## 二、当前架构基础

### 2.1 已有的检索管线

```
retrieve_by_kp(kp_name)
  → get_embedding(query)              # DashScope text-embedding-v4, 1024维
  → query_documents(embedding)        # pgvector <=> 余弦距离
  → 1.0 - distance → similarity       # 距离转相似度
  → filter by score_threshold (0.5)   # 低分过滤
  → _rerank_by_keyword_overlap()      # 关键词重叠加分（最多 +0.15）
  → return top-N
```

**优点**：简单、可靠，pgvector 单次检索 10-50ms。

**不足**：只有一条路，向量召回的盲区没有兜底。

### 2.2 已有的数据资产（可直接复用）

| 资产 | 位置 | 对多路召回的价值 |
|------|------|-----------------|
| `document_chunk.text` | 向量表 | 天然适合做关键词 ILIKE 匹配 |
| `document_chunk.metadata` | JSONB 列 | 已存 chunk_type/language/difficulty/course，可直接做元数据过滤 |
| `kg_node` + `kg_edge` | 知识图谱表 | 已构建 REQUIRES/RELATED_TO 边，可用于图谱召回 |
| Agent 缓存机制 | `agents/utils.py` | 已有 request-scoped 缓存，多路结果可复用同一缓存键 |

### 2.3 当前缺失的能力

- ~~无 PostgreSQL 全文检索索引（`tsvector` / `GIN`）~~ → 已用 jieba + ILIKE 替代
- 无 chunk ↔ KGNode 的映射关系
- ~~无多路结果融合逻辑~~ → 已实现 RRF 跨路融合
- 无重排序模型（仅有关键词重叠加分，+0.15）

## 三、可新增的召回路径

### 路径 A：关键词召回（jieba 分词 + PostgreSQL ILIKE）⭐⭐⭐⭐⭐ **✅ 已实现**

**优先级最高，成本最低，已于 2026-05-26 落地。**

采用 jieba 分词 + PostgreSQL ILIKE 匹配方案，避免了对 PostgreSQL 服务端中文分词扩展（zhparser / pg_jieba）的依赖：

```
实现方式:
  1. jieba.lcut(query) 精确模式分词
  2. 过滤停用词和单字 → 得到有效关键词列表
  3. 对每个关键词构建 text ILIKE '%kw%' 条件（OR 连接）
  4. 以匹配到的关键词数量 (match_count) 作为排名字段
  5. 结果归一化后送入 RRF 融合管道
```

| 维度 | 评估 |
|------|------|
| 改造成本 | 低。~200 行新增代码，无迁移 |
| 检索延迟 | < 10ms（ILIKE + 多条件 OR） |
| 检索效果 | 精确匹配、专有名词、代码片段效果好；语义泛化弱 |
| 与现有代码的耦合 | 无。新增独立函数，不修改现有检索 |
| 中文分词 | Python 侧 jieba，无需 PostgreSQL 扩展 |
| 开关控制 | `rag.hybrid.enabled` 一键开关 |

**代码位置**：
- `backend/rag/retriever.py` → `retrieve_keyword()`, `_tokenize_keywords()`
- `backend/db/vector.py` → `query_keyword()`

---

### 路径 B：知识图谱召回 ⭐⭐⭐⭐

**已有 KG 数据，但缺少 chunk↔node 的关联。**

当前 KG 构建时，LLM 从文档 chunk 中提取知识点节点，但没有记录"节点 X 是从哪些 chunk 提取的"这一映射。要启用 KG 召回，需要补充这个关联。

```
实现方式:

  方案 B1（轻量）：基于名称的模糊匹配
    1. 将用户 query 用 jieba 分词
    2. 匹配 KGNode.name 包含关键词的节点
    3. 从匹配到的节点出发，沿 REQUIRES 边扩展 1-2 跳
    4. 用扩展到的所有节点的 name 作为额外查询词
    5. 再走向量/关键词检索拿到对应 chunk

  方案 B2（精确，需迁移）：建 chunk-KGNode 映射表
    1. 新增表 chunk_kg_node(chunk_id, kg_node_id, relevance)
    2. KG 构建时记录每个节点来源于哪些 chunk
    3. 检索时：query → 匹配 KGNode → 映射表 → 直接拿到 chunk
```

| 维度 | 方案 B1（轻量） | 方案 B2（精确） |
|------|---------------|---------------|
| 改造成本 | 低，无新表 | 中，1 迁移 + KG Builder 改动 |
| 检索延迟 | ~20ms（含查 KG + 二次检索） | ~10ms（直接 JOIN） |
| 检索效果 | 中等（名称匹配有误差） | 好（精确映射） |
| 核心缺口 | jieba 已可用 | 需要重建已有文档的 KG |

**推荐路径**：先用 B1 跑通效果，验证 KG 召回的价值后，再决定是否投入 B2 的迁移成本。

### 路径 C：元数据过滤 ⭐⭐⭐

**已有 JSONB 列，可以直接用。但它是过滤而非召回。**

```sql
-- document_chunk.metadata 已存储:
-- {"chunk_type": "definition", "language": "zh", "difficulty": "beginner", "course": "人工智能导论"}

-- 过滤示例：只要中文、初级、定义类的 chunk
SELECT * FROM document_chunk
WHERE metadata @> '{"language": "zh", "difficulty": "beginner", "chunk_type": "definition"}'
ORDER BY ...
```

这更像一个**前置过滤器**而非独立召回路径。建议集成到向量/关键词检索的 `where` 条件中，让学生画像的"认知风格"和"学习阶段"驱动元数据选择。

| 维度 | 评估 |
|------|------|
| 改造成本 | 几乎为零。JSONB 列和 `@>` 操作符已就绪 |
| 需补充的 | 前端或 Agent 需要传递元数据过滤条件（如 `difficulty=beginner`） |
| 受益场景 | 个性化学习——初学者优先看基础概念，进阶者优先看定理证明 |

---

### 路径 D：不做的

**跨模态召回（图片/公式检索）**：项目当前不涉及多模态文档，不需要。

**Cross-encoder 重排序**：效果最好但调用一次 LLM 重排 20 条候选的成本等于一次生成请求，与 10% 采样策略矛盾。短期建议保持轻量级的关键词重叠重排。

## 四、融合策略

### 已实现：RRF（Reciprocal Rank Fusion）

```
RRF_score(chunk) = Σ ( weight_i / (k + rank_i(chunk)) )
                   i ∈ {vector, keyword, ...}

其中 k=60（平滑常数，可配置）
```

**为什么选 RRF 而不是加权求和？**

| 策略 | 优点 | 缺点 |
|------|------|------|
| 加权求和 | 可调权重，灵活 | 各路分数尺度不同，需要归一化（cosine 0-1 vs match_count 0-N） |
| **RRF** | 无需归一化，只看排名，被多个搜索系统验证有效 | 损失了分数置信度信息 |

对于本项目，RRF 实现简单且各路分数天然不可比（余弦距离 vs match_count 量纲完全不同），RRF 是更安全的选择。

### 融合流程

```
                         ┌─────────────────┐
                         │   用户 query     │
                         └────────┬────────┘
                                  │
          ┌───────────────────────┼───────────────────────┐
          │                       │                       │
          ▼                       ▼                       ▼
┌─────────────────┐   ┌─────────────────┐   ┌─────────────────┐
│  向量召回        │   │  关键词召回      │   │  KG 召回         │
│  pgvector <=>   │   │  jieba + ILIKE  │   │  名称匹配+扩展    │
│  pre-fetch 3x   │   │  match_count    │   │  （规划中）       │
└────────┬────────┘   └────────┬────────┘   └────────┬────────┘
         │                     │                     │
         ▼                     ▼                     ▼
   list[chunk_id,    list[chunk_id,        list[chunk_id,
    余弦相似度]       match_count]         KG 距离]
         │                     │                     │
         └─────────────────────┼─────────────────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │   RRF 跨路合并        │
                    │   _rrf_fusion_cross  │
                    │   _path()            │
                    │   按 RRF_score 排序   │
                    │   去重（同 chunk_id） │
                    └──────────┬──────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │   轻量重排序          │
                    │   关键词重叠加分      │
                    │   父块回填           │
                    └──────────┬──────────┘
                               │
                               ▼
                    ┌─────────────────────┐
                    │   返回 Top-K chunk   │
                    └─────────────────────┘
```

## 五、配置参数说明

多路召回通过 `configs/config.yaml` 中 `rag.hybrid` 配置节控制，所有参数均有默认值。

### 5.1 配置参数一览

```yaml
# configs/config.yaml
rag:
  hybrid:
    enabled: false                       # 总开关
    paths: [vector, keyword]             # 启用的召回路径
    rrf_k: 60                            # RRF 平滑常数
    vector_weight: 1.0                   # 向量召回路权重
    keyword_weight: 1.0                  # 关键词召回路权重
```

### 5.2 参数详解

#### `rag.hybrid.enabled`

| 属性 | 值 |
|------|-----|
| 类型 | `bool` |
| 默认值 | `false` |
| 作用 | 多路召回总开关 |

- `false`（默认）：仅使用向量召回，行为与引入多路召回前完全一致
- `true`：启用多路召回，并行执行 `paths` 中列出的所有召回路径，RRF 合并后返回

> **回滚**：任何时候将 `enabled` 改回 `false` 即可零代码回退到纯向量模式。

#### `rag.hybrid.paths`

| 属性 | 值 |
|------|-----|
| 类型 | `list[str]` |
| 默认值 | `["vector", "keyword"]` |
| 可选值 | `"vector"`, `"keyword"` |

控制启用哪些召回路径：

| 值 | 对应函数 | 说明 |
|----|---------|------|
| `"vector"` | `retriever.retrieve()` | pgvector 余弦相似度语义检索 |
| `"keyword"` | `retriever.retrieve_keyword()` | jieba 分词 + PostgreSQL ILIKE 精确匹配 |

示例：

```yaml
# 仅关键词召回（调试/评估用）
paths: [keyword]

# 仅向量召回（等同于 enabled: false）
paths: [vector]

# 双路召回（推荐配置）
paths: [vector, keyword]
```

#### `rag.hybrid.rrf_k`

| 属性 | 值 |
|------|-----|
| 类型 | `int` |
| 默认值 | `60` |
| 取值范围 | `1 ~ 120`（推荐 `30 ~ 60`） |

RRF（Reciprocal Rank Fusion）平滑常数。公式：`score = weight / (k + rank)`。

- **k 越小**：排名靠前的 chunk 权重越大，各路径差异更明显
- **k 越大**：各路权重越均匀，名次差异被平滑

```
k=30:  第1名=1/31=0.032,  第10名=1/40=0.025  (差距 28%)
k=60:  第1名=1/61=0.016,  第10名=1/70=0.014  (差距 14%)
```

#### `rag.hybrid.vector_weight` / `rag.hybrid.keyword_weight`

| 属性 | 值 |
|------|-----|
| 类型 | `float` |
| 默认值 | `1.0` |
| 取值范围 | `0.0 ~ 2.0`（推荐 `0.5 ~ 1.5`） |

各路召回的权重系数，直接乘到 RRF 分数上。

```yaml
# 侧重语义理解（默认配置）
vector_weight: 1.0
keyword_weight: 1.0

# 侧重精确匹配（适合代码/公式类知识库）
vector_weight: 0.7
keyword_weight: 1.3

# 仅语义检索
vector_weight: 1.0
keyword_weight: 0.0
```

### 5.3 推荐配置

```yaml
# 开发环境 / 调试阶段 — 关闭混合检索，减少变量
rag:
  hybrid:
    enabled: false

# 生产环境 / 通用场景 — 双路均衡召回
rag:
  hybrid:
    enabled: true
    paths: [vector, keyword]
    rrf_k: 60
    vector_weight: 1.0
    keyword_weight: 1.0

# 代码/公式密集型知识库 — 侧重关键词
rag:
  hybrid:
    enabled: true
    paths: [vector, keyword]
    rrf_k: 45
    vector_weight: 0.7
    keyword_weight: 1.3
```

### 5.4 配置生效位置

配置在以下调用链中生效：

```
Agent.generate()
  → retrieve_context()           # backend/agents/utils.py:270
    → if cfg.hybrid.enabled:
        retrieve_hybrid()        # backend/rag/retriever.py:296
          → asyncio.gather(
              retrieve(),        # 向量召回（已有）
              retrieve_keyword() # 关键词召回（新增）
            )
          → _rrf_fusion_cross_path()  # RRF 跨路融合
          → _rerank_by_keyword_overlap()
          → _resolve_parent_chunks()
```

## 六、实施方案

### 第一期：路径 A 关键词召回 ✅ 已完成（2026-05-26）

**改动文件清单**：

| 文件 | 改动类型 | 改动量 |
|------|---------|--------|
| `configs/config.yaml` | 新增 `rag.hybrid` 配置节 | ~8 行 |
| `backend/config.py` | 新增 `HybridConfig` 数据类 + 加载逻辑 | ~20 行 |
| `backend/db/vector.py` | 新增 `query_keyword()` | ~85 行 |
| `backend/rag/retriever.py` | 新增 `retrieve_keyword()`, `retrieve_hybrid()`, `_rrf_fusion_cross_path()`, `_tokenize_keywords()` | ~170 行 |
| `backend/agents/utils.py` | `retrieve_context()` 集成 hybrid 路径 | ~20 行 |

**核心设计决策**：

1. **为什么用 jieba + ILIKE 而不是 PostgreSQL FTS？**
   PostgreSQL 中文全文检索需要服务端安装 `zhparser` 或 `pg_jieba` 扩展，增加了部署门槛。jieba 在 Python 侧完成分词，用 `ILIKE '%kw%'` 做匹配，零服务端依赖，且对于万级数据量性能足够。

2. **为什么用 RRF 而不是加权求和？**
   向量余弦相似度（0-1）和关键词匹配数（0-N）的量纲完全不同，直接加权需要归一化，而 RRF 只依赖排名，天然避免量纲问题。

3. **为什么不在多查询扩展（策略 C）中启用混合检索？**
   策略 C 将查询扩展为 3-5 条子查询分别检索，本身已提供多样性。若每条子查询再走双路，检索次数翻倍（3×2=6 次），收益递减。因此混合检索仅在单查询模式下生效。

### 第二期：KG 召回（验证一期效果后决定）

```
1. KG Builder 改造: 构建时写入 chunk-KGNode 映射
2. 新增 chunk_kg_node 表（或利用现有 document_chunk.metadata JSONB）
3. KG 召回: query → 匹配节点 → 扩展 1-2 跳 → 取对应 chunk
4. 在 retrieve_hybrid() 中开启 paths: [vector, keyword, kg]
```

## 七、对现有系统的影响评估

| 关注点 | 影响 |
|--------|------|
| **检索延迟** | 向量 10-50ms + 关键词 <10ms，并行执行，总延迟取 max ≈ 向量延迟（几乎不变） |
| **LLM 成本** | 不增加 LLM 调用。关键词召回是纯数据库操作 |
| **数据库负载** | 关键词 ILIKE 查询比向量检索开销略高（多条件 OR + 全表扫描），万级数据量下可接受。如需优化可加 `pg_trgm` GIN 索引 |
| **Agent 兼容** | `retrieve_context()` 对上层完全透明，Agent 无感知，只拿到更好的 chunk |
| **评估系统** | 现有评估对 chunk 质量和相关性打分，天然适用 |
| **回滚难度** | 极低。`hybrid.enabled: false` 即回退到纯向量模式，行为与改动前完全一致 |

## 九、不做的及原因

| 方案 | 为什么不做 |
|------|-----------|
| 接入外部 BM25 引擎（Elasticsearch） | 项目数据量在万级，jieba + ILIKE 完全够用，额外引入 ES 运维成本太高 |
| Cross-encoder 重排序 | 每次重排需调 LLM，额外成本 ≈ 一次生成请求。10% 采样策略下收益有限 |
| 多模态召回 | 项目不涉及图片/音频/视频文档 |
| 学习型融合权重 | 需要标注数据来训练各路召回的权重系数，当前无标注数据 |
| PostgreSQL FTS 扩展（zhparser/pg_jieba） | 增加服务端部署依赖，jieba Python 侧分词已满足需求 |

## 十、结论

**路径 A（关键词召回）已于 2026-05-26 落地。**

一期只需要 ~300 行新增代码、零数据库迁移，就能弥补向量检索在精确匹配上的盲区。对现有 Agent 管道完全透明，回滚只需一行配置。

通过 `configs/config.yaml` 中的 `rag.hybrid` 配置节即可灵活控制：
- `enabled`: 一键开关，`false` 回退纯向量模式
- `paths`: 选择启用的召回路径组合
- `rrf_k`: 调整融合的排名敏感度
- `*_weight`: 按场景调整各路径权重

二期（KG 召回）的核心瓶颈在于 chunk↔KGNode 映射缺失，需要等一期验证了多路召回的价值后再投入。
