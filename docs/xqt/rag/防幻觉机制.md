# 项目防幻觉机制详解

---

## 先理解问题：大模型为什么会产生幻觉

在讲"怎么防"之前，先搞清楚"问题从哪来"。

LLM 在生成学习资源时，天然面临三种幻觉风险：

| 幻觉类型 | 表现 | 危害 |
|----------|------|------|
| **事实捏造** | 编造一个不存在的公式、定理、算法步骤 | 学生学到错误知识 |
| **概念混淆** | 把概念 A 的定义套到概念 B 上 | 知识体系混乱 |
| **来源不明** | 说"根据教材……"但教材根本没这句话 | 不可追溯、无法验证 |

核心矛盾：LLM 本质上是**语言模型**而非**知识模型**。它的训练目标是"预测下一个 token 让文本看起来合理"，而不是"输出真实可靠的事实"。当它不确定的时候，它会编得**看起来很合理**——这正是最危险的地方。

本项目处理的是教育场景，内容准确性是底线。所以防幻觉不是选配功能，而是架构的核心约束。

---

## 整体架构：五层递进防护

本项目的防幻觉机制不是靠一个环节，而是**五层递进**，从检索前到生成后全覆盖：

## 第零层：Query Rewrite — 检索前改写

### 解决的问题

用户输入往往是口语化的、带指代的、与个人画像相关的，直接拿去做向量检索效果差。例如：

- 学生说"你再详细讲讲那个公式"，其中"那个"指代上一轮对话中的具体公式
- 学生薄弱点在"反向传播"，但只说"帮我学深度学习"

### 三种策略

实现在 `backend/agents/utils.py:284-388`：

**策略 A — 对话去上下文化（Decontextualization）：**

```python
# utils.py:299-304
if cfg.query_rewrite_decontextualize and chat_history:
    recent = chat_history[-6:]  # 最近 6 轮
    formatted = "\n".join(
        f"- {m['role']}: {m['content'][:120]}" for m in recent
    )
    decontext_section = f"对话历史（用于指代消解）：\n{formatted}"
```

将"那个公式"改写为"梯度下降更新公式 \( \theta = \theta - \eta \nabla J(\theta) \)"。

**策略 B — 画像感知（Profile-aware Rewriting）：**

```python
# utils.py:308-317
if cfg.query_rewrite_profile_aware and profile:
    profile_parts = []
    if getattr(profile, "knowledge_weak", None):
        profile_parts.append(f"薄弱知识点：{', '.join(profile.knowledge_weak[:5])}")
    if getattr(profile, "learning_goal", None):
        profile_parts.append(f"学习目标：{profile.learning_goal}")
```

让查询偏向学生的薄弱领域，检索更精准。

**策略 C — 多角度查询扩展（Multi-angle Expansion）：**

```python
# utils.py:363-388
async def _expand_queries(query: str, n: int = 3) -> list[str]:
```

将一个查询扩展为多个角度（概念定义、原理推导、应用示例、常见误区、跨概念关联），各自独立检索后用 RRF（Reciprocal Rank Fusion）融合结果。避免单一查询视角的盲区。

**容错设计：** 每次改写失败都有回退方案（`_build_fallback_query()`），不会阻断检索流程。

## 第一层：多策略检索与置信度过滤

### 解决的问题

RAG 的核心思想是"先查到相关资料，再让 LLM 基于资料回答"。但向量数据库总是会返回结果，无论查到的内容跟问题有没有关系。

本项目的向量库是 **PostgreSQL + HNSW 索引**（`backend/db/vector.py`），不是 ChromaDB。检索器在此基础上叠加了多层过滤和增强。

### 混合检索（Hybrid Retrieval）

`retriever.py` 支持两路并行检索，结果通过 RRF 融合：

| 路径 | 实现 | 优势 |
|------|------|------|
| 语义检索 | BGE-M3 / DashScope text-embedding-v4 向量 + HNSW | 捕获语义相似性 |
| 关键词检索 | jieba 分词 + PostgreSQL `ILIKE` | 精确匹配专业术语 |

两路互补：语义检索能理解"多层感知机"≈"MLP"，关键词检索不会漏掉精确术语匹配。

### 相似度阈值过滤

`retriever.py:90` 的 `_parse_results()` 对语义检索结果按 `score_threshold`（默认 0.5）过滤，低于阈值的结果直接丢弃。

### 关键词重叠 Re-rank

```python
# retriever.py:93-94
if chunks:
    chunks = _rerank_by_keyword_overlap(query, chunks)
```

在语义检索的 Top-K 候选上，用 jieba 关键词做二次精排。语义相似但关键词不匹配的 chunk 会被降级，提升精确率。

### 父块回填（Parent-child Chunking）

```python
# retriever.py:96-97
chunks = await _resolve_parent_chunks(chunks)
chunks = chunks[:_n_results]
```

检索时用子块（精确定位），返回时替换为父块（完整上下文）。同一个父块的多个子块去重，只保留分数最高的那个。这解决了"检索到的片段太短，缺少上下文"的问题。

### 多样感知排序（Diversity-aware Ordering）

```python
# retriever.py:434, 488-528
diverse_chunks = _diversify_order(chunks)
```

按 section 分组后 round-robin 交错排列，避免 top-k 全部集中在同一个子主题（如全是"定义"部分而没有"应用"部分）。

### Citation 编号安全

```python
# retriever.py:474-484
if shown_count < total:
    result += (
        f"\n\n[注意：以上仅展示了前 {shown_count} 条参考资料，"
        f"共检索到 {total} 条。请勿引用 [{shown_count + 1}] 及更大的编号。]"
    )
```

当 context 因 max_tokens 限制被截断时，显式告知 LLM 实际展示范围，防止 LLM 引用不存在的编号。

### 增强的引用格式

```python
# retriever.py:439-461
source_info = f"来源：{chunk.source}"
if chunk.page:
    source_info += f"，第 {chunk.page} 页"
if chunk.section:
    source_info += f"，{chunk.section}"
# 附加元数据：chunk_type（定义/定理/示例/习题/总结）、language、difficulty
```

每条引用不仅带文件来源和页码，还带内容类型、语言、难度标签，让 LLM 更好地理解每条参考资料的属性。

### 优雅降级

第一层有完备的容错设计，所有失败情况都返回空列表而非抛异常：

```python
# retriever.py:53-55 — 向量库为空
if doc_count == 0:
    logger.warning("[RAG] 向量库为空（0 条文档），RAG 降级为纯 LLM 生成。")
    return []

# retriever.py:66-68 — Embedding 失败
if not embedding:
    logger.warning("[RAG] Embedding 返回空向量，无法执行语义检索。")
    return []

# retriever.py:428-429 — format_context 空输入
if not chunks:
    return "（暂无参考资料）"
```

三种情况都会让生成 Agent 进入"空引用模式"（触发 ⚠️ 声明），系统不会崩溃。

### 用户级数据隔离

```python
# retriever.py:72-80
if user_id:
    user_filter = {"$or": [{"user_id": user_id}, {"user_id": ""}]}
```

只检索当前用户上传的文档或公共文档，防止跨用户数据污染导致的"张冠李戴"式幻觉。

## 第二层：Prompt 约束 — NEVER/IMPORTANT 分级禁令

### 解决的问题

第一层只保证了"喂给 LLM 的资料是相关的"，但没有约束 LLM **怎么用**这些资料。LLM 很可能：
- 瞄了一眼参考资料，然后主要靠自己的参数化知识生成
- 混合了参考资料的片段和自己的"脑补"
- 无法区分哪些来自教材、哪些来自训练数据

### 分级禁令体系

所有生成 Agent 的系统提示词统一遵循 NEVER/IMPORTANT 两级禁令体系（定义于 `configs/prompts.yaml`）：

| 优先级 | 关键词 | 适用场景 | 示例 |
|--------|--------|---------|------|
| 最高 | **NEVER** | 不可逆伤害：编造事实、虚假引用 | "禁止编造 API——编造不存在的 API 会直接导致学生写出无法运行的代码" |
| 高 | **IMPORTANT** | 必须做到的质量门槛 | "正文中来自参考资料的每一条关键陈述，标注来源编号 [n]" |

两条原则来自 `docs/design/rag/系统提示词书写原则.md`：
- **每条禁令必须给出理由** — 防止 LLM 将其合理化
- **负向指令必须具体** — "禁止编造参考资料中不存在的数据、公式、定义或结论" 而非 "注意准确性"

### 6 个生成 Agent 的统一 NEVER 规则

所有 Agent（doc / code / mindmap / quiz / summary / safety）共享以下 NEVER 规则：

1. **禁止编造事实** — 不得写入参考资料中不存在的数据、公式、定义、结论、API
2. **禁止凭记忆补充** — 即使"知道"某个相关概念，如果参考资料中没有，就不能写入正文
3. **禁止跳过空引用检查** — 如果 context = `（暂无参考资料）`，必须显式声明 ⚠️ 警告

### 各 Agent 的特殊规则

| Agent | 特殊 NEVER 规则 | 特殊 IMPORTANT 规则 |
|-------|----------------|-------------------|
| **doc** (`prompts.yaml:63-97`) | — | `[n]` 引用追溯 + 覆盖声明 + 画像适配 |
| **code** (`prompts.yaml:24-61`) | 禁止编造 API/函数签名 | 注释中用 `[n]` 标注来源；`💡 补充` 标注自行添加的逻辑 |
| **mindmap** (`prompts.yaml:98-140`) | 禁止编造概念节点；空引用返回 `{"name": "知识库暂无参考资料", "children": []}` | 层级保真（不重排、不嫁接） |
| **quiz** (`prompts.yaml:265-311`) | 禁止编造答案和虚假干扰项 | 解析溯源引用 `[n]`；素材不足时减少题量不强行凑数 |
| **summary** (`prompts.yaml:375-409`) | 禁止编造数据/数字/公式 | `[n]` 来源标注；`💡 学习建议` 前缀区分补充内容 |
| **safety** (`prompts.yaml:337-373`) | 禁止放过捏造内容；禁止忽略引用错误；禁止输出修正内容 | 逐项对比；具体问题描述；学习场景敏感 |

### Pre-generation Check — 隐藏思维链

每个 Agent 的 Prompt 都包含一个 **Pre-generation Check** 环节（不输出给用户）：

以 doc_agent 为例 (`prompts.yaml:81-87`)：

```
# Pre-generation Check（执行但不输出）
在动笔之前，在心里回答以下问题：
- 参考资料覆盖了"{kp_name}"的哪些子主题？列出了哪几个？
- 有哪些该知识点常见但参考资料中缺失的子主题？
- 基于以上判断，我的文档可以做到多完整？

如果参考资料少于 3 条：在生成的文档末尾简要声明"覆盖范围受限于当前参考资料"。
```

这利用了 LLM 的 Chain-of-Thought 能力，让模型在正式输出前先"自查"参考资料的覆盖范围，从而减少越界编造。

### 空引用处理

当 `format_context()` 返回 `（暂无参考资料）` 时，每个 Agent 都有明确的行为规定：

| Agent | 空引用行为 |
|-------|----------|
| doc / code / summary | 开头声明 `⚠️ 当前知识库暂无此知识点的参考资料，以下内容基于通用知识，仅供参考` |
| mindmap | 返回 `{"name": "知识库暂无参考资料", "children": []}` |
| quiz | 在 JSON 首个元素附加 `"_note": "当前知识库中暂无相关参考资料..."` |

### 自我知识的前缀隔离

当 LLM 确实需要补充参考资料中没有的内容时，必须使用 `💡 补充`（代码）或 `💡 学习建议`（文档/总结）前缀将其与参考来源内容明确区分。这样读者能清楚地知道哪些是可追溯的、哪些是 LLM 的通用知识。

### 温度控制

不同的 Agent 使用不同的 temperature，事实性要求越高的 Agent 温度越低：

| Agent | temperature | 原因 |
|-------|------------|------|
| safety | 0.1 | 审核需要确定性输出 |
| doc / quiz / summary | 0.3 | 事实性内容，不可随机 |
| code | 0.4 | 代码逻辑需要一定灵活性 |
| mindmap | 0.3 | 结构化输出 |

### role: "system" 策略

所有 Agent 和 Judge 的系统提示词统一使用 `role: "system"` 而非 `role: "user"`。根据实验，system role 对 LLM 的约束力更强，LLM 更倾向于遵守其中的规则。

## 第三层：SafetyAgent 独立审核

### 解决的问题

前两层都在"生成前"和"生成中"设防。但 LLM 还是可能"跑偏"——比如参考资料说梯度下降学习率通常取 0.01，它生成时写成了 0.1。

这就需要**生成后的独立审核**。而且这个审核不能用规则（没有固定的"正确答案"可以比对），只能再用一次 LLM。

**为什么让 LLM 审 LLM 有效？** 生成 Agent 的 Prompt 是"请写一篇好文章"，SafetyAgent 的 Prompt 是"请找出错误"——角色不一样，提示词不一样，比自检有效得多。

### 在图中的位置

`graph.py:117-123` 定义了 SafetyAgent 的路由位置：

```python
# 所有 5 个生成 Agent → safety_agent
for agent_name in ["doc_agent", "mindmap_agent", "quiz_agent",
                    "code_agent", "summary_agent"]:
    graph.add_edge(agent_name, "safety_agent")

# safety → recommend → END
graph.add_edge("safety_agent", "recommend_agent")

# KG 和 clarify 绕过 safety
graph.add_edge("kg_agent", "recommend_agent")   # 数据工程操作
graph.add_edge("clarify_agent", END)             # 对话追问
```

### 审核流程

`safety_agent.py:23-89` 的实现：

```python
async def run(state: AgentState, config=None) -> AgentState:
    # 1. 取参考资料原文 + 生成内容预览（成本取舍）
    context = "\n".join(state.retrieved_docs[:max_ref])
    draft_preview = state.draft_content[:preview_chars]

    # 2. 构造审核 prompt，包含 4 项检查清单
    prompt = SYSTEM_PROMPT.format(context=context, draft_preview=draft_preview)

    # 3. 调用 LLM 审核（temperature=0.1，确定性输出）
    raw = await chat_completion(
        [{"role": "system", "content": prompt}],
        temperature=0.1,
        max_tokens=300,  # 只需返回 passed + issues
    )

    # 4. 解析审核结论
    result = json.loads(cleaned)
    passed = result.get("passed", True)
    issues = result.get("issues", [])

    # 5. 只审不修：无论是否通过，始终保留原始 draft_content
    state = state.model_copy(update={
        "safety_passed": passed,
        "final_content": state.draft_content,
    })
    if not passed and issues:
        state.metadata["safety_issues"] = issues
```

### 审核检查清单

SafetyAgent 的 Prompt 包含 4 项强制审核检查 (`prompts.yaml:355-359`)：

1. **事实准确性** — 正文中的关键事实、数据、公式是否可在参考资料中找到原文依据？
2. **引用有效性** — 每个 `[n]` 引用标记指向的内容是否确实来自对应的参考资料条目？是否存在引用不存在的编号（如正文有 `[4]` 但参考资料只有 3 条）？
3. **误导性表述** — 是否存在明显错误或误导性表达？
4. **学习场景适配** — 内容难度和深度是否适合学生学习场景？

### 关键设计决策

**决策一：只审不修**

```python
# safety_agent.py:65-69
# 无论是否通过，始终保留原始 draft_content（不让 LLM 重写文档）
state = state.model_copy(update={
    "safety_passed": passed,
    "final_content": state.draft_content,
})
```

如果让 SafetyAgent 修正内容，等于让"裁判"下场"踢球"，可能用一个错误替代另一个错误。审核不通过的标记（`safety_passed = false`）和具体问题（`issues`）已经给了下游系统足够的决策依据。

**决策二：只审核前 N 字和前 M 条参考资料**

```python
# safety_agent.py:44-47
max_ref = app_config.agents.safety.max_ref_docs        # 前 3 条
preview_chars = app_config.agents.safety.draft_preview_chars  # 前 500 字
```

这是成本取舍：全量审核 token 消耗太大，而经验表明前 500 字的质量基本代表了整体水平。

**决策三：fail-open 保守通过**

```python
# safety_agent.py:74-87
except json.JSONDecodeError:
    # JSON 解析失败 → 保守通过
    state = state.model_copy(update={
        "safety_passed": True, "final_content": state.draft_content,
    })
except Exception:
    # LLM 调用失败 → 保守通过
    state = state.model_copy(update={
        "safety_passed": True, "final_content": state.draft_content,
    })
```

SafetyAgent 自己也可能出错（JSON 格式不对、网络超时等）。这时候的策略是 **fail-open 而非 fail-closed**——宁可放行也不要阻断用户。原因：这是学习辅助系统，前两层防护已经过滤了大部分风险。

## 第四层：代码级硬约束 + 评估监控

### 4.1 RecommendAgent — kp_id 数据库校验

`recommend_agent.py:106-110` 实现了不依赖 LLM 的硬性校验：

```python
# 过滤掉 kp_id 不在知识图谱中的虚假推荐
if valid_kp_ids:
    valid_recs = [r for r in recommendations
                  if r.get("kp_id") in valid_kp_ids]
    if len(valid_recs) < len(recommendations):
        logger.warning(f"[RecommendAgent] 过滤掉 "
            f"{len(recommendations) - len(valid_recs)} 条无效推荐")
    recommendations = valid_recs
```

即使 Prompt 约束了 LLM "只能从可选知识点中选择"，LLM 仍可能编造不存在的 `kp_id`。**代码层的 DB 校验是最后一道硬防线**，直接过滤掉任何不在数据库中的虚假 ID。

### 4.2 safe_json_loads — 5 策略递进式 JSON 解析

`backend/agents/utils.py:70-155` 实现了 5 层递进的 JSON 安全解析，应对 LLM 输出的各种格式问题：

| 策略 | 处理的问题 |
|------|-----------|
| 1. 直接解析 | 正常 JSON |
| 2. 反斜杠修复 | LaTeX 命令（`\frac`、`\partial`）在 JSON 字符串中被错误转义 |
| 3. JSON 块提取 | LLM 在 JSON 前后添加了解释性文字 |
| 4. 截断修复 | `max_tokens` 导致 JSON 被截断（补全未闭合括号和引号） |
| 5. ast.literal_eval | Python 风格的 dict/list 字面量 |

这确保了 SafetyAgent 和所有 Agent 的 JSON 输出不会因格式问题导致审核失败。

### 4.3 Judge 系统 — 4 维度 LLM-as-Judge 评估

`backend/evaluation/judge.py` 实现了完整的自动化评估，直接量化幻觉：

| Judge | 评估维度 | 防幻觉作用 |
|-------|---------|-----------|
| **Judge 1: Chunk Relevance** | 每条 chunk 对查询的相关性（0/1/2） | 检测检索失败——喂给 LLM 无关内容是幻觉的根源 |
| **Judge 2: Faithfulness** | 逐句溯源：生成内容中每句话是否在参考资料中有依据 | **核心幻觉检测**：计算 `hallucination_rate = 1 - faithfulness_score` |
| **Judge 3: Completeness** | 知识点关键方面的覆盖程度 | 检测知识缺口——当 LLM 严格遵守参考资料但资料本身不完整时 |
| **Judge 4: Citation Accuracy** | `[n]` 引用标注与参考资料的实际对照 | 检测虚假引用——引用了不存在的编号或内容不匹配 |

**Faithfulness Judge 的核心逻辑** (`judge.py:46-66`)：

```
将答案拆解为独立的陈述句，逐句判断：
- "supported": 该陈述可以在参考资料中找到直接或间接依据
- "unsupported": 该陈述在参考资料中找不到依据（可能是捏造或来自 LLM 自身知识）
```

**Citation Accuracy Judge 的特殊处理** (`judge.py:414-419`)：

```python
if ref_idx <= len(retrieved_chunks):
    chunk = retrieved_chunks[ref_idx - 1]
else:
    return {"verdict": "vague", "explanation": "引用编号超出参考资料范围"}
```

对引用超出范围的直接标记为 vague，不给 LLM 自辩机会。

### 4.4 多 LLM 交叉验证

`judge.py:510-528` 可选启用多 LLM 交叉验证：

```python
if cross_validate:
    cv_providers = config.evaluation.cross_validation.providers
    if len(cv_providers) >= 2:
        cv_result = await self._cross_validate(...)
        cross_validation_disagreement = cv_result.get("disagreement", False)
```

用不同的 LLM provider 对同一份生成内容独立评分，当评分差异 > 0.3 时标记为不一致——避免单一 LLM 的评分偏差。

### 4.5 Golden Dataset 回归测试

`backend/evaluation/golden_dataset.py` 维护 15 条手写黄金查询（覆盖概念/算法/对比/应用四类），每次运行对比上一次结果：

- 任意指标下降 > 10% → 告警（防止防幻觉机制被意外破坏）
- faithfulness 硬性阈值 0.7（不达标 = FAIL）
- hallucination 警戒线 0.15

### 4.6 Health Check — 无 LLM 代理指标

`backend/evaluation/health_check.py` 提供无需 LLM 调用的轻量级监控：

| 指标 | 触发条件 | 关联的幻觉风险 |
|------|---------|--------------|
| `empty_result_rate > 30%` | 检索频繁返回空 | 退化到纯 LLM 生成，幻觉风险升高 |
| `score_p50 < 0.3` | 检索质量低 | 低质量参考资料被喂入 |
| `retrieval_latency_p95 > 5000ms` | 检索延迟高 | 系统降级风险 |

## 补充设计：KG 构建的特殊路由

知识图谱构建（`kg_agent`）是一个特殊场景——它**不经过 SafetyAgent**：

```python
# graph.py:122
graph.add_edge("kg_agent", "recommend_agent")  # KG 跳过 safety，直接到 recommend
```

为什么不审？
- KG 构建是**数据工程操作**（从文档中提取实体和关系），不是面向用户的文本生成
- 实体和关系是否正确，取决于后续的人工验证或用户反馈，而非另一轮 LLM 审核
- KG 构建的输出是结构化数据（节点名 + 关系类型），不是自由文本，幻觉风险天然更低

`clarify_agent`（追问澄清）也绕过 SafetyAgent，因为它是在对话历史基础上的简短回复，不生成新资源。

这体现了架构设计的原则：**根据任务性质决定是否需要审核**，而非一刀切。

## 实测效果

根据 `docs/design/rag/优化效果报告.md`（2026-05-28，15 条黄金查询）：

| 指标 | 优化前 | 优化后 | 变化 |
|------|--------|--------|------|
| **Faithfulness** | 0.445 | **0.915** | **+105%** |
| **Hallucination Rate** | 0.333 | **0.085** | **-74%** |
| **Citation Accuracy** | 0.750 | **0.867** | +16% |
| **Judge 成功率** | 60% | **100%** | +67% |

关键结论：
- 幻觉得到有效控制：从"三成内容为编造"降至"不到一成"，低于 15% 警戒线
- Faithfulness 跃升 105%：14/15 查询达标，唯一不达标的 `weight_decay`（0.50）是因为检索到的 chunk 缺少数学推导细节
- Completeness 下降（0.409 → 0.168）是 **anti-fabrication 的预期副作用**——LLM 不再填补参考资料中缺失的内容，完整度根因在检索覆盖不足
- Judge 可靠性从 60% 修复至 100%：解决了 max_tokens 截断、list 类型守卫、截断 JSON 修复三个 bug

## 附录：面试问答参考

### 标准回答（1-2 分钟）

> 我们这个项目是教育场景，内容准确性是底线，所以防幻觉不是选配功能，而是架构核心约束。我们做了**五层递进防护**，从检索前一直到生成后全覆盖。
>
> **第零层是查询改写。** 学生输入往往是口语化的，比如"那个公式怎么推导"，"那个"指代什么向量检索根本不知道。我们用 LLM 把用户消息和最近 6 轮对话历史一起做指代消解，改写成独立完整的检索语句，同时根据学生画像中的薄弱知识点让查询偏向薄弱领域。
>
> **第一层是检索质量控制。** 向量检索和关键词检索两路并行，RRF 融合。向量擅长语义泛化——查"过拟合"能返回讲"正则化"的内容；关键词擅长精确命中——查 API 名不会返回相近但不相关的东西。检索结果还要做相似度阈值过滤、关键词 re-rank、父块回填保证上下文完整、按 section 做 round-robin 多样排序避免 top-5 全来自同一节。最后 format_context 给每条引用打上 `[n]` 编号和来源页码。
>
> **第二层是 Prompt 约束。** 所有 6 个生成 Agent 的系统提示词按 NEVER/IMPORTANT 两级禁令重写。NEVER 层绝对禁止编造事实、凭记忆补充、跳过空引用检查——每条禁令带原因，防止 LLM 把它合理化。IMPORTANT 层强制要求每条关键陈述标注 `[n]` 引用、文末区分"来自参考资料"和"学习建议"。还有一个 Pre-generation Check，让 LLM 在动笔前先在心里自查参考资料覆盖了哪些子主题。temperature 对事实性 Agent 降到 0.3，prompt 用 system role 提升约束力。
>
> **第三层是独立审核。** 生成内容不会直接输出，先经过 SafetyAgent——用另一个 LLM 以完全不同的角色和提示词做四项审核：事实核查、引用验证、误导检测、学习场景适配。关键设计是只审不修——发现问题只标记不重写，避免"用一个错误替代另一个错误"。审核失败时 fail-open 保守通过，不阻断用户。
>
> **第四层是代码级硬约束加持续监控。** 比如推荐 Agent 返回的 kp_id 必须在数据库里真的存在，代码层直接过滤掉不存在的 ID——不依赖 LLM 自觉。我们还有 LLM-as-Judge 四维度评估：逐句 faithfulness 溯源、引用准确性验证、完整度评估，配合 golden dataset 做回归测试。实际效果是 faithfulness 从 0.445 升到 0.915，幻觉率从 33% 降到 8.5%。

### 精简版（30 秒）

> 五层防护：检索前 LLM 改写查询消除指代歧义 → 检索中向量+关键词混合检索互补盲区 → 生成中 NEVER/IMPORTANT 分级禁令强制引用追溯 → 生成后独立 SafetyAgent 四项审核只审不修 → 代码级硬校验加四维度 LLM-as-Judge 持续监控。实测 faithfulness 0.445→0.915，幻觉率 33%→8.5%。

### 常见追问

**"为什么用两个 LLM 做审核，自己审自己不行吗？"**

> 角色不一样。生成 Agent 的 prompt 是"请写一篇好文章"，SafetyAgent 的 prompt 是"请找出这篇文章的事实错误"——这是两种完全不同的心智模式。好比作者和审稿人，自己看自己的文章容易有盲区。而且我们做了"只审不修"：SafetyAgent 发现问题只标记 issues，不改内容，避免裁判下场踢球。

**"检索不到资料怎么办？"**

> 三层降级：向量库为空退空列表、embedding 失败退空列表、无结果过阈值退空列表。生成 Agent 拿到空上下文后，prompt 强制要求在开头打出 "⚠️ 当前知识库暂无此知识点的参考资料，以下内容基于通用知识，仅供参考"，明确告诉学生这内容不可验证。同时 `💡 补充` 前缀把 LLM 自身知识跟参考来源严格隔离。

**"怎么验证防幻觉真的有效？"**

> 我们有完整的评估体系：golden dataset 15 条手写查询涵盖概念/算法/对比/应用四类，每次运行对比上次结果，任意指标跌超 10% 就告警。Faithfulness Judge 做逐句溯源——把生成内容拆成独立陈述句，逐句判断在参考资料中有没有依据。还有多 LLM 交叉验证，用不同 provider 独立打分，差异超过 0.3 标记不一致。

**"SafetyAgent 发现了问题之后怎么处理？"**

> 当前是 fail-open：问题写入 `safety_issues` 列表，和评估数据一起记录到 collector，但不阻断内容输出。同时这些 issues 会作为辅助线索喂给 Faithfulness Judge，帮它更快定位疑似捏造的句子。为什么不做 fail-closed？因为这是学习辅助系统，不是医疗诊断，前四层已经过滤了大部分风险，审核失败宁可放行不要阻断用户体验。但随着数据积累，未来可以在高置信度场景下改为 fail-closed。
