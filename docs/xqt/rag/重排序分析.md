# 重排序分析

> 2026-05-26 初稿 → 2026-06-01 更新（方案一期已实施）

---

## 一、什么是重排序？为什么需要它？

### 问题

检索阶段（向量召回 + 关键词召回）返回 15 条候选 chunk，但：

1. **召回 ≠ 精确排序**：向量余弦相似度衡量的是"语义相近"，而非"直接回答问题的程度"。一条 chunk 可能和 query 语义高度相似，但实际上不包含用户要的答案。
2. **单路排序有盲区**：向量检索对精确术语不敏感，关键词检索对语义泛化不敏感，需要将两路结果按统一标准重排。

### 解决思路

**重排序（Reranking）**是在粗召回之后，用更强的模型或规则对候选集做精细排序：

```
粗召回（多路并行）              融合 + 重排序                      精排结果（Top-5）
──────────────────           ──────────────                    ────────────────
向量召回  15 条   │                              │
                 ├──→ RRF 跨路融合 ──→ 关键词加权 ──→ 最终 Top-5
关键词召回 15 条  │       （排名级合并）    （0.25 boost）   （送入 LLM）
```

**收益**：重排序环节决定了最终哪些 chunk 能进入 LLM 的上下文窗口——这是 RAG 质量的最后一道关卡。

## 二、当前重排序机制（三层递进）

项目的重排序并非单一环节，而是**三层递进式**的精排管线：

### 2.1 第一层：RRF 跨路融合（排名级）

`backend/rag/retriever.py:_rrf_fusion_cross_path` (line 259)

两路召回的分数量纲天然不可比——向量路径返回余弦相似度（0~1），关键词路径返回匹配词数量（离散整数）。RRF 只看排名不看原始分数，从根上规避了归一化问题。

```python
def _rrf_fusion_cross_path(
    path_results: dict[str, list[RetrievedChunk]],
    k: int = 60,
    weights: Optional[dict[str, float]] = None,
) -> list[RetrievedChunk]:
    for path_name, ranked_list in path_results.items():
        w = weights.get(path_name, 1.0)
        for rank, chunk in enumerate(ranked_list, 1):
            rrf_score = w / (k + rank)        # RRF 核心公式
            # 同一 chunk 在多路中出现 → 累加 RRF 分
            if chunk.chunk_id in fused:
                fused[chunk.chunk_id] = (chunk, existing_score + rrf_score)
            else:
                fused[chunk.chunk_id] = (chunk, rrf_score)
    # 按 RRF 累积分降序
```

| 参数 | 值 | 说明 |
|------|-----|------|
| `k` | 60 | RRF 平滑常数，越大各路权重越均匀 |
| `vector_weight` | 1.0 | 向量召回路权重 |
| `keyword_weight` | 1.0 | 关键词召回路权重 |

配置在 `configs/config.yaml` 的 `rag.hybrid` 节。

### 2.2 第二层：关键词重叠加权（分数级）

`backend/rag/retriever.py:_rerank_by_keyword_overlap` (line 621)

在 RRF 融合之后，对合并结果中的每条 chunk 按 query 关键词命中率进行微调加分。

**与初版文档（2026-05-26）的差异**：此函数已按方案一完成优化：

| 项目 | 初版（已废弃） | 当前实现 |
|------|--------------|---------|
| 分词方式 | 正则 `[\u4e00-\u9fff]{2,}` | **jieba 精确模式**（与关键词召回路共用 `_tokenize_keywords()`） |
| 加分幅度 | 固定 0.15 | **0.25**（由 `config.rag.re_rank_keyword_boost` 控制） |
| 原始分数保存 | 直接覆盖 | 保存到 `metadata["cosine_score"]`，`score` 为调整后的值 |

```python
def _rerank_by_keyword_overlap(query: str, chunks: list[RetrievedChunk]) -> list[RetrievedChunk]:
    keywords = _tokenize_keywords(query)  # jieba 分词，与关键词召回路一致

    for chunk in chunks:
        if "cosine_score" not in chunk.metadata:
            chunk.metadata["cosine_score"] = chunk.score  # 保留原始分数

        text_lower = chunk.text.lower()
        overlap = sum(1 for kw in keywords if kw.lower() in text_lower)
        boost = min(overlap / max(len(keywords), 1), 1.0) * config.rag.re_rank_keyword_boost
        chunk.score = round(chunk.score + boost, 4)

    return sorted(chunks, key=lambda c: c.score, reverse=True)
```

**设计考量**：
- jieba 分词与关键词召回路共用 `_tokenize_keywords()`，确保一致性
- 停用词过滤（中英文共 80+ 词），单字过滤（`keyword_min_length=2`）
- 加分幅度 0.25 是经验值——太小对排序影响有限，太大可能把低质量 chunk 拉到前面

### 2.4 完整管线（当前实际执行顺序）

```
retrieve_hybrid(query)
  │
  ├─1. 并行召回（prefetch_count=15 条/路）
  │     ├── vector path:   embedding API → HNSW cosine 检索 → score≥0.5 过滤
  │     └── keyword path:  jieba 分词 → PostgreSQL ILIKE 匹配
  │
  ├─2. RRF 跨路融合（_rrf_fusion_cross_path）
  │     两路 chunk 按排名合并，同 chunk_id 累加 RRF 分
  │     结果按 RRF 累积分降序，去重
  │
  ├─3. 关键词加权重排（_rerank_by_keyword_overlap）
  │     每条 chunk.score += keyword_overlap_ratio × 0.25
  │     保留原始 cosine_score 到 metadata["cosine_score"]
  │
  ├─4. 父块回填 + 去重（_resolve_parent_chunks）
  │     子块映射到父块文本，同父块的子块只保留分数最高者
  │
  ├─5. 截断（_n_results=5）
  │
  └─6. format_context(query, chunks)
        ├── 多样感知排序（_diversify_order: section round-robin）
        ├── token 预算控制（context_max_tokens=3000）
        └── citation 编号安全（截断告警）
```

### 2.5 Score 的生命周期

```
pgvector cosine distance
  → 1 - distance = score (0~1)
  → RRF 融合（score 被替换为 RRF 累积分）
  → keyword boost (+0.25 max)，原始分保存到 metadata["cosine_score"]
  → 按 score 降序排列
  → diversity round-robin 重排（不改 score，只调整展示顺序）
  → 截断为 top-5 → 送入 format_context()
```

**关键发现**：score 信息**从未直接传递给 LLM**。`format_context()` 只输出编号 + 来源 + 文本内容，LLM 不知道哪条 chunk 更相关。这意味着重排序的价值完全体现在"把更好的 chunk 排在更前面以通过 token 预算截断"这一环节。

## 四、可选升级方案

以下方案尚未实施，作为后续优化储备。

### 方案 A：API 重排序服务（Cohere / Jina / Voyage）⭐⭐⭐⭐

**做法**：在候选集（15 条）上调用第三方重排序 API。

```
候选 15 条 → API reranker (Cohere Rerank / Jina Reranker) → 取 Top-5
```

**代表性服务**：

| 服务 | 模型 | 价格 | 延迟 |
|------|------|------|------|
| Cohere Rerank 3.5 | 多语言 | $2/1M 次搜索 | ~200ms |
| Jina Reranker v2 | 多语言 | 免费额度 1M tokens/月 | ~300ms |
| Voyage Rerank | 英文为主 | $0.1/1K 次 | ~150ms |

| 维度 | 评估 |
|------|------|
| 改造成本 | 中。新增配置节 + `_rerank_neural()` + pipeline 集成 |
| 额外延迟 | +200~500ms（取决于服务商） |
| 额外成本 | Jina 有免费额度；Cohere $2/1M 次，日均 1000 次 ≈ $0.06/日 |
| 效果提升 | 显著。语义级重排，能理解 query-chunk 深层关系 |
| 风险 | 低。服务不可用时降级到关键词重排 |

### 方案 B：本地重排序模型（BGE-Reranker-v2-m3）⭐⭐⭐⭐⭐

**做法**：部署本地 BGE-Reranker-v2-m3 模型（Cross-Encoder），在进程内完成重排序。

```python
from sentence_transformers import CrossEncoder

model = CrossEncoder("BAAI/bge-reranker-v2-m3")
pairs = [[query, chunk.text] for chunk in chunks]
scores = model.predict(pairs, batch_size=16)
```

| 维度 | 评估 |
|------|------|
| 改造成本 | 中。新增 `sentence-transformers` 依赖 + 模型加载 + pipeline 集成 |
| 额外延迟 | +50~200ms（CPU）/ +10~30ms（GPU） |
| 额外成本 | 零 API 费用。模型 ~2.5GB，首次加载 ~2s |
| 内存占用 | ~5GB（GPU）/ ~3GB（CPU） |
| 效果提升 | 显著。BGE-Reranker-v2-m3 在中英文 benchmark 排名前列 |
| 风险 | 低-中。对机器资源有要求；需管理模型生命周期 |

**与方案 A 的对比**：

| | API 重排序（方案 A） | 本地模型（方案 B） |
|------|------|------|
| 延迟 | 200-500ms（网络） | 50-200ms（本地计算） |
| 成本 | 按量付费 | 零 API 费用（但占机器资源） |
| 质量 | Cohere >= BGE | BGE 多语言优秀 |

## 六、重排序与 format_context 的衔接

重排序的最终效果通过 `format_context()` 体现（`backend/rag/retriever.py:408`）：

1. **Diversity round-robin** 确保不同 section 的 chunk 交错排列
2. **Token 预算截断**（默认 3000 tokens）——排前面的 chunk 优先保留，排后面的被丢弃
3. **Citation 编号安全**——若发生截断，显式告知 LLM 可引用的编号范围

这意味着重排序的意义在于"**把更重要的 chunk 放到更前面**"——在 token 预算有限时，排名顺序直接决定了哪些信息能被 LLM 看到。

## 七、后续建议

1. **方案 B（BGE-Reranker-v2-m3）是推荐方向**：候选集仅 15 条，批处理推理极快（50-200ms），零 API 成本，数据不出进程，适合项目的中英混合知识库
2. **插入点清晰**：RRF 融合后 → `_rerank_neural()` → 关键词加权降级 → 父块回填 → 截断
3. **降级链完整**：BGE-Reranker 不可用 → 关键词加权（当前方案），保证核心功能不中断
4. **评估系统就绪**：可通过 golden eval 量化引入前后的 P@5 / MRR / Faithfulness 变化

## 八、不做的事及原因

| 方案 | 原因 |
|------|------|
| LLM-as-Reranker（用当前 LLM 打分） | 15 条 × 200 tokens = 3000 tokens 输入，延迟 1-5s，成本等于一次完整生成 |
| 训练专用重排序模型 | 无标注数据，无训练基础设施，ROI 极低 |
| 完全移除关键词重排 | 零成本的兜底方案，适合作为神经网络不可用时的降级路径 |
| 对每条 query 调用多个重排序器投票 | 延迟和成本翻倍，边际收益递减 |
