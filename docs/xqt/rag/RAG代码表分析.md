# RAG 系统代码与表格处理能力分析报告

> 分析日期：2026-05-25 | 分析范围：`backend/rag/`、`backend/db/vector.py`、`backend/db/models.py`、`backend/evaluation/`、`configs/config.yaml`

---

## 一、总体结论

**当前 RAG 系统对代码和表格的处理能力不足。** 系统在设计上以"自然语言散文"为核心假设，缺乏对代码块和表格等结构化内容的识别、保护和检索优化。以下是逐环节的详细评估。

---

## 二、各环节分析

### 2.1 文档加载（`backend/rag/loader.py`）

| 格式 | 解析库 | 策略 |
|------|--------|------|
| PDF | `pymupdf4llm` → Markdown | 主路径，回退到 `PyPDFLoader` |
| DOCX | `mammoth` → Markdown | 单路径 |
| MD/TXT | `path.read_text()` | 直接读取 |

**代码/表格相关处理：无。**

- `pymupdf4llm` 和 `mammoth` 均能将 PDF/DOCX 中的表格转换为 Markdown 管道表格（pipe table），代码块也能保留在 Markdown 输出中，但 `loader.py` 本身不作任何代码/表格的识别、标记或分类。
- `TextChunk` 数据类（第 31-69 行）只有 `text`、`doc_id`、`source_path`、`page`、`section` 和 `metadata` 字段，**没有 `content_type` 字段**（无法标记某块是"代码"或"表格"）。
- 自动检测仅限 **语言检测** (`_detect_language()`，第 570-586 行)，在 `metadata["language"]` 中写入 `"zh"`/`"en"`/`"mixed"`，与代码/表格无关。

### 2.2 文本切分（`backend/rag/loader.py`）

切分分两阶段：

**阶段一：按 Markdown 标题切分（`_split_markdown_by_headers`，第 464-532 行）**

- 按 `#` / `##` / `###` 三级标题作为章节边界
- **代码块保护：有。** 切分前先用正则提取所有围栏代码块（`` ``` ... ``` ``），替换为占位符，切分后再还原。这防止了代码中的 `#`（如 Python 注释、shell shebang）被误识别为标题。
- **表格保护：无。** 表格行以 `|` 开头，与标题无关，此阶段不会破坏表格，但也无特殊关照。

**阶段二：按字符数切分（`split_text`，第 252-298 行）**

- `chunk_size = 500` 字符，`overlap = 50` 字符
- 有句子边界感知：在切分点附近 20% 范围内找 `。！？.!?\n` 作为切分位置
- **代码块保护：无。** 500 字符边界可以切在代码块中间任意位置，破坏代码的语法完整性。
- **表格保护：无。** 一张超过 500 字符的 Markdown 表格会被截断，导致：
  - 表头与数据行分离
  - 单行被拦腰截断
  - 表格的语义信息（列对应关系）丢失

**影响举例：**

```
# 原始表格（约 600 字符的 Markdown 管道表格）
| 算法 | 时间复杂度 | 空间复杂度 | 适用场景 | 优缺点 |
|------|-----------|-----------|---------|--------|
| ...（多行数据）... |

# 切分后可能变成：
Chunk N:   | 算法 | 时间复杂度 | 空间复杂度 | 适用场景 | 优缺点 |
           |------|-----------|-----------|---------|--------|
           | 冒泡排序 | O(n²) | ...（截断）

Chunk N+1: | ... | 堆排序 | O(n log n) | O(1) | 大数据量 | 不稳定 |
```

此时 Chunk N 和 Chunk N+1 各自都不是一张完整的表格，检索召回后 LLM 无法理解残缺表格的含义。

### 2.3 向量嵌入（`backend/rag/indexer.py` + `backend/services/llm.py`）

| 项目 | 详情 |
|------|------|
| 嵌入模型 | DashScope `text-embedding-v4`，1024 维 |
| 批量限制 | 单次 API 最多 25 条 |
| 并发数 | 8 |
| 增量索引 | 基于 MD5 content_hash 去重 |

**代码/表格相关处理：无。**

- 所有文本内容（散文、代码、表格、列表）统一用同一个模型嵌入，不做任何内容类型区分。
- 嵌入时不添加任何结构化预处理（如代码语法高亮 token、表格结构标记）。
- `text-embedding-v4` 是通用嵌入模型，对代码语义的捕获能力未经专项评估。通用模型对代码的嵌入质量通常低于专用代码模型（如 CodeBERT、UniXcoder 等）。

### 2.4 向量存储（`backend/db/models.py` + `backend/db/vector.py`）

**`document_chunk` 表结构：**

| 列 | 类型 | 说明 |
|----|------|------|
| `id` | `BigInteger` (PK) | 雪花 ID |
| `chunk_id` | `String(128)` (UNIQUE) | `{doc_id}_{chunk_index}` |
| `doc_id` | `String(128)` | 所属文档 ID |
| `text` | `Text` | 文本内容 |
| `embedding` | `Vector(1024)` | 嵌入向量 |
| `source` | `String(512)` | 原始文件路径 |
| `page` | `Integer` | PDF 页码 |
| `section` | `String(256)` | 章节标题 |
| `user_id` | `String(64)` | 用户隔离 |
| `metadata` | `JSONB` | 扩展元数据 |
| `content_hash` | `String(32)` | MD5 增量对比 |

**代码/表格相关设计：无。**

- 没有 `content_type` 列或 metadata 字段。
- 索引写入时（`indexer.py` 第 119-134 行）仅写入 `doc_id`、`source`、`page`、`section`、`user_id`、`content_hash` 以及来自 loader 的 `metadata`（目前仅有 `language` 和 `course`）。
- 检索时无法按内容类型过滤（无法实现"只检索代码块"或"排除表格碎片"）。
- 检索算法：pgvector 余弦距离 + HNSW 索引（`ef_search=100`），没有针对代码/表格的相似度计算优化。

### 2.5 检索（`backend/rag/retriever.py`）

**检索流程：**

1. 查询嵌入 → 2. 向量相似度搜索（`prefetch_count = n_results × 3`，最少 15 条）→ 3. 分数阈值过滤（`score_threshold = 0.5`）→ 4. 关键词重叠加权（+0.15 boost）→ 5. Top-N 截断（默认 `n_results = 5`）

**代码/表格相关处理：无。**

- 关键词重叠 re-rank（`_rerank_by_keyword_overlap`，第 225-245 行）：提取查询中的中文双字词（`[\u4e00-\u9fff]{2,}`）和英文三字词（`[a-zA-Z]{3,}`）与 chunk 文本匹配。这对自然语言有效，但对代码符号（如 `for`、`int`、`def` 等短关键字会被 3 字符限制过滤掉）和表格结构（列名通常是短英文词）几乎无效。
- 没有 content_type 元数据过滤能力。
- `format_context` 函数（第 161-210 行）支持展示 `chunk_type`、`language`、`difficulty` 等元数据标签，但目前数据库中不存在 `chunk_type` 数据，这些标签永远不会被渲染。

### 2.6 评估体系（`backend/evaluation/`）

评估框架完善（metrics、collector、judge、reporter），但：

- **没有针对代码/表格检索质量的专项评估。**
- 没有代码/表格查询的测试数据集。
- 4 维度 LLM-as-Judge（相关性 / 忠实性 / 完整性 / 引用准确性）均为通用维度，无不代码/表格特定标准（如"代码是否可运行"、"表格结构是否完整"）。
- `loader.py`、`indexer.py`、`retriever.py`、`vector.py` 核心模块均无单元测试。

## 三、问题汇总

| # | 问题 | 严重程度 | 影响 |
|---|------|---------|------|
| 1 | **切分破坏代码块完整性** | 高 | 代码被截断后无法理解，LLM 生成错误代码 |
| 2 | **切分破坏表格结构完整性** | 高 | 表格截断后语义丢失，LLM 无法正确回答表格相关问题 |
| 3 | **缺少 `content_type` 元数据** | 中 | 无法按内容类型过滤，代码/表格检索混在普通文本中 |
| 4 | **无内容类型感知的检索策略** | 中 | 代码查询（如"如何实现XXX"）可能召回不相关的散文而非代码示例 |
| 5 | **关键词 re-rank 对代码/表格无效** | 中 | 代码关键字短（`for`、`if`、`def`），被 3 字符限制过滤 |
| 6 | **通用嵌入模型对代码语义捕获有限** | 中 | 代码语义检索精度可能不足 |
| 7 | **缺少代码/表格检索质量评估** | 低 | 无法量化问题严重程度，改进效果无法衡量 |
| 8 | **核心 RAG 模块无单元测试** | 低 | 修改切分/检索逻辑时缺少回归保护 |

## 四、改进建议

### 短期（低成本、高收益）— **已于 2026-05-25 实施**

1. **代码块边界保护（~20 行代码）** ✅ 已实施
   - 在 `split_text()` 中照搬 `_split_markdown_by_headers` 已有的代码块占位符策略：切分前提取 `` ``` ... ``` ``，切分后还原。
   - 或者更简单：检测切分点是否落在代码块内，若是则前移至代码块起始位置。

2. **表格边界保护（~15 行代码）** ✅ 已实施
   - 在 `split_text()` 中检测切分点是否落在 Markdown 表格区域（连续以 `|` 开头的行），若是则前移至表格开始或后移至表格结束。
   - 对超长表格（单张 > 500 字符），保留表头行在每个分片中：
     ```
     Chunk N:   表头 + 数据行 1-5
     Chunk N+1: 表头（重复） + 数据行 6-10
     ```

3. **降低关键词 re-rank 的英文最小长度（1 行修改）** ✅ 已实施
   - 将 `retriever.py` 第 233 行的 `{3,}` 改为 `{2,}`，使 `for`、`if`、`int` 等常见代码关键字能被匹配。

### 中期（中等投入、显著改进）

4. **增加 `content_type` 元数据**
   - 在 loader 中添加启发式检测：围栏代码块 → `"code"`，连续管道表格行 → `"table"`，其余 → `"text"`。
   - 写入 metadata JSONB，索引和检索链路直接复用现有基础设施，无 schema 变更。
   - 在 retriever 中支持 `where={"content_type": "code"}` 过滤。

5. **实现混合检索（当前系统的自然延伸）**
   - 系统已有 `retrieve_with_queries()` 多查询检索基础设施。
   - 对含代码关键字的查询（如包含 `def`、`class`、`import`、`function`、`代码`、`示例`），自动追加代码导向的子查询。
   - 同理，对含表格关键字的查询（如 `对比`、`区别`、`参数`），追加表格导向的子查询。

### 长期（架构级优化）

6. **引入专用代码嵌入模型**
   - 对标记为 `content_type="code"` 的 chunk 使用 CodeBERT / UniXcoder 等代码专用模型嵌入。
   - 需要额外的嵌入模型部署，但可显著提升代码检索精度。

7. **结构化表格处理**
   - 将表格解析为结构化 JSON（列名 → 值映射），以结构化形式存储。
   - 检索时将自然语言问题转为对表格结构的查询，而非纯语义匹配。

8. **建立代码/表格检索评估基准**
   - 从知识库中抽取含代码/表格的文档，人工标注 20-50 条 (query, relevant_chunk_ids) 对。
   - 集成到现有 evaluation 框架中，持续监控检索质量。

## 四-B、短期方案实施详情（2026-05-25）

### 修改文件

| 文件 | 改动 | 行号 |
|------|------|------|
| `backend/rag/loader.py` | 新增 `_find_table_regions()` 函数 | 252-268 |
| `backend/rag/loader.py` | 重写 `split_text()`：增加代码块占位符保护 + 表格边界感知 + 表头重复 | 270-395 |
| `backend/rag/retriever.py` | `_rerank_by_keyword_overlap()` 英文最小长度 `{3,}` → `{2,}` | 233 |

### 实施策略

**代码块保护：**
- 切分前用正则 ```` ```[\s\S]*?``` ```` 提取所有围栏代码块，替换为 `__CODE_BLOCK_N__` 占位符
- 在占位符文本上执行字符级切分（占位符短，不会在中间被切断）
- 切分完成后还原占位符为原始代码块
- 结果：代码块始终保持语法完整，永不截断

**表格边界保护：**
- `_find_table_regions()` 用正则识别 Markdown 管道表格（表头行 + 分隔行 + 数据行）
- 在 `split_text()` 的切分循环中：
  - 若切分点落在表格区域内，且表格能放入当前 chunk → 扩展到表格结束
  - 若表格太大 → 在行尾（`\n`）处切分，保证每行完整
  - 若 chunk 从表格内部开始（续前表）→ 自动重复表头+分隔行
  - 若重叠区域落在表格内 → 对齐到行首，避免产生残缺行

**关键词 re-rank：**
- 英文词最小长度从 3 降为 2，使 `if`、`or`、`in`、`to` 等代码高频短关键字可参与重加权
- 中文保持 2 字及以上不变（已足够短）

### 边界情况处理

| 场景 | 处理方式 |
|------|---------|
| 代码块嵌套在表格内 | 先提取代码块（占位符），再检测表格，顺序正确 |
| 表格无数据行（仅表头+分隔行） | `(?:...)*` 支持 0 行，正常匹配 |
| 表格含对齐冒号（`|:---|:---:|`） | 分隔行正则 `[-:| ]+` 覆盖 |
| chunk_size 大于表格 | 整个表格保留在一个 chunk 中 |
| 表格在文本末尾（无尾随换行） | 正则 `[ \t]*\n` 不要求末尾换行，`$` 隐式匹配 |
| 代码块超长（> chunk_size） | 占位符还原后整个代码块在单个 chunk 中（chunk 可能超长但完整性优先） |

### 验证结果

- 项目测试套件：**150 项全部通过**，0 失败，0 退化
- 手工验证：代码块完整性、表格边界保护、表头重复、重叠行对齐均正确
