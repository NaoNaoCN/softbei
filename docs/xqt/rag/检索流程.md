# RAG 检索流程详解

> 最后更新：2026-05-27

本文档从"一个查询如何到达 LLM"的视角，串联父子切割、HNSW 向量检索、元数据、jieba 分词、tsvector 关键词检索等机制，说明它们各自的作用和相互影响。

---

## 1. 总体数据流

```
                          ┌──────────────────────┐
                          │   索引阶段（写入）      │
                          └──────────────────────┘
文档文件 (PDF/DOCX/MD)
  → loader.py        解析 + 切分 → TextChunk 列表
  → indexer.py       全量替换：delete_by_doc_id → embed → upsert
  → vector.py        INSERT INTO document_chunk (含 embedding, metadata, text_search)
  → PostgreSQL        数据沉淀在 document_chunk 表

                          ┌──────────────────────┐
                          │   检索阶段（读取）      │
                          └──────────────────────┘
用户查询 (query string)
  → retriever.py     retrieve() 或 retrieve_hybrid()
  → vector.py        query_documents() 向量检索 / query_keyword() 关键词检索
  → PostgreSQL        HNSW <=> 余弦距离 / tsvector @@ tsquery
  → retriever.py     _parse_results → _rerank → _resolve_parent_chunks → truncate
  → format_context() 格式化为 LLM prompt 字符串
```

**关键区别**：索引阶段的切分由 `loader.py` 的 `chunk_size`/`parent_max_chars` 控制；检索阶段的重排和父块回填由 `retriever.py` 的 `_rerank_by_keyword_overlap`/`_resolve_parent_chunks` 控制。两者解耦——切分策略变化不影响检索逻辑。

## 2. 数据模型：document_chunk 表

```sql
CREATE TABLE document_chunk (
    id              BIGINT PRIMARY KEY,          -- Snowflake 主键
    chunk_id        VARCHAR(128) UNIQUE NOT NULL, -- 业务唯一标识
    doc_id          VARCHAR(128) NOT NULL,        -- 所属文档 ID
    collection_name VARCHAR(64) DEFAULT 'knowledge_base',
    text            TEXT NOT NULL,                -- 原始文本
    embedding       vector(1024),                -- 语义向量 (BGE-M3 / text-embedding-v4)
    source          VARCHAR(512),                 -- 原始文件路径
    page            INTEGER,                      -- 页码 (PDF 来源)
    section         VARCHAR(256),                 -- 章节标题
    user_id         VARCHAR(64),                  -- 上传用户 ID（NULL=全局共享）
    parent_chunk_id VARCHAR(128),                 -- 指向父块的 chunk_id（子块用）
    is_parent       BOOLEAN DEFAULT FALSE,        -- 是否为父块
    text_search     TSVECTOR,                     -- 全文检索向量（jieba 分词 → to_tsvector）
    metadata        JSONB DEFAULT '{}',           -- 扩展元数据（language, chunk_type, ...）
    created_at      TIMESTAMP
);
```

### 各列的检索角色

| 列 | 写入方 | 读取方 | 作用 |
|----|--------|--------|------|
| `embedding` | indexer → upsert_documents | query_documents (<=>) | 语义相似度排序 |
| `text_search` | indexer → upsert_documents | query_keyword (@@ tsquery) | 关键词精确匹配 |
| `is_parent` | indexer（父块=True，子块=False） | query_documents / query_keyword（WHERE is_parent=FALSE） | 排除父块，只检索子块 |
| `parent_chunk_id` | indexer（子块记录父块 ID） | retriever._resolve_parent_chunks | 子块→父块映射，大上下文回填 |
| `metadata` | indexer（language, chunk_type 等） | _parse_results → RetrievedChunk.metadata → format_context | 标签渲染（[定义, 中文, 进阶]） |
| `user_id` | indexer | 所有检索（WHERE user_id = ...） | 多用户数据隔离 |
| `collection_name` | upsert_documents | 所有检索（WHERE collection_name = ...） | 集合隔离（当前固定 "knowledge_base"） |

## 3. 索引阶段（写入）

### 3.1 切分策略

`loader.py::_parse_markdown_to_chunks()` 是切分的入口。根据 `config.rag.parent_chunking.enabled` 的值：

```
enabled=false（当前默认）
  _parse_markdown_to_chunks()
    → _split_markdown_by_headers()  按 Markdown 标题分节
    → split_text()                 每节按 chunk_size=500 切分，overlap=50
    → 所有 chunk 都是子块，is_parent=False，无 parent_chunk_id

enabled=true
  _parse_markdown_to_chunks_parent_child()
    → _split_markdown_by_headers()  按 Markdown 标题分节
    → _split_into_parents()        每节按 parent_max_chars=2000 切父块
    → split_text()                 每个父块按 chunk_size=500 切子块
    → 输出：父块(is_parent=True) + 子块(is_parent=False, parent_chunk_id=父块ID)
```

**父子切割的动机**：小 chunk（500 字符）适合精确检索，但上下文不足。通过父子机制，检索时先用小 chunk 精确匹配，再回填大 chunk（2000 字符）给 LLM，兼顾精度和上下文完整性。

### 3.2 写入流程

`indexer.py::index_chunks()` 三步全量替换：

```
Step 1: 收集 unique_doc_ids → 对每个 doc_id 执行 delete_by_doc_id()
        （清空该文档所有旧 chunk，包括旧的 embedding 和 text_search）

Step 2: 写入父块（如果有）
        - embedding = NULL（父块不参与向量检索）
        - text_search = to_tsvector('simple', jieba分词结果)
        - is_parent = True

Step 3: 写入子块（分批，每批 ≤ API_MAX_BATCH=10）
        - embedding = get_embeddings_batch(text)  → 调用 DashScope text-embedding-v4
        - text_search = to_tsvector('simple', jieba分词结果)
        - is_parent = False
        - parent_chunk_id = 父块 chunk_id（如果有）
```

### 3.3 text_search 的生成

`indexer.py::_tokenize_for_tsvector()`：

```python
def _tokenize_for_tsvector(text: str) -> str:
    import jieba
    words = jieba.lcut(text, cut_all=False)        # 精确模式分词
    tokens = [w.strip() for w in words if len(w.strip()) >= 1]
    return " ".join(tokens)                        # 空格连接
```

然后在 SQL 中：`to_tsvector('simple', '分词 结果 空格 连接')`。

**为什么用 `'simple'` 配置**：jieba 已经完成了中文分词，不需要 PostgreSQL 再做 stemming 或 stop-word 处理。`'simple'` 配置仅按空格分隔并转为小写，对 jieba 输出的中文 token 没有副作用。

### 3.4 embedding 的生成

```python
# indexer.py → _embed_batch() → llm.get_embeddings_batch()
# 调用 DashScope text-embedding-v4 API，每批最多 10 条
# 输出 1024 维 float 向量
# 父块不调用 embedding API（embeddings=[None]）
```

## 4. 检索阶段（读取）

### 4.1 向量检索（retrieve）

```
retrieve(query)
  │
  ├─ get_embedding(query)                     # query → 1024维向量
  ├─ query_documents(embedding, n*3)          # 预取 3x 候选
  │    └─ SQL: SELECT ..., embedding <=> CAST(:emb AS vector) AS distance
  │        WHERE is_parent = FALSE            # 只检索子块（父块无 embedding）
  │        ORDER BY distance                  # <=> 是余弦距离（0=同向, 2=反向）
  │        LIMIT :n_results
  │        SET LOCAL hnsw.ef_search = 100     # HNSW 检索精度
  │
  ├─ _parse_results(raw, threshold=0.5)       # distance→score: score = 1.0 - distance
  │    └─ 过滤 score < 0.5 的噪声结果
  │
  ├─ _rerank_by_keyword_overlap(query)        # jieba 关键词重叠加权（最高 +0.25）
  │
  ├─ _resolve_parent_chunks(chunks)           # 子块→父块回填 + 去重
  │
  └─ truncate to n_results=5                  # 截断为最终结果
```

### 4.2 关键词检索（retrieve_keyword）

```
retrieve_keyword(query)
  │
  ├─ _tokenize_keywords(query)                # jieba.lcut → 过滤停用词/单字
  ├─ query_keyword(keywords, n_results)
  │    └─ SQL: SELECT ..., ts_rank(text_search, to_tsquery('simple', 'kw1 & kw2 & ...')) AS rank
  │        WHERE is_parent = FALSE
  │          AND text_search IS NOT NULL       # 排除未回填的旧数据
  │          AND text_search @@ to_tsquery('simple', :tsquery)
  │        ORDER BY rank DESC
  │        LIMIT :n_results
  │
  └─ _parse_results(raw, threshold=0.0)       # ts_rank 已有排序，不设阈值
       └─ distance = 1.0 - rank → score = 1.0 - (1.0 - rank) = rank
```

**ILIKE vs tsvector 对比**：

| 维度 | 旧方案（ILIKE） | 新方案（tsvector/tsquery） |
|------|----------------|--------------------------|
| 匹配方式 | `text ILIKE '%kw%'`（子串） | `text_search @@ to_tsquery`（词级） |
| "学习"是否匹配"学生" | 是（子串误匹配） | 否（词边界精确） |
| 排序 | match_count（命中数/最大值） | ts_rank（词频+文档长度归一化） |
| 索引 | 无（全表扫描） | GIN 索引 |
| 分词 | 查询时分词，索引时不分词 | 索引时分词（jieba），查询时分词（jieba） |

### 4.3 混合检索（retrieve_hybrid）

当 `config.rag.hybrid.enabled = true` 时启用。向量和关键词两路**并行**执行，然后 RRF 融合。

```
retrieve_hybrid(query)
  │
  ├─ asyncio.gather ──────────────────┐
  │                                    │
  ├─ _vector_path()                   ├─ _keyword_path()
  │    retrieve(n*3)                  │    retrieve_keyword(n*3)
  │                                    │
  └─ path_results = {"vector": [...], "keyword": [...]}
  │
  ├─ _rrf_fusion_cross_path(path_results)    # RRF 跨路融合
  │    └─ 对每个 path 的每个 chunk：
  │         rrf_score = weight / (rrf_k + rank)
  │         同 chunk_id 出现多路 → 累加 rrf_score
  │         排序：按 rrf_score 降序
  │
  ├─ _rerank_by_keyword_overlap(query, merged)
  ├─ _resolve_parent_chunks(merged)
  └─ truncate to n_results
```

**并行机制**：向量路径和关键词路径各自独立执行，一个失败不影响另一个。RRF 只看排名不看绝对分数，因此两路的分数量纲差异（余弦相似度 vs ts_rank）不影响融合结果。

## 5. 跨切机制详解

### 5.1 父块回填（_resolve_parent_chunks）

**适用范围**：所有检索路径（`retrieve` 和 `retrieve_hybrid` 都会调用）。

**为什么需要**：子块 500 字符对 LLM 而言上下文不足。父块 2000 字符提供更完整的段落。

**算法**：

```
输入：re-rank 后的子块列表（已按 score 降序）

1. 收集映射：child_chunk_id → parent_chunk_id（从 metadata 读取）
2. 去重：同一 parent_chunk_id 只保留 score 最高的子块
3. 批量查询：SELECT chunk_id, text FROM document_chunk
              WHERE chunk_id = ANY(parent_ids) AND is_parent = TRUE
4. 回填：用父块 text 替换子块 text，保留子块的 score 和来源信息
5. 无父块的子块：保留原样（向后兼容旧数据）
```

**对 mix（混合检索 RRF 融合后）的影响**：RRF 融合时 `chunk_id` 去重已经发生——向量和关键词可能命中同一个子块。但 `_resolve_parent_chunks` 是在 RRF 融合之后运行的，它做的是**不同子块→同一父块**的去重。两者不冲突。

### 5.2 RRF 融合（_rrf_fusion_cross_path）

**公式**：`sum(weight / (k + rank_per_path))`，其中 k=60。

**含义**：
- k=60 较大 → 排名靠前的 chunk（rank=1..5）的分数差异不大，减小了"排名第一"的绝对优势
- 权重默认均为 1.0 → 两条路径平权
- 如果某个 chunk 在向量路径排名第 1（rrf=1/61≈0.0164），在关键词路径排名第 1（rrf=1/61≈0.0164），累加 rrf=0.0328

**与 _rerank_by_keyword_overlap 的配合**：RRF 只看排名不看分数值，因此 `_rerank_by_keyword_overlap` 必须在 RRF **之前**（对单路结果加权）或 RRF **之后**（对融合结果加权）。当前实现是 RRF 之后，对整个 merged 列表做一次重排序。

### 5.3 关键词重排序（_rerank_by_keyword_overlap）

**执行时机**：
- `retrieve()` → 向量结果后，父块回填前
- `retrieve_hybrid()` → RRF 融合后，父块回填前
- `retrieve_keyword()` → 不执行（关键词路径已天然按关键词排序）

**算法**：

```python
keywords = jieba.lcut(query)
for chunk in chunks:
    chunk.metadata["cosine_score"] = chunk.score    # 保存原始分
    overlap = count(kw in chunk.text for kw in keywords)
    boost = min(overlap / len(keywords), 1.0) * 0.25  # 最高 +0.25
    chunk.score = round(score + boost, 4)
```

**与 tsvector 关键词检索的关系**：当混合检索启用时，关键词路径通过 tsvector `@@` 匹配保证了精确命中，RRF 已将其排名融合。`_rerank_by_keyword_overlap` 再做一层 jieba 关键词加权，三层冗余但互补：
1. tsvector `@@`：词级精确匹配（保证不丢）
2. RRF 融合：排名级合并（保证各路最佳都有机会）
3. re-rank 加权：分数微调（同义词/近义表述的细微区分）

### 5.4 HNSW 向量索引

**配置**：

| 参数 | 值 | 位置 |
|------|-----|------|
| M | 16 | 建索引时设定（migration） |
| ef_construction | 200 | 建索引时设定（migration） |
| ef_search | 100 | 每次查询 `SET LOCAL hnsw.ef_search=100`（vector.py:310） |

**对检索的影响**：
- `ef_search=100` 是高精度设定，意味着 HNSW 图遍历时维持 100 个候选。越大越精确但越慢。
- `M=16` 控制每个节点的最大连接数，影响索引大小和精度。
- `is_parent = FALSE` 过滤：父块 `embedding IS NULL`，即使不过滤也不会在向量检索中出现（`<=>` NULL 返回 NULL）。但显式过滤节省了扫描成本。

**与增量索引的关系**：HNSW 支持"插入即索引"（新向量加入图结构即时可用），不需要像 IVFFlat 那样定期 REINDEX。当前全量替换流程（delete_by_doc_id → upsert all）中，每批 upsert 后新向量立即可被检索。

### 5.5 元数据渲染（format_context）

**数据来源**：`document_chunk.metadata` JSONB 列。

**流程**：
```
loader 自动填充（language, course）
  → indexer 透传（**c.metadata）
    → vector.py 存入 JSONB
      → retriever 读取并拆分（_parse_results：fixed_keys → 固定字段，其余 → RetrievedChunk.metadata）
        → format_context 渲染为中文标签
```

**渲染效果**：
```
[1] （来源：math_intro.pdf，第3页，梯度下降 [定义, 中文, 进阶]）
梯度下降是一种迭代优化算法，用于寻找函数的局部最小值...
```

**当前自动填充的元数据字段**：
- `language`：`zh`/`en`/`mixed`（由 `_detect_language()` 检测中英文字符比例）
- `course`：从文件路径的父目录名提取

**可扩展但未自动填充的字段**：`chunk_type`（定义/定理/示例/习题/总结）、`difficulty`（入门/进阶/高级）。这些字段的标签映射已就绪，只需在索引时通过 LLM 分类调用填充。

## 6. 各机制的生效条件和互斥关系

| 机制 | 生效条件 | 检索阶段参与方 |
|------|---------|--------------|
| 向量检索（HNSW） | 始终生效 | `retrieve()` / `retrieve_hybrid()` 的 vector path |
| 关键词检索（tsvector） | `hybrid.enabled=true` 时生效 | `retrieve_hybrid()` 的 keyword path |
| jieba 重排序 | 始终生效（除了 keyword-only path） | `_rerank_by_keyword_overlap()` |
| RRF 融合 | `hybrid.enabled=true` 时生效 | `_rrf_fusion_cross_path()` |
| 父块回填 | 仅当 chunk 有 `parent_chunk_id` 时生效 | `_resolve_parent_chunks()` |
| 元数据渲染 | 仅当 metadata 有对应字段时生效 | `format_context()` |
| 用户隔离 | 当调用方传入 `user_id` 时生效 | 所有 retrieve 函数 |
| 父子切割 | `parent_chunking.enabled=true` 时生效 | `loader.py`（索引阶段）→ 影响回填 |

**父子切割的连锁效应**：`parent_chunking.enabled=true` 只影响索引阶段的切分方式。启用后：
1. 索引产生父块（`is_parent=True`）和子块（带 `parent_chunk_id`）
2. 父块不参与任何检索（`is_parent=FALSE` 过滤）
3. 检索到的子块在 `_resolve_parent_chunks` 中被替换为父块文本
4. 最终给 LLM 的是 2000 字符的大上下文（父块），而非 500 字符的小片段（子块）

即使 `parent_chunking.enabled=false`，检索流程中的所有步骤仍然正常运行——`_resolve_parent_chunks` 检测到没有 `parent_chunk_id`，直接返回原始结果。

## 7. 配置速查

```yaml

rag:
  chunk_size: 500               # 子块切分大小（字符）
  chunk_overlap: 50             # 相邻块重叠
  n_results: 5                  # 最终返回条数
  score_threshold: 0.5          # 向量检索最低余弦相似度
  context_max_tokens: 3000      # format_context 的 token 预算

  hybrid:
    enabled: false              # 混合检索开关（当前关闭）
    paths: [vector, keyword]    # 召回路列表
    rrf_k: 60                   # RRF 平滑常数
    vector_weight: 1.0          # 向量路径权重
    keyword_weight: 1.0         # 关键词路径权重

  # parent_chunking:            # 默认不配置 = 关闭
  #   enabled: true
  #   parent_max_chars: 2000    # 父块最大字符数
  #   child_chunk_size: 500     # 子块大小（null=使用 chunk_size）
```

## 8. 一条查询的完整生命周期（混合检索启用时）

以一个具体例子串联所有机制：

```
用户输入："反向传播算法的数学推导"
  │
  ├─ [1] 并行：向量路径 + 关键词路径
  │
  ├─ 向量路径：
  │    query → text-embedding-v4 → 1024维向量
  │    → HNSW <=> 在 document_chunk 中找 Top-15（5×3）
  │    → 只搜子块（is_parent=FALSE）
  │    → score = 1.0 - cosine_distance
  │    → 过滤 score < 0.5
  │    → 得到 12 个候选子块
  │
  ├─ 关键词路径：
  │    query → jieba.lcut → ["反向", "传播", "算法", "数学", "推导"]
  │    → 过滤停用词/单字 → ["反向", "传播", "算法", "数学", "推导"]
  │    → tsquery: '反向 & 传播 & 算法 & 数学 & 推导'
  │    → text_search @@ to_tsquery → ts_rank 排序
  │    → 只搜子块（is_parent=FALSE），排除未回填旧数据（text_search IS NOT NULL）
  │    → 得到 8 个候选子块
  │
  ├─ [2] RRF 融合：
  │    向量路 rank=1 的子块: rrf = 1.0/(60+1) = 0.0164
  │    关键词路 rank=1 的子块: rrf = 1.0/(60+1) = 0.0164
  │    如果两路命中同一子块 → rrf = 0.0328（累加）
  │    → 融合后得到 15 个去重子块
  │
  ├─ [3] jieba 重排序：
  │    对融合后的每个 chunk，计算关键词命中比例
  │    boost = min(hit_count / 5, 1.0) × 0.25
  │    → 关键词全部命中的子块 +0.25 分
  │
  ├─ [4] 父块回填（如果 parent_chunking 启用）：
  │    查询 parent_chunk_id → 批量获取父块 text
  │    → 来自同一父块的多个子块只保留最高分的
  │    → 用父块的 2000 字符文本替换子块的 500 字符文本
  │
  ├─ [5] 截断到 Top-5
  │
  └─ [6] format_context：
       [1] （来源：math_intro.pdf，第3页，反向传播 [定义, 中文, 进阶]）
```

### 各阶段对最终结果的影响

| 阶段 | 影响 | 可控性 |

| format_context | LLM 可读性 | `context_max_tokens` |
