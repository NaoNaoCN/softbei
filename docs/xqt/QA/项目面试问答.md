## 一、多智能体系统（LangGraph）

### Q1: 项目为什么选择 LangGraph 而不是 LangChain 的 Chain？

**答：**

LangChain Chain 是线性流水线（A → B → C），适合固定的顺序处理。但本项目的场景需要**条件路由**——根据学生画像完整度、资源类型、是否追问等动态决定下一步走哪个 Agent。

LangGraph 的 `StateGraph` 天然支持这一需求：

1. **条件边**：`profile_agent` 输出后用 `route_after_profile()` 判断画像是放行还是追问；`planner_agent` 输出后用 `route_by_resource_type()` 分发到 doc/mindmap/quiz/code/summary/kg/clarify/recommend 八个节点。
2. **共享状态**：11 个 Agent 共享一个 `AgentState`（Pydantic BaseModel），通过 `model_copy(update={...})` 做不可变更新，数据流清晰可追溯。
3. **图编译缓存**：图实例是模块级单例，首次调用编译后缓存，后续调用直接执行。

如果用 Chain：
- 条件分支需要写大量 if/else 嵌套
- 状态传递需要手动管理
- 新增资源类型需要改主流程代码

**LangGraph 对 LangChain 的关系**：LangGraph 是 LangChain 生态的一部分，底层仍然用 LangChain 的 ChatModel 抽象，但图执行引擎是独立的。

### Q2: 11 个 Agent 是如何协同的？路由逻辑是怎样的？

**答：**

完整拓扑（DAG，非并行 fan-out）：

```
START → profile_agent ──(画像完整?)──→ planner_agent
                         │
                         └──(不完整)──→ END（追问后等待用户补充）
                                         
planner_agent ──(条件路由: resource_type)──→ doc / mindmap / quiz / code / summary / kg / clarify / recommend
                                                 │                          │
                                                 └──────────┬───────────────┘
                                                            ↓
                                                     safety_agent（kg 和 clarify 跳过）
                                                            ↓
                                                     recommend_agent → END
```

**每次运行只走一条路径**——不是 11 个全跑。路由由两个条件函数控制：

1. `route_after_profile()` — `profile_complete == True` → `planner_agent`；否则 → `END`
2. `route_by_resource_type()` — 按 `resource_type` 枚举值映射：
   - `doc` → `doc_agent`
   - `mindmap` → `mindmap_agent`
   - `quiz` → `quiz_agent`
   - `code` → `code_agent`
   - `summary` → `summary_agent`
   - `kg` → `kg_agent`
   - `clarify` → `clarify_agent`
   - 兜底 → `recommend_agent`

**为什么不是并行 fan-out？** 教育场景下学生一次通常只需要一种资源。如果一次请求生成文档 + 思维导图 + 题目，走的是批量生成接口（`POST /generate/batch`），在 API 层 `asyncio.gather` 并行发起多次图调用，而非在图内部并行。

### Q3: AgentState 的设计理念是什么？为什么 db 不放 State 里？

**答：**

`AgentState` 包含所有业务数据：`user_id`、`user_message`、`profile`、`resource_type`、`kp_id`、`retrieved_docs`、`draft_content`、`final_content`、`safety_passed`、`metadata` 等。

**设计原则：**

1. **不可变更新**：每个 Agent 用 `state.model_copy(update={...})` 返回新副本，绝不原地修改。任何 Agent 不会意外修改其他 Agent 的数据。
2. **纯数据**：State 只含业务数据，不含基础设施依赖。`db` 会话通过 LangGraph 的 `RunnableConfig` 传递：
   ```python
   # 调用侧
   graph.ainvoke(state, config={"configurable": {"db": db}})
   
   # Agent 侧
   db = config["configurable"].get("db")
   ```
3. **可测试性**：测试时可以注入 mock db 会话，不经过真实数据库。
4. **可序列化**：State 不含不可序列化对象，方便 checkpoint 和回放。

**为什么 db 不放 State？** State 是会被序列化存储的（LangGraph 支持 checkpoint 持久化）。数据库连接不可序列化，也不应该被序列化。这是 LangGraph 官方推荐的做法。

### Q4: 为什么某些 Agent 跳过 SafetyAgent？

**答：**

两个 Agent 绕过安全审计：

1. **kg_agent** → 直接到 `recommend_agent`：知识图谱构建是数据工程操作（从文档提取实体和关系），不是面向用户的文本生成。实体和关系是否正确，取决于后续人工验证，而非 LLM 审核。
2. **clarify_agent** → 直接到 `END`：追问澄清是基于对话历史的简短回复，不生成新学习资源，没必要审核。

这体现了设计原则：**根据任务性质决定是否需要审核，而非一刀切。**

### Q5: 项目如何做容错处理？

**答：**

多层次的容错设计：

| 层级 | 策略 | 具体实现 |
|------|------|---------|
| LLM 调用 | 指数退避重试 | tenacity，最多 5 次，3s → 30s |
| JSON 解析 | 5 策略递进解析 | 直接解析 → 反斜杠修复 → 块提取 → 截断修复 → ast.literal_eval |
| 画像合并 | 降级回退 | DB 失败时回退到内存合并 |
| RAG 检索 | 返回空上下文 | Embedding 失败/向量库为空/无结果时返回空列表，Agent 用通用知识生成 |
| 安全审计 | fail-open 保守通过 | LLM 调用失败/JSON 解析失败 → 默认通过，不阻断输出 |
| 推荐验证 | 代码级硬校验 | LLM 输出的 kp_id 在 DB 中做存在性验证，不存在的直接过滤 |
| 路由兜底 | 多重默认值 | 无法匹配的 resource_type → `recommend_agent`；解析失败 → `ResourceType.doc`；kp_id 为空 → 取用户消息前 50 字符 |

### Q6: 添加一个新资源类型（如"视频讲解"）需要改哪些地方？

**答：**

6 步扩展：

1. 创建 `backend/agents/video_agent.py`，实现 `async def run(state, config) -> AgentState`
2. 在 `backend/models/schemas.py` 的 `ResourceType` 枚举中添加 `video`
3. 在 `backend/agents/graph.py` 的 `build_graph()` 中：
   - `graph.add_node("video_agent", video_agent.run)`
   - `graph.add_edge("video_agent", "safety_agent")`
4. 在 `planner_agent.py` 的 `route_by_resource_type()` 映射字典中添加 `ResourceType.video: "video_agent"`
5. 在 `planner_agent.py` 的系统提示词中添加 video 类型描述
6. 在 `configs/config.yaml` 的 `agents` 节添加 video 的 temperature、max_tokens 配置

无需修改主流程代码，无需修改其他 Agent。

## 二、RAG 检索增强生成

### Q7: RAG 检索的完整流程是怎样的？

**答：**

从用户查询到 LLM 上下文，共 5 个阶段：

**阶段 1：Query Rewrite（查询改写）**
- 对话去上下文化：用最近 6 轮对话历史做指代消解（"那个公式" → "梯度下降更新公式"）
- 画像感知：将学生薄弱知识点注入改写 prompt
- 多角度扩展：一个查询扩展为概念定义、原理推导、应用示例、常见误区等多个角度，各自检索后 RRF 融合

**阶段 2：双路并行检索**
- **语义检索**：query → Embedding API（1024 维向量）→ HNSW `<=>` 余弦距离检索 → 过滤 is_parent=FALSE 的子块
- **关键词检索**：query → jieba 分词 → PostgreSQL `tsvector @@ tsquery` → ts_rank 排序

**阶段 3：结果融合与精排**
- RRF（Reciprocal Rank Fusion）融合两路结果：`rrf_score = weight / (k + rank)`，k=60
- jieba 关键词重叠 re-rank：最高 +0.25 权重
- 父块回填：子块用 `parent_chunk_id` 查找父块，用 2000 字符的大上下文替换 500 字符的小片段
- 多样感知排序：按 section 分组 round-robin 交错，避免 top-5 全来自同一节

**阶段 4：阈值过滤与截断**
- 相似度阈值 0.5（只保留 cosine_similarity >= 0.5）
- 截断到 top-5
- format_context 格式化为带 `[n]` 引用标记的字符串

**阶段 5：缓存**
- 请求级缓存：同一知识点在同一次图调用中只检索一次

**最终效果**：混合检索 + RRF + re-rank 三重冗余，语义泛化能力（"过拟合"能查到"正则化"）和精确匹配能力（术语精确命中）互补。

### Q8: 为什么做混合检索而不是纯向量检索？

**答：**

纯向量检索有盲区：

1. **专业术语漏检**：向量相似度计算的是语义近似，"Batch Normalization"和"Layer Normalization"语义相近但含义不同，纯向量可能返回错误的那个。
2. **稀有词汇失效**：低频专业名词的 embedding 训练不足，检索质量差。

关键词检索（PostgreSQL tsvector + jieba 分词）补充了向量检索的不足：

| 维度 | 向量检索（HNSW） | 关键词检索（tsvector） |
|------|-----------------|---------------------|
| 优势 | 语义泛化，能理解同义表达 | 精确匹配，不会漏掉术语 |
| 劣势 | 近似检索，可能召回语义相近但无关的内容 | 无法处理同义词、近义词 |
| 适用场景 | 概念理解、原理解释 | 精确术语查找、API 名称匹配 |

两路 RRF 融合后，同义表达能命中（向量路径），精确术语不会漏（关键词路径），互补盲区。

### Q9: 父子切割（Parent-Child Chunking）解决什么问题？

**答：**

**核心问题**：检索精度和上下文完整性之间的矛盾。
- 小 chunk（500 字符）检索精度高，但上下文不足，LLM 看不懂片段在说什么
- 大 chunk（2000 字符）上下文完整，但信息密度低，检索时容易引入无关内容

**解决方案**：索引阶段拆成父子两层：
- **子块**（500 字符，有 embedding）：用于检索，精确匹配
- **父块**（2000 字符，无 embedding）：不参与检索，但被子块引用

检索流程：用子块精确匹配 → 通过 `parent_chunk_id` 回填父块文本 → 给 LLM 的是 2000 字符的完整段落。

**额外好处**：
- 同一父块的多个子块去重，只保留分数最高的
- 父块不调用 embedding API，减少了嵌入成本
- 父子切割是可选功能（`parent_chunking.enabled`），关闭后系统降级为普通切分，不影响运行

### Q10: PostgreSQL 的 tsvector 全文检索和 LIKE/ILIKE 有什么区别？

**答：**

项目从 ILIKE 迁移到了 tsvector + GIN 索引。关键差异：

| 维度 | 旧方案（ILIKE） | 新方案（tsvector/tsquery） |
|------|----------------|--------------------------|
| 匹配方式 | `text ILIKE '%kw%'`（子串匹配） | `text_search @@ to_tsquery`（词级匹配） |
| "学习"是否匹配"学生" | 是（子串误匹配） | 否（jieba 分词保证词边界） |
| 排序 | 人工计数 / 无排序 | ts_rank（词频 + 文档长度归一化） |
| 索引 | 无（全表扫描） | GIN 索引（高效） |
| 分词 | 查询时分词 | 索引时 jieba 分词，查询时 jieba 分词 |

**为什么用 `'simple'` 配置？** jieba 已经完成了中文分词，不需要 PostgreSQL 再做 stemming 或 stop-word 处理。`'simple'` 配置只按空格分隔并转小写，对 jieba 输出无副作用。

### Q11: 项目如何做防幻觉？效果如何？

**答：**

五层递进防护，从检索前到输出后全覆盖：

| 层 | 位置 | 做什么 | 怎么拦 |
|----|------|--------|--------|
| 第零层 | 检索前 | Query Rewrite | LLM 改写消除指代歧义 + 画像感知 + 多角度扩展 |
| 第一层 | 检索中 | 检索质量控制 | 混合检索 + RRF融合 + 阈值过滤 + re-rank + 父块回填 + 多样排序 |
| 第二层 | 生成中 | Prompt 约束 | NEVER 级绝对禁止 + IMPORTANT 级强制规则 + Pre-generation Check + [n] 引用标注 |
| 第三层 | 生成后 | SafetyAgent 独立审核 | 另一个 LLM 做 4 项审核，只审不修 |
| 第四层 | 全流程 | 代码硬约束 + 监控 | DB 过滤虚假 kp_id + LLM-as-Judge 4 维度评估 + Golden 回归测试 |

**关键设计决策**：
- 第二条防线使用 system role + 低温度（0.1-0.4）提升约束力
- SafetyAgent 只审不修——发现问题标记 issues，不重写内容（避免用一个错误替代另一个错误）
- fail-open 策略——审核失败时保守通过，不阻断用户体验
- 空引用处理——参考资料为空时强制声明 `⚠️ 暂无参考资料`

**实测效果**（15 条黄金查询）：
- Faithfulness：0.445 → **0.915**（+105%）
- Hallucination Rate：33.3% → **8.5%**（-74%）
- Citation Accuracy：0.750 → **0.867**（+16%）

## 三、LLM 集成与 Prompt 工程

### Q12: 项目如何支持多个 LLM 提供商？切换成本是多少？

**答：**

`backend/services/llm.py` 统一封装，通过 `openai.AsyncOpenAI` 客户端访问所有提供商：

| 提供商 | 标识 | base_url |
|--------|------|----------|
| 通义千问（DashScope） | `qwen` | DashScope API 地址 |
| DeepSeek | `deepseek` | DeepSeek API 地址 |
| 星火 | `spark` | 讯飞 API 地址 |
| OpenAI | `openai` | 标准 OpenAI 地址 |

所有提供商暴露相同的接口：
```python
async def chat_completion(messages, model=None, temperature=0.7, max_tokens=4096, provider=None) -> str
async def get_embedding(text: str) -> list[float]
```

**切换成本**：改 `configs/config.yaml` 中的一行配置：
```yaml
llm:
  provider: "qwen"  # 改为 "deepseek" / "spark" / "openai"
  model: "qwen3.6-plus-2026-04-02"
  base_url: "https://dashscope.aliyuncs.com/compatible-mode/v1"
```

Agent 代码完全不需要修改——所有 Agent 通过 `chat_completion()` 调用，不直接依赖特定提供商。

**重试机制**：tenacity 指数退避（最多 5 次，3s → 30s），`RateLimitError` 和 `PermissionDeniedError` 触发重试。千问配额不足时自动降级到备用模型。

### Q13: Prompt 的设计规范是什么？

**答：**

所有 Agent 的系统提示词遵循以下规范：

**1. 分级禁令体系**：
| 优先级 | 关键词 | 适用场景 | 示例 |
|--------|--------|---------|------|
| 最高 | NEVER | 不可逆伤害：编造事实、虚假引用 | "禁止编造 API——编造不存在的 API 会直接导致学生写出无法运行的代码" |
| 高 | IMPORTANT | 必须做到的质量门槛 | "正文中每一条来自参考资料的关键陈述，标注来源编号 [n]" |

**2. 每条禁令必须带理由** — 防止 LLM 合理化违反：
- 不好："禁止编造内容"
- 好："禁止编造参考资料中不存在的数据、公式、定义或结论——学生会将编造内容误认为教材内容，导致学习错误"

**3. 标准 Prompt 结构**（每个生成 Agent 统一）：
```
# Role — 定义角色是什么、不是做什么
# Rules — NEVER/IMPORTANT 分级禁令，每条带原因
# Pre-generation Check — 生成前自查清单（不输出给用户）
# Output — 格式规范
```

**4. role 选择**：所有 Agent 用 `role: "system"` 而非 `role: "user"`——system role 对 LLM 的约束力更强。

**5. 温度控制**：事实性任务低温（safety: 0.1, doc/quiz/summary: 0.3），创意性任务中温（code: 0.4）

**6. 提示词外置**：所有 prompt 在 `configs/prompts.yaml` 中管理，不在 Agent `.py` 文件中硬编码。

### Q14: 空引用（知识库没有相关资料）时怎么处理？

**答：**

这是对学生诚实的关键设计：

**检索层**：`format_context()` 收到空列表时返回 `"（暂无参考资料）"`

**生成 Agent 层**：拿到空引用上下文后，按 Agent 类型差异化处理：

| Agent | 空引用行为 |
|-------|----------|
| doc / code / summary | 开头声明：`⚠️ 当前知识库暂无此知识点的参考资料，以下内容基于通用知识，仅供参考` |
| mindmap | 返回 `{"name": "知识库暂无参考资料", "children": []}` |
| quiz | JSON 首个元素附加 `"_note": "当前知识库中暂无相关参考资料..."` |

**设计原则**：
- 宁可告诉学生"现在没法帮你"，也不能让 LLM 编造资料来冒充有出处的内容
- `💡 补充` 前缀明确区分 LLM 自身知识和参考资料来源内容

## 四、系统架构

### Q15: 项目的后端架构是怎样的？为什么选择 FastAPI？

**答：**

**技术栈**：FastAPI（异步 Web 框架）+ SQLAlchemy 2.0（异步 ORM）+ PostgreSQL + LangGraph（Agent 编排）+ pgvector（向量检索）

**为什么 FastAPI？**

1. **原生 async/await**：LLM 调用是 IO 密集型操作（一次调用 2-10 秒），async 让事件循环在等待 LLM 响应时不阻塞其他请求
2. **自动 OpenAPI 文档**：Pydantic 模型自动生成交互式 API 文档（/docs）
3. **依赖注入**：`Depends(get_session)` 自动管理数据库会话生命周期，请求结束自动 commit/rollback
4. **后台任务**：`BackgroundTasks` 原生支持异步后处理
5. **流式响应**：`StreamingResponse` + SSE 支持 LLM 流式输出

**全链路异步**：
```
HTTP 请求 → FastAPI async handler → SQLAlchemy AsyncSession → LangGraph ainvoke() → AsyncOpenAI → LLM API
```
整个链路没有同步阻塞，事件循环在等待 LLM 响应时可以处理其他请求。

---

### Q16: 后台任务如何处理数据库会话生命周期？

**答：**

这是项目中的一个重要设计点。两种会话模式：

**模式 1：请求作用域会话（HTTP 请求内）**
```python
async def get_session():
    async with _session_factory() as session:
        try:
            yield session
            await session.commit()    # 请求成功 → 提交
        except Exception:
            await session.rollback()  # 请求失败 → 回滚
            raise
```
会话生命周期 = HTTP 请求生命周期。通过 `Depends(get_session)` 注入路由。

**模式 2：后台任务会话（HTTP 响应后）**
```python
async def run_generation(task_id, user_id, ...):
    async with _session_factory() as session:
        # 独立的数据库会话，不受 HTTP 请求生命周期影响
        ...
```

**为什么需要模式 2？**
- 资源生成（调用 LLM）耗时 5-30 秒，HTTP 请求不能等这么久
- 请求触发后台任务后立即返回 `task_id`，前端轮询任务状态
- 后台任务运行时，HTTP 请求的会话早已关闭
- 如果复用请求会话会产生 `Session is closed` 错误

**后台任务的四种模式**：
1. FastAPI `BackgroundTasks.add_task()` — 从路由触发
2. `asyncio.create_task()` — 即发即忘
3. 托管 `asyncio.Task`（模块级 set 持有引用）— 防止被 GC
4. `asyncio.gather(return_exceptions=True)` — 批量并行执行

### Q17: JWT 认证是如何工作的？

**答：**

**注册流程**：
1. `POST /auth/signup` → 检查用户名唯一
2. bcrypt 12 轮哈希密码
3. 插入 user 表
4. 返回 JWT Token（含 `sub` = user_id，`exp` = 24 小时后）

**登录流程**：
1. `POST /auth/login` → 查询用户
2. bcrypt 验证密码
3. 返回 JWT Token

**请求鉴权**：两级鉴权策略：
1. JWT 优先：验证 `Authorization: Bearer <token>` 请求头
2. Query 参数回退：兼容过渡期的 `?user_id=...` 方式
3. 两者皆无 → 401

**安全要点**：
- 密码用 bcrypt（12 轮），不存明文
- `JWT_SECRET` 从环境变量注入，不入库、不入配置文件
- 前端 localStorage 存储 Token（当前方案，生产环境建议 httpOnly Cookie）
- 敏感路由额外校验资源所有权（`resource.user_id == user_id`），不匹配返回 403

### Q18: 如何处理多用户数据隔离？

**答：**

**数据库层**：
- 所有业务表（user、student_profile、chat_session、resource_meta 等）通过 `user_id` 外键关联用户
- `document_chunk` 表通过 `user_id` 字符串字段隔离，不用 FK（因为公共知识库 `user_id=''` 对全部用户可见）

**检索层**：
```python
# 向量检索时的用户隔离
WHERE (user_id = :user_id OR user_id = '')  # 私有文档 + 公共知识库
```

**应用层**：
- 所有 API 通过 `get_current_user_id()` 提取当前用户
- 敏感操作额外校验资源归属
- `request.user_id == resource.user_id` 校验不通过 → 403

### Q19: 项目的配置文件管理方式是什么？

**答：**

**层级结构**：
```
configs/config.yaml          # 非敏感配置（temperature、pool_size 等）
.env                         # 敏感配置（LLM_API_KEY、JWT_SECRET、DATABASE_URL）
backend/config.py            # Python 数据类，加载并解析配置
```

**加载流程**：
```
config.yaml 中的 ${ENV_VAR} 占位符 → 读取 .env 对应环境变量 → 替换 → 解析为 Python dataclass
```

**设计约定**：
- `config` 是模块级单例：`from backend.config import config` 全局访问
- **绝不实例化第二个 Config 对象**——可能导致配置不一致
- Prompts 外置在 `configs/prompts.yaml`，通过 `config.prompts["agents"][agent_name]["system_prompt"]` 访问

### Q20: 前端的技术选型和架构是怎样的？

**答：**

**技术选型**：原生 HTML/CSS/JS，无前端框架。选择原因：

## 六、设计与工程实践

### Q21: 为什么这个项目选择 Pydantic v2 而不是 v1？

**答：**

1. **性能**：Pydantic v2 核心用 Rust 重写（pydantic-core），数据验证速度快 5-50 倍
2. **更好的类型推断**：`model_validate()` 替代 `parse_obj()`，类型检查更严格
3. **`model_copy(update=...)`**：Pydantic v2 的 `model_copy()` 是浅拷贝 + 更新操作，正是 Agent 所需的不可变更新模式
4. **更好的序列化控制**：`model_dump()` 替代 v1 的 `dict()`，语义更清晰
5. **生态对齐**：FastAPI 0.100+、LangChain 近期版本都推荐 v2

---

### Q22: 项目如何处理 LLM 调用的并发控制？

**答：**

1. **asyncio.Semaphore 信号量控制**：
   - 知识图谱构建：`Semaphore(10)` — 最多 10 个并发 LLM 调用
   - 嵌入批处理：`Semaphore(8)` — 最多 8 个并发 Embedding API 调用

2. **连接池控制**：
   - 数据库连接池：`pool_size=10 + max_overflow=20` 限制并发数据库操作
   - asyncpg 异步驱动：同一连接上的多个查询自动排队

3. **批量操作**：
   - `asyncio.gather(*tasks, return_exceptions=True)` — 单个任务失败不影响其他
   - 预先生成 Snowflake ID，批量 INSERT 一次提交

**为什么控制并发？**
- LLM API 有速率限制（QPS 限制）
- 无控并发可能导致 API 返回 429（Rate Limit）或连接池耗尽
- 信号量控制保证了系统稳定性，用轻微的性能下降换取可靠性

### Q23: 项目有哪些监控和可观测性手段？

**答：**

**日志系统**：
- 框架：loguru（结构化日志 + 滚动文件）
- trace_id：通过 `contextvars` 在整个请求生命周期中传递
- Agent 前缀：每条日志带 `[AgentName]` 便于 grep 定位
- 懒求值：`logger.info("kp={}", kp)` 而非 f-string

**RAG 评估系统**（四层）：
| 层 | 评估内容 | 方式 |
|----|---------|------|
| L1 健康检查 | 向量库连通性、索引状态 | 无 LLM，<5ms |
| L2 检索评估 | P@5、Recall@5、MRR、NDCG@5 | LLM Judge |
| L3 生成评估 | Faithfulness、Completeness、Citation Accuracy、Hallucination | LLM Judge |
| L4 黄金回归 | 15 条手写查询，全链路对比 | LLM Judge |

**关键机制**：
- Golden dataset 回归测试：任意指标下降 > 10% 告警
- LLM-as-Judge 多 LLM 交叉验证：评分差异 > 0.3 标记不一致
- Health Check 无 LLM 代理指标：空结果率 > 30%、检索延迟 P95 > 5s 告警

### Q24: 如果让你重新设计这个项目，你会做哪些改进？

**答：**

这是一个开放性问题，下面是一些可以考虑的改进方向：

1. **流式生成**：当前非流式模式下，用户需要等待整个资源生成完毕才能看到结果。流式输出可以显著改善体验。

2. **Agent 并行能力**：当前一次只生成一种资源。未来可以让 planner 返回多种资源类型，在图内部并行执行多个生成 Agent。

3. **更完善的缓存**：当前 RAG 检索只有请求级缓存。高频知识点的检索结果可以缓存到 Redis，减少重复的 embedding 调用和向量检索。

4. **强化安全审计**：当前 SafetyAgent 对未通过审核的内容采取 fail-open 策略。可以在高置信度场景下改为 fail-closed（拒绝输出），或在 metadata 中携带更详细的 issue 信息供前端展示。

5. **i18n 国际化**：当前从系统提示词到 UI 都是中文硬编码。如需支持多语言教学，需要将提示词和 UI 字符串抽离为国际化方案。

6. **数据库查询优化**：部分列表查询的 N+1 问题虽然已通过 `selectinload` 处理，但随着数据量增长和查询复杂度提升，仍有进一步优化空间。

7. **A/B 测试框架**：对于 prompt 优化、temperature 调参等，可以引入 A/B 测试框架，基于真实用户反馈数据驱动决策。

8. **前端框架升级**：当前原生 JS 方案适合快速原型，但在组件复用和状态管理上有局限。可以逐步迁移到轻量框架（如 Alpine.js）或完整框架（如 Vue 3）。

### Q25: 项目中最让你自豪的技术决策是什么？

**答：**

这道题没有标准答案，以下是几个可以展开的点：

1. **五层防幻觉体系**：从 Query Rewrite 到代码级硬约束，层层递进，实测 faithfulness 从 0.445 提升到 0.915。每个技术决策都有清晰的"为什么"——不是堆砌技术，而是解决实际问题。

2. **Agent 不可变状态**：`model_copy(update=...)` 的决策看似简单，但在多 Agent 系统中消除了大量的"谁改了哪个字段"的调试噩梦。11 个 Agent 各写各的字段，数据流完全可追溯。

3. **LangGraph 条件路由而非并行 fan-out**：很多多 Agent 系统为了炫技做并行，但教育场景下一次只需要一种资源。选择条件路由是对的，少即是多。

4. **配置外置 + 提示词外置**：Temperature、max_tokens、prompt 全在 YAML 文件中，调参不需要改代码。这让非技术人员（教育专家）也可以参与 prompt 优化。

5. **"只审不修"的 SafetyAgent 设计**：让 LLM 审核 LLM 的输出已经很冒险了，如果再让它"修正"，等于用一个幻觉替代另一个幻觉。只标记问题、不修改内容——这个约束来自对 LLM 局限性的深刻认知。
