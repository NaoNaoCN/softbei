# 多轮对话历史管理

## 一、当前实现

### 1.1 存储模型

```
ChatSession (会话)
  ├─ id, user_id, title, last_used_at, created_at
  └─ ChatMessage (消息)  ← ON DELETE CASCADE
       ├─ id, session_id, role (user/assistant), content
       ├─ resource_type (生成的资源类型), extra (JSON)
       └─ created_at
```

消息按 `(session_id, created_at)` 建立联合索引，支持按会话 + 时间高效查询。

### 1.2 加载流程

```
POST /chat
  │
  ├─ 1. load_chat_history(session_id, db)
  │      SELECT * FROM chat_message
  │      WHERE session_id = ?
  │      ORDER BY created_at DESC
  │      LIMIT max_turns * 4    ← DB 层取缓冲，避免加载全量
  │      → 反转恢复时间正序
  │
  ├─ 2. truncate_history(history, max_turns=10, max_tokens=4000)
  │      Step 1: history[-(10*2):]        ← 按轮数截断（最近 10 轮）
  │      Step 2: 从后往前累加 token       ← 按 token 预算截断
  │              超出 4000 token 时截断
  │      Step 3: 确保从 user 消息开始     ← 避免孤立的 assistant 消息
  │
  └─ 3. 注入 initial_state.chat_history → 传给 AgentState
```

### 1.3 Token 估算

```python
def estimate_tokens(text: str) -> int:
    cn_chars = sum(1 for c in text if '\u4e00' <= c <= '\u9fff')
    other_chars = len(text) - cn_chars
    return int(cn_chars / 1.5 + other_chars / 4.0)
```

粗略估算，中文按 1.5 字符/token，英文按 4.0 字符/token。没有使用实际 tokenizer。

### 1.4 过期清理

`chat_cleanup.py` 后台任务每 N 小时（默认 24）执行一次：删除 `created_at` 早于 `session_expiry_days` 天前的所有 ChatSession，关联的 ChatMessage 通过 `ON DELETE CASCADE` 自动删除。

### 1.5 当前方案的局限性

| 问题 | 具体表现 |
|------|---------|
| **简单截断丢失关键信息** | 最早的几轮可能包含"用户是初学者，偏好图形化学习"等关键画像信息，但这些在纯时间截断中最先被丢弃 |
| **Token 估算不精确** | 字符比例估算法与实际 tokenizer 偏差可达 20-30%，导致截断过早或过晚 |
| **无压缩/摘要机制** | 历史要么保留原文，要么完全丢弃，没有中间形态 |
| **会话级清理粒度过粗** | 整个 session 统一过期，无法保留重要会话中的关键消息 |
| **无选择性保留** | 所有消息无差别对待——"帮我生成一份笔记"和"设置学习目标为通过期末考试"同等对待 |
| **截断后丢失上下文连续性** | 如果第 11 轮引用了第 1 轮建立的概念，截断后 LLM 完全不知道这个概念的来历 |

## 二、思考 1：如何更好地提取历史

核心矛盾：**LLM 上下文窗口有限，但对话信息的价值不是均匀分布的**。简单的时间截断假设"越近越重要"，这在教育场景下不成立——用户第 1 轮说的"我是初学者"比第 8 轮说的"帮我再解释一下"信息密度高得多。

### 2.1 分层历史架构（推荐方案）

将历史拆分为三个层次，按信息密度和时效性分别处理：

```
┌──────────────────────────────────────────┐
│  L1: 即时上下文（最近 3 轮，完整保留）      │
│  - 保证对话的连贯性和来回引用               │
│  - 用户说"刚才那个例子"时 LLM 能找到        │
├──────────────────────────────────────────┤
│  L2: 结构化事实（对话中沉淀的持久信息）       │
│  - 画像更新："我是大二学生，正在学机器学习"    │
│  - 偏好变更："我更想要代码示例而不是理论解释"  │
│  - 领域上下文："我们这学期用的是周志华西瓜书"  │
│  → 提取后写入 StudentProfile / metadata    │
│  → 不占用 chat_history token 预算          │
├──────────────────────────────────────────┤
│  L3: 摘要层（3-10 轮，LLM 生成摘要）         │
│  - 每几轮对话后用轻量 LLM 生成 1-2 句摘要    │
│  - 历史注入格式：                            │
│    [前情摘要]                                 │
│    第1-3轮：用户询问了梯度下降的数学原理，     │
│    系统生成了包含公式推导的文档。              │
│    第4-5轮：用户要求用代码示例补充，           │
│    系统生成了Python实现。                     │
│    [最近对话]                                 │
│    user: 这个代码里的learning_rate参数...     │
│    assistant: learning_rate控制步长...        │
└──────────────────────────────────────────┘
```

### 2.2 实现细节

**L2 结构化事实提取**：每次对话结束后（或每 N 轮），用一个极低成本的 LLM 调用（temperature=0，max_tokens=200）扫描最近的 exchange，判断是否有新的偏好/事实/上下文需要持久化。如果有，更新 `StudentProfile` 或 `ChatSession.metadata`。这部分内容不占用 chat_history 的 token 预算——通过独立的 profile 上下文注入。

```
用户: 我更喜欢看视频而不是读文档
  → LLM 提取: {"preference_update": {"preferred_format": "video"}}
  → 写入 StudentProfile.preferences
  → 下轮对话 profile_agent 自动感知，无需从 chat_history 回查
```

**L3 摘要层**：摘要不需要每轮都更新。策略：
- 触发条件：累计 3 轮未摘要，或历史即将触发 token 截断
- 摘要指令：只保留后续对话可能引用到的信息（定义过的术语、达成的共识、做出的决策），忽略纯寒暄和已解决的问题
- 存放位置：可存在 `ChatSession.summary` 字段或独立的 `ChatSummary` 表

### 2.3 对比现有方案

| 维度 | 当前（纯截断） | 分层方案 |
|------|--------------|---------|
| 保留第 1 轮画像信息 | 10 轮后被丢弃 | L2 持久化，永久保留 |
| 第 6 轮引用第 1 轮概念 | LLM 不知情 | L3 摘要覆盖 |
| Token 效率 | 10 轮 × 平均 200 tokens/轮 ≈ 2000 | L1(3轮×200) + L3(摘要150) ≈ 750 |
| 额外 LLM 调用 | 0 | 每 3 轮一次摘要调用（轻量） |

### 2.4 其他可考虑的提取策略

- **语义分块而非按轮次**：如果用户连续 3 轮都在问同一个知识点的不同角度，这 3 轮属于一个"语义块"，应该一起摘要而非单独处理
- **基于信息增益的保留决策**：计算每轮对话的"信息增量"（是否引入了新知识点、新偏好、新决策），信息增益低的轮次优先丢弃
- **用户标记**：允许用户手动"钉住"某些重要消息，这些消息不在自动截断范围内

## 三、思考 2：如何平衡 Token 消耗和效果

### 3.1 Token 花在哪里了

以当前系统为例，一次对话的 LLM 输入包含：

| 组成部分 | 估计 Token | 占比 |
|----------|-----------|------|
| System prompt | 800-1500 | 20-30% |
| RAG 检索上下文 | 1000-2500 | 25-40% |
| 学生画像 | 100-300 | 3-5% |
| 对话历史 | 500-1500 | 15-25% |
| 用户当前消息 | 50-200 | 3-5% |

注意 RAG 上下文（`context_max_tokens=3000`）和 system prompt 是两个大头。对话历史的 token 消耗实际上排第三。优化历史管理虽然有用，但更大的收益在 prompt 精简和检索结果压缩上。

### 3.2 平衡策略：按场景动态分配

不同的对话阶段，历史的重要性不同：

| 阶段 | 历史价值 | 建议历史长度 |
|------|---------|-------------|
| 第 1 轮（画像采集） | 无历史 | 0 |
| 第 2-3 轮（需求澄清） | 高：上一轮的澄清问答是延续的 | 保留全部 |
| 第 4+ 轮（深入学习） | 中：最近 3 轮 + 之前的关键决策 | 分层（L1 最近 3 轮 + L3 摘要） |
| 切换主题后 | 低：旧主题的历史与新主题无关 | 重置为 L3 摘要 + 新主题最近 3 轮 |

### 3.3 精确 Token 计数

当前的中英文字符比例估计误差在 20-30%，替换为实际 tokenizer（如 `tiktoken`）成本极低但效果显著。实现方式：

```python
import tiktoken

# 使用 cl100k_base 编码（GPT-4/Qwen 兼容）
enc = tiktoken.get_encoding("cl100k_base")

def estimate_tokens(text: str) -> int:
    return len(enc.encode(text))
```

精确计数意味着可以减少安全余量——原来为了防止超限可能少截 20% 的 token，精确后可以全部用满。

### 3.4 压缩比与效果的关系

基于通用 LLM 使用经验：

| 压缩方式 | 压缩比 | 关键信息保留率 | 适用场景 |
|----------|--------|--------------|---------|
| 原文保留 | 1:1 | 100% | 最近 3 轮 |
| LLM 摘要 | 约 5:1 | 80-90% | 3-10 轮 |
| 关键词提取 | 约 20:1 | 40-60% | 10+ 轮 |
| 纯丢弃 | 无穷 | 0% | 仅当确定无关 |
| 事实持久化 | 约 50:1 | 90%+ | 画像/偏好类信息 |

最优策略是组合使用：不同信息按价值走不同路径。近轮原文保留 + 中轮 LLM 摘要 + 远轮事实持久化 + 无关轮丢弃。

### 3.5 时间窗口问题

假设用户每天进行 20 轮对话，每轮 400 token（user+assistant），一天就是 8000 token。即使保留 10 轮（约 4000 token），对于需要长时间跨度的学习场景（如课程持续一学期），10 轮覆盖的时间窗口只有半天。这意味着周一建立的概念理解，到周三早上已经被截断丢弃。这是简单的"最近 N 轮"策略的固有问题——**时间窗口太短**。

解决方案：不是简单地扩大 N（token 爆炸），而是提高历史的信息密度。LLM 摘要把 20 轮的"我们讨论了梯度下降的三种变体，用户理解了批量梯度下降但需要更多随机梯度下降的例子"压缩进 100 token。信息密度提升 20-80 倍，时间窗口自然就从半天扩展到数周。

## 四、思考 3：历史长期堆积如何删除

### 4.1 当前清理策略的问题

当前 `chat_cleanup.py` 的 `cleanup_expired_sessions()` 对整个 session 做"一刀切"：session 创建超过 N 天就整体删除。这导致：

- 一个用户在学习机器学习，三周后想回顾之前的讨论——session 已经被清理
- 但如果不过期清理，`chat_message` 表会无限增长（活跃用户每天产生数千条消息）
- profile_agent 从对话历史中提取的画像信息存在 `StudentProfile` 表，不依赖 chat_message——所以画像数据不受清理影响。但对话细节（"上次你推荐的那个优化器叫什么"）会丢失

### 4.2 多级删除策略

```
Level 0: 保留所有消息（最近 7 天）
  → 用户可能随时引用最近的讨论细节

Level 1: 保留关键消息 + 摘要，删除普通消息（7-30 天）
  → 关键消息 = 包含决策/偏好变更/知识点定义的消息
  → 普通消息 = 纯寒暄、已完成的操作、重复确认
  → 删除前对每个 session 生成一份完整摘要

Level 2: 仅保留摘要 + 结构化数据（30-90 天）
  → 原始消息全部删除
  → ChatSession.summary 字段永久保留
  → 相关资源（ResourceMeta）、学习记录（LearningRecord）不删除

Level 3: 完全删除（90+ 天）
  → 整个 session + summary 删除
  → 保留去除了 PII 的匿名化统计数据供系统分析
```

### 4.3 关键消息判断标准

哪些消息值得在 Level 1 保留而非删除：

| 保留条件 | 示例 |
|----------|------|
| 包含学习偏好变更 | "我更喜欢看视频而不是读文档" |
| 包含关键决策 | "我想先把线性回归搞懂再看逻辑回归" |
| 包含知识点理解突破 | "啊我懂了，SGD 每次用一个样本更新" |
| 关联了持久化资源 | 该轮生成了一个 ResourceMeta |
| 情绪/动机表达 | "这部分太难了，我想先放一放" |
| 用户明确标记 | 用户手动"收藏"的消息 |

这些可以由一个低成本 LLM 调用在消息写入时做实时分类标记（`ChatMessage.importance`），而非删除时才扫描。

### 4.4 实现架构

```python
# 新增字段
ChatSession.summary: Optional[str]       # 会话级别摘要
ChatMessage.importance: int = 0          # 重要性评分 (0-5)
ChatMessage.message_type: str            # "chat" | "decision" | "preference" | "understanding"

# 新增清理任务
async def cleanup_old_messages():
    """
    Level 1: 对 7-30 天的消息做选择性保留
    Level 2: 对 30-90 天的 session 做摘要归档
    Level 3: 删除 90+ 天的全部数据
    """
```

### 4.5 用户在闭环中的角色

最有效的清理策略是让用户参与进来：

- **"是否保存这段对话？"**：完成一个知识点后主动询问，用户确认后生成完整摘要并持久化到学习档案
- **学习里程碑自动保存**：当系统检测到用户完成了某个知识点的学习（quiz 正确率 > 80%，或用户明确表示理解了），自动生成摘要并标记为不可清理
- **"你上次学到哪里了？"**：新对话开始时利用保存的摘要快速恢复上下文，而不是重新遍历整个历史

### 4.6 存储成本测算

假设日活 100 用户，每人每天 20 轮：

| 策略 | 单用户日增量 | 90 天存量 | 年存储量 |
|------|------------|----------|---------|
| 全量保留 | ~16KB | ~1.4MB | ~5.8MB |
| 当前方案（30 天过期） | ~16KB | ~0.5MB | ~0.5MB（稳态） |
| 多级删除方案 | ~16KB（7 天全量）+ ~3KB（摘要） | ~0.2MB | ~0.3MB（稳态） |

多级删除在效果（保留关键信息的跨时间可访问性）和成本（存储和检索效率）之间提供了更好的平衡。

## 五、总结

| 维度 | 当前方案 | 改进方向 |
|------|---------|---------|
| 历史提取 | 时间倒序 + 轮数/Token 硬截断 | 分层提取：近轮完整 + 中轮摘要 + 远轮事实持久化 |
| Token 平衡 | 固定上限，字符估算 | 精确 tokenizer + 按场景动态分配预算 + prompt 和 RAG 上下文联合优化 |
| 长期清理 | Session 级一刀切过期 | 多级删除：关键消息重要性标记 + 摘要归档 + 用户参与决策 |
| 核心改进成本 | — | 每次对话后额外 1 次轻量 LLM 调用（摘要/重要性标记），约 100-200 token 输出 |
