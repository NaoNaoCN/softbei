# 防幻觉机制设计与市场方案对比分析

## 一、问题定义

LLM 在教育场景下的幻觉有三类，危害逐级递增：

| 类型 | 表现 | 教育场景危害 |
|------|------|-------------|
| **事实编造** | 生成参考资料中不存在的数据、公式、定义 | 学生学到错误知识，事后纠正成本极高 |
| **引用虚构** | `[n]` 标注指向不存在的来源，或源文无此信息 | 学生误以为有据可查，建立虚假信心 |
| **遗漏关键信息** | 参考资料有的内容没覆盖，生成片面结论 | 学生形成不完整的知识体系 |

本项目的核心立场：**在教育场景下，忠实度 > 完整度。宁可说"我不知道"，也不能编造。**

---

## 二、本项目防幻觉机制（四层防御）

```
             ┌──────────────────────────────────┐
   Layer 1   │  Prompt 工程 — 结构性防幻觉       │
             │  NEVER/IMPORTANT 分级 + 空上下文声明 │
             ├──────────────────────────────────┤
   Layer 2   │ RAG 质量保障 — 输入侧防幻觉        │
             │  混合检索 + 父-子块 + 多样排序     │
             │  + 引用安全格式化                  │
             ├──────────────────────────────────┤
   Layer 3   │ Safety Agent — 输出侧防幻觉        │
             │  独立 LLM 节点核查生成内容          │
             ├──────────────────────────────────┤
   Layer 4   │ 评估监控 — 反馈侧防幻觉            │
             │  LLM-as-Judge 忠实度 + 幻觉率       │
             │  + 交叉验证 + 高幻觉告警            │
             └──────────────────────────────────┘
```

---

### Layer 1：Prompt 工程 — 结构性防幻觉

**核心理念**：不是简单说"不要编造"，而是用分级指令体系让 LLM 真正遵守。

**五级禁令体系**（来自 `configs/prompts.yaml`）：

| 级别 | 关键字 | 含义 | 示例 |
|------|--------|------|------|
| 最高 | **NEVER** | 绝对禁止，不可逾越 | "禁止编造参考资料中不存在的数据、公式、定义" |
| 高 | **IMPORTANT** | 必须做到，质量底线 | "正文中每条关键陈述标注来源编号 [n]" |
| 中 | Do NOT | 默认禁止，可例外 | — |
| 低 | Avoid | 偏好性建议 | — |

每条禁令附带**理由**，防止 LLM 自行合理化违规：

```
# 不好
禁止编造内容

# 实际使用的
## NEVER — 绝对禁止
1. 禁止编造事实：不得写入参考资料中不存在的数据、公式、定义或结论。
   一旦编造，学生会学到错误知识——这是不可接受的。
```

**空上下文声明**：每个生成 Agent 的 prompt 都包含：

> 如果参考资料为"（暂无参考资料）"，必须在开头醒目声明"当前知识库暂无此知识点的参考资料，以下内容基于通用知识，仅供参考"。

这意味着 RAG 失败时，LLM 被**显式要求**承认知识的局限性，而不是静默编造。

**禁止自行编写参考资料列表**：prompt 明确规定：

> 正文只需标注 [n] 编号，文末的 [n] → 来源对照清单由系统自动追加。你若凭印象罗列来源，极易与真实来源错位或编造。

这直接解决了一个常见的幻觉模式——LLM 自以为知道文件名和页码，编造出看起来合理的来源清单。

### Layer 2：RAG 质量保障 — 输入侧防幻觉

更好的检索质量 = 更少的信息空白 = 更少的幻觉动机。

**2.1 混合检索减少漏检**

单一向量检索对专有名词、代码片段、公式的召回存在盲区。本项目并行执行向量语义检索 + jieba 关键词 ILIKE 检索，RRF 融合。覆盖越全，LLM 需要"补全"的空白越少。

**2.2 父-子块保障上下文充足**

子块（500 字符）精准匹配 → 父块（完整小节）提供上下文。如果只给 LLM 一个 150 字的碎片，它很可能会"合理推断"周围的内容——这就是幻觉土壤。完整小节让 LLM 有充足的依据。

**2.3 多样性重排序避免视角单一**

top-k 全来自同一 section 时，LLM 只能看到一种角度，对其他角度可能产生投射性编造。Round-robin 交错排列保证多视角覆盖。

**2.4 引用安全格式化 — 程序化保证 [n] 编号有效性**

这是本项目最具体的防幻觉机制。`format_context_with_sources()` 同时返回两部分：

- 上下文文本（含 `[1] [2] ... [n]` 标记的参考资料）
- `CitationSource[]` 列表（每个 source 的 index 严格对应）

token 截断后的处理：

```
[注意：以上仅展示了前 5 条参考资料，共检索到 12 条。
请勿引用 [6] 及更大的编号。]
```

这直接防止了"正文引用 `[8]` 但清单只到 `[5]`"的悬空引用幻觉。LLM 被明确告知有效引用范围。

### Layer 3：Safety Agent — 输出侧防幻觉

**为什么 safety 必须是独立 Agent，而非 prompt 里的一句话？**

这是整个架构中最重要的防幻觉决策。早期原型尝试在生成 prompt 末尾加"请自查内容是否准确"，结果 LLM 总是回答"检查完毕，内容准确"，但实际抽样发现仍有 20%+ 的幻觉未检出。

原因：同一个 LLM 无法有效审核自己刚生成的内容——"自我审核偏差"。

**独立 Safety Agent 的工作方式**（`backend/agents/safety_agent.py`）：

```
生成 Agent（doc/mindmap/quiz/code/anim/summary）
  → 产出 draft_content
  → safey_agent（独立 LLM 调用）
     输入: draft_content + retrieved_docs（参考资料原文）
     输出: { passed: true/false, issues: [...] }
  → 通过: final_content = draft_content
  → 不通过: safety_issues 写入 state.metadata，但仍返回给用户
              （宁可让用户看到有瑕疵标注的内容，也不静默截断）
```

Safety Agent 的 prompt 明确要求：

```yaml
## IMPORTANT — 必须做到
1. 正文中的关键事实、数据、公式 → 是否可在参考资料中找到原文依据？
2. 每个 [n] 引用标记 → 引用的内容是否确实来自对应的参考资料条目？
   是否存在引用不存在的编号？
```

关键设计点：

- **只审核不重写**：safety_agent 不修改 draft_content，只标记问题。避免"修改过程引入新的幻觉"
- **保守通过**：LLM 调用失败或 JSON 解析失败时，默认 `passed=true`，不阻塞用户。宁愿有漏网之鱼，也不让基础设施故障导致用户等待
- **独立温度**：safety 使用极低温度（0.1），保证审核标准严格一致

### Layer 4：评估监控 — 反馈侧防幻觉

**4.1 LLM-as-Judge 忠实度评估**

独立 LLM 逐句溯源：将生成内容拆为陈述句 → 逐句判断能否在参考资料中找到依据 → 输出 verdict（supported / unsupported）：

```json
{
  "statements": [
    {"text": "梯度下降的学习率通常设为 0.01", 
     "verdict": "unsupported", 
     "evidence": null}
  ],
  "faithfulness": 0.85,
  "issues": ["学习率 0.01 在参考资料中没有依据"]
}
```

忠实度公式：`faithfulness = supported 句数 / 总句数`。幻觉率 = 1 - faithfulness。

**4.2 交叉验证**

单次 Judge 可能误判。对关键评估增加第二次独立 Judge 调用（不同 LLM 实例），两次忠实度差异 > 0.3 时标记异常并记录。这降低了 LLM-as-Judge 自身的误判风险。

**4.3 分级告警**

```python
if hallucination_rate > 0.3:
    logger.warning(f"[RAGJudge] 幻觉率偏高 ({hallucination:.1%})！")
if faithfulness_score < 0.5:
    logger.warning(f"[RAGJudge] 忠实度过低 ({faithfulness:.1%})")
```

高幻觉率 + 低忠实度触发日志告警，累积趋势可反映 prompt/RAG 配置的问题。

**4.4 Golden 数据集**

15 道手工标注查询（`golden_queries.yaml`），每个查询标注了 `expected_aspects`。定期跑全管线评估，对比不同版本之间的幻觉率变化。

## 三、与市场主流方案的对比

### 3.1 对比总览

| 方案 | 防幻觉核心思路 | 优势 | 劣势 | 本项目是否采用 |
|------|--------------|------|------|-------------|
| **RAG 基础方案** | 检索相关文档 → 注入 prompt → LLM 基于参考资料回答 | 简单，工程成本低 | 检索质量决定上限；无输出审核；LLM 可能忽略上下文 | 是（并在此基础上叠加了 Layer 2/3/4） |
| **Self-RAG** | LLM 自己判断是否需要检索 + 自己评估生成质量 | 自适应，不总是检索 | 自评不可靠（同 LLM 自审偏差）；额外 token 消耗大 | 否（本项目的 safety_agent 用独立 LLM 替代自评） |
| **CRAG (Corrective RAG)** | 检索后先评估文档相关性，不相关时纠错或重新检索 | 检索质量闭环 | 仅解决检索侧，不解决生成侧幻觉；纠错逻辑复杂 | 部分（混合检索的 RR 打分可视为轻量版，但未做正式纠错回环） |
| **Chain-of-Verification (CoVe)** | 生成后 → 独立 LLM 生成验证问题 → 回答验证问题 → 对比修正 | 验证问题可针对生成内容定制 | 3-4 次额外 LLM 调用，延迟大；验证问题质量依赖 LLM | 部分（safety_agent 可视为单步验证，未做验证问题生成链） |
| **Guardrails (NeMo)** | 规则引擎 + LLM 双重过滤，支持可编程护栏 | 规则确定性高，延迟低 | 规则维护成本高；规则无法覆盖语义级幻觉 | 否（本项目用 safety_agent 的 LLM 审核替代规则引擎） |
| **FactVer / RARR** | 将生成内容的每个事实声明与搜索引擎/知识库做外部事实验证 | 验证来源独立于 RAG，可信度高 | 依赖外部搜索 API；延迟显著增加；教育垂直领域搜索引擎覆盖差 | 否（教育内容的权威来源在课程文档中，外部搜索反而降低准确性） |
| **Prompt Engineering 方案** | 精心设计的指令体系降低幻觉概率 | 零延迟成本 | 单一措施效果有限，需要组合 | 是（本项目的 Layer 1，与市场最佳实践一致） |

### 3.2 与 Self-RAG 的详细对比

Self-RAG（Self-Reflective RAG）的核心是让**同一个 LLM** 在生成后对自己打分。本项目选择了不同路径：

| 维度 | Self-RAG | 本项目 |
|------|----------|--------|
| 审核者 | 生成 LLM 自身 | 独立 safety_agent（独立 LLM 调用） |
| 自审偏差 | 存在：LLM 倾向于给自己的输出高分 | 不存在：不同 LLM 调用，无利益冲突 |
| Token 开销 | 每次生成额外 ~500 token（自评指令 + 评分输出） | 每次生成额外 ~800 token（完整审核 prompt + JSON 输出） |
| 多维度 | 可同时评 faithfulness / relevance / 是否需要检索 | 当前仅 faithfulness + 引用准确性，可扩展 |
| 实现复杂度 | 需要微调或复杂 prompt 构造 | 即插即用，任何 LLM 可做 safety |

选择独立 safety_agent 的理由：在教育场景下，幻觉的代价（学生学到错误知识）远大于额外的 LLM 调用成本。

### 3.3 与 Chain-of-Verification 的详细对比

CoVe 的四步流程：Generate Baseline → Plan Verifications → Execute Verifications → Final Verified Response。本项目未完全采用 CoVe，原因：

**不需要的步骤**：CoVe 的 "Plan Verifications"（生成验证问题列表）在教育场景下与 safety_agent 直接核对参考资料原文相比，多了一道中间环节。验证问题质量本身依赖 LLM，引入了新的不确定性。直接对照原文更可靠——教育场景下"正确答案"就在参考资料里，不需要 LLM 生成验证问题。

**可借鉴的步骤**：CoVe 的 "Final Verified Response"（根据验证结果修正生成内容）是一个有价值的步骤。当前 safety_agent 只标记问题不修正，未来可以考虑对低忠实度内容触发自动重生成。

### 3.4 与 Guardrails 类方案的对比

Guardrails（如 NeMo Guardrails）基于规则的状态机 + LLM 审核。本项目的 safety_agent 可以理解为 Guardrails 的 LLM 审核部分，但缺少规则层。

**互补方案**：理想状态下，应该在 safety_agent 之前加一层**低成本规则过滤**：

```
生成内容 → 规则检查（正则匹配、关键词黑名单、引用格式校验）
  → 规则未触发：直接通过
  → 规则触发：进入 safety_agent 深度审核
```

这样可以减少 80%+ 的 LLM 审核调用，只对"可疑"内容触发完整的 LLM 审核。

### 3.5 教育场景的特殊性：为什么通用方案不够

| 教育场景的独有挑战 | 通用方案的问题 | 本项目的应对 |
|------------------|-------------|-------------|
| 知识点有"唯一正确答案" | 通用 Chatbot 的"不同观点都合理"逻辑不适用 | 参考资料 = 标准答案，safety 逐句对照 |
| 错误知识的纠正成本高 | 通用场景下用户可自行判断对错 | 宁可标注"暂无参考资料"也不编造 |
| 引用溯源是强需求 | 通用方案很少保证引用准确性 | CitationSource 联动机制程序化保证 |
| 学生信任系统 | 一次幻觉可能破坏学生对整个系统的信任 | 四层防御叠加，任一层的漏网由下层捕获 |

## 四、当前方案的局限与改进方向

| 局限 | 改进方向 | 优先级 |
|------|---------|--------|
| Safety Agent 只标记不修正 | 当 safety_passed=false 时触发自动重生成（换一个 LLM 实例或降低温度重试） | 高 |
| Safety Agent 全量审核，成本高 | 加一层轻量规则过滤（引用格式校验、事实陈述密度检查），只对可疑内容触发 LLM 审核 | 中 |
| 无检索质量的闭环纠错 | 引入 CRAG 思路：检索到不相关文档时自动重检索或扩展查询 | 中 |
| 无用户反馈闭环 | 用户对"这个内容有错误"的反馈应直接写入评估数据集，形成增量改进 | 中 |
| 交叉验证仅评估层使用，不在线上 | 将交叉验证前移到 safety_agent：两个不同 LLM 独立审核，结果不一致时严判 | 低 |
| Golden 数据集规模小（15 题） | 从用户反馈和生成记录中自动扩展 golden 题目 | 低 |

## 五、总结

本项目的防幻觉策略可以总结为四个字：**分层防御，独立核查**。

- **Layer 1（Prompt）阻止 LLM "想做"** → 分级禁令 + 理由说明 + 空上下文声明
- **Layer 2（RAG）提供 LLM "能做"的土壤** → 充分、多样、可溯源的上下文
- **Layer 3（Safety）独立核查 LLM "做了什么"** → 另一个 LLM 审视输出，消除自审偏差
- **Layer 4（评估）量化监控"做得好不好"** → 忠实度/幻觉率指标 + 趋势追踪

与市场方案相比，最大的不同是：**不信任单个 LLM 的自我评估能力，强制引入独立审核节点**。这在教育这个对准确性要求极高的垂直场景下是必要的架构选择。
