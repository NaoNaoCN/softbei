# 面试问题与答案

---

## 一、项目概述

**Q: 简单介绍一下这个项目。**

这是一个面向高等教育的个性化学习多智能体系统。用户通过对话与系统交互，系统自动分析学习意图，结合 RAG 检索增强生成和知识图谱，为学习者生成个性化的学习资源——包括结构化文档、思维导图、测验题、代码示例、教学动画、知识总结等，并提供学习路径规划和艾宾浩斯遗忘曲线分析。

技术栈：FastAPI + LangGraph（12 节点 Agent 管道） + PostgreSQL + pgvector + SQLAlchemy 2.0 async。我在其中主要负责后端整体架构和 Agent 协同管道的设计与实现。

**Q: 项目的核心亮点是什么？**

三个层面：一是基于 LangGraph 的 12 节点条件路由多智能体管道，不是简单的 Chain 串联，而是有状态、有分支、有兜底的图结构；二是完整 RAG 管线——混合检索 + RRF 融合 + 父-子块 + 多样重排序 + 引用安全格式化 + 三层优雅降级；三是 LLM-as-Judge 四维评估体系，从检索质量到生成忠实度/完整性/幻觉检测全链路可量化。

## 二、Agent 与 LangGraph

**Q: LangGraph 和 LangChain 的 Chain 有什么区别？为什么选 LangGraph？**

LangChain 的 Chain（`RunnableSequence`）只能表达线性 DAG——A → B → C，无法条件分支。我们的场景中，profile_agent 要判断画像是否足够以决定提前终止，planner_agent 要根据意图分发到 7 种不同的生成节点，之后还要统一经过 safety → recommend 收尾。这是典型的有条件路由的有向图，LangGraph 的 `StateGraph` + `add_conditional_edges` 原生支持，Chain 做不到。

**Q: Agent 之间如何传递状态？**

所有 Agent 共享一个 Pydantic v2 的 `AgentState`，包含 `user_message`、`profile`、`chat_history`、`resource_type`、`kp_id`、`draft_content`、`final_content` 等字段。每个 Agent 的签名是 `(state, config) -> state`，通过 `state.model_copy(update={...})` 返回新副本而非修改原对象。LangGraph 引擎自动将每个节点返回的新 state 传给下一个节点，保证运行时不可变性。

**Q: 多轮对话的历史是怎么管理的？**

没有用 LangGraph 的 checkpointer。每轮对话结束后，user 和 assistant 的消息持久化到 PostgreSQL 的 `chat_message` 表。下一轮对话时，`load_chat_history()` 从 DB 加载历史 → `truncate_history()` 按 token 预算截断（最多 N 轮 × 2 条，hard cap 4000 token）→ 注入 `initial_state.chat_history`。这样做的原因是 chat_message 表支持 SQL 查询、前端历史列表展示，且与 LangGraph 版本解耦。

**Q: planner_agent 如何做路由分发？路由失败怎么办？**

两级判断。第一级——意图分类 LLM：判断用户输入是 `clarify`（模糊/追问）还是 `generate`（明确请求）。clarify 直接走 `clarify_agent → END`，不进入生成管道。第二级——资源类型 LLM：当 intent=generate 时，输出 `resource_type`（doc/mindmap/quiz/code/anim/summary/kg），graph.py 中用静态 dict 做映射。映射表是静态的，不存在 LLM 自由发挥产生非法路由的风险。如果 LLM 输出未命中任何 key，LangGraph 抛异常，上层 try/except 捕获后走 `recommend_agent` 兜底。

**Q: 为什么不是并行 fan-out？比如同时生成文档和测验？**

一次对话聚焦一种资源。并行 fan-out 会增加 LLM 调用成本和延迟，且多资源间可能出现信息不一致。用户可以通过多轮对话逐步获取不同类型资源，每次生成结果都经过 safety check，保证质量。

**Q: 流式输出是怎么实现的？**

`stream_invoke()` 使用 `graph.astream()` 异步迭代器，每完成一个节点就 yield 状态快照。FastAPI 端用 `StreamingResponse` + `text/event-stream` 推送，前端显示对应阶段提示（"正在分析意图..." → "正在检索资料..." → "正在生成文档..."）。

**Q: 为什么要设计 12 个 Agent？合并成更少的 Agent 不行吗？**

可以，但会让系统在多个维度上退化。这是有意为之的职责拆分，每个 Agent 存在都有独立理由：

**（1）本质原因：LLM 的 prompt 复杂度上限**

如果把 profile_agent + planner_agent + 6 个生成 agent + safety_agent + recommend_agent 合并成一个，系统 prompt 会变成一段需要 LLM 同时处理"判断画像是否完整 → 选择资源类型 → 按对应格式生成 → 自我安全检查 → 生成推荐"的巨型指令。实测中，超过一定复杂度的 prompt，LLM 会选择性忽略规则——尤其是 safety 规则。一个反例：早期原型中曾把 safety 检查写成生成 prompt 末尾的一句"请检查你生成的内容是否准确"，结果 safety 通过率几乎 100%（LLM 总是回答"是的，内容准确"），但实际仍有幻觉。只有把 safety 拆成独立 Agent，用另一个 LLM 调用来审视前一个 LLM 的输出，才真正有效。

**（2）每个 Agent 有独立的配置空间**

不同的任务对 LLM 的要求完全不同。profile_agent 需要低温度（0.3）以保证画像提取的结构化一致性；doc_agent 需要中温度（0.7）以平衡内容准确性和表达流畅性；quiz_agent 需要较高温度来生成有区分度的干扰项。合并成一个 Agent 只能用一个 temperature、一个 max_tokens，无法按任务调优。

**（3）safety_agent 必须是独立节点**

这是最重要的架构决策。safety_agent 不是 prompt 里的一句提醒，而是 LangGraph 中所有生成 Agent（doc/mindmap/quiz/code/anim/summary）的必经节点——共 6 条边指向它。它在管道中充当"质检关"，用独立的 LLM 调用逐句核查内容。如果 safety 逻辑混在生成 prompt 里，LLM 倾向于"自我肯定"——自己审核自己的输出极少会标记问题。拆分后，safety LLM 只看到最终文本，不参与生成，天然避免了自我审核偏差。

**（4）哪些 Agent 确实可以合并？**

诚实地说，6 个生成 Agent（doc/mindmap/quiz/code/anim/summary）在**代码层面**高度相似——都是 `读 state → 调 LLM → 返回 state`，最大差异在 system prompt。可以抽象为一个 `generation_agent` + `resource_type` 参数 + 动态选择 prompt。目前拆分的主要原因：
- 独立的 system prompt 文件（`configs/prompts.yaml`），每个数百行，合并后 prompt 文件维护成本爆炸
- 独立配置（temperature / max_tokens 按 agent 粒度覆盖）
- 语义清晰——新成员看 graph.py 的节点列表就能理解系统能力

如果资源类型扩展到 30 种，当前架构就要重构为参数化生成。但 6 种时，拆分的维护成本 < 合并的复杂度成本。

**（5）profile_agent + planner_agent 为什么也不合并？**

profile_agent 有提前终止能力——首次对话用户画像为空，它直接追问并 `→ END`，不进入后续管道。合并后会失去这种"对话入口按需截断"的能力。此外，profile 更新和 intent 分析的 LLM 调用在 token 消耗上差异很大（profile 需要加载画像历史，planner 需要加载知识点列表），合并调用会导致每次判断画像是否足够时都附带不必要的上下文。

**一句话总结**：少 Agent 可以减少 LLM 调用次数降低延迟，但代价是 prompt 复杂度爆炸、safety 检查失效、配置粒度丧失。当前 12 个是"每个 Agent 有一件独立要做的事"的平衡点，不是为多而多。

## 三、RAG 检索增强生成

**Q: RAG 管线的整体架构是怎样的？**

三阶段：文档加载（loader: PDF/DOCX/Markdown/TXT → TextChunk）→ 向量化索引（indexer: DashScope text-embedding-v4, 1024 维 → pgvector HNSW 索引）→ 混合检索（retriever: 向量 + 关键词双路并行 → RRF 融合 → re-rank → 父块上下文 → 多样排序 → 引用格式化）。

**Q: 为什么需要混合检索？单一向量检索有什么问题？**

向量检索擅长语义泛化但不擅长精确匹配。例如用户搜"SGD"，向量模型可能关联到"随机梯度下降"但也会错误关联到其他优化相关但无关的片段。关键词检索（jieba 分词 + ILIKE）对专有名词、代码片段、公式的召回更精准。两者互补——语义泛化 + 精确匹配。

**Q: RRF 融合具体怎么做的？**

RRF（Reciprocal Rank Fusion）公式：`score(d) = Σ weight_path / (k + rank_path(d))`，k=60 为平滑常数。两路分数量纲不可比（余弦相似度 vs 关键词匹配数），RRF 只看排名，天然避免归一化问题。同一 chunk 在两路都出现时 RRF 分累加（两路共识信号增强）。最后按 RRF 分降序排列。

**Q: 父-子块策略是什么？解决什么问题？**

长文档切成子块（500 字符）用于向量化和检索匹配（小块检索更精准），同时保留父块（完整小节）的引用关系。检索时用子块匹配，返回时将同属一个父块的子块合并去重，最终提供父块完整上下文给 LLM。小块检索精准但缺乏上下文，大块上下文充足但检索信号被稀释——父-子分离兼顾两者。

**Q: 多样性重排序为什么需要？怎么实现的？**

top-k 检索结果经常全部来自同一个 section（比如都从"定义"部分命中）。如果返回给 LLM 的 5 条全是同一角度，生成内容会偏颇。做法：按 chunk 的 section 字段分组 → round-robin 轮流从各组取一条 → 排列成最终列表。

**Q: 引用安全是怎么保证的？如何防止 LLM 虚构引用？**

`format_context_with_sources()` 返回两个值：上下文文本 + `CitationSource[]` 列表，每个 source 的 index 与正文中的 `[n]` 编号严格对应。token 截断后明确标注"以下展示前 N 条中的前 M 条"，防止出现正文引用了 `[5]` 但参考资料清单只到 `[4]` 的悬空编号。

**Q: RAG 失败时怎么处理？**

三层优雅降级：向量库为空/不可用 → 返回空列表；Embedding API 失败 → 返回空向量；jieba 分词后无有效词 → 关键词路返回空。任一路失败不抛异常，最终 LLM 收到"（暂无参考资料）"时，prompt 要求其声明而非静默编造。降级不阻塞主流程。

## 四、LLM 工程化

**Q: 如何支持多个 LLM 厂商？**

四家厂商（通义千问/DeepSeek/星火/OpenAI）都提供 OpenAI-compatible API，统一用 `openai.AsyncOpenAI` 客户端，仅切换 `base_url` + `default_model`。`_make_client(provider)` 工厂函数根据 provider 名返回对应的 client 和默认模型。Agent 层只需传 `provider="qwen"` 即可切换，完全不感知底层差异。

**Q: 重试策略怎么设计的？**

使用 `tenacity` 的 `@retry` 装饰器：最多 5 次，指数退避 3-30s。只对网络/限流类异常重试（`RateLimitError`、`PermissionDeniedError`、`TimeoutError` 等），业务错误不重试（避免重复执行有副作用的操作）。

**Q: 千问配额不足怎么处理？**

千问 API 账号欠费时返回 `RateLimitError`，但消息体含 `"quota"` 关键字。正常限流重试有意义（等几秒后可恢复），但配额耗尽重试无意义（额度不会自己恢复）。所以特殊处理：捕获 `RateLimitError` → 检查是否含 quota 关键字 → 如果是，立即切换到千问的备用 model 重试一次 → 仍失败才向上抛。如果是普通限流（不含 quota 关键字），走正常指数退避重试。

**Q: Embedding 失败怎么处理？**

`get_embedding()` 返回空列表而非抛异常。上游 RAG 检索检测到空向量 → 返回空 chunk 列表 → 最终 LLM 收到"暂无参考资料" → 声明而非编造。整个链路不倒。

## 五、后端架构

**Q: 为什么选择 FastAPI + async？**

核心瓶颈是 I/O——LLM API 调用、pgvector 向量检索、PostgreSQL 查询都是异步操作。FastAPI 的 `async def` + `await` 能最大化单线程的并发能力，不阻塞事件循环。SQLAlchemy 2.0 原生支持 async session，`asyncpg` 是性能最好的 PostgreSQL 异步驱动。

**Q: 通用 CRUD 怎么设计的？**

泛型函数而非每个 model 一个 repository。核心函数签名：

```python
async def select(session, model, filters=None, where=None,
                 order_by=None, limit=None, offset=None,
                 loadRelations=None) -> Sequence[ModelT]
```

`filters`（dict，仅 `==` / `is None`）覆盖 80% 简单查询，`where`（原生 SQLAlchemy 表达式）覆盖 `or_` / `in_` / `like` 等复杂条件。`loadRelations` 支持嵌套路径如 `"items.kp"`，内部用 `selectinload` 链式构建，避免 N+1。

**Q: Snowflake ID 的 JavaScript 精度问题怎么解决？**

64-bit Snowflake ID 超过 `Number.MAX_SAFE_INTEGER`（2^53-1）。自定义 `BigIntJSONResponse` 类，内部 `_SafeIntEncoder` 递归遍历 JSON 树，超过安全范围的 int 序列化为字符串。不修改 ORM 字段类型，不影响 DB 层和 Python 层的数值计算。

**Q: 用户注销时怎么处理关联数据？**

`delete_user_cascade()` 在一个事务内按"先子表后父表"顺序清理 13 张表。因为历史外键大多未配置 `ON DELETE CASCADE`，必须手动保证删除顺序。核心链路：profile_history → quizzes → resources → learning_paths → study_plans → chat_sessions → kg_nodes/edges → user。任一步失败则整体回滚。

**Q: 日志体系怎么设计的？**

Loguru + 自定义 patcher 自动注入 `trace_id`。三个约定：惰性格式化（`{}` 而非 f-string，只在达到日志级别时才 format）、Agent 前缀（`[DocAgent]` 等，方便 grep）、异常用 `logger.exception()`（自动附 traceback）。8 个日志级别从 TRACE 到 CRITICAL 按场景区分使用。

## 六、评估体系

**Q: RAG 评估体系包含哪些指标？**

四层架构：

| 层 | 指标 | 方法 |
|----|------|------|
| L1 健康检查 | 向量库连通性、索引统计 | 启动时 ping，<5ms |
| L2 检索质量 | P@5, Recall@5, MRR, NDCG@5, Hit Rate | LLM Judge 逐 chunk 打分 0/1/2 |
| L3 生成质量 | 忠实度、完整性、引用准确度、幻觉率 | LLM Judge 逐句溯源 |
| L4 Golden 评估 | 全套指标 | 15 道手工标注查询 |

**Q: LLM-as-Judge 忠实度评估怎么做？**

LLM Judge 拿到"参考资料 + AI 生成答案"，逐句拆解 → 逐句判断能否在参考资料中找到依据 → 输出 verdict（supported / unsupported）和 evidence。忠实度 = supported 句数 / 总句数。幻觉检测：unsupported 陈述中如果含虚构引用编号（如引用不存在的 `[7]`），标记为幻觉。

**Q: 怎么控制评估的 LLM 调用成本？**

采样策略：dev 环境 100%，prod 环境 10%。采样基于 session_id 哈希，保证同一会话内采样决策一致。Judge 通过 `asyncio.create_task()` 异步执行，不阻塞用户响应。

## 七、知识图谱

**Q: 知识图谱是怎么构建的？**

两条路径：有目录时走 TOC 路径——从 PDF 提取目录 → 构建 Chapter/KnowledgePoint/SubPoint 骨架 → 将文档块按页码范围分组 → 每组并发调用 LLM 提取 Concept 节点 → 批量推理边（同组内 IS_PART_OF/CONTAINS/REQUIRES + 跨组 RELATED_TO）→ 后处理补全层级关联；无目录或目录 < 3 项时走 Fallback 路径——按页码简单分组后做节点提取和全局边推理。

**Q: LLM 并发怎么控制？**

节点提取和边推理是 LLM 密集型操作。使用 `asyncio.Semaphore(config.knowledge_graph.llm_concurrency)` 限制并发数（默认 10），防止同时发起过多 API 调用导致限流。边推理批次间有重叠（overlap=8），确保跨批次边界的节点对不被遗漏。

**Q: 前端查询某颗子树时，BFS 怎么做？**

请求 `/kg/graph?root_id=kp_xxx&depth=3`：先加载该文档全量节点构建邻接表 → 沿 IS_PART_OF/CONTAINS 边做 BFS 找所有子孙 → 按 depth 过滤类型（`type_levels[:depth]`，如 depth=3 只返回 Course/Chapter/KnowledgePoint）→ 边只保留两端都在可见集合内的。depth 下推到 DB 层（`node_type IN allowed_types`），避免加载全量。

## 八、通用追问

**Q: 项目中遇到的最大技术挑战是什么？**

知识图谱构建的 LLM 质量稳定性。单次调用 OK，但整个文档可能有 200+ 知识节点，需要数十次 LLM 调用，批次间的一致性很难保证。解决方案：用 TOC 先建骨架确定层级结构 → LLM 只负责补 Concept 级别的细粒度节点 → 边提取分批且有重叠 → 后处理补全层级边。把确定性的结构工作（TOC 解析、层级补全）从 LLM 手中拿走，LLM 只做它擅长的语义理解。

**Q: 如果重新设计这个系统，你会怎么改进？**

三点：一是引入 LangGraph 的 PostgresSaver checkpoint 做状态持久化，替代目前的 DB 表手动管理，可以利用 LangGraph 的时间旅行调试能力；二是 Agent 间通信目前只靠 AgentState 字段，复杂场景下字段数会膨胀，可以考虑引入专用 message 类型；三是评估体系目前 LLM-as-Judge 是离线采样，理想情况应接入在线 guardrail（如生成后实时做低成本的规则检查，异常时再触发完整 Judge）。

**Q: 你对 Agent 架构的理解是什么？**

Agent 的本质是"LLM + 工具 + 状态管理 + 路由决策"。LLM 是大脑，工具（RAG 检索、数据库查询、知识图谱查询）是手脚，状态管理（AgentState）是记忆，路由是决策链。LangGraph 的价值在于把路由逻辑从 LLM 内部 prompt 中抽离出来变成显式的图结构——更可控、可调试、可测试。不要把 LLM prompt 写成"如果 A 则做 X，如果 B 则做 Y"的巨型 if-else——那是图引擎该做的事。

**Q: 项目团队规模和你的角色？**

软件杯赛题项目，我主要负责后端架构设计和 Agent 协同管道的实现，包括 LangGraph 图结构设计、AgentState 状态模型、RAG 管线、LLM 多厂商适配层、评估体系和知识图谱构建服务。

**Q: 项目中用到了哪些设计模式？**

- **不可变状态模式**：`model_copy()` 而非直接修改，保证状态传递可追溯
- **策略模式**：多 LLM 厂商通过工厂函数 `_make_client(provider)` 切换策略
- **模板方法**：所有 Agent 遵循统一结构（读 state → 调 LLM → 返回新 state），具体逻辑在 `run()` 中实现
- **优雅降级**：RAG 三层降级、Embedding 失败降级、LLM 配额降级——失败不崩溃，有限功能也比零功能好

## 九、独特设计：解决了哪些市面上的痛点

### 痛点 1：AI 生成教育内容时虚构事实和引用

**市面现状**：通用 LLM 在教育场景下会凭空编造知识点、公式、出处。学生无法区分哪些是正确内容、哪些是幻觉。

**我们的设计**：

- **引用安全格式化**（`CitationSource` + `[n]` 标记联动机制）：不是简单地让 LLM"记得加引用"，而是程序化保证 `[n]` 编号与参考资料清单一一对应。token 截断后自动标注有效引用范围，彻底杜绝正文引用 `[5]` 但清单只到 `[4]` 的悬空编号。

- **safety_agent 作为独立管道节点**：不是 prompt 里一句话"注意安全"，而是独立的 LangGraph 节点。生成内容必须经过 safety_agent 做事实核查——逐句对照参考资料验证，标记 supported / unsupported，生成安全报告（`safety_issues`）。

- **LLM-as-Judge 幻觉检测**：评估层自动检测 unsupported 陈述中是否包含虚构引用编号。这意味着不仅有生成时的 guard，还有事后的量化监控。

### 痛点 2：教育场景对内容准确性要求远高于通用场景

**市面现状**：大多数 AI 教育工具是一层 LLM wrapper——检索到几段文本，拼接一个 prompt，直接输出。没有多层次的质量保障。

**我们的设计**：

- **父-子块策略**：子块（500 字符）精准匹配检索信号，父块（完整小节）提供充足上下文。解决了"小块检索精准但上下文不足、大块上下文充足但信号稀释"的矛盾。这是 RAG 领域的经典 trade-off，我们的方案在工程上直接解决了。

- **多样性重排序**（section-aware round-robin）：top-k 检索结果常全部来自同一 section（如都从"定义"部分命中），导致 LLM 只能看到单一角度。我们按 section 分组后 round-robin 交错排列，保证不同子主题在上下文窗口中都有代表。

- **RRF 融合而非简单拼接**：向量召回和关键词召回的量纲不可比（余弦相似度 0~1 vs 关键词命中数 0~N）。大多数系统简单地把两路结果拼在一起，导致排序混乱。我们使用 RRF（只看排名，k=60 平滑），并且同一 chunk 在两路都出现时分数累加——这是"两路共识"信号。

### 痛点 3：学习资源生成的个性化不足

**市面现状**：大多数 AI 教育产品对所有学生输出同样的内容，最多在 prompt 里加一句"请用简单语言"。没有真正的学生建模。

**我们的设计**：

- **profile_agent 作为对话入口**：不是简单的 prompt 拼接，而是独立的 Agent 节点。首次对话时主动采集学习目标、当前水平、偏好风格、已知概念等，构建结构化学生画像（`StudentProfile`），存入 DB 并在后续对话中持续更新。

- **画像驱动的全链路个性化**：planner_agent 分析意图时带画像上下文（"该生是初学者，偏好视觉化学习"），RAG 检索时做 profile-aware 查询扩展，资源生成时根据画像调整深度和风格。各 Agent 的 prompt 中动态注入画像信息。

### 痛点 4：教育培训场景缺乏系统化的质量评估

**市面现状**：大多数项目没有评估体系，或者只有零散的手动测试。无法量化回答"这个 RAG 系统到底好不好"。

**我们的设计**：

- **四层评估内建到管线中**：不是事后的学术实验，而是与生成管道同进程运行。L1 健康检查（<5ms）→ L2 检索质量（P@5/Recall@5/MRR/NDCG@5）→ L3 生成质量（忠实度/完整性/幻觉率）→ L4 Golden 评估（15 道手工标注查询）。

- **采样 + 异步 Judge 的成本控制**：dev 100%，prod 10%。Judge 通过 `asyncio.create_task()` 异步运行，不阻塞用户响应。评估数据自动聚合为日报。

- **A/B 实验原生支持**：`experiment_group` 字段从 AgentState 贯通到评估记录。切换 prompt / 模型 / 参数时，可以直接对比两组评估指标，用数据而非直觉做决策。

### 痛点 5：单一 LLM 厂商依赖导致的可用性风险

**市面现状**：多数项目硬编码一个 LLM provider，API 挂了或额度用尽时整个系统不可用。

**我们的设计**：

- **四厂商统一适配层**：通义千问 / DeepSeek / 星火 / OpenAI 统一为 `AsyncOpenAI` 接口，切换只需改 `provider` 参数。Agent 层完全不感知底层差异。

- **千问配额不足自动降级**：这是生产环境的真实问题——千问测试账号常因欠费/额度耗尽返回 `RateLimitError`。我们的处理不是简单重试（重试无意义，额度不会自己恢复），而是检测到 quota 关键字后立即切换备用模型重试一次。普通限流则走正常指数退避。

- **全链路优雅降级**：向量库挂了 → 返回空列表 → RAG 降级为纯 LLM 生成 → 声明"暂无参考资料"。Embedding API 挂了 → 同样的降级路径。任何单点故障不导致整个请求失败。

### 痛点 6：知识图谱构建的 LLM 调用质量不稳定

**市面现状**：纯 LLM 驱动的知识图谱构建——给 LLM 一段文本，让它输出所有节点和边。结果一致性差，跨批次的节点命名不统一，层级关系遗漏严重。

**我们的设计**：

- **TOC 先建骨架的混合策略**：不把所有工作交给 LLM。PDF 目录解析是确定性的——提取 Chapter/KnowledgePoint/SubPoint 的层级结构。LLM 只负责补 Concept 级别的细粒度节点和推理关系边。确定性工作由规则完成，语义理解工作交给 LLM。

- **边批次重叠 + 后处理补全**：批次间有 8 个节点的重叠，防止跨批次边界的节点对被遗漏。后处理 `_fill_missing_hierarchy_edges()` 根据节点类型层级规则自动补全 IS_PART_OF 关系——这类显而易见的边不应该依赖 LLM。

**一句话总结**：这个系统不是"LLM + prompt"的浅层包装，而是在教育这个对准确性要求极高的垂直场景下，围绕"如何让 AI 生成内容可信、个性化、可评估"建立了一套完整工程体系。
