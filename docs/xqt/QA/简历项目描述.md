## 项目名称

**个性化资源生成与学习多智能体系统**（第十五届中国软件杯 A3 赛题）

## 项目概述

面向高等教育场景的智能学习系统，基于 LangGraph 构建 12 节点多智能体协同管道，结合 RAG 检索增强生成与知识图谱，为学习者自动生成个性化学习资源（文档、思维导图、测验题、代码示例、教学动画、知识总结等），并提供自适应学习路径规划与学习行为分析。

## 技术栈

- **后端框架**：FastAPI (async) + Uvicorn
- **Agent 框架**：LangGraph StateGraph + LangChain
- **LLM**：多厂商适配层（通义千问 / DeepSeek / 讯飞星火 / OpenAI），统一 OpenAI-compatible 接口，支持 streaming、thinking mode、指数退避重试与配额降级
- **数据库**：PostgreSQL + pgvector 向量扩展 + SQLAlchemy 2.0 async ORM + Alembic 迁移
- **RAG**：pgvector HNSW 向量检索 + jieba 关键词检索 + RRF 融合 + 父块上下文 + 多样性重排序
- **向量化**：DashScope text-embedding-v4 (1024 维)
- **文档解析**：pymupdf4llm (PDF → Markdown) + mammoth (DOCX → Markdown)
- **认证**：JWT (HS256) + bcrypt + 邮件验证

## 核心职责与产出

### 一、多智能体协同管道

- 设计并实现 12 节点 LangGraph StateGraph 有状态多智能体管道，节点包括 `profile_agent` → `planner_agent` → 6 类资源生成 agent（`doc / mindmap / quiz / code / anim / summary`）→ `safety_agent` → `recommend_agent`，以及独立调度的 `kg_agent` 和 `clarify_agent`
- 实现条件路由：planner_agent 根据意图类型（`clarify` / `generate`）和资源类型（7 种）动态分发到对应生成节点；profile_agent 根据学生画像完整度决定继续对话或提前终止
- 采用 Pydantic v2 `BaseModel` 作为 Agent 间统一状态载体（`AgentState`），通过 `model_copy(update={...})` 模式实现不可变状态传递，避免跨节点副作用
- 支持 `invoke()`（同步一次性生成）与 `stream_invoke()`（SSE 流式 token 级输出）双模式，前端通过 `text/event-stream` 实时接收生成内容
- 将外部化的 Agent 系统提示词集中管理在 `configs/prompts.yaml`，遵循结构化提示词规范（Role / Rules / Pre-generation Check / Output 四段式，NEVER > IMPORTANT > Do NOT > Avoid 优先级体系），运行时通过 `.format()` 注入上下文变量

### 二、RAG 检索增强生成管线

- 设计并实现完整 RAG 管线：文档加载（`loader.py`）→ 向量化索引（`indexer.py`）→ 混合检索（`retriever.py`，716 行）
- 实现**混合检索**：pgvector 语义向量检索（HNSW 索引 + cosine 距离 `<=>` 算子）+ jieba 分词关键词检索（ILIKE + `ts_rank`），通过 Reciprocal Rank Fusion (k=60) 融合多路召回结果，支持可配置路径权重
- 实现**查询重写**：去上下文化（decontextualize）+ 学生画像感知扩展（profile-aware expansion）+ 可选多查询并行检索（multi-query）
- 实现**父-子块策略**：子块用于精准检索匹配，父块提供完整上下文，去重后返回
- 实现**关键词重叠重排序**（keyword overlap boost）与**多样性重排序**（section-aware round-robin interleaving），避免 top-k 集中在同一子主题
- 实现**引用安全格式化**：token 估算截断（中英文自适应字符/token 比）+ `[n]` 引用标记 + 截断后有效引用范围声明，防止虚假引用
- 检索失败时优雅降级为纯 LLM 生成模式，声明"暂无参考资料"而非静默编造

### 三、多厂商 LLM 统一适配层

- 设计 `backend/services/llm.py` 多厂商适配层，将通义千问、DeepSeek、讯飞星火、OpenAI 四家 LLM 统一为 OpenAI-compatible `AsyncOpenAI` 客户端接口
- 实现 `@retry` 指数退避重试（最多 5 次，3-30s 指数退避），特殊处理千问账号额度不足（`RateLimitError` 含 quota/insufficient_quota 关键字）时自动切换到备用模型的降级逻辑
- 支持 Qwen3 deep-thinking 模式的 `enable_thinking` 参数透传
- 实现通用 Embedding 单例客户端，支持批量调用（最多 10 条/次），Embedding 失败优雅降级

### 四、后端工程架构

- 基于 FastAPI 构建 RESTful API，含 20 个 ORM 模型、60+ 个 API 端点，按功能域划分路由标签（system / auth / chat / knowledge-graph / generate / resources / quiz / study-plan / pathway / documents / records / analytics / evaluation）

## 1. LangGraph 12 节点多智能体协同管道

### 1.1 为什么选择 LangGraph 而不是 Chain/自定义编排？

LangGraph 提供的是**有状态有环图（StateGraph）**，天然适合多步对话场景。Chain（LangChain 的 `RunnableSequence`）只能表达线性 DAG，无法做条件分支后再回到对话入口。我们的场景中，profile_agent 可能判断画像不足直接结束（提前终止），planner_agent 根据意图分发到 7 种不同生成节点——这是典型的**条件路由（conditional edge）**场景，LangGraph 原生支持。

### 1.2 状态管理：AgentState 不可变传递

所有 Agent 共享一个 Pydantic v2 `BaseModel` — `AgentState`。每个 Agent 的 `run()` 函数签名为 `(state, config) -> state`，通过 `state.model_copy(update={...})` 返回**新副本**而非修改原对象：

```python
# 每个 agent 返回新状态，避免跨节点副作用
state = state.model_copy(update={
    "resource_type": ResourceType.doc,
    "kp_id": "kp_abc123",
})
```

这种不可变模式的优点：
- 每个节点的输入/输出可追溯，调试时可回放任意节点的中间状态
- 后续节点无法"意外"污染前置节点的计算

**面试追问：既然每个节点返回新副本，修改的历史记录是怎么存储的？**

这里需要区分两个层面：

**（1）单次图执行内的状态流转（运行时）**

LangGraph 在 `ainvoke()` 过程中，内部自动维护状态链：节点 A 返回的 state 副本 → 传给节点 B → 节点 B 返回的新副本 → 传给节点 C → ...。这个传递由 LangGraph 引擎驱动，开发者无需手动管理。

**（2）跨轮对话的持久化（存储层）**

本项目**没有使用 LangGraph 的 checkpointer**（如 MemorySaver / SqliteSaver / PostgresSaver）。每轮对话的历史通过 PostgreSQL `chat_message` 表持久化。

具体流程：

```
POST /chat (用户第二轮消息)
  │
  ├─ 1. load_chat_history(session_id, db)  ← 从 chat_message 表加载历史
  │      SELECT * FROM chat_message WHERE session_id = ? ORDER BY created_at
  │      返回 [{"role": "user", "content": "第一轮问题"},
  │             {"role": "assistant", "content": "第一轮回答"}]
  │
  ├─ 2. 构建 initial_state（含 chat_history）
  │      AgentState(user_message="第二轮问题", chat_history=[...], ...)
  │
  ├─ 3. graph.ainvoke(initial_state)
  │      ┌─ profile_agent → model_copy 返回新 state
  │      ├─ planner_agent → model_copy 返回新 state
  │      ├─ doc_agent      → model_copy 返回新 state（含 draft_content）
  │      ├─ safety_agent   → model_copy 返回新 state
  │      └─ recommend_agent → model_copy 返回新 state（含 final_content）
  │
  ├─ 4. INSERT INTO chat_message (role="user", content="第二轮问题")
  │    INSERT INTO chat_message (role="assistant", content=final_content)
  │       ← 将本轮对话写入 DB，供下一轮加载
  │
  └─ return final_state
```

关键设计决策：为什么不用 LangGraph checkpoint 而用 DB 表？

- **查询灵活**：chat_message 表可直接按 session_id、时间范围、关键词等条件查询，checkpoint 是黑盒序列化 blob
- **跨会话访问**：前端展示对话历史列表时，直接查 SQL 表比反序列化 checkpoint 高效
- **解耦**：对话历史是业务数据，与 Agent 运行时状态语义不同。分开存储避免 LangGraph 版本升级时 checkpoint 格式不兼容导致历史数据不可读
- **截断控制**：`truncate_history()` 按 `max_turns × 2` + token 预算截断后注入 initial_state，避免 state 无限膨胀。checkpoint 做截断更复杂

db 会话通过 `config={"configurable": {"db": db}}` 注入，不走 state，因为 db session 本身是非序列化的连接资源，放在 config 里语义更清晰。

### 1.3 条件路由实现

核心路由在 `planner_agent.py` 中，**两级判断**：

**第一级 — 意图分类**：用 LLM 判断用户输入是 `clarify`（追问/模糊）还是 `generate`（明确生成请求）。clarify 直接路由到 `clarify_agent` → END，不进入生成管道。

**第二级 — 资源类型路由**：当 intent=generate 时，LLM 输出 `resource_type`（`doc` / `mindmap` / `quiz` / `code` / `anim` / `summary` / `kg`），graph.py 中用 `add_conditional_edges` 做映射分发。映射表为静态 dict，不存在 LLM 自由发挥产生非法路由的风险。

```python
# graph.py 中的路由映射（静态 dict，LLM 输出必须命中）
graph.add_conditional_edges("planner_agent", planner_agent.route_by_resource_type, {
    "doc_agent": "doc_agent",
    "mindmap_agent": "mindmap_agent",
    # ...
    "kg_agent": "kg_agent",
    "recommend_agent": "recommend_agent",  # 兜底
})
```

如果 LLM 输出的 resource_type 未命中任何映射，LangGraph 会抛出异常，上层 `try/except` 捕获后走 `recommend_agent` 兜底。

### 1.4 流式输出（SSE）

`stream_invoke()` 使用 `graph.astream()` 异步迭代器，每完成一个节点就 yield 一次状态快照。FastAPI 端用 `StreamingResponse` + `text/event-stream` 推送给前端。前端逐 token 渲染，用户看到的是打字机效果。每个 chunk 的结构为 `{node_name: {state_snapshot}}`，前端据此显示不同的阶段提示（"正在分析画像..." → "正在生成文档..." → "正在安全检查..."）。

### 1.5 为什么不是并行 fan-out？

所有资源生成是互斥的——一次对话只生成一种资源。并行 fan-out 适用于"同时生成文档 + 测验 + 总结"的场景，但会增加 LLM 调用成本和延迟，且不同资源间可能存在信息不一致。当前设计是一次对话聚焦一种资源，用户可通过多轮对话逐步获取。

### 1.6 追问策略：profile_agent 的两段式对话

profile_agent 是第一道关卡。首次对话时用户画像为空，agent 主动追问学习目标、当前水平、偏好风格等。追问不是无限制的——设定 `max_profile_rounds`，超过后直接进入 planner，避免陷入无限追问循环。

## 2. RAG 检索增强生成管线

### 2.1 为什么需要混合检索？

单一向量检索的局限：对专有名词、代码片段、公式的召回率低——"SGD"和"随机梯度下降"在语义空间中距离可能很远。关键词检索刚好互补：jieba 分词后用 `ILIKE` 做字符串匹配，对精确术语命中率高。

混合检索 = 语义泛化（向量）+ 精确匹配（关键词），两条路并行执行后融合。

### 2.2 RRF 融合公式

```
RRF_score(d) = Σ weight_path / (k + rank_path(d))
```

其中 `k=60`（平滑常数，防止单个 rank=1 的结果主导），`weight` 为各路权重（默认 vector=1.0, keyword=0.8）。

选 RRF 而非线性加权的核心原因：两路分数量纲不可比（余弦相似度 0~1 vs 关键词匹配数 0~N）。RRF 只看排名，天然避免归一化问题。

同一 chunk 在两路都出现时，RRF 分累加（相当于两路共识信号增强）。

### 2.3 父-子块策略

文档解析时将长文档切为**子块**（默认 500 字）用于向量化和检索匹配，同时保留**父块**（完整小节）的引用。检索时用子块匹配（更精准），返回时将同属一个父块的子块合并去重，最终提供父块的完整上下文给 LLM。

为什么这么做？小块检索精准但上下文不足，大块上下文充足但检索信号被稀释。父-子分离兼顾两者。

### 2.4 关键词重叠重排序

RRF 融合后再做一次 re-rank：对每个 chunk，用 jieba 提取查询关键词，计算与 chunk 文本的关键词重叠率。重叠率高的 chunk 获得一定的分数加成，上限由 `re_rank_keyword_boost`（默认 0.25）控制。这样保证 RRF 排序后，关键词匹配度高的结果不被淹没。

### 2.5 多样性重排序

top-k 检索结果经常全部来自同一个 section（如都从"定义"部分命中）。最终返回给 LLM 的 5 条如果全是同一角度，生成内容会偏颇。

做法：按 section 分组 → round-robin 轮流从各组取一条 → 排列成最终列表。保证不同子主题都有代表。

### 2.6 引用安全格式化

LLM 必须用 `[n]` 标记每个事实陈述的出处。`format_context_with_sources()` 返回两个值：上下文文本 + `CitationSource[]` 列表（每个 source 的 index 与 `[n]` 严格对应）。token 截断后，会标注"以下展示前 N 条参考资料中的前 M 条"，防止出现悬空编号（正文引用了 [5] 但参考资料清单只到 [4]）。

### 2.7 优雅降级

三个层面的降级：
1. 向量库为空/不可用 → 返回空列表
2. Embedding API 失败 → 返回空向量
3. 关键词分词后无有效词 → 关键词路返回空

任一环节失败都不抛异常，而是返回空列表或降级标识。最终 LLM 收到"（暂无参考资料）"时，prompt 要求其声明而非静默编造。

## 3. 多厂商 LLM 统一适配层

### 3.1 统一接口设计

所有厂商（千问/DeepSeek/星火/OpenAI）都提供 OpenAI-compatible API，因此统一使用 `openai.AsyncOpenAI` 客户端，仅切换 `base_url` + `default_model`。

```python
def _make_client(provider: str) -> tuple[AsyncOpenAI, str]:
    prov = _get_provider_config(provider)
    return AsyncOpenAI(
        api_key=config.llm.api_key,
        base_url=prov.base_url,
        timeout=Timeout(connect=10, read=120, write=30, pool=10),
    ), prov.default_model
```

Agent 层调用 `chat_completion(messages, provider="qwen")` 即可切换厂商，完全不感知底层差异。

### 3.2 重试策略

使用 `tenacity` 库的 `@retry` 装饰器：

| 参数 | 值 | 含义 |
|------|-----|------|
| `max_attempts` | 5 | 最多重试 5 次 |
| `backoff_multiplier` | 3s | 退避基数 |
| `backoff_min/max` | 3s / 30s | 退避区间 |
| 触发异常 | `RateLimitError`, `PermissionDeniedError`, `TimeoutError`, `ConnectionError`, `ConnectTimeout`, `ReadTimeout` | 仅网络/限流类异常重试，业务错误不重试 |

### 3.3 千问配额不足自动降级

千问 API 在账号欠费/额度耗尽时，返回 `RateLimitError` 但消息体含 `"quota"` / `"insufficient_quota"` 关键字。重试无意义（额度不会自动恢复），所以特殊处理：捕获后立刻切换到千问的另一个备用 model 重试一次，仍失败才向上抛。

```python
except RateLimitError as e:
    if provider == "qwen" and _is_quota_error(e):
        client2, next_model = _make_client("qwen")
        # 重试一次，成功后返回
    raise
```

这个判断不能简单地"遇到 RateLimitError 就降级"，因为正常的并发限流应该走指数退避重试而非切换模型。

### 3.4 Embedding 单例

Embedding 客户端是模块级单例 `_embedding_client`，避免每次请求新建 HTTP 连接池。首次调用时惰性初始化，后续调用复用同一连接池。

## 4. 后端工程架构

### 4.1 通用 CRUD 设计为何不用 repository 模式？

考虑到项目规模（20 张表）和团队规模（小型），选择了**泛型函数**而非每个 model 一个 repository 类。核心函数签名：

```python
async def select(session, model, filters=None, where=None, 
                 order_by=None, limit=None, offset=None, 
                 loadRelations=None) -> Sequence[ModelT]
```

`where` 参数接收原生 SQLAlchemy 表达式（`or_` / `and_` / `in_` / `like`），与 `filters`（仅 `==` / `is None`）互补。`loadRelations` 支持嵌套路径（如 `"items.kp"`），内部用 `selectinload` 链式构建，避免 N+1 查询。

### 4.2 Snowflake ID 与 JSON 序列化

使用 64-bit Snowflake ID 作为主键。JavaScript 的 `Number` 只能安全表示到 `2^53-1`，超出会丢失精度。解决方案：自定义 `BigIntJSONResponse`，内部 `_SafeIntEncoder` 遍历响应 JSON，超过安全整数范围的 int 转为字符串 `"1234567890123456789"`。

### 4.3 用户注销的级联删除

`delete_user_cascade()` 在单事务内按**"先子表后父表"**的依赖顺序逐表清理，涉及 13 张表、20+ 条 DELETE 语句。因为历史设计中大部分外键未配置 `ON DELETE CASCADE`，必须手动保证顺序。任一步失败则整体回滚。核心顺序：

```
profile_history → student_profile
quiz_attempt → quiz_item → resource_meta
learning_record
generation_task → generation_batch
learning_path_item → learning_path
study_plan_item → study_plan
chat_session (chat_message 由 CASCADE 自动删)
kg_edge → kg_node
kg_build_task / email_verification
document_chunk
user  ← 最后删除
```

### 4.4 日志体系

Loguru + 自定义 patcher 自动注入 `trace_id`。约定：惰性格式化（`{}` 占位符而非 f-string）、Agent 前缀 `[AgentName]`、异常用 `logger.exception()`。

## 5. RAG 四维 LLM-as-Judge 评估体系

### 5.1 四层评估架构

| 层 | 内容 | 触发方式 | 成本 |
|----|------|---------|------|
| L1 健康检查 | 向量库连通性、索引统计 | 启动 + 定时 | <5ms |
| L2 检索质量 | P@5, Recall@5, MRR, NDCG@5, Hit Rate | 每次检索后 | LLM Judge |
| L3 生成质量 | 忠实度 / 完整性 / 引用准确度 / 幻觉率 | 采样触发 | LLM Judge |
| L4 Golden 评估 | 15 道手工标注查询的全管线评测 | 手动/CI | LLM Judge |

### 5.2 LLM-as-Judge 如何工作

以忠实度评估为例：LLM Judge 拿到"参考资料 + AI 生成答案"，逐句拆解 → 每句判断是否能在参考资料中找到依据 → 输出 `{"verdict": "supported|unsupported", "evidence": "..."}` → 忠实度 = supported 句数 / 总句数。

幻觉检测：unsupported 的陈述中，如果含有虚构的引用编号（如引用了不存在的 `[7]`），标记为幻觉。

### 5.3 采样策略

评估有 LLM 调用成本，不能每次生成都做。策略：dev 环境 100% 采样，prod 环境 10% 采样。采样决策基于 session_id 哈希，保证同一会话内采样一致性。

### 5.4 A/B 实验支持

`AgentState.metadata` 中携带 `experiment_group` 字段（"control" / "experiment" 等），评估记录按分组统计，可对比不同 prompt/模型/参数的效果。

### 5.5 自动日报

每次异步 Judge 完成后自动调用 `RAGReporter.save_daily_report()`，将最近 500 条评估记录汇总写入 Markdown 日报文件，方便离线查看趋势。

## 6. 知识图谱构建服务

### 6.1 两条构建路径

**TOC 路径**（有目录时）：从 PDF 提取 TOC → 按层级构建骨架（Chapter / KnowledgePoint / SubPoint）→ 将文档块按 TOC 页码范围分组到对应章节 → 对每组并发调用 LLM 提取 Concept 节点 → 批量推理边（同组内的 IS_PART_OF / CONTAINS / REQUIRES）→ 跨组推理 RELATED_TO 边 → 后处理补全层级关联。

**Fallback 路径**（无 TOC 或 TOC < 3 条）：按页码分组合并文本 → 并发提取节点 → 全局边推理。精度低于 TOC 路径。

### 6.2 LLM 并发控制

节点提取和边推理是 LLM 密集型操作。使用 `asyncio.Semaphore` 限制并发数（`config.knowledge_graph.llm_concurrency = 10`），防止同时发起过多 API 调用导致限流或内存溢出。信号量在 `asyncio.gather` 外层控制。

### 6.3 边批处理与重叠

边推理时将所有节点分批（`edge_batch_size = 40`），批次间有重叠（`edge_overlap = 8`），确保跨批次边界的节点对不会被遗漏。每批让 LLM 在两批节点的笛卡尔积中找关系。

### 6.4 后处理补全

`_fill_missing_hierarchy_edges()`：LLM 提取的边可能遗漏层级关系（如 Concept 未连接 IS_PART_OF 到其 SubPoint）。后处理根据节点命名规则和类型层级自动补全这些显而易见的边，减少 LLM 遗漏。

### 6.5 BFS 子树展开

前端请求 `GET /kg/graph?root_id=kp_xxx&depth=3` 时，后端先加载该文档全量节点构建邻接表（`children_adj`），再沿 `IS_PART_OF` / `CONTAINS` 边做 BFS 找出所有子孙节点，最后按 `depth` 参数过滤类型（`type_levels[:depth]`），只返回指定层级之前的节点。边的过滤策略：只保留两端都在可见节点集合内的边。

### 6.6 任务状态机

构建是异步后台任务（`BackgroundTask`），前端通过轮询获取实时进度：

```
pending → running → done
                 → failed
```

`KGBuildTask` 表记录了 `progress（0-100）`、`stage`（当前阶段描述）、`nodes_count`、`edges_count`（已完成的数量）。前端根据这些字段渲染进度条和阶段提示。
