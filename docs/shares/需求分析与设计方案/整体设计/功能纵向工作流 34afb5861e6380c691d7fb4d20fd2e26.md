## 1. 用户注册 / 登录

### 功能说明

用户注册与登录是整个系统的入口门卫，所有个性化功能（画像、资源生成、学习路径）都依赖于已登录的用户身份。系统通过 JWT 令牌在前后端之间传递身份信息，后续每个 API 请求都携带该令牌以完成鉴权。

**对应上层需求：** 题目要求系统面向”学生用户”提供个性化服务，用户体系是画像维度（§2.1 功能1）和学习历史记录（§2.2 功能5）的前提基础。虽然注册/登录本身不在评分项中，但没有它，所有个性化功能均无法落地。

### 触发点

`streamlit_app/app.py` 侧边栏登录表单

### 注册流程

```
[Streamlit 侧边栏]
  用户填写 username / password
        ↓
  POST /auth/register
        ↓
[backend/main.py → /auth/register]
  接收 UserRegisterIn(username, password)
        ↓
[backend/auth/] (待实现)
  bcrypt 哈希 password
  INSERT INTO user (username, hashed_password)
        ↓
[backend/db/models.py → User 表]
  返回 UserOut(user_id, username)
        ↓
[Streamlit]
  st.session_state.user_id = user_id
  跳转到 Profile 页
```

### 登录流程

```
[Streamlit 侧边栏]
  用户填写 username / password
        ↓
  POST /auth/login
        ↓
[backend/main.py → /auth/login]
  接收 UserLoginIn(username, password)
        ↓
[backend/auth/] (待实现)
  查询 user 表，bcrypt 校验
  生成 JWT access_token
        ↓
  返回 TokenOut(access_token, user_id)
        ↓
[Streamlit]
  st.session_state.access_token = token
  st.session_state.user_id = user_id
  后续所有请求携带 Authorization: Bearer <token>
```

**关键文件**
- [backend/main.py](../backend/main.py) — `/auth/register`, `/auth/login` 路由
- [backend/db/models.py](../backend/db/models.py) — `User` ORM 模型
- [streamlit_app/app.py](../streamlit_app/app.py) — session_state 管理

## 2. 学习档案查看与编辑

### 功能说明

学习档案（Student Profile）是整个个性化系统的”大脑”——所有 Agent 的决策都以它为输入。档案记录了学生的专业背景、学习目标、认知风格、薄弱知识点等 8 个维度，既可由用户手动编辑，也会在对话和测验过程中被系统自动更新。

**对应上层需求：** 直接对应 §2.2 功能1「对话式学习画像构建」的核心要求——画像维度不少于 6 个（本系统实现 8 个）、画像持久化存储、画像可视化展示。手动编辑入口是画像构建的补充路径，让用户可以随时修正系统推断的结果。该功能也是评分项「功能实现及技术要求（45%）」中画像维度达标的直接体现。

### 触发点

`streamlit_app/pages/1_profile.py`

### 查看档案

```
[pages/1_profile.py]
  页面加载时
        ↓
  GET /profile  (携带 JWT)
        ↓
[backend/main.py → GET /profile]
  从 JWT 解析 user_id
        ↓
[backend/services/profile.py → get_profile(user_id)]
  SELECT * FROM student_profile WHERE user_id = ?
        ↓
[backend/db/models.py → StudentProfile 表]
  返回 StudentProfileOut(major, learning_goal,
    cognitive_style, daily_time_minutes,
    knowledge_mastered, knowledge_weak)
        ↓
[pages/1_profile.py]
  渲染各字段展示卡片
```

### 编辑并保存档案

```
[pages/1_profile.py]
  用户修改表单字段，点击"保存"
        ↓
  PUT /profile  body: StudentProfileIn
        ↓
[backend/main.py → PUT /profile]
  接收 StudentProfileIn
        ↓
[backend/services/profile.py → create_or_update_profile()]
  UPSERT student_profile
  INSERT INTO profile_history (snapshot, version)  ← 保留历史版本
        ↓
[backend/db/models.py → StudentProfile / ProfileHistory 表]
  返回更新后的 StudentProfileOut
        ↓
[pages/1_profile.py]
  st.session_state.profile = 新档案
  显示成功提示
```

**关键文件**
- [streamlit_app/pages/1_profile.py](../streamlit_app/pages/1_profile.py)
- [backend/services/profile.py](../backend/services/profile.py) — `get_profile`, `create_or_update_profile`
- [backend/db/models.py](../backend/db/models.py) — `StudentProfile`, `ProfileHistory`

## 3. 对话式画像初始化（Onboarding 流程）

### 功能说明

新用户注册后画像为空，系统需要通过自然语言对话引导用户建立初始画像，而不是让用户填写枯燥的表单。这个流程**完全复用 `/chat/{session_id}` 端点**，不需要任何新接口——区别仅在于前端的引导逻辑和 `profile_agent` 的行为模式。

核心设计原则：画像字段不要求一次对话全部收集完毕。`profile_agent` 每轮累积已知字段，当用户发出资源请求但画像仍缺少必要字段时，自动生成追问并提前结束本轮图执行（跳过所有生成 Agent），直到字段充足才放行到 `planner_agent`。

**对应上层需求：** 直接对应 §2.2 功能1「对话式学习画像构建」的核心约束——“交互方式：自然语言对话（非表单填写）”，以及”画像从对话中自动抽取（LLM 结构化提取）“和”画像随学习进展动态更新”两条子需求。

### 触发条件

```
[streamlit_app/app.py 或 pages/1_profile.py]
  用户登录后，检测 GET /profile → 404 或 profile 所有字段均为空
        ↓
  侧边栏显示提示："先来聊聊你的学习情况吧 →"
  跳转到 chat 页面，前端预置引导消息（纯前端渲染，不走后端）：
    "你好！我是你的学习助手。请简单介绍一下你的专业、
     学习目标，以及目前对哪些知识点比较熟悉？"
```

### 多轮对话累积流程

```
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
  第 N 轮对话（每轮都走同一个 /chat/{session_id}）
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[用户输入]  如："我是计算机专业大三，想搞懂梯度下降"
        ↓
  POST /chat/{session_id}
        ↓
[Node 1: profile_agent]
  1. 调用 LLM 从 user_message 中提取画像字段（JSON）
  2. 与数据库中已有画像做增量合并（merge_chat_updates）
  3. 检查"必要字段完整性"：
       必要字段 = {kp_id 可推断} 或 {learning_goal 非空}
       可用默认值兜底的字段 = cognitive_style（默认 "text"）
  4. 判断本轮意图：
       is_resource_request = 消息中含资源请求意图
       has_min_fields      = 必要字段已足够

        ↓ 条件路由（新增）

  ┌─────────────────────────────────────────────────────┐
  │  情况A：纯自我介绍，无资源请求                         │
  │    → profile_agent 生成确认回复                       │
  │      "好的，我记下了！你目前薄弱的知识点是哪些？"       │
  │    → 直接 → END（跳过 planner 和所有生成 Agent）       │
  ├─────────────────────────────────────────────────────┤
  │  情况B：有资源请求，但必要字段不足                      │
  │    → profile_agent 生成追问消息                       │
  │      "你想学梯度下降，我来帮你生成资料。               │
  │       不过我还不了解你的基础——学过微积分吗？            │
  │       偏好代码示例还是文字讲解？"                      │
  │    → 直接 → END（本轮不生成资源）                      │
  ├─────────────────────────────────────────────────────┤
  │  情况C：有资源请求，且必要字段已足够                    │
  │    → 继续 → planner_agent（进入正常资源生成流程）       │
  └─────────────────────────────────────────────────────┘

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
```

### 典型多轮对话示例

```
轮1  用户: "我是计算机专业大三，想搞懂机器学习"
     → 情况A：提取 major=计算机, learning_goal=机器学习
     → 系统: "好的！你对哪个方向更感兴趣——监督学习、
              神经网络，还是其他？目前学过哪些数学基础？"

轮2  用户: "梯度下降搞不太懂，学过微积分"
     → 情况B：提取 knowledge_weak=[梯度下降], knowledge_mastered=[微积分]
              但 cognitive_style 未知（用默认值兜底）
              kp_id 可推断为 kp_303，字段已足够 → 情况C
     → 系统: [生成梯度下降讲解文档，流式返回]

轮3  用户: "能给我出几道练习题吗"
     → 情况C：画像已有，kp_id 沿用上轮 kp_303
     → 系统: [生成练习题]
```

### AgentState 所需新增字段

```python
# backend/models/schemas.py → AgentState
is_onboarding: bool = False          # 前端标记：当前是否处于画像初始化阶段
profile_complete: bool = False       # profile_agent 判断后写入，供条件路由使用
clarify_message: Optional[str] = None  # 追问内容，情况A/B时写入，由 recommend_agent 透传给前端
```

### graph.py 路由变更

```python
# profile_agent 出口新增条件边（替换原有固定边）
graph.add_conditional_edges(
    "profile_agent",
    profile_agent.route_after_profile,   # 新增路由函数
    {
        "planner_agent": "planner_agent",  # 情况C
        END: END,                          # 情况A / B（追问直接结束）
    },
)
```

- [streamlit_app/app.py](../streamlit_app/app.py) — 画像为空时的引导跳转逻辑
- [backend/agents/profile_agent.py](../backend/agents/profile_agent.py) — `run()` 完整性检查 + `route_after_profile()` 路由函数
- [backend/agents/graph.py](../backend/agents/graph.py) — `profile_agent` 出口条件边

## 4. 对话驱动的资源生成（Chat 流程）

### 功能说明

这是系统的核心功能，也是”多智能体”架构最集中的体现。用户通过自然语言对话表达学习意图（如”我想学梯度下降”），系统自动完成：①从对话中提取并更新学习画像；②理解意图并决定生成哪种资源；③调用对应的专项 Agent 结合 RAG 知识库生成内容；④经安全校验后流式返回给用户，并附带推荐资源。整个过程对用户透明，体验上就是一次智能对话。

**对应上层需求：** 这是 §2.2 功能1（画像构建）、功能2（多智能体资源生成）、功能4（智能辅导）三个需求的交汇点，也是评分权重最高的「功能实现及技术要求（45%）」和「创新价值与实用性（35%）」的核心演示场景。题目要求”必须体现多智能体架构”，本流程通过 LangGraph 状态机串联 9 个 Agent 来满足这一硬性要求。非功能需求中的「流式输出」（§2.3）也在此处实现。

这是系统最核心的功能，用户通过自然语言对话触发多智能体流水线。

### 触发点

`streamlit_app/app.py` 主聊天界面（或任意页面的对话框）

### 完整调用链

```
[Streamlit 聊天界面]
  用户输入消息，如"我想学反向传播"
        ↓
  POST /chat/{session_id}
  body: ChatMessageIn(content, stream=True)
        ↓
[backend/main.py → POST /chat/{session_id}]
  1. 保存用户消息到 chat_message 表
  2. 构建 AgentState 初始值：
       user_id, session_id, user_message,
       profile (从 profile 服务读取)
  3. 调用 graph.stream_invoke(state)
        ↓
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━
              LangGraph 多智能体流水线
━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[Node 1: profile_agent]
  输入: AgentState.user_message + 历史对话
  操作:
    - 调用 LLM 提取用户意图中的档案信息
    - 调用 profile.merge_chat_updates() 增量更新档案
    - 更新 AgentState.profile
  输出: 更新后的 profile 字段

        ↓

[Node 2: planner_agent]
  输入: AgentState.user_message + profile
  操作:
    - 调用 LLM 分析意图
    - 确定 resource_type (doc/mindmap/quiz/code/summary)
    - 确定 kp_id (知识点 ID)
    - 更新 AgentState.resource_type, kp_id
  输出: resource_type, kp_id

        ↓ (条件路由 → 根据 resource_type 分发)

[Node 3a: doc_agent]        [Node 3b: mindmap_agent]
  当 resource_type=doc         当 resource_type=mindmap
  操作:                        操作:
    RAG 检索相关文档              RAG 检索相关文档
    LLM 生成学习文档              LLM 生成思维导图 JSON
    写入 AgentState.draft         写入 AgentState.draft

[Node 3c: quiz_agent]       [Node 3d: code_agent]
  当 resource_type=quiz         当 resource_type=code
  操作:                        操作:
    RAG 检索题目素材              RAG 检索代码示例
    LLM 生成题目列表              LLM 生成代码示例
    写入 AgentState.draft         写入 AgentState.draft

[Node 3e: summary_agent]
  当 resource_type=summary
  操作:
    RAG 检索知识点内容
    LLM 生成知识总结
    写入 AgentState.draft

        ↓

[Node 4: safety_agent]
  输入: AgentState.draft_content
  操作:
    - 调用 LLM 或规则引擎检查内容安全
    - 设置 AgentState.safety_passed = True/False
    - 若不通过则写入 error_message
  输出: safety_passed

        ↓

[Node 5: recommend_agent]
  输入: AgentState.kp_id + profile
  操作:
    - 查询知识图谱相邻节点
    - 生成推荐资源列表
    - 写入 AgentState.metadata["recommendations"]
  输出: 推荐列表

        ↓ END

━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━━

[backend/main.py]
  4. 将 final_content 存入 resource_meta 表
  5. 将 assistant 回复存入 chat_message 表
  6. 以 SSE 流式返回 token 给前端
        ↓
[Streamlit]
  实时渲染流式 token
  对话结束后展示推荐资源卡片
```

### RAG 检索子流程（在各生成 Agent 内部调用）

```
[doc_agent / mindmap_agent / ...]
  调用 retriever.retrieve_by_kp(kp_id, query)
        ↓
[backend/rag/retriever.py]
  1. 调用 llm.get_embedding(query) 获取查询向量
  2. ChromaDB.query(embedding, n_results=5)
  3. 过滤 similarity < threshold 的结果
  4. 调用 format_context() 拼接带引用的上下文字符串
        ↓
[backend/rag/indexer.py 预先建立的向量索引]
  ChromaDB collection: "knowledge_base"
  每条记录: (chunk_text, embedding, metadata{source, page, kp_id})
        ↓
  返回 List[RetrievedChunk] → 拼入 LLM prompt
```

## 4. 直接触发资源生成（Generate 流程）

### 功能说明

Generate 页面是资源生成的”快捷入口”。当用户已经明确知道自己想要什么（比如”给我生成 kp_303 梯度下降的思维导图”），不需要经过对话推断，可以直接选择知识点和资源类型一键触发。由于 LLM 生成耗时较长，系统采用异步任务模式：立即返回 task_id，前端轮询进度，生成完成后渲染结果。

## 9. 测验与评估

## 10. RAG 知识检索管道

### 功能说明

RAG（检索增强生成）管道是系统防幻觉机制的核心基础设施。它分为两个阶段：离线阶段将课程知识库（PDF/DOCX/Markdown）切块、向量化后存入 ChromaDB；在线阶段在每次 Agent 生成内容前，先从向量库中检索与当前知识点最相关的文本片段，将其作为上下文注入 LLM prompt，确保生成内容有据可查、来源可溯。

**对应上层需求：** 对应题目硬性约束「需自行构建至少一门完整高校专业课程的初始知识库」（§一 约束项），以及 §2.3 非功能需求中的「防幻觉」机制——RAG 引用溯源（生成内容标注知识库来源）和置信度过滤（相似度低于阈值时提示无相关内容）正是 §4.5 防幻觉机制设计的第 1、2 条。技术选型上使用 LangChain 作为 RAG 框架（§3.5），BGE-M3 或讯飞 Embedding API 作为向量化模型（§3.3）。

这是一个离线预处理 + 在线检索的两阶段管道。

### 阶段一：离线索引（知识库构建）

```
[知识库文件]
  knowledge_base/ 目录下的 PDF / DOCX / Markdown
        ↓
[backend/rag/loader.py]
  parse_pdf() / parse_docx() / parse_markdown()
  → 提取纯文本，保留 source / page 元数据
  → split_text(text, chunk_size=500, overlap=50)
  → 返回 List[TextChunk]
        ↓
[backend/rag/indexer.py → index_directory()]
  对每个 TextChunk:
    调用 llm.get_embedding(chunk.text)
    → 若 USE_SPARK_EMBEDDING=false: 本地 BGE-M3 模型推理
    → 若 USE_SPARK_EMBEDDING=true:  调用讯飞星火 Embedding API
  并发执行（max_workers=8）
        ↓
  ChromaDB.add(
    ids=[chunk_id],
    embeddings=[vector],
    documents=[chunk.text],
    metadatas=[{source, page, kp_id, section}]
  )
  持久化到 CHROMA_PERSIST_DIR
```

### 阶段二：在线检索（Agent 调用时）

```
[Agent 内部调用]
  retriever.retrieve_by_kp(kp_id, query_text, top_k=5)
        ↓
[backend/rag/retriever.py]
  1. llm.get_embedding(query_text) → query_vector
  2. ChromaDB.query(
       query_embeddings=[query_vector],
       where={"kp_id": kp_id},
       n_results=top_k
     )
  3. 过滤 distance > threshold 的低质量结果
  4. 构建 List[RetrievedChunk]
        ↓
  format_context(chunks) →
    "【来源: xxx.pdf, 第3页】\n内容...\n\n【来源: ...】\n..."
        ↓
  拼入 LLM system prompt 的 context 部分
```

**关键文件**
- [backend/rag/loader.py](../backend/rag/loader.py) — 文档解析 + 分块
- [backend/rag/indexer.py](../backend/rag/indexer.py) — 向量化 + 存储
- [backend/rag/retriever.py](../backend/rag/retriever.py) — 语义检索
- [backend/services/llm.py](../backend/services/llm.py) — `get_embedding()`

## 11. LLM 调用层

### 功能说明

LLM 调用层是所有 Agent 和 RAG 组件的统一出口，封装了多 Provider 切换、重试、流式输出和 Embedding 三种调用模式。它的存在让上层 Agent 代码无需关心”当前用的是哪家模型”——只需调用 `llm.chat_completion()` 即可，底层自动处理 API 密钥选择、指数退避重试、Qwen 模型池轮换等细节。

**对应上层需求：** 对应 §3.3 技术选型中「主力 LLM：讯飞星火大模型 API」的落地实现，以及「建议策略：主要演示和文档中突出讯飞星火，实际开发中可多模型并用」的工程化支撑。非功能需求 §2.3 中的「流式输出」通过 `stream_chat_completion()` 实现。题目合规要求（§六）中使用讯飞相关工具，在此层通过 `provider="spark"` 默认配置体现，并可在文档中明确标注 API 调用方式。

所有 Agent 和 RAG 组件都通过统一的 LLM 服务层调用大模型。

### 普通调用（非流式）

```
[任意 Agent]
  llm.chat_completion(
    messages=[{"role": "system", "content": "..."},
               {"role": "user",   "content": "..."}],
    provider="spark",   # 可选 spark/deepseek/qwen/openai
    temperature=0.7
  )
        ↓
[backend/services/llm.py]
  根据 provider 选择 API base_url + api_key
  构建 openai.AsyncOpenAI(base_url=..., api_key=...)
        ↓
  @retry(stop=stop_after_attempt(3),
         wait=wait_exponential(min=1, max=10))
  client.chat.completions.create(
    model=model_name,
    messages=messages,
    temperature=temperature
  )
        ↓
  若 provider=qwen 且触发 quota 限制:
    自动切换 Qwen 模型池中的下一个模型重试
        ↓
  返回 response.choices[0].message.content
```

### 流式调用

```
[main.py 的 /chat 路由]
  llm.stream_chat_completion(messages, provider)
        ↓
[backend/services/llm.py]
  client.chat.completions.create(stream=True, ...)
        ↓
  async for chunk in response:
    yield chunk.choices[0].delta.content
        ↓
[main.py]
  StreamingResponse(generator, media_type="text/event-stream")
        ↓
[Streamlit]
  逐 token 渲染到聊天界面
```

### Embedding 调用

```
[retriever.py / indexer.py]
  llm.get_embedding(text)
        ↓
[backend/services/llm.py]
  若 USE_SPARK_EMBEDDING=false:
    sentence_transformers.SentenceTransformer("BAAI/bge-m3")
    model.encode(text) → numpy array → list
  若 USE_SPARK_EMBEDDING=true:
    调用讯飞星火 Embedding API
    返回 List[float]
```

**关键文件**
- [backend/services/llm.py](../backend/services/llm.py) — 全部 LLM 调用逻辑
- [backend/config.py](../backend/config.py) — provider 配置读取
- [configs/config.yaml](../configs/config.yaml) — llm 配置节
